# Доставка конечных удостоверений операторскими задачами

Автоматически заменяемый файл нельзя подключать отдельным Docker bind mount: после `os.replace` контейнер продолжает видеть прежний inode. Потребитель предоставляет минимальный каталог leaf/key как read-only directory mount либо собственные exact volumes с helper-доставкой. Directory mount не разрешает включать issuer key или credentials соседних ролей. Общий read-only gate описан в [спецификации инфраструктуры](SPEC.md#общий-gate-жизненного-цикла-сертификатов).

Этот технический интерфейс дополняет существующие локальные операторы PostgreSQL и Telemetry Delivery. Он не является сервисом, удостоверяющим центром, новым таймером или транспортом предметных сообщений. Источник полномочий — прежнее одобрение конкретного оператора; источник атомарной записи и проверки конечных файлов — публичный помощник потребителя. Ограничения выдачи, отзыва и профилей остаются в [PostgreSQL SPEC](postgresql/SPEC.md#операторское-продление-локального-sql-клиента) и [Telemetry Delivery SPEC](observability/delivery/SPEC.md#продление-локальных-удостоверений).

## Привязка

`bind-delivery --state <прежний-каталог> --input <закрытый-json>` выполняется под прежней блокировкой. JSON версии 1 содержит ровно `schema_version`, `consumer_owner`, `installation_id`, `project`, абсолютный исполняемый `docker`, локальный `docker_endpoint`, `daemon_id`, неизменяемый `image`, массив `destinations` и объект `report`. Запись сертификата содержит ровно `id`, `volume`, `role`, `file`; запись отчёта — `volume`, `role`, `file`. Идентификаторы сертификатов должны точно соответствовать прежнему одобрению; для SQL это `client`. Имена файлов простые, без каталогов; имя тома равно `<project>_<role>`.

Версия 2 предназначена для существующей owner-установки, где канонический `installation_id` является проверяемым slug и совпадает с `project`, а volumes могут не иметь устаревшей метки `io.aelev.project`. В этом профиле обязательны точные `io.aelev.owner`, `io.aelev.installation` и `io.aelev.role`; ослабление имени volume, driver/scope/options или других меток не допускается. Версия входа помощника и сохранённого binding совпадает с версией привязки.

Проверяются прежнее неотозванное одобрение, ключи, CA, subject/расширения и хеши исходных сертификатов, точный Docker daemon, локальный образ с capability `io.aelev.certificate-delivery=1`, локальные volumes без driver options и точные метки `io.aelev.owner`, `io.aelev.installation`, `io.aelev.project`, `io.aelev.role`. Устойчивая привязка дополнительно сохраняет хеш Docker CLI, время создания и метаданные томов. Повтор допускает только ту же привязку; изменение назначения не является безопасным повтором и требует отдельного разбора. Прежнее одобрение, срок и число выдач не переписываются.

## Доставка и отказ

Проверочнику выделяется только ограниченный временный tmpfs на 16 МиБ для сборки проверяемого набора; он не переживает контейнер и не является новым хранилищем. Положительная доставка и восстановление прерванной записи проверяются раздельно.

`once` после прежней проверки/продления передаёт помощнику только публичные PEM leaf/issuer и прежний публичный отчёт. Строгая PEM-проверка исключает ключи и посторонние хвосты. Приватные ключи клиента уже находятся у потребителя; ключи CA, пароль, одобрение и операторский журнал не передаются. Помощник запускается как UID/GID 10001 с read-only root, без сети, capabilities и Docker socket, с ограниченными памятью/процессами; writable mounts ограничены точно одобренными volumes. Фиксированный вход — `python /opt/aelev/certificate-delivery.py`; произвольная команда потребителя не принимается.

Вход помощника версии 1 содержит `owner` оператора, `schema_version`, `consumer_owner`, `installation_id`, `destinations`, `report_destination`, `report`, `certificates`. В сертификате — только `id`, `certificate_base64`, `issuer_certificate_base64`. Положительный отчёт требует полного набора сертификатов; отрицательный не может содержать ни одного. Успех возвращает ровно `code=CERTIFICATE_DELIVERY_VERIFIED`, `installation_id`, `report_sha256` и словарь `certificate_sha256` по `id`. JSON для хеша кодируется UTF-8 через `json.dumps(sort_keys=True, separators=(",", ":"))`; хеши сертификатов относятся к декодированным PEM-байтам. Метаданные томов проверяются также после ответа. Отсутствие подтверждения не означает успех и не разрешает перезапуск runtime.

Потребитель проверяет собственную identity установки, свежесть отчёта, неизменность ключа, subject, issuer и расширений, подписи старого и нового leaf одной CA, отсутствие регрессии срока. Сертификат заменяется атомарно по правилам владельца, публичный успешный отчёт записывается последним; прерванный точный повтор завершает прежнюю запись. Отзыв доставляет только отрицательный отчёт и не заменяет leaf. При недоступной доставке хостовый отчёт отрицателен; прежний отчёт в томе устаревает и становится ошибкой существующего мониторинга, а не бесконечным ложным успехом.

## Существующий таймер

Исправление публичного помощника выполняют явным `bind-delivery --expected-helper <прежний-image-ID>` с новым закреплённым `image`. Разрешено изменить только image при неизменных одобрении, daemon/CLI, UUID/владельце, volumes, метаданных и путях назначения; полная прежняя привязка архивируется до атомарной замены. Повтор после потерянного ответа не создаёт новую историю. Неверный прежний image или изменение области назначения запрещены; новый helper не выдаёт новых прав. Публичный оператор должен объявлять `io.aelev.renewal.helper-update=1`.

`upgrade-delivery --state <прежний-каталог>` обновляет только доказанный действующий пользовательский LaunchAgent macOS. Сохраняются label, интервал, Python, state, права и история; новый таймер не создаётся. Для Homebrew `opt`/`Cellar` сохраняется прежнее написание команды только после проверки того же физического исполняемого файла; это не разрешение смены интерпретатора или версии. Скрипт и стандартно-библиотечный помощник сначала размещаются неизменяемой парой, старое определение и устойчивое намерение сохраняются до переключения. Потерянный ответ bootstrap согласуется чтением того же label; отключённая вручную задача или изменённый скрипт/интервал не включаются автоматически. Linux/Windows-планировщик локального профиля этим интерфейсом не добавляется.

Канонический транспорт — `renewal_delivery.py` в этом каталоге. `release_renewal_delivery.py` формирует одинаковые воспроизводимые публичные ZIP-артефакты в `vendor` двух поставок; зависимости Python/ОС не меняются. Исходники соседнего провайдера не используются при сборке или работе потребителя. Проверки транспорта находятся в `test_infrastructure/test_renewal_delivery.py`; X.509, допуск и фактические конечные файлы проверяются отдельно владельцами.

Нативная задача не записывает новый байткод рядом с неизменяемой парой. Повтор учитывает оставшийся от прежнего запуска только закрытый `__pycache__` владельца с обычными одиночными файлами CPython 3.13 для этих двух модулей; чужие файлы, ссылки и открытые права запрещены. После доказанного завершения обновления следующий выпуск сохраняет полное прежнее намерение в `timer-delivery-history` и создаёт новое под той же блокировкой. Проверяются точные байты текущего определения, хеш исходной пары и реально загруженный скрипт; незавершённая операция или ручное отключение не заменяются новым намерением.
