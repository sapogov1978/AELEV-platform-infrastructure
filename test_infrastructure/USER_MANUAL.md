# Руководство: Проверки инфраструктурной композиции

Здесь проверяется только верхнеуровневая оркестрация [Compose](../compose.yml): состав, порядок реальных задач подготовки, общий запуск, остановка, сохранение данных и адресная очистка. Проверки компонентов остаются в собственных `test`. Корень не получает каталога прикладных ресурсов.

[Сохраняющий перезапуск 25 октября 2026](planned-restart-result-20261025.md): реальный stop/cleanup/start прежних контейнеров, сохранность всех томов и истории, SQL HA и свежая доставка; модель и очередь Advance выключены.

## Аудит документации

Результат очистки исторических каталогов 2026-10-12 фиксирует точные удалённые материалы, восстановление, проверку ссылок и неизменность Compose/контейнеров; это не новый жизненный тест.

[Результат последовательной сверки 2026-10-11](documentation-result.md) фиксирует чтение поставок, разрешение Compose, полноту описания env, ссылки/диаграмму и исполняемые примеры руководства. Это не повторный полный lifecycle; рабочие контейнеры не перезапускались. Общая агентская навигация — [INDEX.md](../INDEX.md).

## Файлы и операторское окружение

При общем старте native Docker fencing может временно остановить собственный SQL peer. Тест допускает ожидание его возврата только до прежнего readiness deadline, при совпадающих labels/cluster, Docker-fencing и здоровом исполнителе, без OOM; готовность требует реального `healthy` процесса. Отсутствие исполнителя, чужая роль, другой механизм и прочие terminal exits по-прежнему прекращают проверку. Тест не запускает остановленную роль сам и не обходит защиту Patroni.

`lifecycle.py` — настоящий совместный жизненный цикл; `resources.py` — учёт владения/очистка; `test_orchestration.py` — отдельные регрессии конфигурационной границы и защиты ресурсов; `test_dependency_security.py` — безопасность собственного кэша Black и временного каталога pytest с проверкой сохранения результата форматирования. `pyproject.toml` и `poetry.lock` закрепляют инструменты на прежнем Python 3.13/Poetry 2.2.1; Playwright 1.56.0 используется только операторским тестом, не runtime. [Результат жизненного цикла](lifecycle-result.md) и [снимок](lifecycle-result.png) предназначены человеку; [прежние модульные проверки](pytest-result.md) и [проверка обновления инструментов](dependency-security-result.md) не выдаются за запуск Docker.

Проверьте `python3.13 --version`, `poetry --version`, `docker version`, `docker compose version` и наличие Chromium. Установка Python/Docker описана в README наблюдения, Poetry — в [официальном руководстве](https://python-poetry.org/docs/#installation). Из этого каталога:

```sh
poetry env use python3.13
poetry install --no-root
poetry run pytest -q
poetry run black --check .
poetry run ruff check .
poetry run mypy .
```

Используйте уже установленный Chromium; при его отсутствии установите тестовый браузер командой `poetry run playwright install chromium`. Не требуется общий тестовый контейнер с Docker socket.

## Реальный тест

Сначала подготовьте собственные env, удостоверения, runtime и рабочие образы всех поставок по [корневому README](../README.md). Для входа нужна существующая учётная запись с ролью просмотра и файл её пароля; секрет не передаётся в CLI или чат. Тест не создаёт фиктивного IdP, Kafka, API, пользователя или издателя.

Условия: нет контейнеров общей группы и работающих самостоятельных писателей её томов. Чужие проекты фиксируются и сохраняются. При обнаружении существующих данных тест по умолчанию отказывает; их штатное использование разрешается только явным `--reuse-existing-data`. Оно не разрешает удаление или сброс этих данных.

```sh
poetry run python lifecycle.py \
  --ui-url https://<ui-host>:<port> \
  --viewer-user <existing-viewer> \
  --viewer-password-file <existing-password-file> \
  --chromium <installed-chromium>
```

Для подготовленного локального стенда с прежними данными дополнительно явно задайте `--reuse-existing-data`. Ограждение PostgreSQL выбирается только собственным env по [00-INFRA-20261106-0006-technical-storage-boundaries](../docs/adr/00-INFRA-20261106-0006-technical-storage-boundaries.md); локально `docker`, флага `--without-watchdog` и обходного Compose больше нет. Локальная PKI браузера допускается лишь через `--allow-local-certificate` и loopback UI URL; рабочие процессы/издатели всё равно проверяют TLS/mTLS. Это не допуск для удалённого production host.

Тест проверяет канонический модельный состав, отсутствие двойного Kafka/внешних сетевых bootstrap, выбранный сервисный механизм ограждения и обязательные файлы владельцев. Для изменённых поставок Keycloak, оболочки, наблюдения, переводчика и PostgreSQL полностью сравниваются разрешённые роли самостоятельного Compose и общей модели: не только названия, но и параметры, зависимости, mounts, секреты и проверки. Значения и секреты из моделей не выводятся. Сначала отдельно запускается Kafka: брокер должен стать healthy без создания контейнеров переводчика. Далее выполняются реальные observability/OIDC/site replication/status-provision задачи, автоматические миграции/topics, проверяются здоровье постоянных ролей, настоящий OIDC/API/DOM и все собственные строки ONLINE. Затем общий `stop/up` сохраняет контейнеры, `down/up` пересоздаёт их с прежними томами/identities и возрастающими sequence. После глубокого `down` тест повторяет канонический двухфазный bootstrap: Keycloak сначала восстанавливает принадлежащую ему ingress-сеть, затем запускаются потребители, которые подключаются к ней через владельческий external overlay. Общее состояние получается через публичный технический API; БД соседей не читаются. Прежний общий отчёт содержит историческое тестовое исключение, не доказывает новый Docker-механизм; его результат находится в [сервисном отчёте](../postgresql/test/fencing-lifecycle-result.md).

В `finally` снимаются созданные контейнеры/сети, удаляются только новые точно учтённые тома, включая свидетелями подтверждённые анонимные mounts. Исходные тома, образы, env/секреты и состояния чужих контейнеров сверяются. Нет глобального prune, удаления общей БД, сброса topics/offsets или перезапуска Docker daemon. При отказе отчёт сохраняет выполненные этапы, ошибку и исход очистки; невыполненные шаги не получают PASS.

WAN, независимые области отказа MinIO/PostgreSQL, аппаратное ограждение, продукционная PKI/ротация, нагрузка, резервное восстановление и внешняя отправка почты не проверяются этим локальным прогоном.

## Изолированная диагностика clean-room

Общий [clean-room gate](clean_room_gate.py) принимает повторяемый `--diagnostic-stage <stage>` из `--list-stages` и `--diagnostic-repetitions 1|2|3`. После обычных build/preflight/BOM он выполняет только выбранные реальные owner-сценарии. Каждый повтор получает отдельный каталог `attempt-N`, отчёт и лог; перед следующим сценарием сверяются Docker baseline и чистота исходников. Отказ сценария сохраняется в `diagnostic-run.json` и не препятствует проверке следующего только при подтверждённой cleanup; изменение baseline останавливает диагностику. Любой неуспех даёт exit 2. Этот режим создаёт профиль `full-local-diagnostic` и не создаёт `clean-room-evidence.json`; успешные отдельные проверки не заменяют полную функциональную приёмку.

В ручном workflow `clean-room-full-local` поле `diagnostic_stage` выбирает один сценарий, а `remaining-stages` запускает telemetry, Translator, SPIRE identity, SPIRE observation и recovery. `diagnostic_repetitions` применим к одному выбранному сценарию. Значение `full` по умолчанию выполняет прежнюю полную приёмку. Разные диагностические сценарии используют независимые одноразовые runners; повтор одного сценария остаётся последовательным.

Три PostgreSQL-повтора дополнительно покрывают отключение каждого узла 1/2/3: lifecycle получает `--fault-target N` и при необходимости один раз выполняет штатный Patroni switchover, затем подтверждает единственного заданного primary, все три SQL-роли и реальную sync-реплику. Прямых promote, новых аренды/координатора или ручного изменения PGDATA нет.

Выбор `telemetry-and-translator` повторяет только эти две стадии после исправления их test-driver входов, сохраняя отдельные отчёты и baseline. Telemetry использует Playwright из lock этого каталога и SDK sender из manifest, включая его native Prometheus и стандартную команду; runtime центрального Delivery с другим ENTRYPOINT для этой роли не подходит.

При отказе PostgreSQL рядом с Markdown-отчётом сохраняется `.diagnostic.json`: фаза сценария, номер намеренно отключённого узла, running/restarting/OOM/exit/health и счётчики фиксированных признаков ошибок. Состояние снимается до удаления тестового кластера. Credentials, raw native logs, host paths и содержимое SQL в этот артефакт не входят.
