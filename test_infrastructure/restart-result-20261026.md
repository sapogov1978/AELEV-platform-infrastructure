# Повторный запуск инфраструктуры — 26 октября 2026

## Итог и граница проверки

По прямому запросу владельца перезапущен постоянный состав установленной инфраструктуры через общий Compose, включая ранее не запущенные модель Index-Translate 9B и исполнитель переводчика. Пошаговый запуск охватил 57 постоянных ролей. Контейнеры, образы, подключения и все 183 Docker volumes сохранены; сборки, миграционные изменения, удаление данных и сброс истории восстановления не выполнялись. Qwen и обработка Advance не включались.

**Финальная приёмка работоспособности не пройдена.** После первоначального прохождения healthcheck повторная проверка обнаружила таймауты проб Platform UI API и издателя SPIRE. Вычислитель переводчика загрузился и прошёл проверку точного выпуска через `/runtimez`, но первый наблюдавшийся реальный запрос завершился HTTP 500 и был возвращён в очередь на повтор. Зелёные heartbeat и строка `ONLINE` не выдаются за успешное вычисление перевода.

На последнем срезе `unhealthy` наблюдаются у Platform UI API и модели переводчика; издатель SPIRE восстановился. Число успешных переводов осталось 2093, опубликованных результатов — 2381. Это не завершённое восстановление работоспособности, несмотря на выполненный перезапуск всех постоянных ролей.

## Почему переводчик отсутствовал после предыдущего запуска

В [протоколе 22 октября](../translator-service/test/bounded-recovery-result-20261022.md) модель и worker были оставлены выключенными из-за нехватки памяти. [Запуск 25 октября](planned-restart-result-20261025.md) восстановил только ранее работавшие контейнеры через `compose start` и сохранил это временное исключение. Поэтому его результат `94/94 healthy` не подтверждает полноту инфраструктуры и работоспособность перевода. Общая композиция содержит обе роли; отдельного запретительного профиля для них нет, worker штатно ожидает готовности модели.

## Что произошло при фактическом запуске 26 октября

У модели сохранены 8 ГиБ RAM и два CPU. Первая попытка загрузки не достигла готовности в установленный предел. В текущем вычислителе предел загрузки нативного runtime берётся из `segment_timeout_seconds=180`, того же параметра, который ограничивает модельный шаг; общий запрос ограничен 240 секундами. Завершение дочернего процесса затем превысило отдельные пять секунд. После одного штатного native-повтора модель загрузилась: локальный llama.cpp вернул `200 /health`, а проверка `/runtimez` подтвердила закреплённый `translator_ref`. Docker не зафиксировал OOM.

На момент диагностики macOS сообщала предупреждающий уровень давления памяти и около 13,6–13,9 ГиБ занятого swap. В cgroup модели наблюдалось около 42% полного CPU pressure за минуту при лимите двух CPU; накопленное квотное throttling составляло лишь около 0,19 секунды. Это признаки конкуренции за ресурсы, а не доказательство, что модель упёрлась только в собственную CPU-квоту. OOM и отсутствие весов этим не подтверждены; размер прочитанного артефакта соответствует модельному выпуску.

Реальный запрос дошёл до `_post`, попал в обработку таймаута/ошибки нативного транспорта и вызвал `_stop_runtime`. Эта функция сбрасывает ссылку на дочерний процесс до подтверждения его завершения, вызывает `kill` и ожидает `wait(timeout=5)`. Исключение `subprocess.TimeoutExpired` из ожидания не обработано и перекрывает исходную причину запроса: частный API возвращает HTTP 500, а worker сохраняет `TRANSLATOR_MODEL_HTTP_ERROR` вместо точного кода исходного отказа. Подтверждённый дефект жизненного цикла требует отдельной адресной правки; увеличением таймаута healthcheck он не исправляется.

## Проверки и наблюдавшиеся результаты

- Три etcd перезапущены последовательно; после каждого подтверждена готовность.
- Перезапущены fencer и реплики PostgreSQL. Штатный Patroni switchover подтвердился HTTP 200; прежний ведущий вернулся репликой. Последующее чтение через новый ведущий подтвердило одного ведущего и две streaming-реплики на timeline 62 с нулевым отставанием. Защита, DCS и данные не пересоздавались.
- Первая проверка сразу после switchover попала в краткую недоступность API прежнего ведущего и остановила операторский сценарий. Результат переключения был сохранён; продолжение сверило текущую топологию и не отправляло switchover повторно.
- Восемь узлов MinIO перезапущены по одному; Kafka и собственные БД Keycloak/переводчика прошли проверки после рестарта. Интерфейсы, наблюдение, издатели и отправители запущены прежними контейнерами.
- Существующий recovery-таймер приостанавливался только на время обслуживания и возвращён. Нового контроллера, регистрации под новыми именами или reset не создавалось.
- Состав 91 регистрации и монотонная история attempts сохранены. Уже существовавшие защитные блокировки не снимались. Модель и worker переводчика отсутствуют в этом журнале: прежнее подключение не было выполнено, пока они оставались выключенными; один Docker healthcheck не означает автоматического восстановления `unhealthy`. Новая регистрация и изменение политик этим перезапуском не подменялись.
- Platform UI принял свежий `ONLINE` всех 15 инфраструктурных владельцев; у переводчика наблюдались свежие `ONLINE` всех восьми проверяемых частей. Это промежуточное наблюдение: последующие таймауты проб отражены в отрицательном результате финальной приёмки.
- Worker начал брать задания при прежней команде `RUNNING`, revision 1. До исполнения было 2093 успешных перевода и 2381 опубликованный outbox. После первого технического повтора эти числа не увеличились; `FAILED=288` также не увеличился. Задание не объявлено завершённым и не потеряно, очередь не очищалась.
- У Platform UI API и издателя SPIRE зафиксированы `Health check exceeded timeout (3s)`; у API наблюдался повторный запуск контроллером. Одноразовые задачи, завершившиеся с кодом 0, не считаются отсутствующими постоянными процессами.

## Оставшееся действие

После отдельного согласования адресная правка жизненного цикла реализована, проверена тестами и установлена только в модель переводчика; [результат и диагностика swap](../translator-service/test/model-lifecycle-swap-result-20261026.md) продолжают этот протокол. Это не отменяет зафиксированную выше неуспешную приёмку: завершённый перевод после замены и устойчивая работа при текущем давлении памяти ещё не подтверждены.

Оставшаяся проверка — реальный завершённый перевод с ACK outbox после замены модели и повторная устойчивая проверка всего состава. Причину опоздания инфраструктурных проб следует оценивать отдельно по ресурсным данным; массовое увеличение таймаутов, новая система восстановления и очередное изменение стека этим протоколом не предлагаются.

Закрытые снимки, журналы шагов и результаты сверки хранятся в игнорируемом `runtime/restart-20261026`. Публичный протокол не содержит текстов заданий, паролей, ключей или полного env. Наличие этого протокола не повышает статус продукта до `PRODUCTION_READY`.
