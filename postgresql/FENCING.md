# Ограждение PostgreSQL

Нормативное решение — [00-INFRA-20261106-0006-technical-storage-boundaries](../docs/adr/00-INFRA-20261106-0006-technical-storage-boundaries.md). Выбор ведущего, аренда, синхронная репликация и восстановление остаются у Patroni/etcd. Ограждение не выбирает новый primary: оно доказывает, что прежняя инкарнация возможного писателя завершена. Потеря heartbeat, HTTP timeout, `unhealthy` и отсутствие объекта сами по себе такого доказательства не дают.

## Прерванная остановка и возврат

Успешный `/fence` означает подтверждённое завершение прежней инкарнации, не готовность запущенной заново реплики. После фиксации `STOP_CONFIRMED` ответ отправляется без ожидания start: точный собственный процесс возвращает существующий последовательный цикл с прежними DCS-проверками, паузами и бюджетом. Исходно ручная остановка не возвращается. Разрыв HTTP после фиксации результата записывается как `fencing_response_delivery_failed` с кодом ответа и типом ошибки без её текста; он не меняет подтверждение на отказ и не инициирует повторное ограждение. Причины операции и задержки возврата остаются в прежнем аудите отдельно.

Если контейнер с тем же ID уже работает с другим `StartedAt`, согласование допустимо только для сохранённого `START_REQUESTED` с разрешённым возвратом и уже израсходованной попыткой. Под действующей native-арендой исполнитель устойчиво завершает прежнее намерение. Если аренда осталась прежней, подтверждается ранее выполненный возврат; если она изменилась, это не квитанция нового ограждения: создаётся отдельное намерение для текущего процесса и заново проверяется его завершение. Это устраняет постоянную блокировку выборов после потери ответа/записи start. Неизменившийся процесс сохраняет прежний бюджет; новая попытка без доказанной смены процесса его не обнуляет. Неожиданная смена инкарнации в других фазах, заменённый контейнер и ручная отмена не дают разрешения запуска.

Повтор продвижения выполняет штатный Patroni, не отдельный выборщик ведущего. Завершение сохранённого возврата отдельно выполняет цикл самого Docker-исполнителя: ему не нужен новый запрос продвижения. Он проверяет только ранее записанные собственные намерения, использует те же блокировки и подтверждает текущую native-аренду либо её отсутствие двумя линейными чтениями разных участников одного etcd-кластера. Согласованный пустой результат отличается от ошибки, неполного ответа, чужого кластера или недоступного endpoint; последние не разрешают запуск. Непосредственно перед start после повторной сверки цели выполняются ещё два чтения; изменение состояния откладывает действие. Подтверждённое отсутствие аренды допускает возврат только прежнего точного остановленного процесса в виде нового штатного Patroni, а не назначение ведущего или SQL-писателя вручную. В намерении и аудите отдельно фиксируется `return_admission=LEASE_ABSENCE_CONFIRMED` либо `LEASE_CONFIRMED`; старое подтверждение ограждения не переиспользуется. Новая команда start допускается не чаще устойчивой паузы и не более трёх раз на намерение; один проход выполняет не больше одной команды. Неудачный запрос ограждения сохраняет фазу `failed`, а отложенный возврат — `return_blocked` и `reason_code` в том же бессрочном аудите. Общий ограничитель рестартов не разблокируется и не сбрасывается этим согласованием.

В собственном томе `/var/lib/aelev-fencing` исполнитель хранит отдельное атомарное намерение для каждого узла: точный container ID и `StartedAt`, исходный признак работы, native-аренду, фазу и число команд возврата. Оно фиксируется до stop. Таймаут ответа не означает неисполненную команду: сначала проверяется фактическое завершение процесса. После перезапуска исполнителя незавершённое намерение сохраняется; остановленная им та же инкарнация может вернуться через новый Patroni только после описанного выше подтверждения состояния DCS. После трёх команд возврата дальнейшие попытки блокируются; неизвестный исход не обнуляет бюджет. Результат уже выполненного start подтверждается чтением вместо повторной остановки. Смена идентичности или невалидное состояние требуют оператора, не догадки о прежней роли.

Перед ручным обслуживанием узла проверьте, нет ли незавершённого намерения, и явно отмените его штатной административной командой внутри исполнителя. Операции используют один неблокирующий файловый барьер; при занятом барьере команда отказывает, а не конкурирует с активным fencing. Команда не запускает контейнер и не меняет DCS. Отмена сохраняется в аудите; после успешной отмены операторская остановка не будет автоматически возвращена:

```sh
python -m aelev_postgresql.fencing_intent inspect --node postgresql-3 --container EXACT_CONTAINER_ID
python -m aelev_postgresql.fencing_intent cancel --node postgresql-3 --container EXACT_CONTAINER_ID
```

`EXACT_CONTAINER_ID` заменяется проверенным полным идентификатором существующего намерения. Команды доступны только доверенному оператору внутри собственного исполнителя; runtime потребителей не получает Docker socket или право записи этого состояния. Произвольная внешняя Docker-команда не образует атомарную транзакцию с владельцем; ручное обслуживание нельзя проводить параллельно незавершённой операции.

Старый аудит без признака предыдущей работы не импортируется как автоматическое разрешение запуска. Для восстановления уже случившегося сбоя оператор отдельно подтверждает конкретные остановленные fencing контейнеры, проверяет их ID/времена и тома, одинаковую текущую аренду через два линейных DCS-чтения, живого ведущего и исполнитель. Реплики возвращаются по одной, только через Patroni/pg_rewind, с проверкой потока репликации и синхронного подтверждения. Ни данные, ни тома, ни DCS не очищаются. Требование переинициализации, несовместимая история или изменившийся ведущий останавливают процедуру. Общий unhealthy-восстановитель не используется как обход запрета запуска остановленных контейнеров, его бюджет не сбрасывается.

Если штатный pg_rewind не может восстановить историю, продолжение требует отдельного согласования конкретной реплики. Перед Patroni reinitialize сохраняются остановленный PGDATA и его контрольная сумма; архив не удаляется после восстановления. Проверяются неизменная аренда, текущий ведущий и идентичность целевой реплики, а копирование явно направляется из ведущего (`from_leader=true`). Это разрешённая оператором замена только локальной копии, не автоматическое удаление данных при rewind failure. Ведущий, DCS и тома не пересоздаются; смена ведущего или расхождение данных останавливают воздействие. [Проверка 19 октября](test/fencing-return-result-20261019.md) отделяет исправление исполнителя от результата восстановления конкретных узлов.

Перед обновлением Docker-поставки согласованно добавьте в собственный `.env` обязательные `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_IMAGE` и `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_RESTART_POLICY`, перечисленные в `.env.example`. Для сохранения прежнего образа первое поле получает его текущий digest, для адресного обновления — новый проверенный digest; образ SQL-узлов остаётся отдельным. Второе поле закрепляет действующую native-политику экземпляра. На экземпляре с исчерпанным бюджетом оператор задаёт `no`, чтобы замена образа не восстановила бесконечные native-рестарты. Скрытых запасных значений в Compose нет. Это не автоматическая перерегистрация нового container ID и не сброс существующего ограничителя.

## Один выбор для самостоятельного и общего запуска

`AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_MODE` обязателен и принимает только `docker`, `kubernetes`, `watchdog`. `off` и автоматического переключения на менее строгую защиту нет. `compose.yml` соединяет собственный `compose.runtime.yml` ровно с одним `compose.<режим>.yml`; дополнительных флагов `-f` не нужно. Верхняя оркестрация включает тот же `compose.yml` с тем же сервисным `.env` и ничего не переопределяет. Режим должен совпадать на всех трёх PostgreSQL; изменение проводится последовательно с контролируемым переключением ведущего, без удаления PGDATA или DCS.

Если включена публикация UI, при изменении состава между watchdog и исполнителем увеличьте `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_DESCRIPTION_REVISION` относительно всех ранее опубликованных ревизий. Минимум для состава с отдельной готовностью `writer` — 4. Обратное переключение также получает новую большую ревизию; одинаковая ревизия не может означать два разных состава по действующему UI-контракту. Identity, UUID и sequence остаются прежними.

В этой рабочей копии выбран `docker`: выключается только конкретный контейнер PostgreSQL, машина не перезагружается. Обычный запуск из каталога поставки:

```sh
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --no-build
docker compose --env-file .env ps
```

Общая оркестрация из `infrastructure` использует ту же команду `docker compose --env-file .env up -d`; только PostgreSQL можно поднять перечислением `etcd-1 etcd-2 etcd-3 postgresql-1 postgresql-2 postgresql-3`. Зависимость добавит собственный исполнитель в Docker-режиме. `stop` сохраняет контейнеры и все данные, `down` удаляет контейнеры и собственную сеть, но не тома без явно запрещённого здесь `--volumes`.

## Docker: завершение точной инкарнации контейнера

На каждом сервере PostgreSQL работает собственный `postgresql-fencer`, из того же сервисного образа. В локальной установке один исполнитель обслуживает три собственных узла одной Docker VM. На разных серверах каждый исполнитель имеет доступ только к своему локальному daemon, а в `FENCING_DOCKER_LOCAL_NODES` указан только локальный `postgresql-N`. Все три маршрутизируемых HTTPS-адреса исполнителей задаются через `NODE_N_FENCING_URL` и включаются в SAN сертификатов. Docker bridge между странами не растягивается; нужны DNS/маршрутизация и firewall.

После захвата штатной аренды Patroni вызывает свой `pre_promote`. Кандидат параллельно обращается к исполнителям обоих остальных узлов. Ограждаются оба, даже если один недавно объявлял себя репликой: сохранённый статус не исключает незавершённое прежнее продвижение. Это увеличивает время переключения, но не создаёт второго источника истины о ведущем. Исполнитель проверяет текущую линейризуемую аренду etcd, две собственные метки кластера/узла и ровно один подходящий контейнер. Он фиксирует намерение в устойчивом журнале, вызывает Docker `stop` с пятью секундами до SIGKILL и проверяет точный container ID, `Running=false`, `Restarting=false`, `Pid=0`.

Только после подтверждения завершения исполнитель возвращает квитанцию, привязанную к кандидату, инкарнации аренды, узлу и UUID попытки. Ранее работавший контейнер запускается заново штатным Patroni, который следует текущей аренде как реплика; остановленный оператором контейнер не запускается автоматически. Перед продвижением кандидат ещё раз сверяет аренду. Нет исполнителя, runtime недоступен, цели неоднозначны, журнал не записался или аренда изменилась — продвижение запрещено. Падение всего сервера без подтверждения завершения процессов намеренно блокирует автоматическое продвижение: этот режим не является внешним аппаратным ограждением недоступной машины.

Исполнитель имеет чувствительное право Docker socket. Его HTTP-интерфейс допускает только эти узлы и mTLS identity, но компрометация самого исполнителя с socket может дать права на весь Docker host; `cap_drop` этого не отменяет. Не публикуйте socket по TCP, ограничьте входящий HTTPS только членами данного кластера, защищайте ключи и поставляйте доверенный образ. PostgreSQL, издатель состояния и platform-ui Docker socket не получают. Издатель может выполнять только GET `/health` с CN `postgresql-probe`; изменяющий POST требует административного CN. Разделение прав Docker daemon через отдельный утверждённый authorization plugin не подменяется списком меток в Python.

### Переменные Docker и общие переменные ограждения

Все суффиксы в таблице имеют префикс `AELEV_INFRASTRUCTURE_POSTGRESQL_`; секретов среди них нет. Неиспользуемые переменные других режимов в рабочий `.env` не добавляются.

| Суффикс | Локальное значение | Влияние и необходимость |
|---|---|---|
| `FENCING_MODE` | `docker` | Выбирает ровно один механизм; отсутствие или неизвестное значение запрещают запуск. |
| `FENCING_TIMEOUT_SECONDS` | `20` | Предел отдельного запроса runtime/DCS/HTTPS, допустимо 5–60 секунд. Не заменяет аренду Patroni и не обещает общее RTO: попытка содержит несколько запросов. |
| `NODE_N_FENCING_URL` | `https://postgresql-fencer:19443` | Защищённый адрес исполнителя конкретного узла. На разных hosts адреса разные; hostname проверяется по SAN. |
| `FENCING_PORT` | `19443` | Собственный HTTPS-порт исполнителя, внутри контейнера и на host. |
| `FENCING_MEMORY` | `128m` | Лимит памяти отдельного Docker-исполнителя; истощение не разрешает обход ограждения. |
| `FENCING_STATE_VOLUME` | `aelev-infrastructure-postgresql-fencing-data` | Устойчивый технический журнал намерений и подтверждений; не PGDATA и не новая аренда. |
| `FENCING_DOCKER_SOCKET` | `/var/run/docker.sock` | Точный локальный Unix socket daemon, доступный только исполнителю. Docker Desktop разрешает его внутри VM; это не переносимый сетевой адрес. |
| `FENCING_SECRET_GID` | `20` | Числовая дополнительная группа только для чтения `secrets/fencing`: каталоги `0750`, файлы `0640`. На площадке задайте фактическую группу доставки; world-readable ключи запрещены. |
| `FENCING_DOCKER_LOCAL_NODES` | `postgresql-1,postgresql-2,postgresql-3` | Разрешённые местные узлы. На host N укажите только `postgresql-N`, а не чужие географические контейнеры. |

При уже существующей локальной PKI создайте только удостоверение нового исполнителя, не заменяя удостоверения/пароли кластера:

```sh
python3.13 prepare-tls.py --fencing-only
```

Нужны существующие `secrets/issuer`, `secrets/admin`, `secrets/node-1` и OpenSSL. Команда отказывает при существующем `secrets/fencing`. Для первоначальной поставки обычный `prepare-tls.py` создаёт и этот материал, если выбран не watchdog. Для внешней PKI выдайте серверный PEM с `serverAuth` и SAN всех настроенных адресов; состав файлов приведён в [secrets/README.md](secrets/README.md). Не доставляйте закрытые CA-ключи исполнителю.

Генерацию с CA выполняют на операторской станции, не требуют от каждого географического узла иметь материалы других узлов. Собственная healthcheck проверяет `https://localhost:<FENCING_PORT>`: серверный SAN также должен включать `localhost`. На узел доставляют только готовый `secrets/fencing`, без `issuer` и чужого PGDATA.

## Kubernetes: завершение точного Pod UID

Здесь выбирают `FENCING_MODE=kubernetes`. Docker socket и host watchdog отсутствуют. Рецепт Compose разрешает параметры, но не служит запуском Kubernetes: PostgreSQL отказывает в этом режиме вне своего точного Pod/namespace, чтобы Docker-писатель не получил подтверждение завершения другого Kubernetes-процесса. Тот же исполнитель работает как отдельный Deployment данной поставки, обращается к HTTPS Kubernetes API под собственным ServiceAccount и имеет только `get/list/watch/delete` трёх явно названных Pods в одном namespace. Доступа к Nodes, workloads соседей, `exec`, Secret API или прав force-delete ему не требуется.

Исполнитель проверяет собственные метки и UID, посылает обычный DELETE с UID precondition и положительным grace period, затем наблюдает изменения с исходного `resourceVersion`. Подтверждением является состояние того же UID `Failed`/`Succeeded` с завершением всех контейнеров, включая init-контейнеры. Такое сообщение публикует kubelet. `404`, событие `DELETED` без терминального состояния, `NotReady`, `Unknown` или потерянная история watch запрещают продвижение. Нельзя обходить это `--force --grace-period=0`: удаление объекта не доказывает остановку процесса на изолированной машине. Автоматическое восстановление Pod принадлежит его StatefulSet и штатному Patroni; исполнитель не выбирает/не создаёт новый primary.

`kubernetes/render-fencing.py` создаёт только собственный исполнитель, Service, PVC, ServiceAccount и минимальный RBAC. Это не полная поставка PostgreSQL в Kubernetes и не замена размещения трёх Patroni/etcd: PostgreSQL Pods должны уже принадлежать данному кластеру и запускать тот же образ/`pre_promote`. Для каждого задаются метки `io.aelev.postgresql.cluster=<CLUSTER>` и `io.aelev.postgresql.node=postgresql-N`, стабильное имя собственного StatefulSet Pod, собственные PGDATA/TLS и все адреса DCS/исполнителей. Перенос самой БД из Compose в StatefulSets, storage topology и anti-affinity требуют отдельного плана миграции; генератор не объявляет этот перенос выполненным.

Пример подготовки после проверки правильного Kubernetes context и существующего namespace:

```sh
if [ ! -f kubernetes/.env ]; then
  (umask 077; cp kubernetes/fencing.env.example kubernetes/.env)
fi
# Заполните реальные Pod names, namespace, storage class и SecretProviderClass.
python3.13 kubernetes/render-fencing.py --env-file .env \
  --env-file kubernetes/.env > kubernetes/fencing.generated.json
kubectl apply --dry-run=server -f kubernetes/fencing.generated.json
kubectl apply -f kubernetes/fencing.generated.json
```

Рендерер не выводит пароли или закрытые ключи и не создаёт Kubernetes Secrets. TLS-файлы поступают через установленный Secrets Store CSI Driver и заранее подготовленный `SecretProviderClass` утверждённого внешнего поставщика секретов; provider и его workload identity должны быть настроены оператором. Имена/состав PEM те же, что у Docker-исполнителя. Проектированные API token/CA выдаёт сам Kubernetes; токен перечитывается для каждого запроса. CSI Driver, provider, namespace, StorageClass, доступ к etcd и подписанный доступный из registry образ — проверяемые предварительные условия, не скрытые автоматически установленные зависимости.

| Суффикс | Значение примера | Влияние |
|---|---|---|
| `FENCING_KUBERNETES_API` | `https://kubernetes.default.svc` | Проверяемый TLS-адрес API control plane; редиректы с bearer token запрещены. |
| `FENCING_KUBERNETES_NAMESPACE` | `aelev-postgresql` | Единственная область трёх разрешённых целей и собственного Deployment. |
| `NODE_N_KUBERNETES_POD` | `postgresql-N-0` | Точное имя Pod; фактический UID сверяется при каждой операции. |
| `FENCING_KUBERNETES_SECRET_PROVIDER_CLASS` | `postgresql-fencing` | Имя уже настроенного CSI-источника собственных PEM-файлов. |
| `FENCING_KUBERNETES_STORAGE_CLASS` | `standard` | Реальная политика выделения постоянного диска технического журнала; класс должен существовать. |
| `FENCING_MEMORY` | `128Mi` | Память Deployment в Kubernetes-формате quantity, не Docker `128m`. |

`FENCING_TIMEOUT_SECONDS`, `FENCING_PORT` и `NODE_N_FENCING_URL` сохраняют смысл из предыдущей таблицы. Для удалённых PostgreSQL адрес Service должен быть действительно маршрутизируемым и подтверждён SAN, а не внутренним DNS чужого Kubernetes cluster. При недоступном kubelet контрольная плоскость не гарантирует нужное подтверждение; безопасность сохраняется ценой остановки продвижения.

## Watchdog: только выделенный host

Выберите `FENCING_MODE=watchdog` и добавьте только `AELEV_INFRASTRUCTURE_POSTGRESQL_WATCHDOG_DEVICE=/dev/watchdog` с точным устройством вашей платформы. `compose.watchdog.yml` передаёт устройство PostgreSQL; исполнителя runtime, его socket, API и квитанций здесь нет. Patroni требует работающий watchdog (`mode=required`, `safety_margin=-1`); отсутствие устройства запрещает продвижение. Устройство должно быть доступно UID/GID 70.

Watchdog может перезагрузить всю машину. Разрешён только выделенный Linux host/VM без чужих workloads и с предварительно проведённым контролируемым испытанием. Общая рабочая станция, Docker Desktop и несколько PostgreSQL-узлов одной машины для этого режима непригодны. Скрипты не открывают/не взводят устройство ради проверки, не загружают драйверы и не меняют права host автоматически. `soft_noboot` не обеспечивает ограждение и не допускается вместо рабочего watchdog.

## Проверка и ограничения

Модульные проверки лежат в `test/test_fencing.py`, конфигурационные проверки разрешают все три рецепта, Kubernetes-манифест проверяется без реального cluster. [test/fencing-lifecycle.py](test/fencing-lifecycle.py) проверяет действующий Docker-кластер: зависший Patroni при ещё живом SQL, завершение прежнего контейнерного процесса, один новый primary, сохранение подтверждённых данных и запрет продвижения без доступного исполнителя. Тест удаляет только свою точно названную временную SQL-таблицу и восстанавливает процессы; действующие тома, identities и другие проекты сохраняются. Результат: [test/fencing-lifecycle-result.md](test/fencing-lifecycle-result.md).

Код и моделирование Kubernetes не заменяют реального испытания kubelet/Pod termination на целевой версии cluster. Watchdog требует отдельного аппаратного учения на выделенных hosts. Локальные контейнеры одной Docker VM не подтверждают географическую независимость, WAN RPO/RTO или независимое резервное восстановление. Результат того же Docker-испытания через корневой Compose: [test/fencing-orchestration-result.md](test/fencing-orchestration-result.md).

Если на операторском host нет Python 3.13, после проверки собственного образа `checks` можно выполнить тот же тест привилегированным runner из каталога поставки. Это Unix-окружение с уже настроенным локальным Docker socket; удалённый Docker context требует отдельно подготовленного доступа, не копирования чужих credentials:

```sh
docker run --rm --workdir "$PWD" \
  -v "$PWD:$PWD" -v /var/run/docker.sock:/var/run/docker.sock \
  aelev/postgresql-checks:local python test/fencing-lifecycle.py
```

Внутренний и host путь bind совпадают для правильного разрешения Compose mounts; это вычисленный текущий каталог, не зашитый персональный путь. Модульные проверки socket не получают. Runner доверенный и имеет операторские права, ограничение проверяемых ролей задаёт сам тест; это не безопасная среда для исполнения произвольного кода.
