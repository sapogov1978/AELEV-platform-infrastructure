# Автоматическое восстановление HA после смены аренды — 19 октября 2026 года

## Результат

Рабочий кластер восстановлен без ручного продвижения: `postgresql-1` — единственный ведущий, `postgresql-2` и `postgresql-3` — `streaming/quorum`, все на timeline 25 с прежним system identifier. Обе реплики на заключительных проверках имели нулевое отставание. На ведущем фактически действует `ANY 1 ("postgresql-2","postgresql-3")`, `synchronous_commit=on`, `fsync=on`, `full_page_writes=on`; собственный `verify` подтверждает неизменность persisted safety-конфигурации.

Исправленные исполнитель и издатель установлены, не оставлены только в исходниках. Ручных `promote`, `reinitialize`, очистки DCS, замены PGDATA, томов или удостоверений не выполнялось. Три SQL-контейнера сохранили ID; две реплики штатно остановлены и возвращены самим ограждением. Ведущий и etcd вручную не перезапускались. Снимки, архивы прежнего восстановления и данные сохранены.

## Подтверждённая цепочка отказа

В журнале прежнего ведущего `postgresql-2` в 01:59:35 UTC, то есть 03:59:35 по Белграду, зафиксировано `demoting self because DCS is not accessible and I was a leader`. Ему предшествовали ошибки чтения/продления аренды через все три etcd endpoints и превышение срока повтора. Демотирование было штатным защитным действием. Причина первоначального роста задержки DCS этим журналом не доказана: нельзя приписывать его только модели, нехватке CPU или сну Mac.

После восстановления связи Patroni получал аренду и голоса других участников, но каждый `pre_promote` завершался отказом HTTP 409 исполнителя. Сохранённые намерения всех трёх узлов находились в `START_REQUESTED`: container ID совпадали с действующими, `StartedAt` уже изменился, процессы работали. Прежний start успел выполниться, однако подтверждение/фиксация завершения было прервано сменой аренды. Старый код разрешал согласовать такой старт только под прежней арендой; любая следующая аренда постоянно отвергалась как изменение инкарнации. Новые команды stop/start уже не выполнялись, поэтому перезапуск SQL наугад не исправлял причину.

Docker `/health` и UI проверяли только жизнь отдельных PostgreSQL/Patroni: все реплики были healthy, хотя реального primary не существовало. Линейные чтения трёх DCS endpoints совпадали; все SQL-участники имели одну историю timeline 24 и одинаковую replay position. Выбор пригодного кандидата оставлен Patroni, не проектному скрипту.

## Исправление и ограничения автоматики

Для того же container ID новый процесс согласуется только при сохранённых `START_REQUESTED`, разрешении возврата, положительном PID и уже учтённой попытке start. Прежнее намерение устойчиво завершается чтением. Под той же арендой допускается квитанция уже выполненного возврата; под новой арендой она не переиспользуется: заново ограждается текущая инкарнация под действующим native lock. После установки Patroni сам выполнил этот путь: аудит содержит `restart_reconciled`, новое `intent`, `terminated`, `restarted`, `confirmed`; в 07:59:18 UTC PostgreSQL завершил продвижение на timeline 25.

На одно незавершённое намерение сохраняются максимум три команды возврата. Несостоявшийся start не получает новый бюджет от смены аренды, перезапуска исполнителя или повторного запроса. Новый бюджет возможен только для отдельного ограждения уже доказанно нового работающего процесса, не для повторения старой неизвестной команды. Неожиданная смена инкарнации в других фазах, заменённый контейнер, ручная отмена, недоказанная остановка или неопределённая аренда закрыто отклоняются. Отказы получают устойчивый безопасный `reason_code`, без текста исключения и секретов.

Это исправление штатного `pre_promote`, а не второй HA-координатор или безлимитный восстановитель. При недоступном кворуме, ограждении или исчерпанных попытках безопасность по-прежнему важнее доступности. Общий операторский восстановитель не сброшен: его прежние попытки и блокировки сохранены, новые ID не зарегистрированы автоматически. Исполнитель сохраняет native `restart=no` после ранее исчерпанных трёх попыток. Издатель сохраняет оставшиеся две native-попытки при одной ранее израсходованной; обязательный собственный `UI_RESTART_POLICY` не позволяет замене образа молча вернуть бесконечную политику из шаблона. Такая блокировка требует отдельного явного допуска после разбора, а не скрытого обнуления истории.

## Проверки

Black, Ruff, строгий MyPy для 13 файлов и весь сервисный `test` прошли: 116 тестов. Регрессии включают восстановление потерянного завершения под новой арендой с обязательным новым stop, запрет согласования неожиданной инкарнации, конечные попытки при многократной смене аренды, устойчивый безопасный код отказа, all-replica/несколько primary/транспортную неопределённость и сохранение оставшегося restart budget издателя. Тестовые контейнеры не получали сеть, Docker socket или тома SQL/DCS; использовался bind собственного дерева исходников, проверки не читали рабочие credentials.

В контрольном чтении выполнено 12 циклов с десятисекундными паузами: 12 новых защищённых read-write подключений с последующей read-only транзакцией и 36 независимых линейных чтений native lease через три etcd endpoints. Ошибок нет, аренда не менялась. Медиана SQL-подключения и короткой транзакции — 0,162 с, максимум — 1,907 с; максимум DCS-чтения — 0,222 с. Максимум SQL включает подключение и несколько команд, не время одного statement; каждый statement ограничен 1,5 с. На заключительной проверке обе реплики `streaming/quorum`, отставание 0 байт. Это короткое окно, не суточное нагрузочное испытание.

После восстановления через собственный API-контейнер Advance и его канонический SQLAlchemy parser завершён прежде блокировавшийся read-only аудит опыта Qwen: все десять выбранных заданий имеют прежние полные отпечатки. Process Control также совпадает: `worker=PAUSED/2`, `durable-delivery=PAUSED/2`, `consumer=RUNNING/3`, `outbox=RUNNING/3`. Проверки не включали обработчик, не меняли решения и не сбрасывали Kafka offsets; обычный приём продолжал работать, неизменность всей общей очереди не утверждается. Исходный диагностический raw-libpq вызов не понимал SQLAlchemy multi-host query с портами; он не считался отказом рабочего подключения. Аудит выполнен тем же parser, что использует рабочий сервис.

Проверены Compose config, относительные ссылки, code fences, заголовок Mermaid и `git diff --check`; рабочий `.env` игнорируется Git. Прежние пользовательские изменения сохранены. Коммит и push не выполнялись.

## Не закрытые этим результатом вопросы

Первопричина первоначальных DCS timeouts требует отдельного измерения нагрузки/планирования, если повторится; увеличение защитных сроков или остановка чужих сервисов здесь не выполнялись. Сразу после возврата primary в журнале присутствовали два прикладных statement timeout, но это не новые отказы выборов или доказательство деградации DCS; короткое контрольное окно не доказывает устранение всех прикладных задержек. Новое искусственное падение рабочего ведущего, географические WAN-учения, Kubernetes/watchdog и восстановление независимой резервной копии не проводились. Реальное самовосстановление проверено на уже существовавшем all-replica отказе, без создания ещё одного рабочего инцидента.

Нормативные правила: [FENCING](../FENCING.md), [SPEC](../SPEC.md), [руководство](../USER_MANUAL.md). Штатная отмена продвижения при отказе hook описана в [документации Patroni](https://patroni.readthedocs.io/en/latest/modules/patroni.postgresql.html).
