# PostgreSQL — руководство пользователя

## Локальная проба издателя

`postgresql-status-publisher` использует собственный `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_IMAGE`, независимо от образа SQL-узлов. Закреплённый `aelev-platform-ui-client==1.1.2` проверяет подтверждённый heartbeat собственного журнала командой `python -S /opt/aelev/publisher-health.py AELEV_INFRASTRUCTURE_POSTGRESQL_`, без сетевой пробы или загрузки драйвера PostgreSQL. Это живость издателя, не готовность SQL-кластера. При обновлении сохраняйте том состояния и пересоздавайте только издатель; такая операция не требует обновления узлов, ограждения или очередей. Автовосстановление по `unhealthy` этим не устанавливается.

## Приоритет CPU и проба исполнителя

До обновления заполните три новых обязательных поля `AELEV_INFRASTRUCTURE_POSTGRESQL_SQL_CPU_SHARES`, `AELEV_INFRASTRUCTURE_POSTGRESQL_ETCD_CPU_SHARES` и `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_CPU_SHARES` из `.env.example`; в локальном профиле каждое равно 4096. Значение задаётся только в собственном env, без скрытого fallback. Это относительная доля при конкуренции внутри Docker VM, не выделенные ядра и не защита от нехватки CPU самой VM на хосте. При cgroup v2 обязательно сравните фактический `cpu.weight`: отсутствие явного Docker-веса и заданные shares преобразуются неодинаково; номинальное увеличение числа не гарантирует повышения относительно нетронутого контейнера. Память, SQL timeout и параметры аренды не изменяются.

Для уже работающих SQL/etcd не запускайте `compose up` ради изменения веса: он может пересоздать контейнеры. После отдельного согласования проверьте точные ID, метки, текущего ведущего, обе streaming-реплики и кворум DCS; примените `docker update --cpu-shares VALUE EXACT_CONTAINER_ID` только к согласованным работающим экземплярам, по одному. `VALUE` должен совпадать с собственным разрешённым Compose. Сверьте фактический вес, неизменность ID/StartedAt, native health и репликацию. Новые контейнеры получат тот же вес из Compose. При ошибке или смене роли дальнейшее воздействие прекращается; возврат прежнего веса выполняется только по записанным исходным значениям и не требует рестарта.

Docker fencing использует лёгкую `python -S -m aelev_postgresql.fencing_probe` вместо загрузки SQL-приложения каждые пять секунд. Проверка сохраняет TLS/mTLS, ограниченный ответ и общий срок; нормативные условия определены в [SPEC](SPEC.md#безопасность-и-ресурсная-изоляция). После регрессий новый digest записывают только в `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_IMAGE`, сохраняя действующую политику рестартов. Обновляют только `postgresql-fencer` через собственный Compose с `--no-deps --no-build`; том аудита, бюджет и identities SQL/DCS сохраняются. Краткая недоступность исполнителя блокирует новое продвижение, не отменяет защиту. Дорогие проверки других владельцев и общая нехватка CPU требуют отдельной диагностики, не автоматического расширения этого обновления.

## Структура поставки

### Нативная проба узла

Опциональное локальное восстановление через [операторскую задачу](../USER_MANUAL.md#ограниченное-восстановление-по-unhealthy) регистрирует SQL/etcd/fencing только с `--guard postgresql/recovery_guard.py`, выполняемым с хоста. Пример предварительной читающей проверки: `python3 recovery_guard.py <точный-container-ID>`. Положительный ответ не является командой рестарта; текущий ведущий получает `PRIMARY_REQUIRES_SWITCHOVER`, неопределённость — отказ. Перед ручным обслуживанием сначала приостановите зарегистрированную цель через `suspend`, после замены потребуется явный новый допуск. Бюджет native/unhealthy общий и сам не пополняется.

`python -S -m aelev_postgresql.probe` проверяет только свой Patroni `/health` и persisted `/config`, без SQL-подключения, загрузки SQL-драйвера или обращения к другим узлам. Загрузка TLS и обращения имеют общий предел три секунды, внешний timeout Docker остаётся пять секунд. TLS/mTLS и сверка безопасной конфигурации обязательны; таймаут не означает доказанную остановку SQL. Подробные инварианты определены в [SPEC](SPEC.md#устойчивость-и-управление). Новый образ устанавливается по одному узлу при подтверждённом здоровье/репликации двух остальных и доступном etcd/fencing; перед обновлением ведущего нужен контролируемый switchover Patroni. Не пересоздавайте все узлы одновременно и не используйте перезапуск вместо исправления отклонённой конфигурации DCS.

```text
postgresql/
├── README.md, SPEC.md, TASKS.md, CHANGELOG.md
├── FENCING.md                    # полномочия и три механизма ограждения
├── compose.yml                   # выбирает ровно один механизм из env
├── compose.runtime.yml           # собственная каноническая топология
├── compose.docker.yml, compose.kubernetes.yml, compose.watchdog.yml
├── .env.example                  # шаблон; .env — рабочие настройки вне Git
├── Dockerfile, entrypoint.sh
├── pyproject.toml, poetry.lock
├── src/aelev_postgresql/          # настройка, проверки, provision, ограждение
├── status_publisher.py, vendor/
├── prepare-tls.py                # первичная локальная PKI
├── kubernetes/
│   ├── fencing.env.example
│   └── render-fencing.py         # собственный исполнитель, не общий кластер
├── secrets/
│   ├── README.md
│   ├── issuer/                   # только оператор, никогда не runtime
│   ├── node-1/, node-2/, node-3/  # отдельные удостоверения PostgreSQL
│   ├── etcd-1/, etcd-2/, etcd-3/  # отдельные удостоверения etcd
│   ├── admin/, fencing/
│   ├── status/, status-admin/
│   └── ...                       # доставляемый материал вне Git/образа
└── test/                         # проверки и читаемые результаты
```

Дерево показывает значимые файлы поставки, а не кэши инструментов. `.env`, содержимое `secrets/` и производные `runtime/` создаются оператором и не входят в Git или образ; документация `secrets/README.md`, где она есть, остаётся в Git. Постоянные данные находятся в именованных Docker volumes из Compose, не в каталоге исходников.

## Назначение

При прерванном Docker fencing сначала используйте [процедуру возврата](FENCING.md#прерванная-остановка-и-возврат): сохранённое намерение не равно ручному выключению, а неизвестный результат команды требует сверки. Старые остановленные контейнеры не запускаются общей unhealthy-задачей; их адресное восстановление требует отдельного подтверждения владельца и последовательной проверки репликации. Обновление только исполнителя допускает отдельный `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_IMAGE`; исчерпанный бюджет сохраняется с `AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_RESTART_POLICY=no`, без обновления SQL-узлов и сброса ограничителя.


Самодостаточная инфраструктурная поставка транзакционной БД: PostgreSQL 17.6, Patroni 4.1.5 и отдельный трёхузловой etcd 3.6.10. PostgreSQL хранит данные, Patroni управляет ведущим и репликацией, etcd хранит только согласованное состояние управления кластером. Компонент не знает имён потребителей, их схем или назначения записей. Нормативное поведение находится в [SPEC.md](SPEC.md), текущие ворота проверки — в [TASKS.md](TASKS.md).

Собственный издатель имеет `stop_grace_period: 2m`: это время на завершение текущего запроса и подтверждение отписки через удалённый HTTPS, не запасное значение env и не бесконечное ожидание. Если связь недоступна, неподтверждённый выход сохраняется в журнале, а UI не скрывает строку как штатно завершённую.

В «Состоянии» верхняя строка называется «Хранилище структурированных данных» (`Structured data storage`) и отражает назначение, а раскрываемый состав показывает технологии и процессы этой поставки. Ревизия 3 добавляет собственный исполнитель ограждения в режимах Docker/Kubernetes; в watchdog-режиме такого процесса нет. UUID, identity и последовательность сохраняются.

Три узла PostgreSQL образуют один кластер с одним ведущим и двумя физическими репликами, не три независимые базы и не три писателя. Подтверждение COMMIT ожидает устойчивой записи WAL ведущим и минимум одной репликой (`ANY 1`). Перенос через WAN увеличивает задержку записи минимум на время связи с подтверждающей репликой. Потеря одной пары PostgreSQL/etcd допускает продолжение; без подходящей реплики запись ждёт, без большинства etcd ведущий прекращает работу. Это не бесконечная доступность и не резервная копия.

## Секреты: получение и подготовка

Полный перечень PEM/паролей находится в [secrets/README.md](secrets/README.md); здесь — порядок происхождения и доставки, не только реакция на отсутствие файла.

| Каталог | Источник и кому разрешена доставка |
|---|---|
| `secrets/node-N` | PKI PostgreSQL выдаёт серверную пару, admin/replication clientAuth и доверие; внешнее хранилище выдаёт admin/replication пароли. Только соответствующему PostgreSQL/Patroni. |
| `secrets/etcd-N` | Отдельная PKI etcd: серверная пара с serverAuth/clientAuth для peer, публичная CA и собственная клиентская проба. Только соответствующему etcd. |
| `secrets/admin` | Административное SQL/REST удостоверение и admin-password; provision-password — пароль точной создаваемой роли. Только явной задаче администратора, не потребителю. |
| `secrets/fencing` | Собственные TLS/etcd удостоверения исполнителя. Нет SQL-паролей или ключей UI; необходимы только в Docker/Kubernetes. |
| `secrets/issuer` | Закрытые ключи локальных CA PostgreSQL/etcd и публичные сертификаты. Создаёт оператор стенда; не доставляются узлам/исполнителю. |
| Kubernetes API-доступ | Проецируемый service-account token и публичная CA API Kubernetes по ограниченному RBAC из [FENCING.md](FENCING.md), не случайный пароль и не cluster-admin kubeconfig. |

Первичная локальная команда — `python3.13 prepare-tls.py` после заполнения собственного env; для добавления только исполнителя к старому стенду — `python3.13 prepare-tls.py --fencing-only`. Обе защищают существующие identities от перезаписи. Генератор создаёт 90-дневные сертификаты, 365-дневные CA и отдельные случайные пароли; SQL-роль/CN должны совпадать. Схема выдачи рабочей PKI и пример CSR находятся в разделе [подготовки TLS](#подготовка-инструментов-и-tls). Пароль новой прикладной роли генерирует/выдаёт её владелец либо внешнее хранилище и временно доставляет как provision-password; после операции он не становится общим паролем PostgreSQL.

Локальная генерация использует `umask 077`: каталоги `0700`, файлы `0600`. Штатный entrypoint с исходными правами копирует только собственную роль в tmpfs и задаёт runtime-права; не раздавайте `issuer` ради чтения узлом. etcd получает только собственный каталог через read-only mount. В Kubernetes TLS доставляется из внешнего источника через CSI; Kubernetes Secret не выбирается каноническим хранилищем.

Генератор явно задаёт SKI локальных CA, SKI/AKI всех leaf, включая fencing, по [OpenSSL X.509 extension configuration](https://docs.openssl.org/3.0/man5/x509v3_config/). Он не зависит от неявного добавления AKI конкретной версией OpenSSL; новые цепочки проверяются `openssl verify -x509_strict`. Существующие identities сохраняются без перезаписи.

При обновлении SQL-паролей согласуйте фактические роли БД, все соответствующие подключения Patroni/репликации и доставленные файлы; изменение исходного файла само по себе не меняет пароль сохранённой роли. Удостоверения обновляют последовательно по узлам, сохраняя большинство etcd, один ведущий и подтверждающую реплику. Нельзя менять CA и сразу отзывать старую цепочку на всех узлах. Watchdog не требует секретного файла устройства; право доступа к устройству и последствия для host отдельно проверяются оператором.

### Секреты издателя состояния

Пути ниже соответствуют шаблону `UI_SECRET_ROOT=./secrets/status`; при другом значении используйте собственный настроенный каталог. Источники доверия определяются адресами, не совместным размещением: узел в другой стране получает публичные цепочки CA и своё удостоверение через защищённую доставку, а не доступ к чужой папке.

| Файл | Откуда получить и зачем |
|---|---|
| `shell-ca.crt` | Проверенная публичная цепочка CA HTTPS-сервера оболочки; получить у её оператора. Это не CA клиентских издателей. |
| `identity-ca.crt` | Проверенная публичная цепочка CA HTTPS IdP; получить у оператора IdP. |
| `publisher.crt`, `publisher.key` | Собственное удостоверение `clientAuth`; его выпускающая CA должна входить в `publisher-ca.crt` приёмника UI. Закрытый ключ принадлежит только этому издателю. |
| `client-secret` | Выдаёт Keycloak для собственного confidential client; сохраняет `postgresql-status-provision`. Не генерируйте произвольный пароль вместо секрета существующего OIDC-клиента. |
| `postgresql-ca.crt`, `postgresql-probe.crt/key` | Доверие PostgreSQL и отдельный clientAuth с CN `postgresql-probe`, только чтение health Patroni/ограждения; не admin key. |
| `etcd-ca.crt`, `etcd-probe.crt/key` | Доверие etcd и отдельный clientAuth для собственной health-пробы DCS, не SQL identity. |
`UI_ADMIN_ROOT` содержит отдельные `admin-user` и `admin-password`: имя и действующий пароль администратора развёртывания Keycloak получают у оператора IdP или из внешнего хранилища. Это не пароль service account и не пароль пользователя браузера. Доставьте их файловым механизмом; например, `install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password`, а имя запишите в `admin-user` без секрета. Provision должен иметь право записи в `UI_SECRET_ROOT`, runtime — только чтение.

Перед локальной подписью проверьте `openssl version` и поддержку OpenSSL 3; при отсутствии используйте утверждённый пакет вашей ОС (`brew install openssl@3` на macOS, `sudo apt-get install openssl` на поддерживаемой Debian/Ubuntu) или подготовленную операторскую станцию. Эти команды не устанавливают CA в системное доверие и не выполняются при запуске контейнера.

Первичная доставка административных файлов (пути источника и имя замените данными своего IdP, не пароль в команде):

```sh
umask 077
install -d -m 750 secrets/status-admin
test ! -e secrets/status-admin/admin-user && test ! -e secrets/status-admin/admin-password || exit 1
STATUS_ADMIN_USER=deployment-admin
printf '%s\n' "$STATUS_ADMIN_USER" > secrets/status-admin/admin-user
install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password
chmod 640 secrets/status-admin/admin-user
```

Имя deployment-admin — пример существующей identity, не команда создания пользователя. Если у вас другое имя или UI_ADMIN_ROOT, задайте их явно; GID каталога/файлов должен совпадать с UI_SECRET_GID, а владелец — с UI_PROVISION_UID. Уже доставленные пароли не перезаписываются первичной командой. После удаления одноразового контейнера пароль не нужен рабочему издателю; локальную административную доставку уберите из runtime-узла или выдавайте заново только на время provision.


Для новой локальной identity можно создать ключ и CSR на доверенной операторской машине. Нужен OpenSSL 3 для `-copy_extensions`; пути `/secure/...` ниже заменяются выбранными операторскими файлами, это не обязательные каталоги сервиса. Публичные CA берутся из проверенного источника; неизвестный сертификат из сети не становится доверенным только потому, что назван `ca.crt`.

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/publisher.key && test ! -e secrets/status/publisher.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=publisher -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/publisher.key -out secrets/status/publisher.csr
# Только локальный тест: ключ CA остаётся на операторской машине, не в runtime.
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/publisher.csr \
  -CA /secure/ui-publisher-ca.crt -CAkey /secure/ui-publisher-ca.key \
  -CAcreateserial -out secrets/status/publisher.crt
install -m 640 /secure/ui-server-ca.crt secrets/status/shell-ca.crt
install -m 640 /secure/idp-ca.crt secrets/status/identity-ca.crt
chmod 640 secrets/status/publisher.key secrets/status/publisher.crt
```

Тестовую CA издателей создаёт оператор локальной оболочки при её явной подготовке PKI; берутся именно `issuer/publisher.crt/key`, не серверный ключ UI. В рабочей среде последнее подписание локальной CA не выполняют: удостоверение и обновляемую identity доставляет утверждённая PKI/SPIRE по [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md). CSR можно передать CA, закрытый ключ нельзя. Перед включением издателя доставьте также перечисленные файлы нативных проб и выполните собственный `--profile provision run --rm postgresql-status-provision` из раздела запуска.


Для новой локальной PostgreSQL-пробы, не являющейся рабочей SVID, используйте собственную операторскую CA, которой доверяет health endpoint; существующие файлы не перезаписывайте. Это отдельная пара, не копия native client key:

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/postgresql-probe.key && test ! -e secrets/status/postgresql-probe.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=postgresql-probe -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/postgresql-probe.key -out secrets/status/postgresql-probe.csr
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/postgresql-probe.csr \
  -CA secrets/issuer/postgresql.crt -CAkey secrets/issuer/postgresql.key \
  -CAcreateserial -out secrets/status/postgresql-probe.crt
install -m 640 secrets/issuer/postgresql.crt secrets/status/postgresql-ca.crt
chmod 640 secrets/status/postgresql-probe.key secrets/status/postgresql-probe.crt
```

Для отдельной локальной etcd-пробы применяются те же ограничения CA и хранения; создайте другую пару, не переиспользуя PostgreSQL probe или native client key:

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/etcd-probe.key && test ! -e secrets/status/etcd-probe.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=etcd-probe -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/etcd-probe.key -out secrets/status/etcd-probe.csr
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/etcd-probe.csr \
  -CA secrets/issuer/etcd.crt -CAkey secrets/issuer/etcd.key \
  -CAcreateserial -out secrets/status/etcd-probe.crt
install -m 640 secrets/issuer/etcd.crt secrets/status/etcd-ca.crt
chmod 640 secrets/status/etcd-probe.key secrets/status/etcd-probe.crt
```


### Хранение, доступ и ротация

Секреты разделяются по среде, владельцу и роли. Локальные файлы — только материал стенда или доставка, не каноническое production-хранилище; рабочий источник — внешнее утверждённое хранилище, доставка в память/tmpfs по 00-INFRA-20261106-0007-workload-and-operator-identity. Не включайте секреты в Git, образ, архив исходников, команды с подстановкой содержимого или отчёты. Не запускайте `set -x`, не публикуйте раскрытый `docker compose config`; проверяйте через `config --quiet`. Резервные копии секретов хранятся отдельно, зашифрованно, с ограниченным доступом; закрытые CA — только у оператора/KMS/HSM, никогда у рабочего процесса.

Для status-файлов установите каталоги `0750`, файлы `0640`, группу из собственного `UI_SECRET_GID`; владельцем каталога должен быть оператор с `UI_PROVISION_UID`, которому разрешена запись client-secret. UID рабочего издателя остаётся заданным собственным образом/Compose; дополнительная группа даёт только чтение. В командном примере ниже STATUS_SECRET_GID — числовое значение уже настроенного UI_SECRET_GID, не новая переменная сервисного env. Не делайте ключи общедоступными ради запуска. Права нативных секретов описаны отдельно выше.

```sh
: "${STATUS_SECRET_GID:?set the numeric GID from your UI_SECRET_GID}"
chgrp "$STATUS_SECRET_GID" secrets/status secrets/status/*
chmod 750 secrets/status
chmod 640 secrets/status/*
```

Для отдельного административного каталога примените ту же группу, `0750` каталогу и `0640` обоим файлам; владельцу из UI_PROVISION_UID должно быть разрешено чтение admin-password и запись client-secret в status. Keycloak использует административный пароль через env, а не status-admin.

Проверьте срок, SAN/EKU и цепочку сертификата до запуска: `openssl x509 -in secrets/status/publisher.crt -noout -dates -ext extendedKeyUsage`, `openssl verify -CAfile /secure/ui-publisher-ca.crt -purpose sslclient secrets/status/publisher.crt`. Локальное удостоверение из команды действует 30 дней и не обновляется автоматически. Для смены CA сначала доставляют доверие старой и новой цепочкам, затем новые удостоверения, проверяют соединения и только после этого отзывают старые. Ротацию проводят через отдельный подготовленный набор файлов и контролируемое пересоздание собственной роли; генераторы первичного запуска не используют для перезаписи активных ключей. Новый client-secret сначала создают в собственном клиенте Keycloak, затем доставляют повторным собственным provision и пересоздают издателя; обычный повтор provision сам по себе не является ротацией. UUID, identity, ревизия и журнал последовательностей при этом сохраняются.


## Структура

- `compose.yml` — единственная точка запуска; включает собственную общую топологию `compose.runtime.yml` и ровно один рецепт `compose.docker.yml`, `compose.kubernetes.yml` или `compose.watchdog.yml`, выбранный сервисным env. Оркестратор не хранит поправок.
- `.env.example` — полный несекретный шаблон; игнорируемый `.env` — реальные настройки этого экземпляра.
- `Dockerfile`, `pyproject.toml`, `poetry.lock`, `src`, `entrypoint.sh` — независимая сборка и небольшие эксплуатационные команды; выбор ведущего не реализован проектным кодом.
- `secrets` — игнорируемые файловые пароли и TLS; закрытые ключи CA находятся только у оператора в `secrets/issuer` и не монтируются в контейнеры.
- `prepare-tls.py` — явное первоначальное создание локальных удостоверений; повторный запуск не перезаписывает существующие.
- `test` — Python-проверки и читаемые результаты; каталог исключён из сборки.
- [FENCING.md](FENCING.md) — механизмы Docker/Kubernetes/watchdog, полномочия, все их env-параметры и оригинальная документация; `kubernetes` содержит генератор только собственного исполнителя.
- История заменённой одиночной поставки доступна в Git; в текущем дереве нет архивного каталога или второго способа запуска.

## Подготовка инструментов и TLS

Нужны Docker с Compose v2 и поддержкой `include`, Python 3.13 для операторских скриптов и OpenSSL. Python внутри образа уже установлен. JDK и keytool здесь не нужны.

```sh
docker version
docker compose version
python3 --version
command -v openssl
openssl version
```

Если инструмента нет: macOS — `brew install python@3.13 openssl@3` и Docker Desktop; Debian/Ubuntu — Docker Engine и Compose из официального Docker-репозитория, `sudo apt-get install openssl`, Python 3.13 из поддерживаемой поставки вашей ОС; Alpine — `apk add openssl`. Python 3.12 не подменяет закреплённый Python 3.13. На сервере без Python 3.13 генератор можно запустить из закреплённого builder-образа с установленным OpenSSL; рабочему PostgreSQL интерпретатор сервера не нужен.

Для первоначальной локальной подготовки из этого каталога:

```sh
if [ ! -f .env ]; then
  (umask 077; cp .env.example .env)
fi
python3 prepare-tls.py
docker compose --env-file .env config --quiet
docker compose --env-file .env build postgresql-1
```

Копирование шаблона выполняют только при отсутствии `.env`. В этой рабочей копии `.env` и TLS уже подготовлены. Генератор создаёт отдельные CA PostgreSQL и etcd, серверные сертификаты каждого узла, административную и репликационную удостоверения, клиентские удостоверения Patroni/etcd и случайные пароли. Срок сертификатов — 90 дней, локальных CA — 365 дней; это операторский стенд, не автоматическая SPIRE-ротация. Пароли не помещаются в `.env`, argv, отчёты или Git. На ошибке генерации результат не используется; частичные удостоверения не перезаписываются автоматически.

Для рабочей установки используйте утверждённую PKI/SPIRE и процедуру ротации, отдельную от тестового домена доверия. Серверный SAN должен включать точный маршрутизируемый `NODE_N_HOST`/`NODE_N_ETCD_HOST`; клиентский PostgreSQL CN совпадает с SQL-ролью. Файловые имена и формат PEM перечислены в [secrets/README.md](secrets/README.md). Пример CSR для имеющегося приватного ключа узла:

```sh
openssl req -new -key secrets/node-1/server.key \
  -out secrets/node-1/server.csr -subj /CN=postgresql-1 \
  -addext 'subjectAltName=DNS:db-1.example.net'
```

Отправьте CSR утверждённому удостоверяющему центру; поместите выданную цепочку в `server.crt`, доверенную цепочку в `ca.crt`. CA должен выдать серверу `serverAuth`, клиенту `clientAuth`; etcd peer-сертификат требует обе цели. CSR и локальный пример DNS не создают рабочую identity. Не копируйте `issuer` и материалы других узлов на сервер: PostgreSQL-узлу нужны только `secrets/node-N`, etcd — только `secrets/etcd-N`; администратору — `secrets/admin`.

## Самостоятельный односерверный запуск

Все команды выполняются из этого каталога после подготовки собственного образа, `.env` и удостоверений. При `FENCING_MODE=docker` обычная команда запускает три etcd, три PostgreSQL/Patroni и собственный исполнитель ограждения; watchdog не требуется и машина не перезагружается. Издатель включается отдельно профилем `ui` после его настройки. Если данные уже используются общей инфраструктурой, управляйте узлами через [её Compose](../README.md): две группы не должны одновременно запускать писателей одного кластера.

```sh
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --no-build --pull never
docker compose --env-file .env ps --all
docker compose --env-file .env exec -T postgresql-1 python -m aelev_postgresql verify
```

`verify` только сравнивает фактическую конфигурацию с безопасной политикой. Для допуска проверьте здоровье всех узлов и etcd, ровно одного ведущего и две реплики по защищённому `/cluster` API Patroni; одна зелёная строка контейнера не доказывает синхронность, целостность резервной копии или независимость площадок. `stop` сохраняет контейнеры и тома, `down` снимает контейнеры/сети без удаления именованных данных. Для подготовленного издателя используйте тот же выбранный профиль при остановке и повторном запуске; не выполняйте `up` всего профиля `provision`.

## Размещение на трёх независимых серверах

На каждом Linux-сервере или виртуальной машине находятся эта же поставка, один собственный том PostgreSQL, один том etcd и свои TLS-файлы. В согласованном `.env` всех узлов задайте маршрутизируемые DNS/IP, порты и `BIND` реального интерфейса. Начальная конфигурация адресов и механизм ограждения должны совпадать у всех участников. Docker DNS из шаблона предназначен только для односерверной проверки; между серверами Docker-сеть не растягивается.

До запуска выберите [механизм ограждения](FENCING.md) через `FENCING_MODE`. Локальный шаблон и рабочий `.env` используют `docker`: собственный mTLS-исполнитель завершает только точный PostgreSQL-контейнер и не перезагружает host. Для разнесённых Docker-серверов задайте три реальные `NODE_N_FENCING_URL`, собственные SAN и только местный узел в `FENCING_DOCKER_LOCAL_NODES`. `kubernetes` использует ограниченный API-исполнитель с подтверждённым завершением Pod UID; `watchdog` требует отдельно проверенного устройства на выделенном host и может перезагрузить всю машину. Неизвестный режим или недоступное подтверждение не разрешают обход.

В трёх терминалах соответствующих host запустите только их пару:

```sh
# Host 1
docker compose --env-file .env up -d --no-build etcd-1 postgresql-1
# Host 2
docker compose --env-file .env up -d --no-build etcd-2 postgresql-2
# Host 3
docker compose --env-file .env up -d --no-build etcd-3 postgresql-3
```

Один и тот же предварительно проверенный образ поставляется всем узлам; для рабочей среды `IMAGE` задаёт адрес registry с digest подписанного выпуска. Образ не требует монорепозитория. Первоначально нужны минимум два etcd и два PostgreSQL для рабочего синхронного подтверждения; проверка штатной поставки требует готовности всех трёх пар. Постоянные процессы перезапускаются при аварийном выходе, но `unhealthy` сам по себе не вызывает перезапуск Docker.

Firewall допускает SQL-порты только разрешённым владельцам своих баз, REST-порты только участникам и операторам, etcd client/peer-порты только членам этого кластера и его административным проверкам. Публичный интернет не является допустимой сетью DCS. mTLS не заменяет firewall. У etcd отдельная CA; Patroni использует HTTPS gRPC gateway, поэтому CN-сопоставление пользователей etcd не выдаётся за действующую ACL. Выданное этой CA удостоверение доверено выделенному DCS данного компонента.

На одной Docker VM аппаратную независимость создать нельзя. Самостоятельный и общий запуск теперь используют реальный Docker-механизм без тестового отключения защиты. Начальный `up -d` может кратковременно остановить соседние PostgreSQL во время ограждения; `compose --wait` способен досрочно вернуть ошибку на такой штатной остановке. Проверяйте итоговую готовность всех частей и один primary после завершения переключения, а не только код этого промежуточного ожидания. Следующий тест — не обычная проверка здоровья: он намеренно создаёт отказ Patroni и ограждения, переключает ведущего и временно нарушает доступность записи. Выполняйте только в отдельно согласованное окно и с точкой запуска, соответствующей действующей группе:

```sh
python3.13 test/fencing-lifecycle.py
```

Полный `test/cluster-lifecycle.py` самостоятельно запускает все реальные роли обычным Compose, проверяет их и удаляет созданные ресурсы; при наличии прежних томов/контейнеров/сети кластера отказывается проводить разрушающие сценарии. Прежний обход без ограждения удалён из текущего дерева, не подключается командами и не является рабочим режимом; история рецепта остаётся в Git.

При неуспехе рядом с заданным `--report` до cleanup создаётся `.diagnostic.json` с фазой сценария, номером намеренно отключённого узла, bounded Docker state и счётчиками фиксированных ошибок Patroni/fencing/DCS. Он не содержит credentials, SQL, container IDs, host paths или raw logs. Изолированный повтор на чистом GitHub runner запускается полем `diagnostic_stage=postgresql-lifecycle`, `diagnostic_repetitions=3` в общем clean-room workflow; эти результаты не заменяют итоговое evidence всех функций.

Process health и persisted DCS config не доказывают уже сформированный SQL sync quorum. Lifecycle дополнительно ждёт до 120 секунд фактический `ANY 1` и минимум одну `streaming` sync/quorum-реплику, прежде чем проверять транзакции; отключённый `synchronous_commit` немедленно отклоняется. Локальные диагностические logs исключены из Git и Docker build context, а безопасный отчёт сохраняется вне исходников.

Опциональный `--fault-target 1|2|3` выбирает узел, который должен быть ведущим перед pair-loss: один защищённый [Patroni REST switchover](https://patroni.readthedocs.io/en/latest/rest_api.html#switchover-and-failover) и последующая проверка всех SQL-ролей/quorum. Три диагностических повтора покрывают все три цели; автоматический обычный full-local сценарий сохраняет естественный исходный выбор Patroni.

## Проверка, подключение и подготовка базы

```sh
docker compose --env-file .env ps
docker compose --env-file .env --profile provision run --rm --no-deps database-provisioner verify
```

После изменения `MAX_CONNECTIONS`/`SHARED_BUFFERS` единственный источник значений остаётся `.env`. Явно примените его через штатный Patroni API, затем проверьте конфигурацию и выполните контролируемый последовательный рестарт узлов, которым Patroni выставил `pending_restart`:

```sh
docker compose --env-file .env --profile provision run --rm --no-deps database-provisioner configure
docker compose --env-file .env --profile provision run --rm --no-deps database-provisioner verify
```

Команда `configure` получает параметры только из env и фиксированной безопасной политики, использует mTLS и административную аутентификацию, не сбрасывает DCS и не меняет идентичность кластера. Проверка здоровья также сверяет DCS с этой конфигурацией. Несовпадение требует явного применения, а не скрытого fallback. Для уже работающего узла до рестарта передайте согласованные env-настройки его контейнеру; не оставляйте различающиеся версии конфигурации на серверах.

`verify` сравнивает фактическую сохранённую конфигурацию DCS с безопасными инвариантами выпуска. `bootstrap.dcs` применяется Patroni только при первом создании кластера: рестарт не исправляет произвольную правку DCS. Отключать строгую синхронность, `fsync`, проверку timeline или выбранное ограждение нельзя; несоответствие означает отсутствие допуска, а не автоматическое изменение действующего кластера. Повторная инициализация etcd или очистка его данных не является способом применить настройки.

Клиент использует PostgreSQL/libpq с тремя адресами и соответствующими портами, `target_session_attrs=read-write`, `sslmode=verify-full`, доверенной CA и собственным клиентским сертификатом/паролем. Например, шаблон технических параметров: `host=db-1.example.net,db-2.example.net,db-3.example.net port=15432,25432,35432 target_session_attrs=read-write sslmode=verify-full connect_timeout=3`. Список не балансирует запись: libpq выбирает доступного ведущего при новом соединении. Уже открытое соединение разрывается при failover; пул должен переподключиться. Драйвер без multi-host требует собственное утверждённое отказоустойчивое маршрутизирующее решение; одиночный HAProxy здесь не добавлен.

Схемой и миграциями владеет потребитель своей базы. Оператор передаёт универсальному provisioner одну точную базу и роль; это не каталог клиентов. Пароль операции находится в `secrets/admin/provision-password`, клиентский сертификат роли выдаётся отдельно с совпадающим CN.

```sh
docker compose --env-file .env --profile provision run --rm --no-deps \
  -e AELEV_INFRASTRUCTURE_POSTGRESQL_PROVISION_DATABASE=database_name \
  -e AELEV_INFRASTRUCTURE_POSTGRESQL_PROVISION_ROLE=database_owner \
  database-provisioner
```

Роль не получает superuser, создание других баз/ролей, replication или bypass RLS. PUBLIC не получает доступ к новой базе. Повтор допускается только для точно помеченной роли и базы того же владельца; чужая база, существующая непомеченная или привилегированная роль приводят к отказу до переназначения. Provisioner не забирает таблицы, схемы и последовательности и не выполняет прикладной DDL. Оркестратор может инжектировать пароль операции через `AELEV_INFRASTRUCTURE_POSTGRESQL_PROVISION_PASSWORD` из approved secret injection; эта переменная не является постоянной настройкой поставщика `.env`.

## Автоматическое продление локального SQL-клиента

Для уже одобренного клиента на Docker volumes установщик потребителя вызывает `bind-delivery`, затем `upgrade-delivery` прежнего таймера и `once`, проверяя доставку. Формат назначения, пределы доступа, сохранение исходной задачи и отрицательная диагностика определены в [общем техническом интерфейсе](../CERTIFICATE_DELIVERY.md). Публичный артефакт этой задачи собирается собственным `Dockerfile.renewal`; он не обновляет SQL-узлы. Не создавайте новую регистрацию или второй таймер ради смены места конечной доставки.

Для существующей локальной identity оператор использует `renewal.py`; [нормативные ограничения](SPEC.md#операторское-продление-локального-sql-клиента) обязательны. Автопродление gateway не покрывает SQL-сертификат. Для внешней production PKI применяется утверждённый механизм SPIRE/CA, не локальный обход защиты.

Операторский закрытый JSON версии 1 содержит ровно `schema_version`, `environment` (`local`/`test`), `role`, `client_root`, `certificate`, `client_key`, `client_ca`, `url_file`, `issuer_certificate`, `issuer_key`, `report`, `openssl`, `docker`, `docker_endpoint`, `daemon_id`, `probe_image`, `network`. Файлы клиента задаются простыми именами внутри его собственного каталога; остальные файловые пути абсолютны. `probe_image` — точный локальный `sha256:...` образ PostgreSQL с psycopg; endpoint — локальный Unix socket, daemon ID и сеть сверяются. JSON не содержит самих секретов, но является закрытым операторским входом и не попадает в Git. Каталог отчёта создают заранее; runtime получает только этот публичный каталог для чтения и свои прежние клиентские файлы. CA-ключ находится вне обоих каталогов.

Команды выполняются в каталоге поставки PostgreSQL; параметры в угловых скобках — пути собственного операторского входа, не готовые credentials:

```sh
python3.13 renewal.py enroll --state <закрытый-каталог-задачи> --input <закрытый-json>
python3.13 renewal.py once --state <закрытый-каталог-задачи>
python3.13 renewal.py install --state <закрытый-каталог-задачи>
```

`install` устанавливает текущему пользователю macOS точный неизменяемый экземпляр скрипта и проверяет загрузку собственной задачи `com.aelev.postgresql-renewal.*`. Безопасный повтор не подменяет изменённый таймер. Запуск идёт раз в минуту; выпуск нужен только в предокне 30 дней. `once --force` выполняет тот же проверяемый цикл раньше срока и допустим для согласованного испытания, а не обходит проверки. Отказ временного подключения оставляет прежний сертификат, сохраняет код и повторяется следующим циклом. При недоступном Docker задача не запускает контейнеры владельца. После выключения хоста она продолжит работу при следующем пользовательском входе; это не внехостовый сервис выдачи.

```sh
python3.13 renewal.py revoke --state <закрытый-каталог-задачи>
```

`revoke` устойчиво отменяет право дальнейшего продления, но не объявляет уже выданный X.509 отозванным: отзыв сертификата выполняется штатным способом CA/SQL-владельца. Не удаляйте состояние для повторной выдачи. При `PG_RENEWAL_BOUND_MATERIAL_CHANGED`, `PG_RENEWAL_LEAF_CHANGED` или `PG_RENEWAL_APPROVAL_REVOKED` сначала разбирают изменение/отзыв, а не создают свежую регистрацию. Непроверенный кандидат и незавершённое намерение сохраняются для сверки; повтор не выдаёт дубликат. По завершении согласованной установки проверяют свежий `PG_RENEWAL_READY`, срок, новое защищённое соединение и появление отчёта в существующем мониторинге потребителя; один успешный `enroll` не закрывает эти проверки.

## Каждая настройка .env

|---|---|---|
| `COMPOSE_PROJECT` | `aelev-infrastructure-postgresql` | Владелец контейнерных ресурсов и меток Compose; не идентичность данных. |
| `IMAGE` | `aelev/postgresql:17.6-patroni-4.1.5` | Самостоятельно собранный runtime; в registry задаётся digest подписанного выпуска. |

| `ADMIN_USER` | `aelev_infrastructure_admin` | Bootstrap superuser и административная TLS identity; не роль приложения. Менять на действующем кластере простым рестартом нельзя. |
| `BIND` | `127.0.0.1` | Интерфейс публикации портов host; для распределённого запуска нужен доступный другим узлам интерфейс с межсетевым экраном. |

| `MEMORY` | `512m` | Лимит одного контейнера PostgreSQL + Patroni; OOM может вызвать failover, поэтому размер рабочей установки выбирают по нагрузке. |

## Фиксированные настройки и опции Compose

Это параметры реализации протокола и политики безопасной поставки, не скрытые дубли настроек `.env`. Изменение безопасной политики требует проверенного выпуска.

| Опции | Почему присутствуют |
|---|---|
| `name`, `image`, `build` | Идентифицируют поставку; сборка использует только собственный каталог, версии base images закреплены digest. Python 3.13 добавляется из совместимого Alpine builder без замены PostgreSQL base или ОС. |
| `x-*`, `<<`, общие environment anchors | Только повторное использование YAML-определения; контейнеры получают одну и ту же каноническую конфигурацию, не дополнительный источник. |
| `NODE_ID`, `ETCD_NAME` | Фиксированная индивидуальная роль 1/2/3, не публичная переменная оператора. |
| `ports` и `connect_address`/advertise URLs | Первые реально открывают порт сервера; вторые сообщают адрес другим узлам. Одно не заменяет другое, advertised адрес проверяется TLS. |
| `volumes`, `create_host_path: false`, `read_only` mounts | Отдельные постоянные данные и обязательные существующие TLS-каталоги; Docker не создаёт пустой каталог вместо отсутствующего материала. Отсутствующий файл внутри каталога также останавливает подготовку/сервер. |
| `read_only: true`, `tmpfs` | Корневая ФС неизменяема; runtime-конфигурация с секретами, pgpass и временные файлы живут в приватной памяти `/run/aelev` и `/tmp`. |
| `security_opt: no-new-privileges`, entrypoint | Подготовка разрешений выполняется root только в собственных томах/runtime; постоянный Patroni/PG работает как UID 70 без получения новых прав. |
| `mem_limit`, `stop_grace_period: 15s` | Ограничивают расход ресурсов и дают Patroni остановить PG до принудительного завершения контейнера. |
| `restart: unless-stopped` / `restart: "no"`, `profiles: [provision]` | Восстановление постоянных процессов; одноразовый provisioner запускается явно через `run --rm`, не при каждом рестарте. |
| `healthcheck`, `interval/timeout=5s`, `retries=30/20`, `start_period=30s` | PG проверяется через HTTPS/mTLS Patroni, etcd — подтверждённой DCS-операцией. Проверка различает живой процесс и готовый узел; срок bootstrap ограничен. |
| `networks` | Собственная локальная связность и выход к настроенным удалённым адресам. Зависимостей `depends_on` между географическими участниками нет; связь проверяют настоящие Patroni/etcd. |
| `ttl=30`, `loop_wait=5`, `retry_timeout=5`, `primary_stop_timeout=5` | Аренда ведущего, частота проверки, бюджет повторов и остановки; `loop_wait+2*retry_timeout <= ttl`. Не доказанное RTO 30 секунд при любой нагрузке. |
| `synchronous_mode=quorum`, `synchronous_mode_strict=true`, `synchronous_node_count=1` | Подтверждение ведущим и любой одной пригодной репликой; запрет незаметного перехода к одиночной асинхронной записи. |
| `check_timeline=true`, `failsafe_mode=false` | Нельзя продвинуть несовместимую timeline или продолжать ведущим без большинства DCS по отдельному аварийному режиму. |
| `pre_promote` либо `watchdog.required`, `safety_margin=-1`, `devices` | Первый требует положительную квитанцию завершения обоих peers в Docker/Kubernetes; второй ограждает весь выделенный host до истечения аренды. Рецепты взаимоисключающие, `off` не поддерживается. |
| `data-checksums`, `fsync`, `full_page_writes`, `synchronous_commit=on` | Проверка страниц и физическая устойчивость подтверждения. Клиентам запрещено ослаблять `synchronous_commit`; SQL superuser не является прикладной ролью. |
| `use_pg_rewind=true`, `wal_log_hints=on` | Возврат прежнего ведущего в реплики по новой timeline; WAL hints поддерживают rewind наряду с checksums. |
| `use_slots=true`, `max_slot_wal_keep_size=4GB` | Удержание WAL для временно отсутствующей реплики с ограничением роста диска; после превышения лимита требуется операторская проверка и пересоздание только её копии. Это не TTL канонических данных. |
| `remove_data_directory_on_*=false` | Ошибка rewind/несовместимая timeline не разрешают автоматическое удаление PGDATA. |
| `ssl=on`, `TLSv1.2`, `sslmode=verify-full`, `pg_hba hostssl/clientcert=verify-full`, `scram-sha-256`, завершающий reject | Шифрование, подлинность обеих сторон и отдельный пароль роли; незашифрованного fallback или `trust` для сетевых клиентов нет. |
| REST `verify_client=required`, `authentication`, `ctl` | Взаимные сертификаты для технического API, отдельное парольное подтверждение административных изменений и удостоверение межузловых запросов. |
| `log.type=json`, PG `log_destination`, etcd `logger=zap` | Технические журналы процессов; WAL/PGDATA не являются системными текстовыми логами. Секреты не входят в проектные сообщения ошибок. |
| `ETCD_INITIAL_CLUSTER*`, listen/advertise URLs | Согласованный начальный состав трёх участников и его идентичность; после bootstrap состав хранится самим etcd, повторный запуск с теми же данными не создаёт новый DCS. |
| etcd `*-CERT-*`, `TRUSTED_CA`, `CLIENT_CERT_AUTH` | Отдельная взаимная аутентификация клиентских и peer-каналов DCS. |
| etcd `HEARTBEAT_INTERVAL=500`, `ELECTION_TIMEOUT=5000` | Окна Raft, миллисекунды; пригодность для конкретной WAN проверяют по RTT/jitter, расстояние само по себе не является настройкой. |
| etcd `AUTO_COMPACTION_RETENTION=1h`, `QUOTA_BACKEND_BYTES=2GiB`, `DATA_DIR` | Ограничивают служебную историю DCS и сигнализируют исчерпание места, не удаляют SQL-данные. |

## Резервное копирование, обновление и миграция

Перед обслуживанием ранее ограждённого Docker-узла проверьте и при необходимости отмените его точное незавершённое намерение по [правилам возврата](FENCING.md#прерванная-остановка-и-возврат). Собственный цикл исполнителя продолжает такие намерения без нового `pre_promote`; обычная ручная остановка не заменяет отмену уже начатого возврата. `last_return_code` показывает сохранённую причину блокировки; отсутствие native-аренды не обходят ручным `promote`, удалением журнала или сбросом общего ограничителя.

Репликация повторяет ошибочный DELETE и не защищает от уничтожения всей площадки. Для рабочего допуска обязательны независимая полная физическая резервная копия, проверенное восстановление, архив WAL для требуемого PITR, мониторинг ёмкости, отставания репликации и действительности TLS. Копирование живой директории PGDATA не является резервной копией. Шифрование дисков и защищённое хранение копий обеспечивает среда размещения; TLS защищает передачу, не диски.

Базовый `pg_basebackup` с потоковой передачей WAL и `pg_verifybackup` уже входят в образ PostgreSQL. Из проверенной SQL-сессии определите текущего ведущего и передайте его защищённый адрес штатному клиенту; пароль читается из файлового секрета/защищённого pgpass, не указывается в команде. На выделенном сервере резервного копирования с установленным PostgreSQL 17:

```sh
pg_basebackup --dbname='host=db-1.example.net port=15432 user=backup_identity sslmode=verify-full sslrootcert=/secure/ca.crt sslcert=/secure/backup.crt sslkey=/secure/backup.key' \
  --pgdata=/protected-backups/aelev-postgresql/backup-YYYYMMDD \
  --wal-method=stream --checkpoint=fast --manifest-checksums=SHA256 --progress
pg_verifybackup /protected-backups/aelev-postgresql/backup-YYYYMMDD
```

`backup_identity` — отдельно выданная оператором роль LOGIN REPLICATION с собственными сертификатом и паролем; универсальные прикладные роли остаются NOREPLICATION. Серверная проверка атрибута REPLICATION, SCRAM и CN не позволяет обычной роли воспользоваться replication-строкой pg_hba. Использование репликационной identity кластера вместо отдельной выдачи не является разграничением backup-прав. Пример не заявляет настроенное непрерывное архивирование: конкретное независимое хранилище WAL, расписание и проверка полного аварийного восстановления остаются открытым воротом в TASKS. Автоматически созданное локальное хранилище не выдаётся за географический backup.

Старый `aelev-infrastructure-postgresql-data` не подключается к кластеру. До миграции остановите старых писателей, сделайте и проверьте согласованную резервную копию, разверните новый кластер с новыми томами, перенесите роли/базы штатными PostgreSQL средствами, сверьте содержимое и права, переключите конфигурацию каждого владельца на три адреса/TLS и лишь затем разрешите запись. Исходный том сохраняется. Эта задача не мигрирует работающие приложения и не меняет собственные БД других инфраструктурных компонентов. Старые одиночные DNS aliases не изображают отказоустойчивый endpoint.

Обновление — по одному узлу при healthy двух остальных и подтверждённой репликации; для рестарта ведущего сначала выполните контролируемый switchover Patroni под административной identity. `configure` применяет настройки из .env в DCS, но не скрывает требуемый перезапуск PostgreSQL. Откат сохраняет данные и совместимые версии PostgreSQL; новая timeline не заменяется старой копией. `down --volumes`, `patronictl reinit`, `pg_resetwal` и удаление DCS запрещены как автоматический способ исправления.

## Проверки и результаты

```sh
python3 -m unittest discover -s test -p test_configuration.py -v
docker build --target checks --build-context tests=./test -t aelev/postgresql-checks:local .
docker run --rm -v "$PWD:/work" aelev/postgresql-checks:local \
  sh -c 'black --check src prepare-tls.py status_publisher.py kubernetes test && ruff check src prepare-tls.py status_publisher.py kubernetes test && mypy src prepare-tls.py status_publisher.py kubernetes test/fencing-lifecycle.py test/cluster-lifecycle.py test/fencing-return-worker.py && PYTHONPATH=/work/src:/work pytest -q test'

```

Контейнер `checks` выполняет модульные и конфигурационные проверки на Python 3.13 без Docker socket. Полный тест отказов запускается Python 3.13 на операторском сервере через его настроенный Docker CLI/context. Если интерпретатора нет, допустим собственный доверенный `checks` как операторский runner с Docker socket и точным bind каталога поставки: это явно привилегированный тест, не read-only модульная проверка. Его команда и учёт сохранности находятся в [FENCING.md](FENCING.md); глобальные Python/Poetry-настройки тест не изменяет.

Читаемый результат полного прогона: [test/cluster-lifecycle-result.md](test/cluster-lifecycle-result.md); сводка остальных проверок и незакрытых ворот — [test/validation-result.md](test/validation-result.md). Отказ прогона также сохраняет результат и удаляет только ресурсы, отсутствие которых зафиксировано до запуска. Образы, `.env`, TLS, прежние контейнеры/сети/тома сохраняются; глобальная очистка или перезапуск Docker не выполняются. Полный допуск к рабочей эксплуатации требует отдельно закрыть проверки выбранного ограждения, географической сети, резервного копирования и цепочки поставки. Аппаратное ограждение проверяется только для `watchdog`; Docker и Kubernetes не должны перезагружать host.

Эти прежние отчёты не доказывают новое ограждение. Текущие проверки Docker через самостоятельный и корневой Compose, 61 сервисная и 30 оркестрационных регрессий, качество кода и непроверенные режимы описаны отдельно: [test/fencing-validation-result.md](test/fencing-validation-result.md).

## Собственное состояние в platform-ui

Ревизия 4 добавляет «Доступность пишущего узла» (`writer`) к прежнему составу. При обновлении задайте `UI_DESCRIPTION_REVISION` больше любой ранее опубликованной ревизии, минимум 4, и закрепите проверенный образ только в `UI_IMAGE`. Пересоздайте только `postgresql-status-publisher` с прежними identity, UUID и томом журнала; SQL, etcd и исполнитель для этого не обновляются. Используйте фактический Compose project действующего контейнера (`docker compose -p <project>`), а не создавайте второй кластер по значению шаблона. `/health` реплик остаётся проверкой жизни; готовность записи отдельно проверяет `/primary`. Причины прерванного ограждения сохраняются в собственном аудите, порядок ограниченного восстановления описан в [FENCING.md](FENCING.md#прерванная-остановка-и-возврат).

Обязательный `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_RESTART_POLICY` сохраняет выбранную native-политику издателя при замене образа. У явно зарегистрированного экземпляра берут только оставшийся конечный бюджет из устойчивого состояния восстановления, не `unless-stopped` из шаблона. Замена ID не даёт нового допуска и не сбрасывает прошлые попытки; их история сохраняется. Начальная незарегистрированная поставка сохраняет прежнее значение `unless-stopped`.

Повторная проверка названия назначения и технологического состава: [результат](test/status-labels-result.md). Она не подменяет прежние испытания жизненного цикла.

Профиль `ui` включает только собственную техническую роль публикации; обычный запуск не зависит от оболочки или IdP. Отдельная строка имеет тип `INFRASTRUCTURE`, не добавляет функциональные разделы. Состав: три PostgreSQL/Patroni, три etcd, собственный издатель и исполнитель ограждения при Docker/Kubernetes; проверяются HTTPS readiness/health, без SQL, изменения конфигурации, выборов ведущего или доступа к базам клиентов. Подтверждённая отрицательная native readiness отличается от отсутствия связи: transport/TLS-ошибка означает `UNKNOWN`. При штатной остановке издатель подтверждает отписку, и строка исчезает; при исчезновении публикаций без отписки строка остаётся с «Нет связи» после срока свежести приёмника.

Поставка использует собственный образ и включённый публичный `aelev-platform-ui-client==1.1.2` в `vendor`; SHA-256 закреплён собственным Poetry lock. Это библиотека транспорта, не общий runtime-образ/каталог продуктов. Сборка после извлечения этого каталога не читает соседние исходники. Протокол, установка артефакта и пример собственного издателя: [руководство оболочки](../platform-ui/USER_MANUAL.md#отправить-метаданные-из-python).

Из этого каталога, после подготовки удостоверений:

```sh
docker compose --env-file .env --profile ui build postgresql-status-publisher
docker compose --env-file .env --profile provision run --rm postgresql-status-provision
docker compose --env-file .env --profile ui up -d --no-build postgresql-status-publisher
docker compose --env-file .env --profile ui stop postgresql-status-publisher
```

Рабочий процесс получает только `secrets/status/{shell-ca.crt,identity-ca.crt,publisher.crt,publisher.key,client-secret}`. Одноразовый `provision` получает отдельные `secrets/status-admin/{admin-user,admin-password}`, не монтируемые в runtime. Закрытые ключи CA не доставляются в контейнеры. Используйте утверждённые цепочки CA, SAN/EKU и ротацию; генерация локального удостоверения описана в руководстве и не заменяет production PKI/SVID. HTTPS-адреса могут находиться в разных странах; общей Docker-сети с UI/IdP нет. `host.docker.internal` и `keycloak:host-gateway` — только локальные адресные alias примера; для удалённой установки задайте реальные FQDN/порты и доступность сети. Проверка сертификатов не отключается.

| Переменная | Назначение |
|---|---|
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_URL` | HTTPS-адрес платформенного технического API. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_IDENTITY_URL` | HTTPS-адрес IdP; должен совпадать с SAN сертификата. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_REALM` | Realm собственной машинной identity. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_CLIENT_ID` | Client ID только собственной роли публикации. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_AUDIENCE` | Аудитория JWT платформенного API. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_MODULE_ID` | Постоянный UUID собственного описания. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_DESCRIPTION_REVISION` | Монотонная ревизия собственного состава, минимум 4 для отдельной готовности `writer`. При смене режима между watchdog и исполнителем увеличьте её; прежний UUID/sequence не сбрасываются, одинаковая ревизия не может описывать два состава. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_INTERVAL_SECONDS` | Интервал публикации; браузер по-прежнему опрашивает раз в минуту. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_TIMEOUT_SECONDS` | Предел каждой собственной сетевой пробы/отправки. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_SECRET_ROOT` | Собственные рабочие удостоверения, без административных файлов. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_SECRET_GID` | Дополнительная группа чтения собственных секретов. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_ADMIN_ROOT` | Отдельные operator credentials только явной одноразовой задачи. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_PROVISION_UID` | UID оператора для одноразовой записи собственного client secret. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_STATE_VOLUME` | Постоянный журнал последовательности и точных повторяемых байтов. |
| `AELEV_INFRASTRUCTURE_POSTGRESQL_UI_MEMORY_LIMIT` | Лимит памяти только издателя. |

Журнал `UI_STATE_VOLUME` сохраняется при stop/start и обновлении; не удаляйте его как кэш: приёмник помнит sequence прежнего UUID. Восстановление требует собственного backup журнала или согласованного нового UUID, не сброса чужой БД/повторного sequence=1. Состояние оболочки восстанавливается повторной публикацией, canonical источник описания/состава остаётся у владельца.

`test/status_publication.py` работает с уже существующей настоящей установкой: OIDC/API/DOM, stop/start частей и издателя, реальное истечение TTL, возврат исходных контейнеров. Пример: `python3.13 test/status_publication.py --ui-url https://<ui-host>:<port> --viewer-user <viewer> --viewer-password-file <password-file> --chromium <installed-chromium> --status-ttl-seconds 120`. Требуются Python 3.13 и Playwright 1.56.0 в операторской тестовой среде; runtime-образ их браузерную роль не запускает. Исключение браузерной проверки сертификата допустимо только явным `--allow-local-certificate` на loopback с локальной PKI; рабочие издатели всегда проверяют TLS. Тест не создаёт фиктивных identities, каталогов, контейнеров, сетей или томов и восстанавливает исходное состояние; отчёт/снимок остаются в `test`. Полный остановленный приёмник UI физически не может доставить собственный свежий отчёт: проверяется UNKNOWN в уже открытом браузере и восстановление после старта.

Результаты текущей проверки публикации состояния: [читаемый отчёт](test/status-validation-result.md), [проверка нативных частей](test/status-native-result.md), [проверка издателя](test/status-publication-result.md). Прежние предметные/кластерные испытания не подменяются этой проверкой.
