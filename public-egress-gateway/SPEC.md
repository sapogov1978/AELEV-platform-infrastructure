# Спецификация Public Egress Gateway

Издатель проверяет точные HTTP 200 и ограниченный канонический JSON readiness, не прежний текстовый ответ. Его Docker-проба отдельно читает собственные UUID/heartbeat автономным файлом из закреплённого клиента 1.1.1 через `python -S`, без загрузки gateway и TLS. Она не подменяет готовность самого gateway и не проверяет разрешения потребителей.

Нормативная ответственность по [00-INFRA-20261106-0011-controlled-public-egress](../docs/adr/00-INFRA-20261106-0011-controlled-public-egress.md): универсальное техническое исполнение ограниченного HTTP(S)-доступа к публичной сети, независимо от функциональных потребителей. Поставка, образ, настройки, TLS, универсальные запреты и собственное состояние принадлежат провайдеру. Права, внешние credentials и доменные данные принадлежат клиентам. Общий Compose включает канонический сервисный файл, не определяет политику клиентов.

## Авторизация

Одна поставка обслуживает один явно настроенный workload `TRUST_DOMAIN`; клиентский CA bundle содержит только authorities этого домена/среды. URI другого домена запрещён даже при наличии файла разрешения. Bundles разных доменов не объединяются; федерация с выбором trust bundle по домену не объявляется поддержанной одним общим CA-файлом. Смена домена требует согласованной замены CA/SVID/прав, не сетевого или HTTP-заголовочного обхода.

Каждый fetch требует доверенного клиентского сертификата с одним точным SPIFFE URI SAN и отдельного действующего разрешения. Identity берётся только из TLS, не из JSON, HTTP-заголовка, адреса клиента или общих scopes. Локальный режим не обходится без сертификата. `/healthz` и `/readyz` следуют [единому контракту проб](../docs/api/health-readiness.md), а `/metrics` сохраняет Prometheus exposition; эти endpoints допускают HTTPS без клиентского ключа и не передают доменные данные, их доступ ограничивает firewall платформы.

Разрешение — ограниченный JSON `schema_version=1` со строго перечисленными полями: `identity`, `expires_at`, `mode`, `max_response_bytes`, `timeout_seconds`, `max_concurrency`, `per_host_interval_seconds`, `credential_scopes`, `post_scopes`. Дополнительные поля, повторяющиеся JSON-ключи, неизвестный режим, нечисловые/неограниченные величины, неверный SPIFFE URI, naive expiry и scopes режима EXPLORATION отклоняются. Предел файла 64 КиБ. Имя файла вычисляется как SHA-256 точного URI; содержимое дополнительно сверяется с URI. Проецируемые Kubernetes-ссылки допустимы только к обычному файлу внутри того же доверенного read-only mount; выход за его границу закрыто запрещён.

Каталог монтируется read-only, клиент не может применять или изменять разрешения через fetch. Операторская утилита проверяет вход и до изменения fsync-сохраняет `INTENT_RECORDED` в отдельной хеш-связанной цепочке, затем устойчиво записывает файл или удаляет точное разрешение и фиксирует `MUTATION_COMMITTED`. Запись содержит хеши actor, identity и grant, последовательность, предыдущее и собственное контрольные значения, но не секреты; повреждение цепочки или невозможность надёжно записать intent запрещают изменение. Если финальная запись не удалась после изменения, сохранённый intent доказывает возможную мутацию, команда возвращает ошибку, а оператор обязан сверить фактический grant до продолжения. Это обязательный локальный структурированный источник 00-INFRA-20261106-0007-workload-and-operator-identity, который целевой `security-audit-collector` преобразует в канонический `SecurityAuditEvent`; он не становится вторым каноническим аудитом и не заменяет платформенную подпись конфигурации. Истечение и отзыв проверяются перед каждым запросом без рестарта; уже допущенный поток не отменяется автоматически. Некорректная замена не открывает доступ. Каталог с нулём разрешений является готовым запретительным провайдером.

## Сетевой барьер

Разрешены только `http`/`https` и порты 80/443, без URL-userinfo, fragments или произвольного туннеля. Проверяется весь набор DNS A/AAAA; любой непубличный адрес блокирует весь запрос. Loopback/private/link-local/metadata/multicast/reserved/special-use и внутренние DNS-суффиксы запрещены во всех средах; deny CIDR может только усилить запрет. Выбранный проверенный IP закрепляется в соединении, HTTPS-сертификат проверяется по исходному hostname. Redirect возвращается как технический ответ, не выполняется автоматически. Каждый следующий запрос вновь проходит все проверки.

`EXPLORATION` принимает только GET/HEAD без тела и credentials, не требует предметного списка заранее известных публичных узлов. `REGULAR` разрешает `Authorization` и `X-Subscription-Token` только точным hosts из разрешения identity и только по HTTPS. POST дополнительно требует HTTPS, точного host/path, `Content-Type: application/json` и синтаксически корректного ограниченного JSON без повторяющихся ключей/нечисловых констант; разрешение другого клиента не учитывается. Стандартные безопасные заголовки ограничены закрытым списком, CR/LF/NUL отклоняются. Cookies и произвольные заголовки не передаются. Передача секретов по HTTP запрещена даже локально.

## Лимиты и отказ

Глобальные пределы ограничивают индивидуальные сверху; фактический размер дополнительно ограничивается запросом. Интервал между запросами определяется максимальным ограничением провайдера и identity. Счётчик конкурентности и расписание host сохраняются при редактировании разрешения, поэтому изменение не сбрасывает активные запросы. Идентичности имеют раздельные квоты/интервалы; общий предел защищает процесс, но не гарантирует справедливое планирование. Лимиты действуют на реплику, не глобально на кластер. Учитывается не более 1024 identities на процесс и 4096 ожидающих hosts на identity; превышение закрыто отклоняется, нет безграничного кеша. Смена полного набора identities выполняется согласованным rolling restart.

Upstream socket timeout ограничивает ожидание отдельного ввода-вывода, не заявляет абсолютную длительность DNS/полной загрузки. Входной JSON ограничен 196608 байт, декодированное тело 65536 байт. Число принятых клиентских соединений ограничено конкурентностью + 16; TLS handshake выполняется вне accept loop, входное ожидание не больше десяти секунд. Compose ограничивает PID и память; `MAX_CONCURRENCY` выбирается с учётом этих пределов. Потребитель обязан использовать ограниченный timeout и устойчивый повтор без прямого fallback.

Обычная загрузка закрыто отклоняет превышение ответа. Если превышение/ошибка обнаружены после начала потока, соединение обрывается: клиент не должен считать полученные байты полным документом. HEAD не передаёт тело и может вернуть размер представления больше предела отдельным `X-AELEV-Upstream-Content-Length`. Явный `truncate=true` позволяет bounded-префикс без утверждения полноты, с `X-AELEV-Response-Truncated: bounded`; credentials для такого исследования не допускаются клиентским контрактом. Полное каноническое содержимое клиент получает только обычным запросом с проверкой завершения.

## Контракт и состояние

Профиль `telemetry` автоматически готовит только собственный том перед первым запуском sender; одноразовый init остаётся без сети и не очищает содержимое. Выбран закреплённый sender 1.0.7 с SQLite 3.53.4 и прямой пробой `python -S /opt/aelev/delivery_health.py`, читающей только локальный heartbeat. Готовность доставки и задолженность проверяются отдельно по mTLS; потеря центрального приёмника не подменяет живость. На завершение sender и собственного Prometheus отведена минута. У постоянных ролей по умолчанию конечные `on-failure:3`; отдельные owner-scoped параметры сохраняют меньшие остатки либо `no`, установленные прежним ограничителем. Новая конфигурация не пополняет уже потраченные попытки.

TLS телеметрии отделён от доступа к публичным сайтам: runtime имеет только собственную local-write identity, sender — отдельные local-write/local-query и central-write. Диагностический `health-ca.crt` содержит публичное доверие серверу sender и выдающему local-query, не приватные CA. Установка телеметрии не изменяет grants, gateway/workload CA либо серверный ключ fetch.

Собственный backend предоставляет Swagger `/docs` и OpenAPI `/openapi.json`, включая ровно три упорядоченные группы: `default` (`GET /healthz`, `GET /readyz`), `gateway` (`POST /v1/fetch`), `metrics` (`GET /metrics`). Отдельный HTTPS-вход только для чтения в том же процессе/контейнере не запрашивает клиентский ключ; любой POST получает 405 без авторизации/проксирования. Защищённый вход fetch не получает исключения из mTLS/индивидуальных прав. Схема использует общий с parser канонический набор полей, методов и ограничений `api_contract.py`, относительный адрес технических GET и явный защищённый `PUBLIC_URL` fetch; клиентские grants или secrets не публикуются. Swagger UI 5.33.1 включён в образ по версии/SHA-256 и обслуживается этим же процессом; подмена конфигурации через query string, внешний валидатор и сохранение авторизации отключены. `Try it out` доступен только техническим GET. Документация имеет восемь одновременно принимаемых соединений, прежний основной бюджет сохраняется; оба входа читают общие метрики процесса.

Владелец публикует собственный абсолютный `DOCS_PUBLIC_URL` с `/docs` как `swagger_url` группы и gateway-компонента в ревизии 2. У издателя ссылки нет, состав не обнаруживается оболочкой. Для удалённого размещения URL доступен браузеру, не только Docker-сети; серверная цепочка/SAN должны быть доверены браузером. Смена ссылки/откат соблюдают возрастающую ревизию без смены UUID/сброса sequence. Корень и platform-ui не получают сведений о конкретных потребителях или новых полномочий.

`POST /v1/fetch` сохраняет прежнюю точную форму: `method`, `url`, `headers`, `body` (base64), `max_bytes`, `truncate`. При успехе возвращаются внешний HTTP status, допустимые внешние заголовки и поток с `X-AELEV-Egress-Result: ALLOWED`; доменная интерпретация запрещена. При отказе возвращаются `status=rejected`, безопасный `code`, идентификатор запроса; 403 — политика/identity, 429 — квота, 400 — неверный JSON, 502/504 — upstream. Это инфраструктурное исключение [Kafka-only правил](../docs/api/grpc.md), не предметный RPC.

Нового доменного хранилища и мигратора нет. Авторизационные ресурсы доставляет оператор; безопасный JSON-журнал и метрики принадлежат провайдеру и не содержат тела, URL-path/query или credentials. Labels маршрутов ограничены `/v1/fetch` и `/unknown`, нет роста от произвольных URL/identities. Gateway экспортирует OTLP logs и server traces с продолжением входного `traceparent` только в настроенный HTTPS/mTLS endpoint. В production отсутствие endpoint или файлов доверия закрывает запуск; local допускает явное отключение. Собственный telemetry sender имеет постоянный журнал, собирает ограниченные Prometheus metrics и доставляет logs/traces/metrics в центральный delivery без каталога потребителей. UI-профиль имеет собственный устойчивый outbox, подтверждение публикаций и штатную отписку по [контракту оболочки](../docs/api/platform-ui-injection.md). Потеря UI или центральной наблюдаемости не останавливает ограниченный fetch; их credentials не являются клиентскими или административными credentials gateway.

## Эксплуатационные допуски

### Локальное операторское продление

Публичная читающая команда `renewal.py describe --state-directory ...` обслуживает только существующее клиентское одобрение, не серверную задачу. Она возвращает ровно `owner=public-egress-gateway`, `schema_version=1`, `code=EGRESS_RENEWAL_BINDING_VERIFIED`, `identity`, `ca_sha256`, `scope_sha256`, `certificate_path`, `ca_path`, `status_path`; хеш scope исключает только `expires_at` и сохраняется при штатном продлении. Приватные пути issuer/state/audit, actor, ключи, исходное одобрение, журнал и декларация прав не возвращаются. Это операторский локальный интерфейс, не HTTP runtime или предметный RPC; путь к файлу не даёт разрешения на fetch.

Команда открывает только уже существующий `.operator-mutation.lock` read-only и пытается взять общий `LOCK_SH` без ожидания; активная мутация даёт `OPERATOR_MUTATION_IN_PROGRESS`, отсутствие блокировки не создаёт её. Проверяются неизменность одобрения, полная цепочка/позиция аудита и отсутствие последующего revoke или незавершённого intent, закреплённый CA, действующий exact grant, прежние scope и ожидаемый digest. Отзыв не снимается последующим apply; expiry, смена CA/scope, недоступность или неоднозначность данных закрывают результат без ремонта. Команда не читает private key, не выполняет OpenSSL, не обновляет отчёт, сертификат, grant, аудит или таймер. Положительное описание не доказывает TLS-handshake или готовность workload. Вывод успеха — ограниченная JSON-проекция в stdout, отказ — безопасный код в stderr и ненулевой exit.

`Dockerfile.renewal` независимо поставляет `renewal.py`, `provision.py`, `authorization.py` и `renewal.sha256` на прежнем закреплённом Python/Bookworm с marker `io.aelev.egress.renewal-interface=1`; рабочий образ gateway не получает операторского кода. Образ является закрепляемым источником нативного артефакта, не новым gateway, планировщиком или автоматической миграцией старого таймера. При замене клиентского действия проверяются exact identity/CA и пути публичных выходов; прежняя серверная задача не затрагивается.

`renewal.py` — отдельная операторская задача существующей локальной PKI, не код gateway или потребителя. Явное `enroll` фиксирует точную уже действующую декларацию, identity, хеш CA, actor и позицию аудита. Проверка раз в минуту продлевает только `expires_at` того же scope и leaf-сертификаты на семь дней при остатке не более трёх дней; изменение прав требует нового явного согласования. Пропавший, отозванный или истёкший grant, смена scope/CA и незавершённое аудируемое действие закрывают автоматическое продление. Отзыв после одобрения остаётся окончательным для этой задачи даже после ручного повторного apply. Apply, revoke и renewal сериализуются общей операторской блокировкой; intent фиксируется до каждой мутации. Потребитель не получает каталог одобрения, CA key или права записи grants.

Leaf продлевается с тем же закрытым ключом: проверенные SAN, цепочка и соответствие ключу предшествуют атомарной замене только сертификата. Поэтому промежуточной несовместимой пары нет; это продление сертификата, не автоматическая смена закрытого ключа. Серверный leaf получает собственное `enroll-server`, закреплённые SAN, отдельные state/таймер и отчёт `server-status.json`; серверная задача не читает grant или закрытые файлы клиента и не останавливается после отзыва клиента. Клиентская задача не имеет операции продления server TLS; прежний `server_directory` допускается только как путь проверки срока. Оба TLS-входа перечитывают изменённые leaf/key и атомарно заменяют полностью подготовленный контекст, сохраняя клиентскую проверку; уже открытые соединения продолжаются. Непригодная замена журналируется и не уничтожает прежний контекст, а просроченный leaf не становится действующим. Runtime не получает инструменты выпуска или CA key.

Публичный атомарный отчёт содержит время проверки, успеха, продления, последнего сбоя и сроки client/server/grant/CA без ключей, путей администрирования и тел сайтов. Его читает наблюдение владельца потребителя; отсутствие свежей проверки не является подтверждением допуска. При остатке CA не более восьми дней продление блокируется с `CA_REPLACEMENT_REQUIRED`; автоматическая смена корней доверия запрещена. Пользовательский таймер macOS работает после логина и пробуждения, а не во время выключения хоста. На Linux тот же `once` запускает утверждённый таймер площадки. Это не production SPIRE, защищённое хранилище секретов или доставка внешнего оповещения; их допуски сохраняются.

Kubernetes/default-deny, WAN, SPIRE-ротация, подпись конфигурации, приём локальных записей каноническим сборщиком аудита, фактическая доставка alert, суммарные бюджеты реплик и отзыв внешних credentials проверяются на целевой платформе. Локальная сборка/lifecycle не присваивает им статус выполненных. Инструкции, миграция и откат находятся в [README](README.md) и [USER_MANUAL](USER_MANUAL.md).
