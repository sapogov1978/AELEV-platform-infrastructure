# Инфраструктурная оркестрация — спецификация

## Самостоятельный выпуск и локальный установщик

Канонический код инфраструктуры принадлежит отдельному репозиторию Platform Infrastructure по [INFRA-ADR-0001](../../docs/adr/20261105-0001-independent-infrastructure-product.md). `bootstrap.py` является публичным административным входом локальной установки по [контракту версии 1](../../docs/api/installation.md). Он выбирает технические возможности без каталога приложений, вызывает прежние владельческие Compose-рецепты и не включает модели, обработку перевода или прикладные очереди. Продукт-потребитель не определяет инфраструктурные runtime-роли и не останавливает общую установку своим shutdown. Версии, данные, identities и принятые технические интерфейсы владельцев сохраняются.

## Общий gate жизненного цикла сертификатов

`certificate_lifecycle.py` является читающим локальным deployment gate ADR-0166. Он обнаруживает распределённые owner-state и установленные Egress LaunchAgent, не содержит центрального списка сервисов и не выдаёт сертификаты. Успех требует единственного активного механизма для каждого точного leaf, загруженного минутного таймера, свежей квитанции не старше 180 секунд, совпадающего SHA-256 и безопасного срока: более 30 дней для обычного 90-дневного leaf и CA, более трёх дней для 7-дневного Egress leaf при CA более 30 дней. Старые отозванные состояния и history остаются доказательством, но не считаются активными владельцами.

Атомарно заменяемые leaf/key монтируются минимальным owner-каталогом либо доставляются в проверенный Docker volume. Отдельный file bind запрещён для автоматически обновляемого leaf, потому что замена inode не меняет уже установленный mount. После ротации процесс с загрузкой TLS при старте проходит точный restart/recreate либо owner reload и новую проверку здоровья; Docker daemon, volumes и журналы не сбрасываются.

## Контейнерный оператор восстановления

Хостовый `import-history --history <файл> --history-sha256 <SHA-256>` предназначен только для отдельно согласованного переноса подтверждённой истории ещё не зарегистрированной нагрузки без специального owner guard. Это не автоматический поиск или замена `register`: оператор заранее проверяет источник и одобряет точные байты квитанции. JSON содержит только `schema_version=1`, `daemon_id`, `name`, полный `expected` fingerprint, `prior_attempts` предшественников и `evidence_sha256` исходного доказательства. Сумма прежних и текущих native-попыток становится накопленным `attempts`; повтор текущего Docker-счётчика в `prior_attempts` запрещён процедурой владельца. Два чтения сверяют инкарнацию, процесс и конечную политику; допускается здоровый живой процесс либо завершившийся с ошибкой при `restart=no`. Импорт сохраняет защитное `CIRCUIT_OPEN`, не меняет Docker и не выполняет start. Совпадающая квитанция повторяется без записи; существующая другая регистрация, ID или Compose-роль не получают второй бюджет. После отдельного подтверждённого операторского старта и проверки здоровья применяется прежний `auto-enable`; последующие удержания повтор импорта не снимает. Контейнерный stdin-протокол не расширяется.

Хостовый `release-replacement` принимает точные имя/ID и `replacement_release_proof` просмотренной регистрации. Он снимает только сохранённый `replacement_block={code: TARGET_REPLACED}` завершённой прежней передачи: та же здоровая свежая инкарнация с native `no`, неизменные attempts/native count, положительный прежний guard, отсутствие предшественника, незавершённого воздействия и иных удержаний обязательны. Снятая причина сохраняется в квитанции и событии, а обычный `CIRCUIT_OPEN` остаётся до явного `auto-enable`. Команда не запускает процесс, не обновляет образ и не пополняет бюджет. Повтор той же квитанции не снимает позднейшие блокировки; другие причины и уже автоматические цели этим входом не переводятся.

Хостовое окно обслуживания после единственного отключения своего таймера до десяти секунд наблюдает его фактическое исчезновение. Асинхронное подтверждение `bootout` не считается уже завершённой остановкой и не вызывает повторной команды. До подтверждения контейнерный писатель не создаётся; истечение срока сохраняет прежний `INTENT`, не запускает таймер наугад и позволяет согласовать только тот же запрос после проверки состояния. Алгоритм восстановления, расписание и накопленная история этим ожиданием не меняются.

Одноразовый macOS-контейнер публичного оператора не является частью журнала после устойчивой фазы `COMPLETE`. Следующее отличающееся окно может архивировать прежнюю квитанцию при отсутствующем helper только когда сохранённый результат имеет точную схему, тот же daemon и ограниченный непустой набор digest-квитанций целей; незавершённая, повреждённая или относящаяся к другому daemon операция по-прежнему закрыто блокирует новый writer. Наличие чужого или работающего контейнера не подменяется квитанцией.

Каждая публичная квитанция `status/suspend/replace/register` содержит булев `automatic_recovery`: выбран ли у точной цели подтверждённый автоматический режим ADR-0155. Признак не означает отсутствие удержания или готовность процесса; `blocked` и `code` сохраняют самостоятельный смысл. Чтение и передача признака не включают режим, не изменяют историю или алгоритм восстановления. Замена сохраняет прежний выбор, а не выводит его из числа попыток либо native-политики `no`.

Публичный stdin-протокол дополнен `action=register` для первоначального подключения точной живой цели к прежнему автоматическому контроллеру. Обязательны полный fingerprint и явная метка владельца `io.aelev.recovery.registration=unguarded-automatic-v1`; это допуск только нагрузки, для которой не требуется отдельный owner guard, не обход guard хранилища. Проверяются daemon, точные имя/ID/image/Compose scope, настоящая healthy-проба и конечная native-политика. Произвольный guard, shell, обнаружение целей и замена чужого ID не принимаются. До первого воздействия проверяется вся переданная область; один ID либо прежняя роль не создают второй бюджет под другим именем.

Намерение `registration=PREPARED` сохраняется до перевода штатным `automatic_enable`. Наблюдённые native-попытки становятся исходной историей, не обнуляются; Docker-повторы отключаются прежним алгоритмом. Потеря ответа согласуется тем же намерением. Повтор `COMPLETE` только проверяет прежнюю инкарнацию: не снимает последующее suspend/защитный отказ, не запускает вручную остановленный контейнер и не переводит старую постороннюю регистрацию. Совместимость status/suspend/replace сохраняется; capability артефакта — `io.aelev.recovery.registration=1`.

Нативный `recovery_host.py` с явным локальным `--endpoint` может подготовить только новый закрытый журнал и установить прежнюю пользовательскую задачу на новой станции. Проверка полномочий/образа/области предшествует инициализации; намерения и срок жизни журнала сохраняются в `registration-bootstrap.json`. Неизвестный каталог не присваивается. Для уже установленного журнала используется прежнее окно обслуживания. Повтор не включает вручную отключённую задачу; POSIX-права и NTFS ACL, LaunchAgent/systemd/Task Scheduler принадлежат тому же оператору. Модель и рабочие роли не получают Docker socket. [Порядок использования и границы проверки](USER_MANUAL.md#первоначальная-регистрация-новой-установки) не заменяют испытание на фактической ОС.

В автоматическом режиме временный отказ чтения Docker сохраняется отдельной диагностикой и не переписывает код уже установленного удержания или ожидания результата собственной команды. Позднее подтверждение прежнего намерения остаётся сверяемым без повторной отправки; явный операторский запрет не превращается в обычную ошибку чтения. У ещё активной цели такая ошибка не создаёт постоянной блокировки.

Для явно переведённых целей действует [ADR-0155](../../docs/adr/20261023-0155-automatic-recovery-after-cooldown.md): прежний `recovery.py` ограничивает частоту воздействий, не возможность восстановления на весь срок жизни. `attempts` и история монотонны; `automatic.burst_attempts` задаёт интервалы 30/120/300 секунд, затем одну попытку раз в 900 секунд. После 1800 секунд непрерывного свежего healthy той же инкарнации серия завершается с отдельным событием, не удалением прежних попыток. Разрыв наблюдения свыше 120 секунд, сон и смена процесса прерывают доказательство устойчивости. Временная пауза видна в `code`/`next_due`, не смешивается с защитным `blocked`.

По [ADR-0171](../../docs/adr/20261028-0171-recovery-resume-and-compose-handoff.md) разрыв проходов свыше 120 секунд создаёт 120-секундный `HOST_RESUME_GRACE` без Docker-воздействий и расхода attempts. Перед воздействием контроллер рекурсивно проверяет ограниченный `com.docker.compose.depends_on` того же project; неготовая зависимость создаёт `DEPENDENCY_WAIT` без расхода попытки. Уже включённая автоматическая цель передаёт историю новой здоровой инкарнации того же точного имени/project/service после 30 секунд устойчивости, только при отсутствующем предшественнике и без защитного удержания или незавершённой команды; native policy остаётся `no`. Изменяющий хостовый CLI ждёт освобождения активного прохода не более 120 секунд и затем закрыто возвращает `RECOVERY_LOCK_BUSY`; ожидание не останавливает таймер и не записывает намерение до получения барьера.

[Диаграмма восстановления](recovery.mmd) отделяет временные ожидания от защитного отказа и ручного удержания; она описывает существующий оператор, не новый процесс.

Хостовый `auto-enable` переводит только точную живую зарегистрированную цель без защитного/операторского удержания и незавершённого воздействия. Явно просмотренный обычный `CIRCUIT_OPEN` можно перевести с сохранением всех attempts и исходной истории; другие блокировки не снимаются. Переход фиксируется до отключения native policy. После подтверждения Docker `restart=no` единственным исполнителем остаётся прежний таймер. Журнал становится версией 2: старые операторы, принимающие только версию 1, закрыто отказывают; совместимый образ публикует `io.aelev.recovery.automatic-recovery=1`. Сам `upgrade` не меняет режим целей. Новых таймеров, обнаружения или Docker socket в runtime нет.

Start остановленной цели требует доказанного аварийного выхода того же процесса: неизменного `StartedAt`, ненулевого кода, единственного согласованного `die` и непрерывного покрытия от последнего подтверждённого работающего процесса до текущей проверки без stop/kill/pause/чужого restart. `FinishedAt` должен принадлежать этому интервалу, событие `die` — следовать не раньше завершения и иметь тот же код. Задержка публикации события Docker не ограничивается произвольным допуском в несколько секунд: принадлежность устанавливается по инкарнации и полному интервалу. Совпадающие записи сохранённого журнала и свежего хвоста считаются одним событием; два различных `die` либо противоречивый код запрещают запуск. Пока событие не пришло, контроллер ждёт без расхода попытки и не сдвигает начало интервала за недоказанный выход. Начало сохраняется также во время паузы и повторно проверяется перед командой; прежние уже сдвинутые или заблокированные записи автоматически не исправляются.

Режим `watch` прежнего контроллера непрерывно читает Docker events параллельно существующему проходу восстановления; отдельного таймера, контроллера или исполнителя не создаётся. В собственном атомарном `docker-events.json` сохраняются только времена покрытия и управляющие события точных зарегистрированных ID с действием и кодом выхода. Сырые события, labels, имена посторонних контейнеров, argv, env и тела запросов не сохраняются. Управляющее событие проходит fsync до публикации покрытия; повтор потока удаляет дубликаты, новая сессия соединяется с прежней только при доказанном пересечении. Разрыв остаётся отдельной эпохой, не заполняется предположениями.

Перед запуском сохранённое покрытие соединяется со свежим ограниченным хвостом Docker. Отставание читателя даёт `AUTOMATIC_OBSERVATION_WAIT` без запуска и блокировки; отсутствие истории, неизвестный результат воздействия, смена fingerprint/политики, отозванные полномочия и guard не становятся автоматическим допуском. Журнал ограничен 16 МиБ, 50 000 управляющих событий и 10 000 эпох; достижение предела запрещает расширять доказанное покрытие, но не удаляет историю. Его архивирование требует отдельной операторской процедуры; автоматического удаления нет. Состояние чтения доступно в `event_observation` существующего отчёта. `once` сохраняется как совместимый однократный проход и использует тот же журнал. Старые неоднозначные остановки не становятся доказанными от установки нового выпуска. Перед ручным обслуживанием по-прежнему обязателен `suspend`: команда stop уже завершившемуся процессу может не оставить различимого события и не заменяет операторское намерение.

Собственное намерение start/restart сохраняется с fsync до единственной команды. Согласование позднего ответа не повторяет команду и, поскольку не вызывает Docker-воздействия, не расходует единственный допустимый action текущего прохода и не задерживает готовое восстановление другой точной цели. Само по себе healthy не снимает защитную блокировку; отрицательный актуальный owner guard откладывает проверку, изменившийся guard закрыто блокируется. После явного внешнего запуска ранее остановленного процесса новая здоровая инкарнация того же exact target без собственного незавершённого намерения позволяет возобновить только наблюдение, не выполнить start. Явное `suspend`, подмена и сохранённая защитная причина этим не отменяются. При замене подтверждённой инкарнации режим/серия и накопленная история передаются с native `no`; незавершённое воздействие старого ID архивируется только после доказательства его отсутствия. `cancel-suspend` не включает независимые Docker-повторы; `reset` не удаляет историю цели нового режима. Старые непереведённые цели сохраняют совместимую семантику ADR-0148, описанную ниже.

Диагностика существующего ограничителя сохраняет `last_failure_diagnostic` и `last_action_diagnostic` в собственных `state.json`/`report.json`. Запись содержит только код решения, фазу проверки цели, её прошедшее монотонное время, тип исключения без текста, признаки Running/OOM, native-счётчик, код завершения и последние три пробы: коды, проверенные отметки времени и длительности. `Output`, env, argv, тела запросов и исходный текст исключений не читаются в диагностическую проекцию. Снимок перед воздействием устойчиво фиксируется вместе с прежним намерением до Docker-команды и остаётся в истории; последующий `CIRCUIT_OPEN` не заменяет исходное свидетельство отказа. Наблюдение не выполняет дополнительных сетевых/Docker-запросов, не меняет решения, защитные барьеры, область целей, три попытки или интервалы. Старые события без сохранённого снимка задним числом не реконструируются.

Хостовый `adopt-stopped` подготавливает только явно указанный ещё не зарегистрированный остановленный предшественник с уже исчерпанным native-бюджетом. Требуются точные имя, ID, image ID и счётчик не меньше трёх; два чтения подтверждают прежний Compose fingerprint, завершённое состояние и `restart=no`. Команда не запускает контейнер и не меняет Docker-политику: устойчиво сохраняет весь прежний счётчик, доказательство и `CIRCUIT_OPEN` с нулевым остатком. Повтор принимает только ту же неизменную квитанцию; существующая регистрация, новый ID или изменившаяся история не перезаписываются. Обычный `replace` затем переносит этот исчерпанный бюджет на здоровую новую инкарнацию, оставляя `restart=no`. Обычный `enroll` по-прежнему требует живой экземпляр с пробой; контейнерный stdin-протокол не расширяется.

Хостовая команда `cancel-suspend` отменяет только точное операторское удержание уже работающего здорового экземпляра. Обязательны прежний ID и SHA-256 доказательство конкретного удержания, полученное `suspension_proof` из зарегистрированной цели; проверяются daemon, полный fingerprint, свежая проба и прежний guard. Новое удержание получает отдельный идентификатор и не отменяется повтором старой команды. Незавершённый рестарт или передача инкарнации запрещают отмену. Наблюдаемые native-выходы учитываются до вычисления остатка; исчерпанный бюджет остаётся `CIRCUIT_OPEN`/`restart=no`. Намерение смены политики сохраняется до Docker-команды, затем проверяются тот же процесс и конечная политика. Потерянный ответ завершается только по подтверждённому результату: неизвестный исход не разрешает повторную отправку. Команда не запускает/не пересоздаёт контейнер, не очищает историю и не предоставляется контейнерным stdin-адаптером.

`Dockerfile.recovery` упаковывает тот же `recovery.py`, Python 3.13.7 и Docker CLI 28.5.1 с закреплёнными исходными образами. Это одноразовый операторский инструмент, не новый контроллер, таймер или runtime-зависимость. Адаптер `recovery_cli.py` принимает ограниченный JSON через stdin: версия 1, точный daemon ID, действие `status`, `suspend`, `replace`, `relocate` либо `release-relocation` и явные fingerprints предшественников. Wildcard, обнаружение, `once`, `enroll`, `reset`, `install`, произвольные команды и пути через адаптер недоступны. Полный набор проверяется до первой записи; замена делегируется прежнему `recovery.replace`, а relocation переносит тот же журнал на явно названную healthy-инкарнацию при подтверждённом отсутствии прежнего Docker ID. Обе операции сохраняют историю, guard, автоматический режим и общий остаток попыток; relocation дополнительно меняет ключ цели только после устойчивой смены native restart policy и восстанавливается из сохранённого намерения при потерянном ответе. Если прежняя цель уже заблокирована, перенос выполняется с `preserve_block`: новая инкарнация остаётся с `restart=no` и тем же кодом до отдельного `release-relocation`, привязанного SHA-256-доказательством к точному состоянию relocation, attempts, fingerprint и автоматическому режиму. Release допускается только для той же running/healthy-инкарнации без незавершённых намерений; исчерпанный неавтоматический бюджет остаётся `CIRCUIT_OPEN`. Хостовые пути Docker в журнале не переписываются: меняется только транспорт выполнения.

Журнал монтируется в `/var/lib/aelev-recovery` с UID владельца; Docker socket получает только оператор. `status` ничего не записывает и возвращает только запрошенную область. Для записи обязательно хостовое окно: `recovery_host.py` проверяет точный прежний таймер, сохраняет намерение, дожидается завершения текущего прохода и останавливает только этот таймер. На macOS сохраняется контейнерный путь; блокировки macOS и Docker Desktop не считаются общими. Только после сверки завершения и неизменности конфигурации восстанавливается тот же таймер; неопределённый результат оставляет его остановленным с устойчивым намерением. Если прежний relocation-helper доказанно завершился до первой записи с единственным безопасным кодом `RELOCATION_UNCONFIRMED`, `repair_failed_relocation` может продолжить только этот же запрос новым закреплённым образом: он сверяет исходный marker, digest запроса, daemon, timer, точный завершившийся helper и ограниченный JSON ошибки, записывает digest состояния до и после, переносит цели с сохранением блокировок и возвращает ровно тот же таймер. Любая другая ошибка или изменившееся доказательство запрещает продолжение. `--host-timer-quiesced` является утверждением доверенного хостового установщика, а не проверкой планировщика из Linux-контейнера.

Планировщики запускают один долгоживущий `watch`, совмещающий чтение событий и прежние проходы восстановления через 15 секунд после завершения предыдущего. На macOS используется прежний LaunchAgent; штатный `upgrade` сохраняет историю и переводит его с `once` на `watch`. На Linux `install` создаёт собственные пользовательские systemd service/timer с повторным запуском завершившегося контроллера через 15 секунд. На Windows создаётся собственная задача Task Scheduler текущего пользователя после входа и раз в минуту, без повышения прав, пароля, параллельных запусков или дополнительных повторов при ошибке. Журнал на Windows защищается ACL текущего SID; блокировка использует стандартный нативный механизм, устойчивая замена файла — `MoveFileExW` с `WRITE_THROUGH`. Разрешены только локальные Unix socket либо точные именованные каналы Docker Desktop; TCP не допускается. В Linux/Windows хостовый адаптер вызывает те же функции публичного `recovery_cli.py` и `recovery.py` под удерживаемым нативным барьером, не переносит права NTFS или блокировки в контейнер и не вводит второй алгоритм восстановления. Проверка генерации этих задач не заменяет реальное испытание на соответствующей ОС.

`scheduler.json` фиксирует платформу, область, неизменяемый выпуск, файлы и фазы установки до регистрации/активации. Сверяются загруженные systemd units либо экспорт точной Windows-задачи; чужая задача, подмена, неизвестная ошибка планировщика и неоднозначная предыдущая установка запрещают продолжение. Повтор подтверждённой установки не включает вручную отключённую задачу. `timer-status` проверяет состояние без записи. `once` не изменяет журнал при незавершённом установочном или обслуживающем намерении. Реальные проверки доступных платформ и ограничения подтверждения перечислены в [отчёте](test_infrastructure/user-schedulers-result-20261022.md); наличие реализации не заменяет прогон на целевом Linux/Windows. Команда `upgrade` ниже пока относится только к macOS, не является реализованным обновлением задач других ОС.

Образ с `io.aelev.recovery.host-interface=2` также предоставляет ограниченный нативный `status` через `recovery_host.py`: проверяет прежний журнал, daemon и полный заданный scope, не обращается к таймеру и не создаёт файлов обслуживания. Он нужен для чтения на Linux/Windows без контейнерного переноса прав, не предоставляет новых команд записи. Параметры хостового CLI сохраняются, записывающий путь остаётся прежним `maintain`.

Для ещё не переведённых целей совместимый режим [ADR-0148](../../docs/adr/20261018-0148-bounded-local-infrastructure-recovery.md) сохраняет прежний общий бюджет трёх попыток и блокировку до разбора; он не является целевым автономным режимом ADR-0155. Exact daemon/ID/image/Compose scope, fsync намерения и owner guard обязательны в обоих режимах. Потребители, UI и издатели не получают Docker socket. PostgreSQL допускает восстановление только собственным read-only guard без выбора ведущего или обхода ограждения. Причина и история сохраняются в операторском состоянии; отдельная система уведомлений не создаётся.

Собственный рестарт сохраняет точный fingerprint, исходный `StartedAt`, номер уже списанной попытки и фазы `PREPARED`, `DISPATCH_INTENT`, `POLICY_PENDING` до отключения native policy, отправки единственной команды и возврата сокращённого остатка соответственно. Следующий проход согласует это намерение до обычной проверки политики. Новая инкарнация подтверждается только у того же контейнера; согласование никогда не выполняет `start` или `restart`. Если отправка ещё не фиксировалась, рестарт не догоняется по старому guard; попытка остаётся списанной. Если команда могла быть отправлена, но новая инкарнация не подтверждена, `RESTART_RESULT_UNCONFIRMED` запрещает повторную отправку. Наблюдаемые native-повторы расходуют тот же бюджет, неизвестные изменения и операторская блокировка не обходятся. Старые записи без доказательства собственного воздействия не получают автоматического допуска. При `replace` незавершённый рестарт предшественника можно архивировать только после подтверждённого отсутствия его точного Docker ID.

Команда `upgrade` обновляет только уже установленный macOS LaunchAgent: проверяет исходные plist/скрипт, daemon и отсутствие незавершённого контейнерного оператора, дожидается прежнего хостового барьера до остановки таймера и сохраняет старый выпуск. Интерпретатор, расписание и журнал остаются прежними; меняется путь неизменяемого скрипта. `upgrade-intent.json` позволяет сверить потерянный ответ загрузки того же таймера без повторной установки. Остановленный вручную таймер не включается; неоднозначная незавершённая операция другого выпуска требует разбора. Эта команда не доступна через контейнерный stdin-адаптер и не сбрасывает бюджеты.

Хостовый `replace --preserve-block` переносит уже существующую защитную блокировку на проверенную здоровую новую инкарнацию того же проекта/роли, только если её native-политика уже `no`. Сохраняются причина, история, guard, отсрочки и потраченные попытки; новый fingerprint не разблокирует оставшийся запас. При повторной смене инкарнации исходная причина берётся из сохранённого `replacement_block`, а не из отображаемого `CIRCUIT_OPEN`. Намерение содержит выбранный режим и исходный код; повтор потерянного ответа требует того же режима и не разрешает переключить его на обычную замену. Native-политика остаётся `no`, блокировка — активной. Незавершённое старое воздействие по-прежнему требует подтверждённого отсутствия точного старого ID. Режим не запускает контейнеры, не сбрасывает бюджет и не расширяет контейнерный stdin-протокол.

По [ADR-0114](../../docs/adr/20261012-0114-infrastructure-public-egress-gateway.md) состав дополнен самостоятельным Public Egress Gateway. Его Compose/env/TLS и собственный издатель включаются тем же способом; корень не содержит деклараций клиентов или их credentials и не выдаёт общих egress-прав. Новые запросы требуют индивидуального exact mTLS/SPIFFE разрешения; пустой каталог является готовым запретительным провайдером. Это явно согласованное точечное изменение плана, не новое переходное окно ADR-0113.

Правила изменения поставки определяет [ADR-0113](../../docs/adr/20261012-0113-infrastructure-plan-stability.md): пересмотр утверждённого плана только при доказанной критической необходимости и явном согласовании; предварительное объяснение и явное согласие обязательны для любого изменения инфраструктуры, включая сопровождение.

По отдельно согласованному [ADR-0154](../../docs/adr/20261020-0154-spire-workload-identity-provider.md) включена самостоятельная [поставка SPIRE](spire/SPEC.md). Корень только включает её канонический Compose; профиль `workload-identity` не активируется обычным запуском до подготовки исходного доверия. Самостоятельные агенты принадлежат установкам своих владельцев и не добавляют в корень прикладные identities. Административный socket, node state и краткоживущие конечные SVID разделены; отзыв не отменяется автоматическим продлением.

Дополнительный `spire/compose.observation.yml` принадлежит тому же владельцу: отдельная безопасная проекция здоровья, издатель, собственный Prometheus/устойчивый sender и одноразовые задачи OIDC/Grafana. Профили наблюдения SPIRE не активируются общим `ui`. Корень не хранит его первоначальные полномочия, адреса или панель и не заменяет его автоматический установщик. Для восстановления используются собственные зашифрованные полные копии, не пересоздание регистраций корневым Compose.

[ADR-0115](../../docs/adr/20261012-0115-owner-local-embedded-sqlite.md) явно дополняет только технологический выбор собственного встроенного технического хранилища. Корень не создаёт общий SQLite-сервис/том, не монтирует базы владельцев и не меняет их схемы. Самостоятельный и общий запуск используют прежние раздельные постоянные данные; доменная PostgreSQL, транспорт и остальные ограничения согласования сохраняются.

Нормативные источники: [ADR-0103](../../docs/adr/20261010-0103-consumer-agnostic-infrastructure-orchestration.md), [ADR-0104](../../docs/adr/20261010-0104-owner-contained-compose-recipes.md), [ADR-0082](../../docs/adr/20261007-0082-self-contained-service-delivery.md), [ADR-0089](../../docs/adr/20261008-0089-compose-owned-local-networks.md), [развёртывание](https://github.com/sapogov1978/discovery-research-platform/blob/8d1a663319ac15d8729cf1422858f37d57096c75/docs/architecture/21-deployment.md). Операционные команды — в [README](README.md).

Корень является точкой совместного жизненного цикла самостоятельных инфраструктурных поставок, не отдельным сервисом или владельцем канонических данных. Compose включает модели и env владельцев без корневых переименований, исправлений и повторных runtime-определений. Имена административных задач уникальны уже у владельцев. Kafka включается ровно один раз непосредственно из своей поставки, независимо от переводчика. Переводчик использует собственные каноническую модель `compose.remote.yml` и локальный рецепт `compose.local.yml`; эту же пару включает его самостоятельный `compose.yml`. Локальная БД и зависимость от healthy Kafka имеют один источник внутри поставки переводчика. Удалённый режим использует `compose.remote.yml` без локального брокера, с обязательной фактической проверкой endpoint перед запуском рабочих ролей.

В корневом env допускается только обязательное имя общей Compose-группы. Конкретные прикладные базы, buckets, роли, OIDC-клиенты, topics, цели наблюдения, панели и функциональные сети не принадлежат ни корню, ни провайдерам. Универсальный административный адаптер не исполняется без задачи и точного входа владельца ресурса.

Нативные продукты наблюдения запускаются без профиля по ADR-0107; полный запуск дополнительно включает только профиль состояния, не весь административный профиль. Перед ним реальные идемпотентные задачи подготавливают собственные ресурсы инфраструктурных владельцев; шесть отдельных init наблюдения принадлежат его продуктам, ошибка запрещает объявлять подготовку завершённой. Миграции и Kafka-барьер переводчика остаются автоматическими зависимостями его собственного Compose. Рабочие роли не получают административных credentials.

Остановка и снятие контейнеров сохраняют данные. Самостоятельные и общая группа никогда не пишут одновременно в одни тома. Повторный запуск сохраняет имена, identities и последовательности издателей. Географическое размещение использует endpoints и отдельные поставки владельцев, не Docker bridge между странами и не файловый каталог другого сервиса.

Тесты оркестрации находятся только в `test_infrastructure`, написаны на Python и используют реальные подготовленные поставки. До запуска фиксируются Docker-ресурсы; тест отказывает при существующих контейнерах общей группы или других писателях тех же томов. В `finally` снимаются только созданные контейнеры и сети, удаляются только доказанно созданные тома, исходные ресурсы сверяются. Отчёт содержит выполненные и невыполненные проверки. Механизм ограждения PostgreSQL выбирается собственным env по ADR-0106, не отключается корнем или тестовым override; локально Docker, отдельные Kubernetes/watchdog допуски не объявляются пройденными.
