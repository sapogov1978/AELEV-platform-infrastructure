# Delivery — руководство пользователя

## Автоматическое продление локальной телеметрии

Для уже одобренного набора на Docker volumes установщик потребителя вызывает `bind-delivery`, `upgrade-delivery` прежней задачи и `once`. [Технический интерфейс](../../CERTIFICATE_DELIVERY.md) задаёт точное назначение, публичный payload, отказ и восстановление переключения таймера; он не допускает выдачу новых прав или передачу закрытых CA в runtime. Новый операторский артефакт не требует обновления sender/приёмника.

Для подготовки уже установленных credentials без выдачи используйте читающий `python3.13 renewal.py export-issuers --state <прежний-каталог-задачи> --consumer-owner <точный-владелец>`. Команда не меняет таймер или состояние и не читает приватные ключи; отозванное либо неподтверждённое одобрение закрыто отклоняется. Формат результата и граница доверия определены в [SPEC](SPEC.md#читающий-экспорт-публичных-issuer). Публичный операторский артефакт собирается `docker build -f Dockerfile.renewal -t <свой-тег> .`; в установщике закрепляют digest, не изменяемый тег. Не монтируйте state/approval в runtime и не подменяйте CA для устранения ошибки проверки подписи. [Проверка экспорта](test/issuer-export-result-20261024.md) отделена от выдачи и переноса потребителя.

`renewal.py` — отдельный операторский вход, также поставляемый публичным sender как `/opt/aelev/telemetry-renewal.py`. Он не запускается внутри runtime и не получает ключи CA через конфигурацию sender. [Нормативные правила](SPEC.md#продление-локальных-удостоверений) ограничивают его существующими одобренными identities и прежними CA. Это локальный профиль с OpenSSL 3, не внешний production SPIRE.

Закрытый JSON содержит ровно `schema_version=1`, `environment=local|test`, `consumer_owner`, абсолютный `openssl`, абсолютный путь публичного `report` и массив `certificates`. В каждой записи ровно `id`, `certificate`, `key`, `issuer_certificate`, `issuer_key`; пути абсолютны, ключ клиента рядом с его сертификатом, ключ CA — вне runtime и публичного каталога. `id` — короткое операторское имя; никакого встроенного списка прикладных владельцев нет. Пароли/ключи не помещают в JSON, argv или Git; указываются только защищённые собственные файлы. Символические ссылки и открытые режимы ключей запрещены. Публичный каталог создаётся до регистрации и монтируется потребителю только для чтения.

```sh
python3.13 renewal.py enroll --state <закрытый-каталог-задачи> --input <закрытый-json>
python3.13 renewal.py once --state <закрытый-каталог-задачи>
python3.13 renewal.py install --state <закрытый-каталог-задачи>
```

Только отдельно разрешённое начальное восстановление истёкших identities добавляет `--allow-expired` к `enroll`; обычная автоматика это право заново не создаёт. `once --force` проверяет тот же путь выдачи раньше срока и не обходит сравнение ключа/CA/subject/расширений. Установщик создаёт проверенный пользовательский LaunchAgent macOS с запуском раз в минуту; неизменяемый скрипт копируется по хешу, изменённый таймер не подменяется. Выключенный хост не выдаёт сертификаты; работа продолжится после пользовательского входа. Отмену выполняют `python3.13 renewal.py revoke --state <закрытый-каталог-задачи>`: это запрет дальнейшей выдачи, не CRL и не отзыв уже существующего сертификата. После отмены не удаляйте журнал ради новой регистрации.

После установки проверяют самостоятельное обновление публичного отчёта, все сроки и новое mTLS-соединение через прежние endpoints. Сам по себе `healthy` операторской задачи не доказывает доставку: дополнительно нужны свежие центральные метрика, лог и трасса. Новые удостоверения подхватываются sender 1.0.8 без изменения ключей/доверия; первоначальный переход со старого SDK требует адресного обновления с полной остановленной копией собственного журнала и сохранением истории восстановления. Другие потребители и центральный приёмник не обновляются автоматически. Ошибки и сроки идут в существующий Prometheus/Grafana, отдельный SMTP/канал не создаётся.

Для установки или обновления потребителя обязательна команда `python3.13 renewal.py check --state <закрытый-каталог-задачи> --max-age 180`; один только exit code `once` или наличие файла отчёта не является gate. При явной смене CA используйте approval schema 2 с `previous_issuer_certificate`, сначала расширьте доверие потребителя старым и новым корнем и только потом публикуйте leaf. Разные owner CA не объединяйте в одном state: например, query CA SPIRE и publisher CA Platform UI сопровождаются отдельными задачами и отдельными квитанциями.

## Локальная проба издателя

Закреплённый `aelev-platform-ui-client==1.1.1` проверяет живость издателя командой `python -S /opt/aelev/publisher-health.py AELEV_INFRASTRUCTURE_DELIVERY_`: читается только подтверждённый heartbeat собственного журнала, без загрузки приложения и сетевых запросов. Неготовность доставки остаётся отдельным наблюдением; исправный издатель не выдаёт её за отказ своего процесса. Обновление только `delivery-status-publisher` сохраняет его том и не требует перезапуска центрального приёмника. Автовосстановление по `unhealthy` этим не устанавливается.

## Структура поставки

### Живость и готовность приёмника

На существующем диагностическом mTLS-порту `GET /healthz` проверяет только ответ HTTP-процесса, `GET /readyz` — готовность доставки. Успехи имеют канонические тела по [контракту проб](../../../../docs/api/health-readiness.md). Docker запускает `python -S /opt/aelev/delivery_health.py`: чтение собственного атомарного heartbeat без импорта приложения, SQL и TLS. Совместимая команда `alive` сохраняется для диагностики; `health` и `/health` остаются проверками готовности, не основанием безусловно перезапускать приёмник при недоступном Loki/Tempo/Prometheus. Диагностика `/status` сохраняет задолженность и безопасные причины ошибок. При подтверждённой остановке или зависании worker/listener весь процесс завершится с сохранением журнала; доменные очереди и процессы не управляются. Контроль внешних зависимостей и тревоги остаются в существующей системе наблюдения.

```text
delivery/
├── README.md, SPEC.md, TASKS.md, CHANGELOG.md
├── compose.yml, .env.example     # .env — рабочие настройки вне Git
├── Dockerfile.status             # свои технические роли и проверки
├── delivery.py                   # приём, журнал, квитанции и повтор
├── Dockerfile.sender             # отправитель в поставке владельца телеметрии
├── sender.json.example           # образец его собственной настройки
├── pyproject.toml, poetry.lock
├── vendor/                       # публичные wheels, закреплённые SHA-256
├── prepare.py                    # собственные init/tls/render
├── deployment.json               # правила подготовки и перечень секретов
├── config/                       # delivery.json
├── status_publisher.py            # только собственные проверки и публикации
├── secrets/                      # доставка вне Git и образа
│   ├── native/                   # собственные TLS и дополнительные секреты
│   ├── status/                   # собственный издатель и нативная проба
│   └── status-admin/             # только явные одноразовые задачи
├── runtime/                      # подготовленные файлы из config/env
└── test/                         # проверки и читаемые результаты
```

Дерево показывает значимые файлы, без кэшей и подробного списка отчётов. `.env`, `secrets/` и производные `runtime/` создаются/доставляются оператором и исключены из Git и сборки. Именованные тома данных и журнала издателя объявлены в Compose; это не папки исходников. `config/`, `deployment.json` и собственный env — источники подготовки, `runtime/` — их результат.

## Назначение


Текущие проверки самостоятельной поставки: [результат](test/standalone-validation-result.md).

Собственный издатель имеет `stop_grace_period: 2m`: это время на завершение текущего запроса и подтверждение отписки через удалённый HTTPS, не запасное значение env и не бесконечное ожидание. Если связь недоступна, неподтверждённый выход сохраняется в журнале, а UI не скрывает строку как штатно завершённую.

Повторная проверка названия назначения и технологического состава: [результат](test/status-labels-result.md). Она не подменяет прежние испытания жизненного цикла.

Это полная самостоятельная поставка delivery: нативный процесс, собственные настройки, сеть, удостоверения и данные, а также независимая UI-часть. Принимает технические пакеты и выдаёт квитанцию после фиксации исходных байтов, затем повторяет доставку в назначенные проекции. Не интерпретирует доменные сообщения. Родительский observability только включает этот же Compose, не дополняет runtime. Отказ другого продукта не останавливает собственный издатель.

Сборка использует только этот каталог, собственный Poetry lock и включённый публичный артефакт `aelev-platform-ui-client` 1.1.1. Общего образа издателя нет; библиотека содержит транспорт, а не перечень продуктов. Канонический протокол: [инъекция UI](../../../../docs/api/platform-ui-injection.md). При извлечении UI-части в отдельный репозиторий публичный контракт доставляется как документация выпуска, не как приватный импорт соседнего сервиса.

Скопируйте `.env.example` в `.env`, задайте реальные HTTPS-адреса UI, IdP и собственного продукта, доступность DNS/портов и правильные SAN сертификатов. Удалённому издателю не нужна Docker-сеть другого узла. Локальный `UI_HEALTH_URL` использует имя собственного нативного процесса в собственной сети; при удалённой пробе задаётся маршрутизируемый HTTPS-адрес. Никаких запасных значений Compose не содержит; отсутствие переменной запрещает разрешение конфигурации.

Секреты `secrets/status`: `shell-ca.crt`, `identity-ca.crt`, собственные `publisher.crt/key`, `client-secret`, а также `probe-ca.crt`, `probe.crt/key` для чтения своего health-интерфейса. Закрытые ключи CA рабочему издателю не передаются. Для явной одноразовой подготовки identity используется отдельный `secrets/status-admin` с `admin-user/admin-password`, не монтируемый в постоянный процесс. Генерация и установка публичного клиента описаны в [руководстве](../../platform-ui/USER_MANUAL.md#создание-и-подключение-ui-нового-сервиса).

Из этого каталога:

```sh
docker compose --env-file .env --profile ui build delivery-status-publisher
docker compose --env-file .env --profile provision run --rm delivery-status-provision
docker compose --env-file .env --profile ui up -d --no-build delivery-status-publisher
docker compose --env-file .env --profile ui stop delivery-status-publisher
```

Общее развёртывание из родительского каталога сохраняет тот же код и параметры. `provision` не стартует автоматически и не является постоянно работающим компонентом. Права на Docker API, остановку чужих процессов или доменные данные не выдаются.

| Суффикс `AELEV_INFRASTRUCTURE_DELIVERY_` | Назначение |
|---|---|
| `COMPOSE_PROJECT` | Имя самостоятельной Compose-поставки нативного процесса и UI-части. |
| `UI_IMAGE`, `UI_PYTHON_IMAGE` | Собственный образ издателя и закреплённая база сборки Python 3.13.7. |
| `UI_URL`, `UI_IDENTITY_URL` | HTTPS-адреса технического API оболочки и IdP, без привязки к их географии. |
| `UI_REALM`, `UI_CLIENT_ID`, `UI_AUDIENCE` | Собственная identity и аудитория JWT, только роль публикации. |
| `UI_MODULE_ID` | Постоянный UUID собственного описания, не переиспользуется для другого владельца. |
| `UI_INTERVAL_SECONDS`, `UI_TIMEOUT_SECONDS` | Интервал отчёта и предел каждого сетевого ожидания; опрос браузера остаётся минутным. |
| `UI_HEALTH_URL` | Только собственный проверяемый HTTPS-интерфейс готовности. |
| `UI_SECRET_ROOT`, `UI_SECRET_GID` | Каталог рабочих удостоверений и дополнительная группа чтения. |
| `UI_ADMIN_ROOT`, `UI_PROVISION_UID` | Отдельные учётные данные оператора и UID явной одноразовой подготовки. |
| `UI_STATE_VOLUME` | Устойчивый журнал последовательности/точных повторяемых байтов, сохраняется при stop/start. |
| `UI_NETWORK` | Собственная сеть издателя; при совместном запуске только его нативный процесс подключается к ней. |
| `UI_MEMORY_LIMIT` | Ограничение памяти издателя, не нативного продукта. |

При ошибке транспорта или TLS результат `UNKNOWN`, а не выдуманный отказ. Подтверждённый ответ собственного интерфейса 503 означает `OFFLINE`; 200 означает готовность. Штатная подтверждённая отписка скрывает строку; отсутствие публикаций без отписки оставляет строку с «Нет связи» после срока свежести приёмника. Техническая проба не доказывает отсутствие потерь, производительность или правильность содержимого хранилища.

Модульные тесты находятся в `test/test_status_publisher.py`. `test/status_publication.py` проверяет существующую реальную самостоятельную установку, stop/start собственного процесса и издателя, изменения API/браузера и продолжение публикаций прочих исходно доступных владельцев. Тест не создаёт фиктивных сервисов и восстанавливает исходные контейнеры в `finally`; данные не удаляет. Аргументы и проверки PKI описаны в родительском README. Отчёт сохраняется в `test/status-publication-result.md`.

При штатной остановке издателя его подтверждённая отписка скрывает строку; без отписки строка остаётся с `connection=LOST` после TTL. Остальные строки продолжают обновляться. При окончательной замене продукта новый владелец получает новые UUID и identity, не захватывает прежний журнал. Прежнее описание снимает прежний владелец через `DELETE` по каноническому контракту инъекции; новый продукт не удаляет чужую строку.

Результат реальной браузерной проверки: [status-publication-result.md](test/status-publication-result.md), [снимок страницы](test/status-publication.png). Дополнительные проверки описаны в [отчёте валидации](test/status-validation-result.md).

## Секреты: получение и подготовка

Стандартный SECRET_ROOT этого владельца — `./secrets/native`; изменённый путь подставляйте во все команды. Обязательные имена перечислены в собственном `deployment.json` и проверяются `prepare.py render`. Открытые сертификаты не являются секретами, но требуют проверенного происхождения.

| Файл в SECRET_ROOT | Источник и назначение |
|---|---|
| `server.crt`, `server.key` | Собственное серверное удостоверение с цепочкой, SAN PUBLIC_HOST и внутренних адресов данного процесса, EKU serverAuth. Выпускает утверждённая PKI. |
| `ca.crt` | Публичные цепочки доверия техническим клиентам/серверам данного контура. Не закрытый ключ CA. |
| `client.crt`, `client.key` | Собственное clientAuth для проверок/исходящих технических соединений. Выдаёт PKI, которой доверяет фактический endpoint. Не ключ другого продукта. |
| `publisher-ca.crt` | Публичное доверие клиентам входа телеметрии; получить у выдающего их PKI-оператора. Не CA издателей UI, хотя техническое имя похоже. |

У отправителя из `sender.json.example` отдельный набор: `server.crt/key` местного входа, `local-publisher-ca.crt` местных источников, `central-ca.crt` центрального delivery, `client.crt/key` собственной передачи, `local-query-ca.crt` и `query-client.crt/key` диагностики. PKI-оператор выдаёт каждую пару по назначению; центральный вход доверяет issuing CA собственного отправителя. Нельзя копировать закрытый ключ архива или соседнего сервиса в sender. Собственные пути sender задаёт его конфигурация, не env центрального архива.

Для новой локальной установки заполните собственный env и вызовите `python3.13 prepare.py tls --issuer-dir /secure/local-observability-issuer`, затем `python3.13 prepare.py render`. Генератор создаёт только файлы этого владельца: сертификаты на 30 дней, локальные CA на 365 дней; непустой SECRET_ROOT не перезаписывает. Один явно выбранный оператором issuer может выдавать совместимые локальные удостоверения независимо размещённых тестовых продуктов, но не становится их общим runtime или общей папкой данных. При самостоятельном вызове без --issuer-dir issuer находится в собственном `secrets/issuer`, не монтируется в контейнеры. Общий запуск через слой сам по себе не подготавливает UI/OIDC-секреты.

В production генератор локальной CA пропускают: собственные ключи/SVID и цепочки доставляет утверждённый внешний источник по ADR-0017. Если PKI работает через CSR, создайте отдельный ключ `openssl req -new -newkey rsa:3072 -nodes -keyout <новый-каталог>/server.key -out <новый-каталог>/server.csr -subj /CN=delivery -addext 'subjectAltName=DNS:<реальный-host>' -addext 'extendedKeyUsage=serverAuth'`; CA возвращает server.crt с правильными SAN/EKU. Для clientAuth выполняется отдельная выдача, не повторное использование server.key. Private CA key в SECRET_ROOT запрещён.

Каталоги имеют `0750`, нативные файлы `0640`, группа SECRET_GID: tls-генератор выставляет её из env; Compose добавляет её нативному процессу независимо от его UID. При внешней доставке примените те же права и группу до запуска, не `chmod 777`. Источники/закрытые CA остаются на операторской машине с `0700/0600`. Перед сменой доверия подготовьте обе цепочки и новый собственный набор, обновите render и контролируемо пересоздайте изменённую роль в действующем проекте; автоматическая ротация локальным генератором не реализована.

### Секреты издателя состояния

Пути ниже соответствуют шаблону `UI_SECRET_ROOT=./secrets/status`; при другом значении используйте собственный настроенный каталог. Источники доверия определяются адресами, не совместным размещением: узел в другой стране получает публичные цепочки CA и своё удостоверение через защищённую доставку, а не доступ к чужой папке.

| Файл | Откуда получить и зачем |
|---|---|
| `shell-ca.crt` | Проверенная публичная цепочка CA HTTPS-сервера оболочки; получить у её оператора. Это не CA клиентских издателей. |
| `identity-ca.crt` | Проверенная публичная цепочка CA HTTPS IdP; получить у оператора IdP. |
| `publisher.crt`, `publisher.key` | Собственное удостоверение `clientAuth`; его выпускающая CA должна входить в `publisher-ca.crt` приёмника UI. Закрытый ключ принадлежит только этому издателю. |
| `client-secret` | Выдаёт Keycloak для собственного confidential client; сохраняет `delivery-status-provision`. Не генерируйте произвольный пароль вместо секрета существующего OIDC-клиента. |
| `probe-ca.crt`, `probe.crt/key` | Публичная CA собственного health-сервера и отдельная clientAuth-проба этого владельца; выдаёт его техническая PKI. Не административные файлы IdP и не закрытый ключ native-процесса. |
`UI_ADMIN_ROOT` содержит отдельные `admin-user` и `admin-password`: имя и действующий пароль администратора развёртывания Keycloak получают у оператора IdP или из внешнего хранилища. Это не пароль service account и не пароль пользователя браузера. Доставьте их файловым механизмом; например, `install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password`, а имя запишите в `admin-user` без секрета. Provision должен иметь право записи в `UI_SECRET_ROOT`, runtime — только чтение.

Перед локальной подписью проверьте `openssl version` и поддержку OpenSSL 3; при отсутствии используйте утверждённый пакет вашей ОС (`brew install openssl@3` на macOS, `sudo apt-get install openssl` на поддерживаемой Debian/Ubuntu) или подготовленную операторскую станцию. Эти команды не устанавливают CA в системное доверие и не выполняются при запуске контейнера.

Первичная доставка административных файлов (пути источника и имя замените данными своего IdP, не пароль в команде):

```sh
umask 077
install -d -m 750 secrets/status-admin
test ! -e secrets/status-admin/admin-user && test ! -e secrets/status-admin/admin-password || exit 1
STATUS_ADMIN_USER=deployment-admin
printf '%s\n' "$STATUS_ADMIN_USER" > secrets/status-admin/admin-user
install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password
chmod 640 secrets/status-admin/admin-user
```

Имя deployment-admin — пример существующей identity, не команда создания пользователя. Если у вас другое имя или UI_ADMIN_ROOT, задайте их явно; GID каталога/файлов должен совпадать с UI_SECRET_GID, а владелец — с UI_PROVISION_UID. Уже доставленные пароли не перезаписываются первичной командой. После удаления одноразового контейнера пароль не нужен рабочему издателю; локальную административную доставку уберите из runtime-узла или выдавайте заново только на время provision.


Для новой локальной identity можно создать ключ и CSR на доверенной операторской машине. Нужен OpenSSL 3 для `-copy_extensions`; пути `/secure/...` ниже заменяются выбранными операторскими файлами, это не обязательные каталоги сервиса. Публичные CA берутся из проверенного источника; неизвестный сертификат из сети не становится доверенным только потому, что назван `ca.crt`.

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/publisher.key && test ! -e secrets/status/publisher.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=publisher -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/publisher.key -out secrets/status/publisher.csr
# Только локальный тест: ключ CA остаётся на операторской машине, не в runtime.
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/publisher.csr \
  -CA /secure/ui-publisher-ca.crt -CAkey /secure/ui-publisher-ca.key \
  -CAcreateserial -out secrets/status/publisher.crt
install -m 640 /secure/ui-server-ca.crt secrets/status/shell-ca.crt
install -m 640 /secure/idp-ca.crt secrets/status/identity-ca.crt
chmod 640 secrets/status/publisher.key secrets/status/publisher.crt
```

Тестовую CA издателей создаёт оператор локальной оболочки при её явной подготовке PKI; берутся именно `issuer/publisher.crt/key`, не серверный ключ UI. В рабочей среде последнее подписание локальной CA не выполняют: удостоверение и обновляемую identity доставляет утверждённая PKI/SPIRE по [ADR-0017](../../../../docs/adr/20260803-0017-zero-trust-and-operational-security.md). CSR можно передать CA, закрытый ключ нельзя. Перед включением издателя доставьте также перечисленные файлы нативных проб и выполните собственный `--profile provision run --rm delivery-status-provision` из раздела запуска.


Для новой локальной пробы (не рабочей SVID) используйте собственную операторскую CA, которой доверяет данный health endpoint; существующие файлы не перезаписываются. Если issuer расположен иначе, замените путь. Это отдельная пара, не копия native client.key:

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/probe.key && test ! -e secrets/status/probe.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=probe -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/probe.key -out secrets/status/probe.csr
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/probe.csr \
  -CA /secure/local-observability-issuer/internal-ca.crt -CAkey /secure/local-observability-issuer/internal-ca.key \
  -CAcreateserial -out secrets/status/probe.crt
install -m 640 secrets/native/ca.crt secrets/status/probe-ca.crt
chmod 640 secrets/status/probe.key secrets/status/probe.crt
```


### Хранение, доступ и ротация

Секреты разделяются по среде, владельцу и роли. Локальные файлы — только материал стенда или доставка, не каноническое production-хранилище; рабочий источник — внешнее утверждённое хранилище, доставка в память/tmpfs по ADR-0017. Не включайте секреты в Git, образ, архив исходников, команды с подстановкой содержимого или отчёты. Не запускайте `set -x`, не публикуйте раскрытый `docker compose config`; проверяйте через `config --quiet`. Резервные копии секретов хранятся отдельно, зашифрованно, с ограниченным доступом; закрытые CA — только у оператора/KMS/HSM, никогда у рабочего процесса.

Для status-файлов установите каталоги `0750`, файлы `0640`, группу из собственного `UI_SECRET_GID`; владельцем каталога должен быть оператор с `UI_PROVISION_UID`, которому разрешена запись client-secret. UID рабочего издателя остаётся заданным собственным образом/Compose; дополнительная группа даёт только чтение. В командном примере ниже STATUS_SECRET_GID — числовое значение уже настроенного UI_SECRET_GID, не новая переменная сервисного env. Не делайте ключи общедоступными ради запуска. Права нативных секретов описаны отдельно выше.

```sh
: "${STATUS_SECRET_GID:?set the numeric GID from your UI_SECRET_GID}"
chgrp "$STATUS_SECRET_GID" secrets/status secrets/status/*
chmod 750 secrets/status
chmod 640 secrets/status/*
```

Для отдельного административного каталога примените ту же группу, `0750` каталогу и `0640` обоим файлам; владельцу из UI_PROVISION_UID должно быть разрешено чтение admin-password и запись client-secret в status. Keycloak использует административный пароль через env, а не status-admin.

Проверьте срок, SAN/EKU и цепочку сертификата до запуска: `openssl x509 -in secrets/status/publisher.crt -noout -dates -ext extendedKeyUsage`, `openssl verify -CAfile /secure/ui-publisher-ca.crt -purpose sslclient secrets/status/publisher.crt`. Локальное удостоверение из команды действует 30 дней и не обновляется автоматически. Для смены CA сначала доставляют доверие старой и новой цепочкам, затем новые удостоверения, проверяют соединения и только после этого отзывают старые. Ротацию проводят через отдельный подготовленный набор файлов и контролируемое пересоздание собственной роли; генераторы первичного запуска не используют для перезаписи активных ключей. Новый client-secret сначала создают в собственном клиенте Keycloak, затем доставляют повторным собственным provision и пересоздают издателя; обычный повтор provision сам по себе не является ротацией. UUID, identity, ревизия и журнал последовательностей при этом сохраняются.


## Нативный процесс: подготовка и отдельный запуск

Сначала проверьте `docker version`, `docker compose version`, `python3.13 --version` и `openssl version`. Установка и границы PKI описаны в [руководстве слоя](../USER_MANUAL.md#подготовка-и-запуск). Для новой установки из этого каталога:

```sh
python3.13 prepare.py init
# Настройте собственный .env: реальные адреса, bind, доверие и лимиты.
python3.13 prepare.py tls --issuer-dir /secure/local-observability-issuer
python3.13 prepare.py render
docker compose --env-file .env --profile ui --profile provision build
docker compose --env-file .env --profile provision run --rm delivery-configuration-init
# Только при первоначальной настройке собственной identity:
docker compose --env-file .env --profile provision run --rm delivery-status-provision
docker compose --env-file .env --profile ui up -d --no-build
python3.13 test/startup.py
docker compose --env-file .env --profile ui stop
# Снять контейнеры и сеть, сохранив данные и удостоверения:
docker compose --env-file .env --profile ui down
```

`init` не перезаписывает существующий env; `tls` не перезаписывает ключи и служит явной локальной PKI, не production-ротацией. Для совместных локальных удостоверений оператор передаёт один issuer; runtime его ключей не получает. Для production доставляется утверждённая PKI/SPIRE с корректными SAN и ротацией. `render` проверяет обязательные значения, пути внутри владельца и секреты, создаёт только объявленные файлы в `runtime`, сохраняя независимые инъекции. Не редактируйте производные файлы вместо исходников `config` и собственного env. Версионированный публичный wheel подготовки закреплён SHA-256 в собственном Poetry lock; общего рабочего образа нет.

Нативный процесс запускается без профиля; `ui` добавляет собственного издателя, а не нативный продукт. Профиль `provision` не запускают целиком через `up`. Явный init проверяет маркер собственного тома без сети/секретов и отказывает на чужом или непустом немаркированном томе. При смене самостоятельной/общей группы сначала снимите прежних писателей без удаления томов. Compose предупреждает о старой метке проекта у сохранённых томов: это не удаление данных, маркер `DATA_OWNER` проверяется независимо.

| Суффикс `AELEV_INFRASTRUCTURE_DELIVERY_` | Назначение нативной настройки |
|---|---|
| `COMPOSE_PROJECT` | Имя самостоятельной Compose-группы; не меняет идентичность уже существующих данных. |
| `PUBLIC_HOST` | Публичное DNS-имя или IPv4 в SAN собственного сертификата при локальной генерации; не подменяет bind или адреса зависимостей. |
| `RUNTIME_ROOT` | Собственный каталог производных конфигураций; монтируется только для чтения. Источники в config. |
| `SECRET_ROOT` | Собственный каталог файловых удостоверений нативного процесса; ключи CA сюда не передаются. |
| `SECRET_GID` | Дополнительная группа чтения нативных секретов; права должны соответствовать файлам на host. |
| `IMAGE` | Закреплённый образ нативного продукта; версия не выбирается скрытым запасным значением. |
| `BIND` | IPv4-интерфейс публикации портов на host. Для удалённых узлов нужен доступный адрес и firewall; 127.0.0.1 ограничивает доступ этим host. |

Локальные aliases host-gateway не создают сеть между серверами. На Linux задайте доступный host-адрес вместо loopback при обмене между bridge и опубликованным портом. Нативная поставка одноузловая, без обещания высокой доступности или бесконечного диска.

## Отправитель на узле владельца телеметрии

Центральный архив не опрашивает чужие машины и не предоставляет удалённый каталог логов. По [ADR-0100](../../../../docs/adr/20261009-0100-durable-owner-telemetry-delivery.md) наблюдаемый владелец сам поставляет местный устойчивый отправитель и собственный Prometheus. Рецепт отправителя — [Dockerfile.sender](Dockerfile.sender), полный пример технических параметров — [sender.json.example](sender.json.example), протокол входов/квитанций — [контракт телеметрии](../../../../docs/api/telemetry.md). Это не общий образ издателя UI и не подключение конкретных приложений к инфраструктурному Compose.

В выбранном sender 1.0.5 Docker-проба — `python -S /opt/aelev/delivery_health.py`: она читает только собственный временный heartbeat PID 1, без повторной загрузки приложения, TLS, журнала, JSON или pathlib. Локальный закрытый сигнал состоит ровно из шести строк: владелец, версия, режим, PID, native start ticks, monotonic nanoseconds. Это не межсервисный формат или долговечный документ. `/tmp` должен оставаться собственной записываемой временной файловой системой; сигнал не переносится между контейнерами и не резервируется. Диагностические mTLS `/healthz`, `/readyz`, `/status` сохраняются; отрицательная готовность внешней доставки не превращается в отрицательную живость процесса. При обновлении владелец явно выбирает эту пробу в собственном Compose; поставка SDK не пересоздаёт центральный приёмник или соседних потребителей.

Для отдельной сборки отправителя нужен явный разрешённый образ Prometheus с digest: ARG PROMETHEUS_IMAGE не имеет запасного значения. Команда выполняется из этого каталога после выбора выпуска:

```sh
docker build -f Dockerfile.sender \
  --build-arg PROMETHEUS_IMAGE='<разрешённый-образ-Prometheus@sha256:digest>' \
  -t aelev/observability-sender:1.0.7 .
```

Владелец принимает проверенный версионированный образ/digest, размещает свой производный delivery.json в `/etc/aelev/delivery.json` только для чтения, монтирует только собственные удостоверения и отдельный постоянный том `/var/lib/delivery`. Поля mode=sender, destinations, пределы, доверие и prometheus_command задаются в его поставке; example не является рабочей конфигурацией. prometheus_command запускает местный сборщик под контролем отправителя, а его конфигурация remote_write направляет метрики в местный устойчивый вход. Логи и трассы также направляются в местные стандартные входы, не в файловый каталог центральной машины. Для каталогов записи обеспечьте доступ контейнерному UID/GID 10001:10001.

Начиная с 1.0.6 sender содержит собственную проверенную SQLite 3.53.4; отдельная библиотечная оболочка потребителя для этого не нужна. Образ сохраняет прежние Python, Alpine и Prometheus, собирает только закреплённый официальный SQLite и проверяет связанную версию. Проверка обновления остаётся обязательной: новый SDK открывают только на изолированной копии остановленного журнала, сверяют целостность, записи, последовательности, байты и задолженность до подключения единственного писателя. Замена образа не является разрешением сбросить исчерпанный бюджет восстановления.

Локальный ARM64-выпуск 1.0.7 добавляет те же фазы и ограниченные позиции собственных потоков, что диагностический приёмник; правила находятся в [спецификации](SPEC.md#приём-счётчики-и-восстановление). Он не меняет пороги, зависимости, HTTP-квитанции или heartbeat-пробу. Получатель отдельно принимает точный digest; установка у одного владельца не обновляет остальных. Для другой архитектуры или внешнего registry требуется отдельно доставленный и проверенный артефакт, а не предположение о доступности локального тега.

При полной ёмкости новые данные не подтверждаются; уже принятые сохраняются. Квитанция центрального журнала проверяется по UUID/SHA-256/durable, а не одному HTTP 200. Доменные процессы не останавливаются из-за телеметрии. Владельцу необходимо отдельно проверить местный приём, недоступность центра, перезапуск и восстановление истории. Registry-публикация/digest admission отправителя ещё остаются открытой задачей в [TASKS слоя](../TASKS.md); локальный тег сборки не выдаётся за опубликованный production-выпуск.

## Обслуживание, обновление и восстановление

### Диагностика остановки критического цикла

Новый диагностический выпуск дополняет отчёт полями `ingestion_phase`, `health_phase`, их возрастом/возрастом прогресса и `supervisor_gap_seconds`: наибольшим промежутком между проверками supervisor во время подтверждения отказа. `POLL_WAIT` означает ожидание следующей готовности сокета, `ACCEPT` — приём, `TLS_SETUP` — подготовку TLS без handshake, `REQUEST_DISPATCH` — передачу обработки потоку, `SLOT_REJECT_CLOSE` — закрытие соединения при исчерпании допуска. `thread_stacks_json` содержит только ограниченные позиции трёх собственных потоков без локальных данных и исходных строк. Сопоставляйте их с фазами и задержками: большой промежуток supervisor сам по себе не доказывает конкретную причину нехватки ресурсов, а стек — положение в момент снимка, не вся история. Отсутствующие поля в прежнем отчёте не восстанавливаются задним числом.

После нового подтверждённого отказа прочитайте собственные `last-failure.json` и `failure-history.jsonl` в постоянном каталоге `/var/lib/delivery`, сохранив их с резервной копией тома. `WORKER_STOPPED` означает завершившийся поток, `WORKER_STALLED` — отсутствие его прогресса; коды `INGESTION_LISTENER_*` и `HEALTH_LISTENER_*` различают вход и диагностику, `WORKER_FAILED` — обработанную ошибку фонового цикла, `SOURCE_PROMETHEUS_EXITED` — завершение собственного сборщика. Фаза вида `JOURNAL_READ_LOGS`, `FORWARD_TRACES`, `CAPACITY_CHECK` или `RETRY_WAIT` показывает последнюю ограниченную операцию; произвольные адреса и тела в отчёт не входят. Предыдущий отчёт не стирается успешным запуском. Отсутствующий файл у старой версии не означает отсутствие прежнего отказа.

Гонка готовности слушающего сокета обрабатывается неблокирующим `accept`; таймауты принятых TLS/HTTP-соединений и критерии подтверждения зависания прежние. Само наличие отчёта не разрешает `reset` бюджета рестартов, удаление архива или повторный запуск соседних продуктов. Адресное восстановление остановленного экземпляра выполняется только после разбора и согласования; при замене сохраняются история и израсходованные попытки ограничителя, автоматическая native-политика не включается поверх исчерпанного бюджета.

Команды этого README выполняются из собственного каталога владельца. Сначала проверьте, какой Compose-проект использует его данные: самостоятельный, слой observability или корень infrastructure. Если контейнеры принадлежат верхнему проекту, выполняйте адресное действие через его Compose; второй самостоятельный up поверх тех же томов запрещён. Первичную генерацию env/PKI не повторяют при обычном старте. Проверяйте конфигурацию через `docker compose --env-file .env --profile ui config --quiet`, чтобы не выводить секреты.

Сохраняйте весь DATA_VOLUME с SQLite-журналом, WAL и контрольными точками доставки при остановленном delivery, не один живой файл SQLite. Архив принятой телеметрии бессрочный: CAPACITY_BYTES ограничивает новый приём, а не разрешает вытеснить старое. При проверке восстановления используйте отдельный том и изолированные назначения: повтор доставки допускает дубли и не должен незаметно писать в рабочие проекции.

Обновление — отдельная операция владельца: согласуйте закреплённый образ, сохраните согласованную копию данных и журнала издателя, подготовьте производные файлы командой `prepare.py render`, затем адресно пересоздайте только изменённые роли в действующем проекте. Не запускайте весь provision и не удаляйте тома. Проверьте нативную готовность, фактический запрос/доставку и подтверждённую публикацию. Старый образ можно вернуть только при совместимости формата данных; иначе нужна соответствующая проверенная резервная копия.

UUID, identity, ревизии и последовательность публикаций также входят в восстановление. UI_STATE_VOLUME не очищают как кэш; после его утраты прежний UUID нельзя начинать с sequence 1. Штатный down без --volumes сохраняет данные. Перенос требует доступных DNS/IP, SAN, доверия и firewall, не общей удалённой папки. Непроверенные WAN, внешняя PKI, нагрузка и резервное восстановление отмечены в собственном [TASKS](TASKS.md); прежний локальный отчёт их не закрывает.

## Обновление журнала и диагностика

Для центрального приёмника 1.0.2 автономная `delivery_snapshot.py` включена в образ; проверяйте архив на отдельном записываемом дисковом каталоге `/tmp`, если он не помещается в безопасный лимит tmpfs. Копия подключается только для чтения, сеть отключается, доставка не запускается. Сохраняйте полный остановленный том, включая служебные файлы и историю отказов, а не только выбранную SQLite. В `AELEV_INFRASTRUCTURE_DELIVERY_RESTART_POLICY` записывается оставшийся нативный бюджет; действующему приёмнику с тремя исчерпанными попытками соответствует `no`, не новый `on-failure:3`. После адресного пересоздания передайте новую инкарнацию штатной команде `recovery.py replace` с точным прежним ID, его счётчиком и новым image ID; эта операция не обнуляет историю или разрешённое число попыток.

Только офлайн-сверка копии использует ограниченный SQLite-кэш 64 МиБ для полного обхода индексов; каждое соединение явно закрывается. Это не изменение кэша рабочего приёмника и не замена `integrity_check` выборочной проверкой. Все пакеты и их digest проверяются до и после открытия новой версией, включая уже доставленные записи архива.

Публичный sender 1.0.6 содержит автономный операторский `/opt/aelev/delivery_snapshot.py`. Только после остановки всех писателей смонтируйте согласованную копию в `/snapshot:ro`, выделите помощнику собственный записываемый `/tmp` и запустите этот файл выбранным sender-образом без сети. Проверка копирует только SQLite и его WAL/SHM в временный каталог, выполняет `integrity_check`, проверяет digest каждого пакета и сравнивает все исходные строки, повторы, ошибки, последовательности и производные счётчики до/после открытия новым SDK. Ссылки и специальные файлы отклоняются, исходные байты повторно хешируются. Ответ содержит только числа, digest и SQLite version; содержимое телеметрии не выводится. Текущий sender не запускается и пакет не отправляется. Успех не разрешает подключить одновременно двух писателей или восстановить отозванную identity.

Размер проверочного `/tmp` рассчитывается по физическому SQLite и WAL/SHM с отдельным запасом, а не по числу pending-пакетов: после подтверждений файл может содержать свободные страницы. Например, журнал 295 МиБ не помещается в tmpfs 256 МиБ даже при двух pending-записях. Память и scratch меняются только у отдельного проверочного помощника, не у рабочего sender. Проверка включает `sqlite_sequence` и сохраняет highwater даже при нуле текущих записей.

Перед обновлением определите действующий Compose-проект и точные тома, закрепите прежние image ID и сохраните собственные журналы через SQLite backup API либо полным копированием тома после остановки всех его писателей. Проверьте `PRAGMA integrity_check` резервной копии и откройте её новым выпуском в изолированном каталоге: число записей, суммы байтов, ошибки и задолженность должны совпадать, исходные записи и хеши — сохраниться. Не копируйте только открытый `.sqlite3` без WAL. Резервные копии телеметрии не коммитят и не выводят их содержимое в лог.

Выпуск с транзакционными счётчиками совместим с прежним `records`: при первом запуске выполняется однократное восстановление небольшой проекции; до его завершения вход ещё не слушает, отправители сохраняют задолженность. Последующие проверки готовности не сканируют все тела. Адресно обновляйте только согласованные приёмник и отправитель; не включайте соседние сервисы, не меняйте UUID, секреты, сроки хранения или рабочую очередь. При откате остановите новый процесс и верните прежний image ID на прежнем томе: добавленная проекция и триггеры совместимы со старым писателем. Не выполняйте `replay` только ради исправления готовности: это повторно применит исторические проекции, а не исправит причину.

Защищённый GET `/status` остаётся доступен при задолженности. `blocking_errors` показывает безопасные коды по сигналу: `http_403` — отказ конечного входа, `transport_timeout` — сетевое ожидание, `tls_failure` — ошибка TLS, `incomplete_ack` — непроверенная квитанция или частичное подтверждение. Старый неизвестный текст не раскрывается. `admission_pressure=1` означает запрет нового приёма или необходимость восстановить его; это не разрешение удалить пакеты. Код HTTP `/health` остаётся отрицательным до восстановления, даже если `/status` отвечает успешно. Остановка Prometheus при давлении ограничена 30 секундами до SIGKILL и ещё 5 секундами ожидания; чужие процессы не затрагиваются.

Compose отправителя должен давать этому пути время завершиться: для ячейки с Prometheus предусмотрите `stop_grace_period: 1m`, для центрального приёмника без дочернего сборщика — `20s`. Это предел штатного выхода, не увеличение таймаута приёма или готовности.

## Проверка самостоятельной поставки

Для собственной уже запущенной самостоятельной поставки проверку UI с остановками запускайте только в согласованном окне. Она адресует проект из собственного env, не уже работающий верхний проект. Подготовьте Python 3.13, Playwright 1.56.0, установленный Chromium и файл пароля существующего оператора:

```sh
python3.13 test/status_publication.py \
  --ui-url https://<адрес-оболочки>:<порт> \
  --viewer-user <оператор> --viewer-password-file <файл-пароля> \
  --chromium <установленный-Chromium> --status-ttl-seconds <TTL-приёмника>
```

Это не читающая диагностика: тест останавливает и возвращает собственные компоненты. Для проверенного loopback с локальной PKI можно явно добавить --allow-local-certificate; рабочие TLS-проверки не отключаются. Наличие издателя подтверждает получение отчёта, не качество или полноту телеметрии. Отчёты прежних выпусков сохраняют историческое значение.

```sh
docker build --build-arg PYTHON_IMAGE=python:3.13.7-alpine3.22 --target checks --build-context tests=./test -f Dockerfile.status -t aelev/delivery-checks:local .
docker run --rm --network none aelev/delivery-checks:local pytest -p no:cacheprovider
```

`test/test_configuration.py` проверяет собственный Compose, обязательность env и изоляцию. `test/startup.py` проверяет уже запущенные реальные контейнеры, TLS готовности и квитанцию собственного издателя, ничего не создаёт и не останавливает; результат — [startup-result.md](test/startup-result.md). Это проверка запуска, не замена полного stop/start, WAN или резервного восстановления. Прежние отчёты UI сохраняют своё историческое значение; для нового полного цикла применяется собственный `test/status_publication.py` с подготовленным операторским браузерным окружением.
