# Нативная проба Kafka и адресная выкладка

## Проверенный выпуск

Выпуск `aelev/kafka:3.9.1-native-health-1` имеет фактический image ID `sha256:70c7736ea6d966bc10320c8e34f2e02326084fe6c2617c071fbf410a2a02675e`. Все десять runtime-слоёв прежнего `apache/kafka:3.9.1@sha256:4ceccc577f03f51f6af8dbfda55194d0d892f4fa7913ffbded567ce3895622ed` сохранены в том же порядке, добавлен один слой с `/opt/aelev/kafka-health`. Entrypoint, Cmd, Env, User, WorkingDir и объявления volumes совпали. GCC/musl-dev находятся только в стадии сборки; библиотеки JVM/ОС не заменялись. Статическая проба использует [протокол Kafka 3.9](https://kafka.apache.org/39/design/protocol/) и не является новым предметным транспортом.

Полная регрессия Kafka — 69 passed. Ruff, Black и строгий mypy прошли. Тесты компилируют настоящий C-клиент и проверяют фрагментацию ответа, correlation, дубликаты/версии/границы, отсутствие контроллера, закрытый порт и общий четырёхсекундный дедлайн. Проверяются также точная Docker-команда без shell/JVM, `init`, исходный `restart=no`, безопасное извлечение архива и отбрасывание повреждённого offset evidence. Python-проверки выполнены в существующем окружении 3.13 с тем же закреплённым SDK Platform UI 1.1.1; зависимости поставки/lock не изменены.

## Изолированный жизненный тест

Первые два проверочных запуска завершились до готовности из-за `UnknownHostException`: при `network=none` произвольное hostname контейнера не разрешалось. Причина сохранена, эти попытки не объявляются успешными. Для теста выбран `hostname=localhost`; рабочая конфигурация этим не менялась, внешняя сеть или host-порт не добавлялись.

Итог `KAFKA_NATIVE_HEALTH_LIFECYCLE_VERIFIED`: новый контейнер `aelev-kafka-native-test-7b35d130f2b7`, отдельный помеченный том, 16 прямых протокольных проверок, оба тестовых сообщения сохранены через stop/start, фактический `init=true`, после создания коротких осиротевших детей zombie — 0. Docker-пробы дали 217,636–337,694 мс. Использовались 896 МиБ RAM, 1 CPU, 512 PID и только собственный новый data volume, без сети/портов. Проверка завершилась с кодом 0, удаление только её точных ресурсов после проверки labels/image подтверждено; рабочие topics не использовались.

## Проверка реальной копии

`test/cold_backup_verify.py` запущен отдельно на прежнем закреплённом публичном Python 3.13.7/Alpine из собственного Kafka-профиля, без сети, socket и рабочих mounts: только backup read-only и приватный 384 МиБ tmpfs, UID 1000, 512 МиБ RAM, 1 CPU. Восстановлены и полностью сверены байты 1132 файлов, 262734077 байт содержимого. Отпечаток дерева данных — `f4587f17d45458cdb231d4a5dd28a31dcbfdbdafe62722687a3ba79a3807023e`. Два других тома в этой копии содержали только пустые каталоги. Результат — `KAFKA_COLD_BACKUP_CONTENT_RESTORED`; это восстановление содержимого, не применение исходных UID/GID к рабочему тому (`ownership_restored=false`) и не запуск второго брокера.

Через штатный read-only `kafka-get-offsets.sh` проверены все 194 partition boundaries из остановленного `replication-offset-checkpoint`: текущий end offset нигде не ниже сохранённой подтверждённой границы. Consumer groups/offsets не сбрасывались и не коммитились проверкой; сообщения не читались. `meta.properties` рабочей Kafka совпал с восстановленной копией: SHA-256 `881c2b212c818ff1ed6629b6eb7c8f0300bf1f09be96f5f72d930fe2773b9609`.

Клиентское ожидание удаления завершённого backup-helper истекло; это не объявлялось незавершённым копированием или основанием повторного запуска. Отдельный успешный поиск того же ID подтвердил его отсутствие. Исходные тома и backup-volume сохранены. Restore-check завершился с кодом 0 и удалён штатным `--rm`. Отпечаток ID остальных 120 контейнеров до/после совпал (`0c21c6aaff2e25fabafb293b43dc1f21eceb8228e991ad19354f66fa1bbe8e9e`), то есть другие поставки не пересоздавались.

Этот результат не закрывает отдельные согласованные изменения переводчика, Advance и общую автоматическую установку модели/SPIRE. Source Research не запускался. Общая остановка/очистка и 100 сайтов не выполнялись; команда включения Advance не выдавалась.
