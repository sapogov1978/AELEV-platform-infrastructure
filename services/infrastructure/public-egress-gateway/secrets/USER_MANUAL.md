# Руководство: Секреты и доверие gateway

Sender дополнительно получает `sender-ca.crt`, собственные `local-write.crt/key` для Prometheus и `health-ca.crt` с публичными цепочками server/local-query. Этот диагностический bundle не содержит CA keys и не изменяет доверие публичного fetch. Файлы телеметрии имеют `0640`, каталоги `0750` и собственный `TELEMETRY_SECRET_GID`; ключи выпуска находятся вне runtime-mounts.

В Git находится только этот документ. Runtime получает read-only `gateway/server.pem`, `server.key`, `server-ca.pem`, `client-ca.pem`; issuer private key и credentials клиентов ему не доступны. Серверная PKI и workload PKI могут быть разными: нельзя молча использовать server CA как разрешение клиентам. Локальная команда [подготовки](../USER_MANUAL.md#подготовка-провайдера) явно использует свой отдельный тестовый CA для обеих сторон, не production trust domain.

Серверный certificate/chain выдаёт утверждённая PKI на реальный DNS/IP SAN. Приватный ключ доставляется из защищённого хранилища, права `0640`, каталог `0750`, группа равна собственному `SECRET_GID`. Корни — публичные bundles проверки; их целостность и происхождение защищаются доставкой. Client CA/SVID — от SPIRE/PKI среды, identity клиента — один URI SAN и отдельное одобренное разрешение. Реальные внешние API keys никогда не находятся в этой папке: их хранит владелец вызова.

Для локальной проверки `prepare.py init-local` создаёт `local-ca/ca.key` с `0600`, `ca.pem` и серверную пару; повтор не перезаписывает файлы. Корневой ключ остаётся вне контейнерного mount. `prepare.py issue-client --identity <URI> --output <новый-каталог-владельца>` создаёт клиентскую пару на семь дней и публичный CA. Не используйте тестовые сертификаты в рабочей среде; после проверки удаляйте только доказанно временную PKI. Корпоративное системное доверие менять не требуется.

Ротация: получить новую пару до срока, проверить точный SAN/chain и доступ UID/GID и атомарно доставить файлы. Listener подхватывает полностью проверенный новый TLS-контекст без рестарта; несовместимая пара не заменяет прежний контекст. Для согласованного локального продления с прежним закрытым ключом предусмотрена [отдельная операторская задача](../USER_MANUAL.md#автоматическое-локальное-продление). Разрешения на точный URI сохраняются только при прежнем одобренном scope; новый URI получает отдельное разрешение, старое отзывается. Потеря bundle/неполная пара закрывает старт. Автоматическая SPIRE-ротация и доказательное учение production CA не объявляются реализованными локальной утилитой.

Для состояния `status/identity-ca.crt` проверяет IdP, `status/shell-ca.crt` — оболочку, `status/publisher.crt` и `publisher.key` — собственную mTLS-identity издателя. `status/client-secret` создаёт одноразовая задача с `0640`; рабочий UID 10001 получает чтение через `UI_SECRET_GID`. Только `status-admin/admin-user` и `admin-password` доступны этой задаче, не издателю. Отдельное OIDC-право позволяет публиковать только собственный module UUID; API keys клиентов/серверный CA private key здесь не используются. Публичный клиент 1.1.0 поставляется как собственный wheel с закреплённым digest, не общий runtime-образ.

Телеметрия использует два раздельных каталога. В `telemetry/client` runtime получает только `sender-ca.crt`, `runtime.crt`, `runtime.key`; в `telemetry/sender` находятся отдельные listener-файлы `sender.crt`, `sender.key`, `local-write-ca.crt`, центральные `central-ca.crt`, `central-write.crt`, `central-write.key` и read-only health identity `local-query-ca.crt`, `local-query.crt`, `local-query.key`. Runtime не видит центральную identity, sender не получает gateway server key или клиентские credentials. Production не допускает пустой OTLP endpoint или отсутствующие обычные файлы; symlink вместо credential закрыто отклоняется.
