# Самостоятельное завершение возврата после fencing — 20 октября 2026 года

## Подтверждённый дефект

В 13:02 UTC исполнитель остановил `postgresql-1` и `postgresql-2`. Их точные сохранённые намерения остались в `STOP_CONFIRMED`, `restart_required=true`, `start_attempts=0`. Container ID и `StartedAt` совпадали с остановленными контейнерами; OOM не зафиксирован. Исходники работающего исполнителя совпадали с предыдущим исправленным выпуском. Значит, это не ручная остановка, потеря журнала или исчерпание попыток самого возврата.

Возврат выполнялся только внутри запроса `pre_promote`. После подтверждения остановки истекла native-аренда; следующий `claim.verify()` отказал, и start не начался. Журнал сохранился, но отдельного исполнения незавершённого намерения не существовало. Предыдущие проверки повторяли запрос ограждения и потому не проверяли отсутствие следующего запроса. Это разрыв продолжения операции, а не основание ослаблять кворум или сбрасывать ограничитель.

В 14:35 UTC три независимых линейных чтения etcd подтвердили отсутствие ключа ведущего. Единственный работающий `postgresql-3` сообщал `running/replica`, timeline 30 и прежний system identifier. Его журнал содержит `following a different leader because i am not the healthiest node`; два других участника недоступны. Требование уже существующей аренды поэтому образовало отдельный замкнутый круг. На первом этапе возврат при отсутствии аренды не выполнялся до отдельного согласования; последующее разрешение и его результат описаны ниже. Первопричина исходных DCS timeouts не установлена; сон, CPU и модель не объявляются доказанной причиной.

## Исправление

Внутри Docker-исполнителя добавлен последовательный цикл возврата, независимый от новых запросов продвижения. Он читает только устойчивые собственные намерения, использует те же блокировки узла и файла, сверяет единственность помеченной цели, полный ID, инкарнацию и положительное завершение процесса. Перед start требуются две совпадающие линейные проверки native-аренды либо её положительно подтверждённого отсутствия; действующий кандидат не запускается. Цикл никогда не отправляет stop, не выбирает ведущего, не создаёт аренду и не выдаёт квитанцию продвижения.

Расход максимум трёх попыток и время следующей команды сохраняются до dispatch. Новый процесс исполнителя и повторный RPC используют тот же бюджет и ту же паузу. Неизвестный результат не возвращает попытку; уже выполненный start согласуется чтением. Один проход отправляет не более одной команды, включая неизвестный результат. Завершённые, отменённые и вручную остановленные цели не запускаются. Последний безопасный код блокировки сохраняется в намерении и аудите; повтор одной причины не раздувает аудит. Если сам цикл остановился, локальный `/health` отрицателен; частая проба по-прежнему не читает Docker, DCS или SQL.

## Проверки

На первом этапе полный прогон PostgreSQL включал 141 прошедший тест, Black, Ruff и строгий MyPy для 15 файлов. Проверены отсутствие следующего RPC, прерывание на каждой сохранённой фазе, новый исполнитель, потерянный ответ/сбой записи завершения, пауза и три попытки при смене аренды, общий барьер RPC и цикла, ручная остановка/отмена, дублирующая цель, подмена меток/ID/инкарнации, неопределённая остановка, потеря/смена аренды и отказ аудита. Остановка фонового цикла даёт отрицательный health без сетевого опроса зависимостей. Расширенный заключительный прогон указан ниже.

Отдельный сценарий [fencing-return-worker.py](fencing-return-worker.py) выполнил настоящий stop/start одноразового Docker-контейнера без SQL, сети, credentials и рабочих томов. Потеря аренды моделируется после stop; новый процесс ОС читает сохранённое намерение и выполняет ровно один start. Повтор нового процесса не запускает цель снова; последующая ручная остановка сохраняется. Результат `PASS`, временный контейнер удалён после проверки точных ID, образа, имени и меток. DCS в этом сценарии явно моделируется; это не учение отказа рабочего primary и не доказательство готовности HA.

Канонический изолированный прогон, без Docker socket и рабочих секретов:

```sh
black --check src prepare-tls.py status_publisher.py kubernetes test
ruff check src prepare-tls.py status_publisher.py kubernetes test
PYTHONPATH=/work/src:/work pytest -q test
mypy src prepare-tls.py status_publisher.py kubernetes test/fencing-lifecycle.py test/cluster-lifecycle.py test/fencing-return-worker.py
```

## Первый этап установки

Перед адресным обновлением сохранена закрытая копия собственного аудита и намерений в `runtime/fencing-before-update-20261020.F2vjVw4N`. Основной том `aelev-infrastructure-postgresql-fencing-data` не заменяется. Текущая native-политика исполнителя — `no`; общий ограничитель уже имел `attempts=3`, `blocked=true`, `code=TARGET_REPLACED`. Его состояние, бюджет и регистрацию не сбрасываем.

Первая адресная команда отказала до замены контейнера: был указан внутренний config digest вместо адресуемого Docker image ID. Прежний fencer остался работающим с тем же ID. Для продолжения используется только фактический `.Id` из `docker image inspect`, а состав исходников сверяется по SHA-256. Этот отказ не выдаётся за успешную установку.

Финальный образ установлен адресно: `aelev/postgresql:fencing-return-worker-final-20261020`, фактический Docker ID `sha256:33f64eec49e167e1f934cb0d175b090a48b0f4e45795c4e929dda8334b1997d2`. Новый контейнер fencer — `04566beebb4e4521a0d9ccd9b0f9ed5544f619748f8da0b79de82f7e21fd2661`, запущен в 14:49:19 UTC; заключительная проба `healthy`, рестартов 0. Прежний том и `restart=no` сохранены. SHA-256 всех трёх установленных модулей совпали с исходниками. Цикл сам сохранил для обеих реплик `last_return_code=NO_LEADER_LEASE`, не изменив `STOP_CONFIRMED` и нулевые попытки. Общий ограничитель после обновления сохранил `attempts=3`, `blocked=true`, `code=TARGET_REPLACED`; автоматический допуск новой инкарнации не выполнялся.

Повтор настоящего Docker stop/start с окончательной проверкой единственности цели также завершился `PASS`; временные контейнеры не остались. Проверки восьми затронутых Markdown-файлов, относительных ссылок, ограждений блоков кода, заголовка Mermaid, конфликтов, пробелов и `git diff --check` прошли. Рабочий `.env` игнорируется Git. Коммит и push не выполнялись.

После первого этапа SQL-контейнеры сохранили исходные ID: `postgresql-1` и `postgresql-2` оставались остановлены, `postgresql-3` работал как реплика. Возврат двух узлов ожидал отдельного согласования случая без native-аренды. Ручного продвижения, очистки DCS/PGDATA, `reinitialize`, смены удостоверений, перезапуска SQL/etcd, сброса лимитов и команд рабочим очередям на этом этапе не выполнялось.

## Согласованный возврат при отсутствии аренды

После явного разрешения оператора добавлено положительное подтверждение отсутствия аренды: два разных участника одного etcd-кластера должны ответить на линейное чтение точного ключа с валидными native-заголовками и согласованным состоянием. Ошибка связи, неполный ответ, совпадающий member ID, иной cluster ID, регрессия ревизии и противоречивый count не считаются пустой арендой. После повторной сверки точной остановленной инкарнации выполняется ещё одна парная проверка; появление, исчезновение или смена аренды откладывают start без расходования попытки. `return_admission=LEASE_ABSENCE_CONFIRMED` записывается отдельно от прежнего claim; права квитанции продвижения не переносятся.

Полный набор расширен до 155 прошедших тестов; Black, Ruff и строгий MyPy для 15 файлов проходят. Отдельный реальный Docker stop/start с `--absence` завершён `PASS`, включая новый процесс исполнителя, единственный start, повтор и сохранение последующей ручной остановки. Его DCS явно моделируется. Дополнительно новая функция read-only исполнена на настоящих mTLS-ответах двух etcd и вернула `LEASE_ABSENCE_CONFIRMED`. У оставшегося SQL-узла до возврата подтверждены неизменная persisted safety-конфигурация, роль replica, timeline 30 и system identifier `7695307915745648673`; запреты автоматического удаления данных при rewind/diverged timelines сохранены.

Перед вторым обновлением отдельная закрытая копия аудита/намерений сохранена в `runtime/fencing-before-no-lease-return-20261020.aDAx00fq`. Собственный образ `aelev/postgresql:fencing-no-lease-return-20261020`, фактический Docker ID `sha256:e70e0da04e6dd4cf1c815c1fe6c531690ef7b201b351de5104ba8d6d4fe096f7`, установлен только в fencer. Его новый ID — `602ff8503bae61681de022f6f430b8a524ab1a01c2b8a5748822fd9e099ae247`, запуск в 16:51:43 UTC. Все три установленных модуля совпадают по SHA-256 с исходниками. Native restart остаётся `no`; общий ограничитель сохраняет три израсходованные попытки и блокировку `TARGET_REPLACED`, без перерегистрации или reset.

В 16:51:53 UTC фоновый цикл вернул прежний контейнер `postgresql-1`, в 16:52:03 UTC — прежний `postgresql-2`. Для обоих исходных намерений аудит подтверждает `LEASE_ABSENCE_CONFIRMED`, одну команду start и завершение; старый claim не переписан. Далее сам Patroni выбрал `postgresql-1` и выполнил обязательное ограждение новых процессов обоих peers. В 16:52:51 UTC штатный `pre_promote` завершился с 0; продвижение создало timeline 31. Это не ручной promote: последующие stop/start peers — часть native hook под действующей арендой. Новый бюджет соответствует отдельной доказанно завершённой инкарнации, а не сбросу попыток прежнего неизвестного start.

`postgresql-3` начал streaming на timeline 31; `postgresql-2` завершил штатный `pg_rewind` и достиг согласованного восстановления в 16:53:31 UTC. `reinitialize`, удаление PGDATA/томов, очистка DCS, ручные команды start/promote SQL-узлам и изменение защитных таймеров не выполнялись. Три SQL-контейнера сохранили исходные ID; все три etcd сохранили времена запуска 12 октября. Заключительно SQL/etcd/fencer healthy, Docker RestartCount 0. Единственный primary — `postgresql-1`; system identifier прежний. SQL подтверждает `ANY 1 ("postgresql-2","postgresql-3")`, `synchronous_commit=on`, `fsync=on`, `full_page_writes=on`; обе реплики `streaming/quorum` и отставание 0 в контрольных срезах.

В коротком контрольном окне выполнены шесть новых защищённых SQL-подключений с read-only транзакциями и локальным statement timeout 1,5 с, проверкой неизменной native-аренды и потоков репликации. Успехов 6, ошибок 0; медиана полного измерения 0,332 с, максимум 1,689 с. Измерение включает DCS, соединение и несколько SQL-команд, не только один statement. Сначала диагностическая команда ошибочно импортировала новый модуль из сохранённого старого SQL-образа; она прекратилась до запросов, затем использованы его штатные модули без обновления SQL. Эта ошибка команды не считается отказом кластера.

Через собственный конфигурационный parser и read-only БД Advance подтверждены прежние команды: `worker=PAUSED`, `durable-delivery=PAUSED`, `consumer=RUNNING`, `outbox=RUNNING`. API, worker, consumer, outbox и trainer восстановили healthy без адресных рестартов. Команды очереди, решения и конфигурация Advance не менялись; его перенос на новый установщик ещё не выполнялся. Проверка не заявляет неизменность всей входящей очереди: разрешённый приём продолжает работать.

Восстановление не доказывает устранение первопричины исходной задержки DCS, суточную устойчивость, независимые области отказа одной Docker VM или WAN-допуск. Намеренная потеря нового ведущего на рабочем стенде ради повторного опыта не выполнялась. Теперь конкретный случай сохранённого stop без следующего RPC и без аренды покрыт реализацией, регрессиями и фактическим восстановлением, а не только запуском контейнера.

Нормативные правила: [SPEC](../SPEC.md), [FENCING](../FENCING.md). Предыдущее восстановление относится к другому прерыванию: [результат 19 октября](ha-lease-recovery-result-20261019.md).
