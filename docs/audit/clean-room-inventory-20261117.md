# Docker baseline полного gate — 17 ноября 2026

Кандидат `8ec6c3b` завершил native build за 766,8 секунды и прошёл preflight/BOM с `source_dirty=false`. Полный gate затем остановился **до запуска runtime stages** с `DOCKER_CONTAINER_INSPECT_FAILED`. Исходный failing container ID не был сохранён; ему не приписывается причина задним числом. Отдельное воспроизведение на том же Engine подтвердило этот отказ на собственном контейнере: `AutoRemove=true` проверен до естественного выхода, реальный list увидел ID, последующий inspect вернул `no such object`. [JSON receipt](clean-room-inventory-20261117.json) закрепляет source/evidence hashes.

По [Docker `--rm`](https://docs.docker.com/reference/cli/docker/container/run/#clean-up---rm) Engine удаляет контейнер после выхода. Поэтому baseline постоянных контейнеров определяется здесь как `HostConfig.AutoRemove=false`. Это явная политика оснастки; она не означает, что Docker гарантирует атомарный snapshot. [Batch inspect](https://docs.docker.com/reference/cli/docker/container/inspect/) возвращает только ID/status/AutoRemove, без Config.Env, argv, logs или credentials. Исчезновение между list и inspect допускает три ограниченных read-only refresh с 30-секундным timeout inspect; неуспех всех попыток, malformed/неполный ответ или неподдерживаемые значения закрывают gate.

Постоянный baseline сохраняет и работающие, и остановленные контейнеры. Его потеря либо изменение status по-прежнему создают несовпадение до/после owner effects. Networks, volumes и images учитываются в прежнем полном составе. Cleanup своих объектов каждого lifecycle stage остаётся обязательным; filter AutoRemove в глобальном container baseline не заменяет эти guards и не выдаёт разрешение удалять чужие ресурсы.

Новая проверка на реальном Engine принудила тот же естественный выход между list/inspect, наблюдала failed read и получила полный постоянный baseline после refresh. Отдельный собственный persistent container остался видимым после остановки, а его status change дал различие snapshot. После удаления только своих двух fixtures все 207 исходных постоянных контейнеров и остальные baseline resources совпали. Историческое неудачное воспроизведение сохранено отдельно.

Прошли пять новых regression methods, 22 адресных и все 212 root tools tests, Black/Ruff и strict mypy изменённого gate. Прогноз corrective scope до правки — 25–35 минут. Изменены только test runner, его regressions, runbook и changelog; сервисные Dockerfiles, locks, runtime source, endpoints и Process Control не меняются. Provider releases и доказанный Translator network queue pair заново не выпускаются и не переоцениваются.

Source archive `8ec6c3b` остаётся отдельным не допущенным кандидатом с сохранённым FAIL. Следующий full gate должен использовать новый чистый source commit и новый BOM; его PASS этим компонентным результатом не объявляется. Уже подготовленные входы нового тестового namespace сохраняются, поскольку bootstrap/runtime files не менялись и runtime stage ещё не начинался. Рабочая установка и её ключи не переключаются. Работа остаётся локальной, без push, cloud jobs, публикации или RESUME.
