# ADR-0177: Точная цель исследования и кандидат логического источника

## Контекст

Один HTTP origin может обслуживать множество независимых пространств. Для `t.me` корень обозначает платформу, а `t.me/world_science_news` и `t.me/students_drunk_parties` являются разными целями без общего содержательного допуска. Одновременно один логический источник может иметь несколько технических адресов: ленту, архив, API и страницу описания. Поэтому ни origin, ни каждый отдельный URL не являются достаточной канонической идентичностью источника.

## Решение

Discovery Scope хранит две разные идентичности. `origin_id` и `origin_url` задают техническую границу безопасности одного origin. `target_id` и `target_url` задают точную пользовательскую цель исследования и могут содержать путь. Приоритет пользовательского списка действует только для идентичного `target_id`; он не переносится на соседние пути общего origin.

Для корневой цели `target_url` равен `origin_url`. Для точной цели путь сохраняется без расширения. Query и fragment не входят в идентичность и запрещены в пользовательской цели. Отсутствие схемы означает HTTPS. Credentials, IP literals и смена origin запрещены.

Deep Screening исследует только точную цель. Для корневой цели допустим весь origin в пределах установленного бюджета. Для цели с путём допустимы сам путь и его потомки по границе сегмента; похожий соседний путь не принадлежит цели. Найденное независимое пространство не добавляется в текущий пакет и не наследует пригодность. Его возможное поступление в Discovery оформляется отдельным будущим admission через канонический маршрут, а не скрытым расширением текущей цели.

Результат Deep Screening V4 содержит `candidates`. Каждый кандидат является проверяемой гипотезой о логическом источнике и объединяет `access_points` с доказательствами. Это не канонический `source_id`, не разрешение на сбор и не выбранный шаблон. Connector Builder самостоятельно проверяет границы кандидата, может разделить или объединить гипотезы, выбирает параметризованный шаблон либо генератор и только затем создаёт собственную идентичность источника.

Корневая цель многопользовательской платформы не означает требование перечислить все пространства. Если в ограниченном бюджете нельзя выделить содержательно ограниченный кандидат, Deep Screening возвращает `REVIEW` с причиной слишком широкой цели. В решении нет специальных правил для `t.me` или иной платформы.

## Контракты и совместимость

`DiscoveryScopeModeChangedV2`, `UserResearchTargetAdmittedV2` и `UserResearchTargetRevokedV2` публикуются по новым major topics с ключом `target_id`. `SensorSurfacePackagePublishedV4` и `SensorSurfacePackageRevokedV4` также разделяются по `target_id`. V1–V3 остаются неизменяемой историей и могут читаться переходными потребителями; новые публикации используют V2/V4. Смешивать новый path target со старым доменным admission запрещено.

## Последствия

- два пространства одного origin не наследуют решение друг друга;
- одна логическая гипотеза может содержать несколько технических точек доступа;
- шаблон Connector Builder можно параметризовать для множества однотипных пространств без создания отдельной реализации на каждый адрес;
- Deep Screening не обязан перечислять арендаторов платформы и не превращает найденные ссылки в скрытый пользовательский список;
- миграция требует новых Kafka major versions и owner-local схем Scope и Deep.

## Критерии проверки

- `t.me/world_science_news` и `t.me/students_drunk_parties` имеют общий `origin_id`, разные `target_id` и независимые решения;
- пользовательская цель с путём допускает только сам путь и его потомков по границе сегмента;
- V4 объединяет доказанные URL в `candidates[].access_points[]`, а не объявляет каждый URL отдельным источником;
- `source_id`, применимость и окончательный выбор шаблона остаются у Connector Builder;
- старые события и owner-local история не переписываются.

## Миграция и откат

Сначала разворачиваются потребитель Deep и новые owner-local миграции, затем создаются V2 topics Scope и V4 topics Deep, после чего Scope повторно публикует действующую редакцию в новом контракте. Откат приложения прекращает новые публикации, но не удаляет таблицы, outbox, Kafka history или V1–V4 события. Возврат к наследованию пригодности по origin требует нового ADR.
