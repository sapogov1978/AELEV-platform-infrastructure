# ADR-0119: Единая операторская учётная запись и SSO между интерфейсами

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261013-0119-unified-platform-operator-sso.md`; SHA-256: `44b0561b08641e632f3a593b188a7ce281aa2427fa9c54d55940ca0e6a4be2e6`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному архитектурному требованию пользователя
- **Дата:** 2026-10-13
- **Основание:** A10, A12, ADR-0017, ADR-0101, ADR-0108, ADR-0111
- **Дополняет:** ADR-0101 в независимой авторизации владельцев и ADR-0111 в операторском входе; запрет передачи токена оболочки и отдельные права сервисов сохраняются

## Контекст

Самостоятельные UI и Swagger используют разные OIDC-клиенты и права, но оператор не должен заводить отдельные человеческие учётные записи и пароли для каждого backend. При переходе из Platform UI повторная форма входа также не должна появляться, если у оператора уже есть действующая сессия общего realm.

## Критерии выбора

- одно имя и один централизованно управляемый пароль человека для операторских интерфейсов;
- отдельные клиенты, audience и минимальные роли каждого владельца;
- отсутствие пароля и чужого access token в приложении, URL, журнале или env сервиса;
- бесшовный вход в Swagger по общей SSO-сессии без ослабления PKCE;
- машинные mTLS/SPIFFE endpoints не превращаются в интерфейсы с паролем.

## Рассмотренные альтернативы

1. Отдельный пользователь и пароль на каждый backend. Отклонено: создаёт несогласованные identities и повторные входы.
2. Передавать access token Platform UI во внедрённый UI или открытую вкладку. Отклонено: нарушает границу origin, audience и владение авторизацией.
3. Использовать один общий OIDC-клиент всех сервисов. Отклонено: объединяет audience, redirect URI и область последствий.
4. Один пользователь `platform-operator` в общем realm, но отдельные клиенты и роли владельцев. Принято.

## Решение

Единственная обычная человеческая учётная запись операторского контура называется `platform-operator`. Её пароль и многофакторная аутентификация принадлежат Keycloak и внешнему хранилищу секретов; сервисы не создают второй пароль, не сохраняют его и не получают его значение. Platform UI может создать начальную учётную запись из отдельного secret-файла только при первом развёртывании, а последующие owner-controlled задачи находят существующего включённого пользователя и назначают только собственные роли.

Каждый UI и Swagger сохраняет собственный публичный или confidential OIDC-клиент, точные redirect URI, audience и права. Переход из Platform UI не передаёт token оболочки. Целевая страница самостоятельно запускает Authorization Code с PKCE S256; действующая сессия общего realm Keycloak завершает вход без повторного ввода имени и пароля, после чего целевой backend получает token своего audience.

Swagger, опубликованный владельцем в Platform UI, автоматически начинает собственный OIDC-flow. Access token остаётся только в памяти страницы, не попадает в URL, `localStorage` или `sessionStorage` и добавляется к запросам Swagger. Одноразовый authorization code возвращается во фрагменте URL и удаляется до показа Swagger, поэтому HTTP-сервер и его access log его не получают. Временные PKCE `state` и `code_verifier` могут пережить redirect только в короткоживущем `SameSite=Lax` cookie, удаляемом до показа Swagger. Обновление страницы запускает новую авторизацию через существующую SSO-сессию.

Правило относится к интерфейсам, предназначенным человеку. Runtime identities, publisher identities, сервисные accounts, Kafka/PostgreSQL credentials, технические mTLS endpoints и аварийные роли остаются отдельными и не используют пароль `platform-operator`.

## Последствия

Оператор вводит один централизованный пароль и переходит между оболочкой, самостоятельными UI и Swagger без повторной формы входа. Компрометация одного client token по-прежнему ограничена его audience и ролями. Цена решения — обязательная точная настройка SSO redirect/origin каждого владельца и невозможность использовать произвольного локального пользователя как штатного оператора.

## Критерии проверки

- конфигурация штатного операторского пользователя, отличного от `platform-operator`, закрыто отклоняется;
- после входа в Platform UI открытие опубликованного Swagger получает собственный token без повторного ввода пароля;
- token Swagger отсутствует в URL и browser storage, а запрос с ним проходит собственную проверку audience и роли;
- пользователь без роли владельца получает 403 даже при действующей общей SSO-сессии;
- machine endpoint не принимает человеческий пароль вместо своей identity.

## Миграция и откат

Сначала существующему `platform-operator` назначаются точные роли владельцев и сверяются OIDC-клиенты, затем owner UI и Swagger включают автоматический PKCE-flow. Прежние отдельные человеческие учётные записи блокируются только после проверки отсутствия требуемых назначений; их пароли не копируются. Откат интерфейса может вернуть ручную кнопку Authorize, но не передачу token оболочки, общий клиент или отдельный сервисный пароль.
