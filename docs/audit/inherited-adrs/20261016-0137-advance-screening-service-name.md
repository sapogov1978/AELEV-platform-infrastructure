# ADR-0137: Имя второй стадии Discovery — advance-screening

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261016-0137-advance-screening-service-name.md`; SHA-256: `d6d31c927d254d8b7caabe4bac1c07d3c254fa43b1fd478857370a59735dbd94`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят
- **Дата:** 2026-10-16
- **Основание:** A5, A10, A12, ADR-0001, ADR-0005, ADR-0078, ADR-0080, ADR-0082
- **Частично заменяет (Supersedes):** ADR-0078, ADR-0079 и ADR-0080 только в имени второй стадии `candidate-screening`; обязанности, порядок каскада, владельцы данных и Kafka-контракты сохраняются

## Контекст

Вторая самостоятельная стадия Discovery уже представлена оператору как «Продвинутый отсев» / `Advanced screening`, но её техническое имя `candidate-screening` описывает входной объект, а не место и обязанность стадии. Оператор запросил единое каноническое имя `advance-screening` перед следующей обработкой. Имя присутствует в каталоге сервиса, Python-пакете, образах, Compose, OIDC, UI и технической identity устойчивой доставки, поэтому несогласованная строковая замена создала бы нового владельца, пустую БД или невоспроизводимую историю.

## Критерии выбора

- одно каноническое имя во всей новой поставке и операторской документации;
- сохранение того же владельца, PostgreSQL, очереди, результатов, модели и места в каскаде;
- точное воспроизведение ранее записанных событий и digest-цепочек без переписывания байтов;
- отсутствие нового topic, версии предметного сообщения или второго активного писателя;
- явный порядок OIDC, Compose и consumer-переключения.

## Рассмотренные альтернативы

1. Изменить только пользовательский заголовок. Отклонено: техническая identity и структура поставки сохранили бы неоднозначное прежнее имя.
2. Удалить прежнее имя из схемы и переписать исторические журналы. Отклонено: это нарушило бы обратную совместимость, идентичность потоков, SHA-256-цепочки и воспроизводимость подтверждений.
3. Переименовать текущую поставку, а прежнюю identity принимать только для неизменяемой истории и согласованного отката. Принято.

## Решение

Каноническое имя сервиса — `advance-screening`, Python-пакета — `advance_screening`, проекта и образов — `aelev-advance-screening` и `aelev/advance-screening`, OIDC audience — `advance-screening`, public client и bootstrap identity UI — `advance-screening-ui`. Каталог поставки, Dockerfile, Compose, документация, активные схемы развёртывания и новые operator/read модели используют это имя. Публичное название остаётся «Продвинутый отсев» / `Advanced screening`.

Это переименование того же владельца, а не новый bounded context, стадия или каноническое хранилище. `SCREENING`, TF-IDF, входные и выходные topics, ключи разделов, payload предметных событий, `policy_ref`, model/bundle digest, очередь, история и маршрутизация в `source-research` или Builder не меняются.

Новые записи устойчивой доставки используют sender/recipient `advance-screening`. Добавочное допустимое значение вводится совместимо в `DiscoveryDeliveryRecorded`; прежнее `candidate-screening` не удаляется из текущей старшей схемы и принимается только для точного воспроизведения уже записанного потока. Старые `stream_id`, `delivery_id`, исходные байты, source, время и digest-цепочки не пересчитываются: при повторной публикации и подтверждении применяется исходная wire identity. Новые предметные сообщения не создаются с прежним именем.

Миграция `0007` меняет только `stage_identity.owner` после всех прежних миграций и не создаёт новую БД, таблицу или версию очереди. Прежняя переменная образа UI временно принимается как Compose alias только при отсутствии `AELEV_ADVANCE_SCREENING_UI_IMAGE`; новые примеры и настройки используют новое имя. Исторические ADR, отчёты, changelog-записи, имена прежних миграций и неизменяемые артефакты сохраняют исходный текст.

## Последствия

Положительные:

- имя поставки совпадает с ролью второй стадии и её устойчивым пользовательским названием;
- новый код, конфигурация, OIDC и наблюдаемость используют одну identity;
- история остаётся проверяемой и пригодной для replay без изменения контракта предметных сообщений.

Отрицательные:

- переход требует согласованного обновления OIDC, Compose, миграции БД, производителей и потребителей;
- схема доставки и общий UI-kit временно знают прежний alias для исторической совместимости;
- смена Compose project name без сохранения storage namespace может создать пустой том, поэтому автоматическое переключение без проверки запрещено.

## Критерии проверки

- активный каталог и Python import имеют имена `services/advance-screening` и `advance_screening`;
- новый Compose использует `advance-screening` для образов, audience, UI client и owner-unique DNS alias;
- миграция `0007` сохраняет существующие таблицы и данные и меняет только владельческую identity;
- новые команды стадии адресуются `advance-screening`, а его результаты маршрутизируются по прежним topics;
- старый delivery-поток повторяется с исходным sender/recipient `candidate-screening`, проходит прежнюю digest-проверку и получает совместимый ACK;
- одновременно не работают писатели двух имён одной очереди;
- текущая документация, ссылки и диаграммы не называют активный сервис прежним именем вне явно помеченной миграционной совместимости.

## Миграция и откат

Сначала публикуется совместимая схема доставки с обоими значениями и обновляются получатели, способные принять прежнюю историю и новое имя. Затем останавливаются все процессы `candidate-screening` без удаления PostgreSQL, томов, Kafka offsets, архивов или model replicas; для существующей установки сохраняется прежний Compose project/storage namespace. После резервной копии применяется миграция `0007`, подготавливаются точные OIDC audience/client и ACL нового имени, запускается только `advance-screening`, и лишь затем Base Screening переключает новые передачи на нового получателя. Отставание и ACK старых и новых потоков сверяются раздельно.

Откат сначала останавливает новый комплект и запрещает новые передачи, затем выполняет совместимый downgrade `0007`, возвращает прежние OIDC/Compose identity и запускает только прежний выпуск против тех же данных. События и архивы нового имени не удаляются; перед повторным включением прежнего издателя должна быть доказана его способность закрыто сохранить незнакомые новые записи либо они остаются остановленными до повторного перехода. Одновременные писатели запрещены в обоих направлениях.
