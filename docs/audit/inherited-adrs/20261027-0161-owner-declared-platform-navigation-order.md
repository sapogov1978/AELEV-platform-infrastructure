# ADR-0161: Порядок функциональной навигации объявляет владелец

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261027-0161-owner-declared-platform-navigation-order.md`; SHA-256: `b839e0a2fda24c9edfd7a810f50f52069f226e0f1c33c0d92928bd69887b9804`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному требованию пользователя от 2026-10-27
- **Дата:** 2026-10-27
- **Основание:** A5, A10, A12, ADR-0101, ADR-0152, ADR-0160
- **Частично заменяет (Supersedes):** ADR-0101 только в ранее неоговорённом порядке кнопок функциональных сервисов; отсутствие каталога продуктов, авторизация, изоляция UI и владение представлением сохраняются

## Контекст

Platform UI получает описания сервисов от независимых владельцев и до этого показывал функциональные разделы в техническом порядке строк SQLite по UUID модуля. Такой порядок не выражает назначение стадий и меняется из-за случайного идентификатора. Добавление Deep Screening выявило, что владелец должен иметь возможность заявить устойчивую позицию в общей навигации, не раскрывая соседей и не создавая в оболочке каталог продуктов.

## Решение

Описание модуля версии 1 получает необязательное целочисленное поле `navigation_order` в диапазоне `0..2147483647`. В левом меню Platform UI функциональные модули сортируются по возрастанию этого значения; отсутствие поля или `null` означает `0`, а равные значения стабилизируются по `module_id`. Поле влияет только на представление и не меняет полномочия, состояние, выбор раздела или предметный транспорт.

Deep Screening публикует `navigation_order=2147483647` и тем самым располагает свою кнопку после владельцев с обычным значением. Он не перечисляет и не запрашивает соседние сервисы, а Platform UI не содержит его имя или отдельное правило.

Поле отсутствует в канонических байтах старого описания, пока владелец его не задаёт. Поэтому старые хеши и идемпотентные повторы сохраняются; добавление, изменение или снятие порядка требует новой `revision` того же владельца. Сначала обновляются API и оболочка, затем владелец публикует новую декларацию.

## Последствия

- порядок навигации перестаёт зависеть от случайного UUID;
- каждый владелец управляет только своей декларацией и не получает знания о других участниках;
- одинаковые значения остаются детерминированными, а старые издатели совместимы без перепубликации;
- `navigation_order` не является приоритетом обработки или разрешением.

## Критерии проверки

- API принимает границы диапазона, отклоняет неверный тип и сохраняет прежние канонические байты при отсутствии поля;
- оболочка ставит модуль с большим значением после модуля с меньшим независимо от входного порядка и UUID;
- Deep Screening публикует максимальное значение в новой ревизии;
- в исходниках Platform UI нет имени Deep Screening или перечня стадий Discovery.

## Миграция и откат

API и оболочка развёртываются до новой декларации Deep Screening. При откате владелец публикует следующую ревизию без `navigation_order`; старую ревизию и том приёмника не переписывают. Kafka-контракты, identity и предметные данные не меняются.
