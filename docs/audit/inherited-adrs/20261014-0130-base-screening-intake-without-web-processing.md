# ADR-0130: Приём очереди Base Screening отделён от чтения Web

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261014-0130-base-screening-intake-without-web-processing.md`; SHA-256: `4c7dd62dee2029de0e7deae6c8090d7dfe61edbf04a266b47ee01cfca1df0daf`; основание включения: цепочка замены. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0132](20261015-0132-base-screening-inline-queue-processing-control.md) в требовании отсутствия `triage-worker` и [ADR-0135](20261015-0135-base-screening-publication-independent-processing.md) в требовании отсутствия `outbox-publisher`; разделение приёма Kafka и Web-обработки остаётся принятым
- **Дата:** 2026-10-14
- **Основание:** A5, A10, A12, ADR-0125, ADR-0128, ADR-0129
- **Уточняет:** [ADR-0128](20261014-0128-base-screening-service-envelope.md) режимом приёма без обработки; обычный пассивный Compose и профиль полной обработки не меняются

## Контекст

Пассивная оболочка из ADR-0128 намеренно не читает Kafka, поэтому новая пустая локальная БД не знает о сохранённых заданиях Zone Ingestion. Нулевой локальный frontier в таком режиме нельзя показывать как отсутствие входной очереди. Одновременно оператору нужен режим публикации UI, в котором задания уже материализованы и измеримы, но Base Screening ещё не читает публичные сайты и не передаёт результаты дальше.

## Решение

Вводится явный профиль `intake`. Он запускает только `delta-consumer` и `policy-projection-consumer` поверх пассивной оболочки. Первый сохраняет опубликованные Zone Ingestion изменения в принадлежащем Base Screening PostgreSQL и формирует локальный frontier, второй поддерживает read-only проекцию политики и локализаций PMS. Профиль не запускает `triage-worker`, `outbox-publisher`, восстановительные рабочие циклы или какой-либо Web-доступ.

Обычный Compose без профиля по-прежнему не читает доменные сообщения. Профиль `active` по-прежнему включает полный набор ролей. `intake` является отдельным явным эксплуатационным действием: он изменяет принадлежащие Base Screening consumer offsets и локальную проекцию, но не арендует и не завершает задания Web-проверки.

Операторский обзор показывает размер собственной очереди обработки как сумму незавершённых состояний `DISCOVERED`, `RUNNING`, `RETRY_SCHEDULED` и `RECHECK`. Терминальные `SKIP` и `EXPANDED` не выдаются за текущую очередь. Рядом показывается факт недавнего heartbeat роли `triage`, а не желаемое состояние process-control. Поэтому остановленная обработка не обнуляет задания.

Второй ряд обзора показывает число завершений за последний час, среднюю скорость последних 24 часов и расчётное время обработки текущей очереди без новых поступлений. При отсутствии завершений оценка срока неизвестна, а не равна нулю. Те же исходные показатели экспортируются owner-scoped Prometheus-метриками.

## Последствия и проверка

Положительные последствия: очередь видна до разрешения Web-доступа; оператор различает приём заданий и их обработку; UI не вычисляет backlog по состоянию контейнера. Цена решения — профиль `intake` уже не является полностью пассивным относительно Kafka и требует точных read ACL и сохранения offsets.

Проверка подтверждает состав трёх режимов Compose, отсутствие `triage-worker` и `outbox-publisher` в `intake`, точное наполнение frontier из сохранённого topic, неизменность числа заданий при остановленном worker, отображение трёх показателей скорости и отсутствие Web-запросов.

## Миграция и откат

После проверки Kafka ACL оператор запускает `docker compose --env-file .env --profile intake --profile ui up -d`. Откат останавливает только обе intake-роли; локальный frontier, inbox и consumer offsets не удаляются и не перематываются. Возврат к полностью пассивной оболочке не превращает сохранённую очередь в ноль.
