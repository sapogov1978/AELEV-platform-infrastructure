# ADR-0103: Инфраструктурная оркестрация без знания потребителей

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261010-0103-consumer-agnostic-infrastructure-orchestration.md`; SHA-256: `dfba747bdc863e04703740dbb7524ab79566ebde8a2686c72f73d524f2d05465`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят; частично заменён [ADR-0104](20261010-0104-owner-contained-compose-recipes.md) в части корневых поправок имён и локальных зависимостей и [ADR-0106](20261010-0106-selectable-postgresql-fencing.md) в части обязательного watchdog; остальные требования действуют; частично заменён [INFRA-ADR-0002](20261106-0002-infrastructure-repository-layout.md) только в размещении исходного дерева и имени репозитория
- **Дата:** 2026-10-10
- **Основание:** A5, A10, A12, ADR-0017, ADR-0082, ADR-0089, ADR-0091, ADR-0097, ADR-0099, ADR-0100, ADR-0101
- **Частично заменяет (Supersedes):** ADR-0088 в части обязательного `extends` и корневого повторного объявления ресурсов включаемых поставок; ADR-0090 в части ресурсов конкретных потребителей в корневом env/Compose; ADR-0094 в части размещения прикладных OIDC-файлов и скрипта в корне инфраструктуры. Размещение оркестрационных файлов непосредственно в корне, изоляция и остальные требования сохраняются.

## Контекст

После разделения провайдеров корень сохранял прикладные базы, bucket, OIDC-клиенты, смешанный realm, устаревшие идентификаторы и функциональные сети. Большой агрегатор повторял mounts и настройки владельцев, а последовательные сервисные проверки не доказывали общий запуск. Перемещение знаний о потребителях на уровень выше провайдера не устраняет нарушение: вся инфраструктура должна предоставлять технические возможности без каталога приложений.

## Решение

Корень `services/infrastructure` является только точкой совместного запуска и остановки инфраструктурных поставок на одном Docker daemon. Состав выражается штатным Compose `include`; каждый включаемый файл загружает env своего владельца и разрешает его относительные пути. Минимальные поправки в корне различают совпадающие имена административных задач и задают зависимости совместного размещения, не копируя runtime. Kafka включается непосредственно из собственной поставки, независимо от переводчика. Переводчик отдельно включает свою каноническую модель без вложенного брокера; локальная поправка делает его собственную БД обязательной и задаёт ожидание healthy Kafka. Самостоятельная односерверная поставка переводчика по ADR-0097 сохраняется; её удаление из общего состава не удаляет Kafka.

Корневой env содержит только обязательное имя общей Compose-группы `AELEV_INFRASTRUCTURE_COMPOSE_PROJECT`. Параметры образов, endpoint, доверия, лимитов, сетей и данных остаются у владельцев. Ни провайдер, ни корень не содержат конкретных прикладных ресурсов, OIDC-клиентов, ролей, пользовательских данных, topics, целей, правил или панелей. Их подготовку исполняет поставка владельца по техническому интерфейсу с отдельной административной identity.

Подготовка собственных ресурсов инфраструктурных продуктов остаётся допустимой: минимальный realm Keycloak, OIDC-клиент оболочки и ограниченные identities издателей, права собственных томов наблюдения, MinIO site replication, миграции и topics переводчика принадлежат соответствующим владельцам. Корень вызывает их задачи, не определяет ресурсы вместо них. Универсальные адаптеры без входа потребителя не являются обязательным init самой инфраструктуры. Весь профиль `provision` не запускается как постоянная группа.

Полный запуск явно включает профили нативного наблюдения и издателей состояния. Нативная инфраструктура сохраняет возможность работать без издателей; отказ оболочки/IdP не становится её общей зависимостью готовности. Остановка и снятие контейнеров сохраняют данные, identities и последовательности. Самостоятельные и общий Compose никогда не становятся одновременными писателями тех же томов.

Разнесение по узлам использует те же самостоятельные поставки, маршрутизируемые endpoints, TLS/mTLS и отдельные identities. Compose одного Docker host не управляет чужими daemon и не создаёт Docker bridge через WAN. Рабочие watchdog, кворум, репликация, backup и PKI не ослабляются ради агрегатора.

## Последствия

Корень перестаёт меняться при добавлении прикладного сервиса. Настройки и относительные пути имеют один источник; небольшие поправки касаются только административных имён и зависимостей совместного размещения. Оператор подготавливает каждой поставке адреса, удостоверения и секреты по её README; копирование пустых env не считается готовностью. Для Compose нужны `include` и `!reset`. Одноузловая проверка композиции не доказывает независимые области отказа, WAN или продукционный допуск.

## Проверка

1. Корневой Compose разрешается из собственных env, включает Kafka ровно один раз непосредственно из поставки брокера и не содержит повторных runtime-определений или функциональных ресурсов. Запуск Kafka отдельно не создаёт ни одной роли переводчика.
2. Все включаемые поставки сохраняют самостоятельный запуск и собственные settings, mounts и данные.
3. Реальные собственные задачи подготовки завершаются с кодом `0`, автоматические миграции и Kafka-барьер не пропускаются.
4. Совместный старт подтверждает здоровье постоянных ролей и настоящий OIDC/API/страницу состояния, stop/start и down/up — восстановление с прежними данными и identities.
5. Python-тесты и читаемые результаты находятся в `test_infrastructure`; существующие ресурсы защищены, созданное удаляется адресно, чужие проекты не меняются.
6. Рабочая PostgreSQL сохраняет обязательный watchdog; локальное исключение допускается только явным тестовым override владельца.

## Миграция и откат

Старый корневой README перемещается в ближайший архив `services/obsolete/infrastructure` с исправленными ссылками. Старые прикладные OIDC-файлы и скрипт удаляются из действующей поставки; их история остаётся в Git. Игнорируемый старый корневой env сохраняется вне действующей инфраструктуры, новый содержит только имя общей группы. Базы, buckets, topics, пользователи и volumes этой миграцией не удаляются. Вывод прежних прикладных credentials или ресурсов из эксплуатации требует отдельного действия их владельца.

Перед общим запуском самостоятельные контейнеры снимаются без удаления томов; общая группа использует прежние явно заданные имена данных. При откате снимаются новые писатели, сохраняются данные/журналы и выбираются прежние совместимые выпуски владельцев. Возврат каталога потребителей в корень инфраструктуры не является допустимым откатом.
