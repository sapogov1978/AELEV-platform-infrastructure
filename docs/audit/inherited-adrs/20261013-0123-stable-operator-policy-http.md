# ADR-0123: Стабильный операторский HTTP API по редакции политики

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261013-0123-stable-operator-policy-http.md`; SHA-256: `ffc68736b8057ee6ea5ee3be53edd27b3915ecabca53e1a740ebc5da370bc165`; основание включения: прямая ссылка из поставки. - **Дата:** 2026-10-13
- **Основание:** A5, A10, A12, ADR-0116, ADR-0120, ADR-0122

## Контекст

Операторский HTTP API использовал `/v3` рядом с отдельным числом версии политики и принимал внутренний UUID `policy_id` для точного чтения и команд жизненного цикла. Это создавало ложное впечатление, что создание следующей версии политики должно изменить все URL API, и заставляло оператора различать технические идентификаторы, которых нет в его предметной задаче. Запрос локализации дополнительно требовал придумать `Idempotency-Key`, хотя единственным операторским вводом является целевой язык.

## Решение

Операторские ресурсы используют стабильные пути без версии HTTP-контракта в URL: `/policies`, `/policies/{version}`, `/policies/{version}/activate`, `/localizations` и `/localizations/{target_language}/retry`. Параметр `{version}` всегда означает положительную числовую редакцию политики, уже возвращённую `GET /policies`; создание редакций 4, 5 и последующих не меняет ни одного маршрута. Внутренний UUID `policy_id` сохраняется для хранения и аудита, но не является входным параметром операторского HTTP API.

Техническая версия самого операторского API возвращается отдельным `GET /status` как `api_version`. Она не является версией политики и не участвует в её создании, чтении, активации или локализации. Обязательное стандартом поле `info.version` в OpenAPI повторяет ту же техническую метаинформацию, но версия не кодируется в ресурсных URL.

`POST /localizations` принимает в теле только `target_language`. PMS сам создаёт идентификатор и digest операторского запроса и устойчиво связывает его с единственной действующей версией. Оператор и UI не создают и не передают `Idempotency-Key`; повторный запрос существующей локализации не создаёт второй набор перевода, а присоединяется к уже существующему каноническому состоянию. Явная команда `retry` по-прежнему создаёт новую сохраняемую попытку.

Прежние HTTP-пути `/v3/*` удаляются одновременно с обновлением собственного UI. Совместимый alias не сохраняется, потому что HTTP API предназначен только оператору, межсервисные клиенты используют Kafka, а два параллельных набора путей закрепили бы уже отвергнутое смешение версий. Kafka-контракты `PolicyPublishedV3`, `PolicyLocalizationRequestedV3`, `PolicyLocalizationProvidedV3` и соответствующие topics остаются без изменений.

## Последствия

Swagger показывает редакцию политики как единственный селектор точной версии, а запрос локализации требует только язык. `policy_id` может присутствовать в техническом ответе и журнале, но оператору не требуется копировать его в URL. Версию HTTP-контракта можно диагностировать через `/status`; она изменяется только вместе с поставкой API, а не при создании политики.

## Критерии проверки

1. OpenAPI не содержит ресурсных путей `/v3/*` и содержит `GET /status` с `api_version`.
2. Точный GET, PUT, DELETE и активация принимают положительный целый `{version}`, а не `policy_id`.
3. Создание новой версии не меняет набор путей OpenAPI.
4. `POST /localizations` принимает тело только с `target_language`, не объявляет заголовок `Idempotency-Key`, а UI его не отправляет.
5. Kafka-контракты и межсервисная граница не меняются.
