# Единый контракт живости и готовности HTTP

Нормативное решение — [00-INFRA-20261106-0004-self-contained-service-delivery](../adr/00-INFRA-20261106-0004-self-contained-service-delivery.md). Контракт относится ко всем принадлежащим AELEV HTTP-приложениям, которые предоставляют стандартные точки живости и готовности, включая API, самостоятельные UI и Platform UI. Он не превращает техническую пробу в межсервисный предметный транспорт.

## Живость

`GET /healthz` проверяет только способность процесса принять HTTP-запрос. Успех имеет HTTP 200, `Content-Type: application/json` и точное тело без дополнительных полей:

```json
{"status":"ok"}
```

Проверка живости не обращается к PostgreSQL, Kafka, внешней сети, моделям или соседним процессам. Отказ процесса выражается отсутствием успешного HTTP-ответа, а не прикладным полем в ответе 200.

## Готовность

`GET /readyz` проверяет минимальные собственные зависимости, без которых данный процесс нельзя включать в обслуживание. Успех имеет HTTP 200, `Content-Type: application/json` и точное тело без дополнительных полей:

```json
{"status":"ready"}
```

Неготовность возвращает 503. Безопасная причина может находиться в стандартном теле ошибки и журналах владельца, но ответ 200 не содержит версии, имени сервиса, идентификатора модели или другой переменной диагностики. Конкретный состав готовности определяет спецификация владельца; эта точка не утверждает продвижение очереди или исправность другого сервиса.

## Адресация

В разделяемой сети потребитель пробы и внутренний обратный прокси используют только уникальное имя вида `<owner>-<role>`. Общие адреса `api`, `ui`, `backend` или `publisher` запрещены, потому что сетевой псевдоним DNS не доказывает владельца процесса. Примеры допустимых адресов: `policy-management-api`, `policy-management-ui`, `zone-ingestion-api`, `zone-ingestion-ui`, `base-screening-api`, `base-screening-ui`.

Издатель состояния сравнивает код и каноническое успешное тело, ограничивает размер ответа и не следует механизму обнаружения. Развёртывание вне Compose предоставляет столь же однозначное маршрутизируемое имя и проверяемую workload identity; правило не требует общей Docker-сети между узлами.
