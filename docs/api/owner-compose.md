# Выполнение одной подготовленной Compose-роли, версия 1

Публичный [node executor](node-execution.md) поддерживает `procedure=owner-compose` по [00-INFRA-0019](../adr/00-INFRA-20261116-0019-pinned-owner-compose-execution.md). `arguments` содержит ровно `ACTION --request ABS_PRIVATE_JSON --request-sha256 SHA256`. ACTION — `plan`, `start`, `task` или `status`. Закрытый JSON закреплён в `request.inputs`; его `executor_root/executor_files` совпадают с `source_root/source_files` outer request, а `inputs` равны остальным outer inputs. Отдельные `owner_root/owner_files` описывают выпуск владельца роли: его аутентификацию и binding к inventory проверяет вызывающий установщик. JSON проверяется по переданному SHA и разбирается из одних bytes; произвольные команды/flags не принимаются.

| Поле private definition | Значение |
|---|---|
| `schema_version` | Целое 1 |
| `executor_root`, `executor_files` | Полный проверенный инфраструктурный release root/regular-file SHA manifest с обоими helpers; совпадает с outer request |
| `owner_root`, `owner_files` | Отдельный проверенный release root/manifest владельца с его каталогом и recipes; helpers не копируются в его репозиторий |
| `catalog`, `role` | Относительный source path каталога и точный `product/role-id` |
| `recipes` | Непустой упорядоченный subset recipes данной роли; пути закреплены source manifest |
| `project_directory`, `project` | Закрытый подготовленный node-local owner workspace вне source и явный Compose project |
| `env_file`, `inputs` | Absolute private env path и absolute regular input path → SHA; private files принадлежат оператору, mode 0600 |
| `image` | Registry `name@sha256:…` или native `sha256:…`; start/task не выполняют build/pull |
| `configuration_sha256` | Hash выбранного resolved service из `plan`; для plan допустим null |

Владелец предварительно доставляет private inputs и готовит workspace под относительные пути своего рецепта. Исполнитель не копирует чужие keys и не создаёт PKI/egress/quality admission. Source paths, configured endpoints, image/command/entrypoint не подменяются. Только процессы выбранного узла используют его Docker daemon. Parent executor исключает наследование API keys, PYTHONPATH и Docker context overrides.

Для роли из частичного overlay owner catalog может содержать явно объявленный companion base file по [recipe-inputs contract](placement.md). Каждый выбранный file по-прежнему обязан входить в role allowlist и immutable manifest; наличие companion не запускает соседние роли. Definition schema сохраняется.

Инфраструктурные инструменты и произвольный owner source могут находиться в разных immutable generations на целевом узле. Для собственной инфраструктурной роли roots могут совпасть. Каталог/recipes всегда выбираются из owner manifest, helper code — из executor manifest; смешанная generation или drift любого из двух источников закрыто отклоняются. Целевой узел получает закреплённые source artifacts через node artifact API, без соседнего checkout и без общего межузлового диска.

`plan` проверяет source/input pins и recipe membership, выполняет `compose --profile '*' config --format json` и возвращает configuration hash без старта и image pull. Полный read-only render нужен для ролей с `provision` и другими profiles: обычный config их исключает, хотя явный `run SERVICE` активирует выбранный service. По [официальным правилам profiles](https://docs.docker.com/compose/how-tos/profiles/) явное выполнение роли и включение всех profiles различаются; здесь wildcard используется только при read-only render и вычислении `config --hash SERVICE`, а effectful команды сохраняют выбранную роль и `--no-deps`. До исправления история двух поколений helper и нативный SQL DAG подтвердили отсутствие такой поддержки; прогноз — 15–20 минут. Resolved model сохраняется в private временном JSON с mode 0600; следующие команды используют только этот snapshot и пустой explicit env. Изменение исходного env после render не меняет запускаемый model. Секретные поля model и raw process output не входят в публичный JSON.

`start` допускается только для runtime/node role. До воздействия проверяются configuration hash, native image ID, выбранные project/service labels и число прежних экземпляров. Running instance с точными bindings сохраняется. Отсутствующая роль запускается с `up --detach --no-deps --no-build --pull never --no-recreate SERVICE`; её точный ID/image/config проверяются после. Stopped/paused/restarting instance, другой image/config или лишняя replica закрыто требуют handoff. Native restart, service namespaces, links и volumes_from отвергаются. `status` читает ту же привязку без старта; health — только наблюдаемый Docker health field, не внешний readiness proof.

`task` допускается только для operation role без существующего контейнера той же project/service. Используется `run --rm --no-deps --pull never -T --interactive=false SERVICE`; дополнительных command/entrypoint/environment arguments нет. Стабильный `-T` сохраняет совместимость с [Compose 2.24.4](https://github.com/docker/compose/blob/v2.24.4/cmd/compose/run.go) и [2.40.3](https://github.com/docker/compose/blob/v2.40.3/cmd/compose/run.go), где long flag называется `--no-TTY`. Предварительный exact image inspect исключает implicit missing-image build/pull. Exit code задачи становится outcome узлового журнала; повтор/unknown обрабатываются прежним node executor, не автоматическим повтором задачи.

Ошибка Docker/Compose сохраняет точный `owner_exit_code` в закрытом child result. Через node executor bounded stdout/stderr команды остаются в `owner-command-failure.json` с mode 0600 внутри текущего operation directory; публичный JSON не содержит raw diagnostics. Внутренний путь задаёт сам node executor и не наследуется Docker-процессом. `pull_policy=build` и несовпадающая фактическая native restart policy закрыто отклоняются.

Timeout `up/run` не является ошибкой входа или доказательством отсутствия эффекта: child возвращает `RESULT_UNKNOWN` с reserved exit 3, а node journal сохраняет тот же статус и не повторяет operation. Обычный известный native task exit остаётся `OWNER_COMMAND_FAILED` с отдельным `owner_exit_code`. Такой выбор следует [Python TimeoutExpired](https://docs.python.org/3.13/library/subprocess.html#subprocess.TimeoutExpired) и [практике side-effect retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/); конкретное правило reconciliation задаёт продукт. Прогноз этой финальной коррекции — 10 минут.

Результаты `OWNER_COMPOSE_PLANNED`, `OWNER_ROLE_RUNNING`, `OWNER_ROLE_STOPPED`, `OWNER_ROLE_ABSENT` и `OWNER_TASK_COMPLETED` сохраняют `owner_readiness_verified=false`, `queue_resume_issued=false`. Общий inventory DAG, native identity admission, live readiness, полный platform E2E и исполняемая подготовка каждого владельца этим интерфейсом не закрываются. Физическая проверка вынесена в [TODO-MVP](../../TODO-MVP.md); остальные software gates сохраняются.

До реализации объявлен прогноз 60–90 минут на criteria/код/проверки. Scope сверяется с placement и node artifact/execution API, прежними immutable source generations и owner recipes. Стек, source каталоги, endpoints и работающие установки сохраняются.
