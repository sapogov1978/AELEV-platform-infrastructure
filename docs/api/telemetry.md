# Техническая телеметрия и подтверждение устойчивой доставки

Нормативное решение: [ADR-0100](../adr/20261009-0100-durable-owner-telemetry-delivery.md). Это техническая возможность инфраструктуры, не доменный контракт и не новый владелец предметный данных или защищённого аудита. Реализация и эксплуатация: [observability](../../observability/README.md).

Встроенный журнал SQLite разрешён [ADR-0115](../adr/20261012-0115-owner-local-embedded-sqlite.md): местный отправитель и центральный приёмник владеют разными постоянными файлами и не читают их друг у друга. Транспортом остаётся защищённый технический интерфейс ниже, не передача файлов или общий том. Центральная принятая история является устойчивым исходным техническим журналом, не пересобираемым кэшем из Loki/Tempo/Prometheus; её резервное восстановление и бессрочное хранение не отменяются выбором движка. Форматы пакетов, квитанций и гарантии доставки сохраняются.

## Стандартные входы

| HTTPS POST | Содержимое | Конечная техническая проекция |
|---|---|---|
| `/v1/logs` | OTLP logs, JSON или Protobuf | Loki |
| `/v1/traces` | OTLP traces, JSON или Protobuf | Tempo |
| `/v1/metrics` | OTLP metrics, JSON или Protobuf | Prometheus, дополнительный технический вход |
| `/api/v1/write` | Prometheus remote_write 1.0, Protobuf/Snappy | Prometheus, основной путь собственного сборщика |

Отправитель не изменяет байты, время события, смысл или метки. Производитель очищает телеметрию от секретов/лишних персональных данных до отправки. `Content-Type`, `Content-Encoding`, `X-Prometheus-Remote-Write-Version` входят в сохраняемые транспортные данные. Размер запроса ограничен, `Content-Length` обязателен; поток без известного ограниченного размера не подтверждается. Доменные команды и произвольные URL не принимаются.

Стандартный клиент получает HTTP 200 и стандартный пустой ответ OTLP только после местной фиксации. При отказе устойчивого приёма возвращается HTTP 503; производитель сохраняет неподтверждённое и повторяет отправку. Издатель с только оперативной очередью не получает обещания сохранности данных до местного подтверждения. Ни Collector с предварительным пакетированием в памяти, ни SDK сами по себе не являются этим журналом.

## Передача между устойчивыми журналами

Для каждого местного пакета назначается UUID, сохраняемый вместе с ним. При повторе используется прежний `X-Aelev-Delivery-Id`; обычный клиент этот заголовок не обязан выставлять. Центральный приём возвращает JSON `{"id":"<UUID>","sha256":"<digest>","durable":true}` только после устойчивой фиксации. Это квитанция транспортной доставки, не бизнес-событие. Отправитель освобождает свою копию только при точном совпадении всех трёх полей. Обычного HTTP 200 от прокси или конечного продукта недостаточно.

Хеш — SHA-256 от UTF-8 JSON `[kind, headers]` с отсортированными ключами и разделителями `,`/`:`, затем байт `00`, затем точные байты тела. `kind` равен `logs`, `traces`, `otlp_metrics` или `metrics`. Имя каждого транспортного заголовка фиксировано как в таблице стандартных входов; отсутствующий заголовок не добавляется. Повтор UUID с тем же хешем идемпотентен, с иным содержимым отклоняется HTTP 409 и остаётся задолженностью отправителя.

Потеря ответа после центральной фиксации приводит к безопасному повтору той же передачи. Обычный SDK может повторить пакет без прежнего UUID — возможны дубли; доставка не менее одного раза не равна однократной обработке.

## Архив и проекции

Центральный журнал сохраняет исходный пакет и отдельно его контрольную точку применения в конечном продукте. Успешная квитанция центрального журнала не означает, что данные уже появились в запросах. HTTP 400/403/429/500, ошибка сети, неполный или недостоверный ответ, частичный OTLP не удаляют пакет. Неизвестный непустой Protobuf-ответ сохраняется консервативно; после исправления совместимости пакет повторяется. Постоянные отказы видны через технические показатели и готовность, не маскируются успешным завершением.

Воспроизведение сбрасывает только контрольные точки проекций и использует прежние байты/время. Его выполняет оператор после устранения причины отказа; вход не даёт отправителю права читать архив или менять чужую телеметрию. Независимые виды сигналов обрабатываются отдельно, внутри каждого — в порядке местного приёма.

Возраст задолженности не вызывает удаление. При исчерпании диска/заданного объёма новое не подтверждается, принятое остаётся. Технические сроки Loki/Tempo/Prometheus относятся к поисковым проекциям, не к неподтверждённой передаче или исходному центральному журналу. Повреждение диска и уничтожение единственной копии не исправляются повторной отправкой и требуют резервирования.

## Удостоверения и диагностика

Доставка уже одобренных leaf/issuer и публичного отчёта в собственные Docker volumes выполняется прежней операторской задачей по [техническому интерфейсу](../../CERTIFICATE_DELIVERY.md). Он не расширяет права, не является входом runtime sender и не переносит CA-ключи; отзыв допускает только отрицательный отчёт. Готовность конечной доставки проверяется отдельно от успешной выдачи на хосте.

Читающий операторский `export-issuers` возвращает только публичные CA уже одобренного точного потребителя по [контракту поставщика](../../observability/delivery/SPEC.md#читающий-экспорт-публичных-issuer). Это не вход отправителя, не выдача сертификатов и не новый источник доверия; ключи и каноническое состояние провайдера потребителю не доступны. Транспорт и квитанции телеметрии не меняются.

В согласованном локальном профиле операторское сопровождение уже выданных leaf-сертификатов и публичный отчёт сроков определены [поставщиком доставки](../../observability/delivery/SPEC.md#продление-локальных-удостоверений). CA-ключи и одобрения не передаются sender или приложению; смена ключа/корня доверия не является автоматическим продлением. Непрерывная жизнь процесса не подменяет готовность доставки; после обновления отдельно подтверждают свежие центральные сигналы. Production SPIRE и исходные требования mTLS не ослабляются.

Вход требует сертификат из области доверия отправителей. Отдельный защищённый диагностический порт принимает удостоверение чтения и предоставляет GET `/health`, `/status`, `/metrics`, а также канонические `/healthz` и `/readyz` по [единому контракту проб](health-readiness.md); POST на нём запрещён. Живость `/healthz` не читает журнал и не проверяет внешние проекции; `/readyz` имеет те же обязательные условия готовности, что `/health`, но каноническое успешное тело. На входном порту чтение журнала запрещено. Проверка TLS не отключается, секреты не передаются в env/заголовках или payload. Производственные SPIFFE/SVID, ротацию и отзыв определяет ADR-0017.

`/status` показывает только числа записей, задолженности, занятых/разрешённых байтов, ошибок и состояние рабочего процесса. `/health` возвращает 503 при непринимающем журнале, ошибках доставки или остановленном обработчике; `/status` остаётся доступным для диагностики. `/metrics` экспортирует собственные технические численные показатели без списка потребителей и содержимого пакетов. Отсутствие соединения не означает потерю данных, а готовность процесса не заменяет проверку полного завершения доставки.

Дополнительные поля `/health` и `/status` — `admission_pressure` (`0` или `1`) и `blocking_errors` (вид сигнала → безопасный код отказа первой неподтверждённой записи). Допустимы `http_<код>`, `incomplete_ack`, `transport_timeout`, `tls_failure`, `transport_failure`, совместимый прежний `http_<код>_or_incomplete_ack` и обобщённый `delivery_failed`. Это техническая диагностика без адресов, идентификаторов отправителей, содержимого и текста исключений; она не меняет формат квитанции или гарантии хранения. Получение численных показателей не требует повторного сканирования тел архива; проекция обновляется атомарно с журналом по [спецификации владельца](../../observability/delivery/SPEC.md#приём-счётчики-и-восстановление).
