# SPIRE native runtime adapter, version 1

Pre-edit scope: reuse the existing independent SPIRE installation and component export APIs through a pinned node procedure, retaining their identities, state and recovery guards. The four supported roles are `spire-server`, `spire-observer`, `spire-status-publisher`, `spire-telemetry-sender`. Estimate announced before implementation: 90–120 minutes for implementation/host/native regressions, followed by 30–45 minutes bounded native integration. No successful qualification or full platform admission is claimed by this draft contract.

`procedure=spire-runtime` uses `plan|start|status --request ABS_PRIVATE_JSON --request-sha256 SHA256`, the same pinned executor/input binding as owner-compose. Its definition extends the [owner-compose definition](owner-compose.md) with `native_lifecycle`: exactly `kind="spire"`, `runtime_image`, `installer_image`, `input_directory`, `server`. Both images are immutable references. The input directory is under the prepared workspace's `secrets/`; every regular file is an explicitly hash-bound private input, at most 128 files and 64 KiB each, with no undeclared entries/symlinks. `server` is exactly explicit `bind_address` and integer `public_port` for Server, otherwise `{}`. Credentials are files, never command values. Source owner/executor are the same pinned infrastructure generation.

The adapter reuses source/catalog/workspace/input validation, then calls only the existing `spire/install.sh` role with `--native-restart-policy no`. There is no update/recovery/replacement/RESUME dispatch. Desired role images, including `observation.sender_image` in a sender component plan, must resolve to the selected immutable native image before effects. The native installer retains full semantic/PKI validation and canonical state ownership. An existing native installation without the adapter's binding requires explicit reconciliation, not implicit adoption.

The definition also contains `expected_runtime`: null for plan/start, or the four typed fields `configuration_sha256`, `container_id`, `native_image_id`, `incarnation_sha256` from the authoritative original target start receipt for status. The controller reconstructs the exact original start request and reads that receipt through existing node status, rather than trusting a new marker. The incarnation hash binds actual container/image/start time/native restart count. Fresh status invokes role-scoped export into its own operation directory and checks actual Docker metadata against this projection. It returns typed `OWNER_ROLE_RUNNING|STOPPED` and actual health; absence, drift, replacement or unknown outcome cannot become readiness. Plan returns `OWNER_NATIVE_PLANNED`; start success is followed by fresh status. Status never installs a runtime and requires the original receipt. Timeout and post-effect uncertainty return reserved exit 3 / `RESULT_UNKNOWN`; existing node journals prevent automatic retry. No additional persistent binding store is introduced.

Legacy templates, native recovery budgets and the former four-file Agent bootstrap stay unchanged. Independent role/node placement and local Workload API remain as accepted in 00-INFRA-0018. Complete runtime inputs, current identities, grants, quality, telemetry, release/image admission and physical-proof TODO-MVP remain separate gates.

Native integration refinement, estimate 15–25 minutes before edits: owner-prepare's nested public directory modes remain compatible with runtime GID access under its private `0700` workspace. The adapter validates that private ancestor, directory ownership/no group-or-world write and exact `0600` input files. It reuses [node-artifact](node-artifact.md) to form a separate private initial bundle in the current operator operation directory, verifying delivered hashes before native installation. The native API receives real `0700` directories without changing the supplied workspace. Failed planning created no runtime resources and its immutable evidence is retained; no new transport or persistent binding state.

Official mechanisms: [SPIFFE Workload API](https://spiffe.io/docs/latest/spiffe-specs/spiffe_workload_api/), [Docker inspect](https://docs.docker.com/reference/cli/docker/container/inspect/), [daemon-local bind mounts](https://docs.docker.com/engine/storage/bind-mounts/), [atomic replace/fsync](https://docs.python.org/3.13/library/os.html#os.replace), [effectful retry limits](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/). The adapter schema is an AELEV integration decision.
