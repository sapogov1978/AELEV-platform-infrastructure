# Интерфейс локальной установки инфраструктуры, версия 1

Дополнительный [контракт размещения v1](placement.md) описывает полную исходную опись ролей и явные node/instance bindings. `tools/placement.py validate|plan` пока проверяет опись без выполнения install workflow и не меняет CLI core v1 ниже.

Канонический вход: `bootstrap.py`; корневая команда `./infrastructure` вызывает его без изменения модели Compose. Команды: `plan`, `init`, `build`, `up`, `status`, `down`. Повторяемый `--capability` принимает `postgresql`, `kafka`, `object-storage`, `identity`, `platform-ui`, `translation`; без параметров выбирается весь этот локальный состав. `platform-ui` требует `identity`. `translation` получает два exact release images, а `init` create-only импортирует существующий `../TranslationProvider/.env.local` в игнорируемый owner-local secret file. `--no-build` применим к запуску ранее собранного выпуска.

`plan` возвращает JSON с `schema_version=1`, `release`, `capabilities`, `services` и `models_included=false` без изменения Docker. `init` создаёт только отсутствующие локальные env/PKI и рендерит Compose. `build` выполняет подготовку и сборку без старта процессов. `up` после проверки владения установкой поднимает выбранные роли и подготавливает собственные ресурсы инфраструктуры. `status` читает состояние, `down` останавливает выбранные роли без удаления volumes.

При обновлении локального checkout `init` может добавить в существующий owner env только новые не-секретные файловые координаты `*_OIDC_CA_FILE`, provider/worker image pins, provider secret path и PostgreSQL fencing GID из соответствующего `.env.example`; существующие значения, secret roots и credentials не меняются. Provider credential копируется только при отсутствии целевого файла, не печатается и не входит в Git. Сам публичный CA-файл доставляется владельческим или full-local процессом отдельно.

Блокировка `runtime/lifecycle.lock` исключает двух одновременных писателей. Оставленная после аварии блокировка требует разбора владельца и не удаляется автоматически по возрасту. Перед воздействием проверяется `com.docker.compose.project.working_dir`; чужая установка с тем же именем Compose закрыто отклоняется.

При явном `init` выпуска 1.1.2 прежние заводские provider pins двух известных выпусков переводятся на точный pin текущего шаблона. Для worker сохраняется прежняя адресная миграция единственного известного старого pin. Иные значения оператора, пути секретов и настройки обработки не меняются; повторный `init` не записывает уже обновлённые pins. Это подготовка конфигурации, без замены контейнеров, изменения очереди или `RESUME`.

Код `0` означает завершение выбранной технической операции; код `2` — отказ с сохранением локального состояния. Успех не является допуском модели, возобновлением очереди или подтверждением production readiness. Сообщения не содержат секреты. Прикладные базы, topics, buckets и права не являются аргументами этого интерфейса: их отдельно подготавливает потребитель через уже принятые административные интерфейсы владельцев.

## Полный локальный профиль

Локальный bridge listener выбирается по фактическому Docker daemon. Docker Desktop использует loopback-публикацию; Linux использует частный адрес своего bridge. Переводятся только отсутствующее либо прежнее заводское назначение, явные operator overrides сохраняются. Ошибки полного CLI сохраняют исходные stdout/stderr в закрытом `runtime/full-runtime-failure-<UUID>/`: каталог `0700`, файлы `0600`. Публичный ответ остаётся ограниченным кодом; `result.json` отдельно отмечает неопределённый результат, который не разрешает автоматический повтор. Эти файлы могут содержать credentials и не входят в публикуемое evidence.

`up --full-runtime --spire-renewal-input PATH` дополнительно принимает закрытый manifest трёх local/test одобрений SPIRE. Формат и ограничения приведены в [SPIRE User Manual](../../spire/USER_MANUAL.md#автоматическое-сопровождение-локальных-сертификатов). Координатор вызывает публичный оператор Telemetry Renewal и возвращает `spire_renewal` с отдельным результатом свежести квитанций и `automatic_maintenance_verified`; разовый `operator`-проход не является подтверждением действующего таймера или полной readiness. Все одобрения проверяются до инициализации; существующие state, CA-ключи и история остаются у операторов.

Штатный полный запуск предоставлен тем же публичным входом: `./infrastructure plan --full-runtime`, `init --full-runtime`, `build --full-runtime`, `up --full-runtime [--no-build]`, `status --full-runtime`, `down --full-runtime`. Этот режим не совмещается с `--capability` и берёт весь состав из `full-local.json`. Он не запускает acceptance-сценарии, не выбирает provider health fixture и не меняет Process Control. Credentials сохраняются; новый runtime требует владельческих входов всех включённых возможностей. `RUNTIME_HEALTHY` не является quality admission, реальным переводом или production-допуском.

Повторный запуск проверяет installation ownership, configuration hash, native image ID и replicas до воздействия. Drift возвращает `FULL_RUNTIME_*_HANDOFF_REQUIRED`. `up` использует `--no-recreate`, provision/migration barriers и проверку всех постоянных ролей. Timeout возвращает `FULL_RUNTIME_COMMAND_RESULT_UNKNOWN` без повтора; далее требуется `status` и владельческая сверка. `down` сохраняет volumes и credentials. Основание — [полный runtime](../adr/00-INFRA-20261112-0017-full-runtime-startup.md).

Успешные `up/status` возвращают `owner_coordinators.core` и `owner_coordinators.spire`: это фактические физические проекты, а не новый владелец данных. Полный перечень ролей сохраняется в `services`.

Для local/test доступен `up --full-runtime --spire-local-input PRIVATE_CONFIG`, взаимоисключающий с `--spire-initial-input`. Закрытый JSON использует [вход подготовки SPIRE](../../spire/USER_MANUAL.md#подготовить-локальный-initial-bundle); `grafana_tokens` можно опустить. В этом случае после готовности core вызывается собственный OIDC-оператор Grafana с отдельными ограниченными токенами папки `infrastructure-spire`, затем локальная подготовка и публичный bootstrap SPIRE. Выдача допустима только для указанного в плане локального endpoint этой Grafana; удалённый endpoint требует своих tokens. Автоматически созданная временная identity снимается после установки и общей проверки; `spire_local_provisioner_retired=true` подтверждает отзыв. При доставленных оператором tokens значение `false` оставляет отзыв у их оператора. Initial config, диагностические файлы и неизменённые выданные credentials сохраняются под `runtime/spire-local-input`; незавершённая выдача не повторяется. Действующая public binding сохраняется и первоначальные входы заново не применяются. Как и полный bundle, этот путь требует отдельного настоящего enrollment/delivery сертификатов; он не создаёт положительные renewal reports.

Для новой установки вместо предварительного запуска SPIRE используйте `./infrastructure up --full-runtime --spire-initial-input PATH`. Это параметр только `up --full-runtime`. Перед подготовкой проверяются явное per-process socket approval и структура/права owner initial bundle. После готовности 53 core-ролей вызывается [публичный bootstrap SPIRE](../../spire/README.md#запуск); проверенная immutable composition сохраняется как абсолютный `AELEV_INFRASTRUCTURE_SPIRE_INSTALLED_COMPOSE` в корневом `.env` с сохранением остальных байтов и env владельца. Завершение требует готовности всех 57 ролей. Повтор при действующей привязке использует её без повторного чтения первоначальных полномочий. Повреждённый/устаревший ранее объявленный экспорт требует владельческой сверки и не трактуется как новая установка. Файлы первоначального набора остаются входом оператора PKI/IdP/Grafana; native installer отдельно проверяет их криптографическую и release-совместимость.

Действующая установка SPIRE подключается через [публичный экспорт владельца](../../spire/USER_MANUAL.md#подключить-установленный-spire-к-общей-композиции): его собственные `.env`, immutable Compose generation и `receipt.json` доставляются вместе. Вместо owner-local `.env` можно передать абсолютный `AELEV_INFRASTRUCTURE_SPIRE_INSTALLED_COMPOSE`, полученный экспортом в отдельный output root. Объявленный ранее экспорт проверяется до подготовки; start/status/stop сверяют текущие container/image IDs, native restart history и сохранённый Compose coordinator. Четыре роли остаются в своём проекте и не передаются корневому `up`; общая готовность повторно читает их точные инкарнации вместе с остальными 53 ролями. Второй контейнер той же роли в корневом проекте отклоняется. `FULL_RUNTIME_SPIRE_PUBLIC_EXPORT_REQUIRED` требует владельческого bootstrap/export, `FULL_RUNTIME_SPIRE_EXPORT_STALE` — новой владельческой сверки и экспорта, `FULL_RUNTIME_SPIRE_OWNER_RUNTIME_NOT_READY` — штатного восстановления остановленной/нездоровой роли. Копирование одного `compose.json` не переносит допуск. Явный полный `down` останавливает core и четыре роли SPIRE через их собственные Compose-проекты без удаления ресурсов; последующий `up` не обходит восстановление владельца. Нативная приёмка fresh bootstrap SPIRE и совместного полного старта остаётся открытым gate кандидата; полный выпуск ещё не допущен.

`python3 tools/full_local.py` является дополнительным интерфейсом clean-room профиля, а не изменением core CLI версии 1. `validate` проверяет контракт `full-local.json`; `plan` печатает полный состав без записи; `init` вызывает сохраняющую инициализацию core, owner-local local-input generators, create-only доставку локального deployment-admin в отдельные admin roots владельцев и публичной CA локального IdP в отдельные OIDC CA files; `build` собирает все buildable-роли и локальные SPIRE targets без запуска. Существующие admin/CA-файлы не заменяются, закрытый CA key не передаётся, production-доставка остаётся внешней. `preflight [--require-images]` возвращает JSON `READY` либо `BLOCKED` с ограниченными кодами без secret values. `bom --output PATH` разрешён только после успешного preflight и по умолчанию требует чистого source tree.

Функциональная приёмка полного runtime выполняется `test_infrastructure/clean_room_gate.py` по [clean-room runbook](../operations/clean-room-reproduction.md). Runner создаёт evidence только после реальных owner lifecycle-проверок и сохранённого Docker/source baseline. Готовый evidence независимо проверяется `test_infrastructure/clean_room.py`; verifier требует точный набор функций из manifest, поддерживаемые schema/profile/release, строгое `source_dirty=false` в BOM, связь release/source/BOM и SHA-256 каждого артефакта. Успех отдельного штатного запуска не заполняет отсутствующее full-local evidence.

Текущий архив формата 2 — ZIP_STORED с отсортированными регулярными файлами относительно корня репозитория, без префикса `services/infrastructure/`. Поле `schema_version=2` в описи относится к формату поставки, а не к версии CLI. Поставляются исходники, документация и инструменты; `excluded_roots=[".codex", "graphify-out"]` явно закрепляет исключённые служебные каталоги. Unix file mode и ZIP timestamp `1980-01-01T00:00:00` фиксированы. Опись закрепляет SHA-256 каждого файла, нормализацию LF для UTF-8-текста, исходный commit и SHA-256 всего архива.

Полная проверка архива предшествует материализации; ссылки, абсолютные пути, traversal, дубли и лишние файлы отклоняются. Git transport в CI получает тот же commit с отключённым auto-CRLF, исключает только объявленные служебные каталоги и восстанавливает байт-в-байт тот же ZIP. Старые неизменяемые выпуски формата 1 сохраняют исторический префикс `services/infrastructure/`; потребитель поддерживает оба формата. Каталог установленного экземпляра задаётся потребителем и не меняется вместе с размещением исходников.
