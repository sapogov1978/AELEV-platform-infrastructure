# ADR-0098: Кластерная инфраструктурная поставка PostgreSQL

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261009-0098-clustered-infrastructure-postgresql.md`; SHA-256: `6adc8bbf40d50faf9a8118553173df3e6a534e82d74ef2cff71d8253afaf2d49`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят; частично заменён [ADR-0106](20261010-0106-selectable-postgresql-fencing.md) в части обязательного watchdog и тестового отключения ограждения; остальные решения действуют
- **Дата:** 2026-10-09
- **Основание:** A5, A10, A12, ADR-0017, ADR-0042, ADR-0082, ADR-0089, ADR-0090
- **Частично заменяет (Supersedes):** ADR-0088 только в части одиночной PostgreSQL-роли, её прежних DNS aliases и автоматического подключения одиночного тома; самостоятельность и изоляция владельцев сохраняются

## Контекст

Оператор согласовал кластерную PostgreSQL и отдельно подтвердил Patroni и etcd. Прежняя поставка имела один процесс, незашифрованный локальный endpoint, Compose fallback и provisioner, переназначавший существующие объекты. Она не обеспечивала подтверждённую репликацию, безопасное продвижение при отказе или географическую независимость.

## Критерии выбора

- Один SQL-писатель, отдельные базы/права, отсутствие знания потребителей.
- Подтверждение транзакции минимум двумя устойчивыми копиями.
- Готовая координация и fencing без проектного алгоритма HA.
- Самостоятельная географическая поставка с сохранением PostgreSQL 17.6, Alpine и Python 3.13.
- Реальная проверка TLS, provisioning, отказа, возврата и безопасного прекращения записи.

## Рассмотренные альтернативы

1. Одиночная PostgreSQL. Отклонена: единственная копия и общий отказ.
2. Только streaming replication и ручное продвижение. Отклонена: ядро PostgreSQL не поставляет полноценный failure detector и fencing.
3. Асинхронный Patroni либо sync без strict. Отклонены: допускают одиночное подтверждение и потерю подтверждённого WAL.
4. Multi-writer/новый распределённый SQL-продукт. Не выбран: меняет стек и семантику без задачи распределения записи.
5. Patroni со строгим синхронным кворумом и отдельным etcd. Принят; отдельный промежуточный SQL-сервер не добавляется, libpq выбирает ведущего по нескольким адресам.

## Решение

Поставка `services/infrastructure/postgresql` содержит три PostgreSQL/Patroni с отдельными томами и три etcd с собственными томами. Каждая пара размещается в независимой области отказа. Docker bridge служит только совместному размещению на одном сервере, не географической сети. Patroni является единственным координатором; etcd хранит только состояние управления этим компонентом и не доступен приложениям.

Политика: `synchronous_mode=quorum`, `synchronous_mode_strict=true`, `synchronous_node_count=1`, `synchronous_commit=on`, `fsync=on`, `full_page_writes=on`, `check_timeline=true`, `failsafe_mode=false`. Подтверждённый обычный COMMIT хранит WAL ведущего и минимум одной пригодной реплики. Без подходящей реплики подтверждение блокируется; без большинства DCS ведущий прекращает работу. WAN оплачивается задержкой подтверждения. Клиент не ослабляет synchronous_commit; timeout/отмена ожидания/потерянный ответ означают необходимость сверки, не доказанный откат. Это не защита от уничтожения всех копий или неверного действия superuser.

Рабочая установка требует надёжного watchdog выделенного Linux-сервера или виртуальной машины в `mode=required`, с ограждением до окончания аренды. Недоступное устройство запрещает продвижение. Локальный сервисный тест на общей Docker VM допускает только явный override без watchdog; он не доказывает защиту от зависшего Patroni или сервера. Настройка и учение устройства, способного перезагрузить весь сервер, выполняются только на выделенных узлах, не на общей станции.

SQL, физическая репликация, REST и оба канала etcd используют TLS/mTLS. SQL дополнительно требует SCRAM и CN роли, административный REST — отдельное подтверждение. DCS имеет свою CA и границу межсетевого экрана, без ложного обещания CN-based ACL через gRPC gateway. Env содержит только `AELEV_INFRASTRUCTURE_POSTGRESQL_*`; обязательные значения не дублируются fallback в Compose. Секреты — файлы/утверждённая инжекция, не Dockerfile, команды или отчёты.

Клиент переподключается по трём адресам с `target_session_attrs=read-write`, `sslmode=verify-full` и своей identity. Provisioner создаёт одну явно указанную роль/базу без привилегий и не захватывает существующие объекты. Миграции и данные остаются у их владельцев; собственные базы других инфраструктурных компонентов не объединяются. Безопасная конфигурация Patroni впервые материализуется в DCS и отдельно сверяется `verify`: рестарт не применяет bootstrap повторно.

## Последствия

Положительные:

- Отказ одной пары допускает автоматическое переключение без потери нормально подтверждённых транзакций.
- Географическое размещение использует те же рабочие процессы и защищённые интерфейсы.
- Нет собственного HA-алгоритма, общего прикладного владения или одиночного промежуточного SQL-сервера.

Отрицательные:

- Требуются шесть процессов, три независимые области отказа, согласованная PKI, fencing и сетевые правила.
- Задержка записи зависит от WAN; без большинства/подтверждающей реплики доступность уступает сохранности.
- Репликация не заменяет независимый backup, WAL-архив, защиту дисков и восстановление.
- Старые одиночные URL/aliases несовместимы с новым интерфейсом; переключение принадлежит владельцу подключения.

## Критерии проверки

1. Изолированная сборка из собственного Poetry lock; три healthy PostgreSQL 17.6/Patroni и три healthy etcd.
2. Один ведущий, две реплики, фактические strict/quorum и SQL `ANY 1`.
3. Реальный provisioner и идемпотентный повтор, отказ чужому владельцу, запрет plaintext и неверной identity.
4. Отказ ведущего вместе с его etcd сохраняет подтверждённые строки; прежний ведущий возвращается только репликой.
5. Без обеих реплик COMMIT остаётся в SyncRep без подтверждения; восстановление репликации возобновляет запись.
6. Без большинства etcd ведущий демотируется; полный stop/start сохраняет данные.
7. Отдельные учения watchdog, сетевой изоляции/зависания, WAN и независимого восстановления; локальный прогон не закрывает эти ворота.
8. Очистка сохраняет все исходные ресурсы/секреты; остаются Python-тест и читаемый отчёт.

## Миграция и откат

Старые одиночные файлы перенесены в компонентный `obsolete` и не поддерживаются как второй способ запуска. Прежний том не подключается и не удаляется. Для действующих данных сначала остановить старых писателей, проверить согласованную резервную копию, поднять новый кластер с новыми томами, перенести роли/базы штатными PostgreSQL средствами, сверить содержимое/права, переключить конфигурацию владельца на multi-host/TLS и лишь затем разрешить запись. Нельзя одновременно запускать старую копию писателем новой истории.

Откат программного выпуска сохраняет совместимые данные, удостоверения и DCS. Возврат к одиночному писателю после новых транзакций требует отдельного проверенного переноса. Ошибка rewind или утрата DCS не разрешают удаление данных либо слепое продвижение. Полный допуск к рабочей эксплуатации отражается в TASKS отдельно от принятия архитектуры.
