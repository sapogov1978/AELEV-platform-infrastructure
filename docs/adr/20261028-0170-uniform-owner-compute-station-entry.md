# ADR-0170: Единый владельческий вход вычислительной станции

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261028-0170-uniform-owner-compute-station-entry.md`; SHA-256: `bbb242e8ab0275c45399d078f1a827583d2551c0d4038be2593c48767c6868e4`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному требованию пользователя от 2026-10-28
- **Дата:** 2026-10-28
- **Основание:** A5, A10, A12, ADR-0082, ADR-0096, ADR-0112, ADR-0153, ADR-0167, ADR-0169
- **Частично заменяет (Supersedes):** [ADR-0167](20261028-0167-service-owned-replaceable-model-modules.md) в части незавершённой эксплуатационной формы отдельных вычислительных Compose-проектов; разделение жизненных циклов и владельческие контракты сохраняются

## Контекст

Advance Screening имеет единые нативные входы для macOS/Linux и Windows, проверяет локальный Docker, отделяет подготовку от запуска и не переносит управляющий сервис на вычислительную станцию. У Translator отдельный `compose.compute.yml` лишь наследовал model/worker из основного `compose.remote.yml`, поэтому вычислительная поставка не была самостоятельной. У Deep Screening существовал отдельный Compose точного образа, но не было одинаковых входов предварительной проверки, подготовки, запуска, состояния и остановки для разных операционных систем.

## Решение

Каждый владельческий вычислительный модуль предоставляет одинаковый внешний жизненный цикл предварительной проверки, подготовки без запуска, запуска, чтения состояния и остановки через `bootstrap.sh` на macOS/Linux и `bootstrap.ps1` на Windows. Translator и Deep Screening называют эти действия `doctor`, `prepare`, `start`, `status`, `stop`; существующий более строгий установщик Advance Screening сохраняет совместимые `doctor`, `install --prepare-only`, `start`, `status`, `stop`. Вход работает только с локальным Docker daemon в режиме Linux containers, запрещает удалённые Docker contexts и принимает только точный image reference `name@sha256:<digest>`. Предварительная проверка не меняет состояние, подготовка не запускает модель, запуск затрагивает только вычислительную поставку, чтение состояния не меняет её, остановка не удаляет volumes и образы.

Одинаковый жизненный цикл не создаёт общий модельный сервис и не унифицирует внутренние движки. Каждый владелец сохраняет собственные образ, выпуск, task, capabilities, identity, ресурсы и допуск. Поддерживаемая аппаратная ветвь является свойством точного образа: несовместимая архитектура, Linux engine или GPU не заменяются молча другой моделью либо backend. Наличие единого входа не является доказательством аппаратного допуска конкретной станции.

Translator удаляет `translator-model` и `translator-worker` из основного `compose.remote.yml`; их единственным каноническим рецептом становится самостоятельный `compose.compute.yml`. Пара сохраняет owner-local Unix socket, а station bundle получает только маршрутизируемые интерфейсы собственной PostgreSQL и Telemetry Delivery. Обычная управляющая поставка не содержит compute-профиля, определения вычислительных ролей или socket volume.

Deep Screening запускает один точный допущенный вычислительный образ, который содержит выбранный владельцем движок и непосредственно реализует `/v1/status` и `/v1/infer`. Compose не запускает отдельный сторонний engine, не выбирает семейство модели и не доверяет capability из env. До допуска такого образа `prepare` и `start` закрыто завершаются на обязательном immutable image reference, а основной сервис остаётся доступным с моделью `NOT_CONFIGURED`.

Advance Screening сохраняет существующий более строгий установщик и эквивалентные стадии жизненного цикла. Его нативные Metal и контейнерные CPU/CUDA ветви не переносятся как общая реализация и не ослабляются до возможностей более простого Compose-входа.

## Последствия

Вычислительные части трёх владельцев можно сопровождать одинаковой последовательностью стадий на подготовленной macOS/Linux/Windows-станции без запуска управляющих API/UI и без удалённого управления Docker. Translator получает настоящий самостоятельный bundle вместо профиля основного Compose. Deep Screening получает воспроизводимый вход для будущего точного образа без возврата несогласованного engine API.

Запуск на новой физической станции по-прежнему требует подтверждённых Docker/Linux containers, маршрутов, identities, TLS, ресурсов и совместимости образа с архитектурой и ускорителем. Для Translator отдельно требуются защищённые маршруты к собственной PostgreSQL и Telemetry Delivery. Эти проверки не подменяются успешным `doctor`.

## Миграция и проверка

Действующая остановленная модель Translator и её очередь не переключаются автоматически. Сначала выпускается immutable вычислительный образ, затем на новой станции выполняются `doctor` и `prepare`, доставляются собственные identities и маршруты, управляющее намерение меняется на `RUNNING`, и только после этого выполняется `start`. Возврат использует прежний точный образ и `stop`; БД, задания, результаты и Kafka offsets не удаляются.

Статические проверки подтверждают отсутствие compute-ролей и профиля в основном Translator Compose, самодостаточность обоих вычислительных Compose, запрет mutable images и remote Docker contexts и наличие одинаковых действий в Unix/Windows-входах. Реальная аппаратная приёмка каждой станции остаётся отдельным обязательным результатом.
