# ADR-0105: Подтверждаемое присутствие издателя и штатная отписка

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261010-0105-publisher-presence-and-graceful-withdrawal.md`; SHA-256: `7d2251129544db72bd8863eab56e8b7066ce621bd134144c1d7ea615931ceeeb`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному согласованию оператора: подтверждаемые публикации и отписка без обратного опроса; частично заменён [ADR-0115](20261012-0115-owner-local-embedded-sqlite.md) только в утверждении о восстановлении всех данных приёмника повторной публикацией, правила присутствия и отписки сохраняются
- **Дата:** 2026-10-10
- **Основание:** A5, A10, A12, ADR-0017, ADR-0082, ADR-0101, ADR-0102
- **Частично заменяет (Supersedes):** ADR-0101 только в правилах присутствия описаний на странице состояния; владение, устойчивость, авторизация, неизвестность просроченного наблюдения и запрет обнаружения сохраняются

## Контекст

Сохранённая декларация не подтверждает текущий запуск её владельца. Старые строки после штатной остановки превращались в постоянные «Нет данных», а успешный HTTP-ответ со старым списком давал зелёный индикатор. Оператор согласовал различие штатного выхода и потери связи: подтверждённая отписка удаляет строку из представления; прекращение публикаций без отписки сохраняет строку с ошибкой связи. Никакой вывод не доказывает состояние чужого контейнера или причину сетевого отказа.

## Критерии выбора

- описание и присутствие задаёт только авторизованный владелец;
- штатный выход не требует удаления истории или смены UUID;
- потеря связи не маскируется исчезновением строки;
- удалённые узлы не требуют обратных входящих портов, Docker metadata или каталога адресов;
- повторы, отписка и возвращение сохраняют единую устойчивую последовательность.

## Рассмотренные альтернативы

1. Удалять строку по истечении срока наблюдения. Отклонено: авария и разрыв связи скрываются как штатная остановка.
2. Опрос издателей из UI. Не выбран: требовал бы дополнительных HTTPS-серверов, удостоверений, входящих правил firewall и защиты присланных адресов; периодическая публикация уже получает подтверждение UI.
3. Подтверждаемые периодические публикации и явная отписка владельца. Принято.

## Решение

Наличие в текущем представлении отделено от сохранённой декларации и сообщения состояния. Владелец сообщает присутствие и отписку по добавочному [контракту инъекции](../api/platform-ui-injection.md#присутствие-и-штатная-отписка). Для отписки не используется постоянный DELETE и не повышается ревизия описания. Штатная остановка отправляет устойчиво записанное сообщение с большей последовательностью и ждёт подтверждения. Новое сообщение присутствия с ещё большей последовательностью возвращает ту же строку с прежним UUID и владельцем.

Связь подтверждается новой принятой публикацией, не исходным временем наблюдения и не повторами старых байтов. При отсутствии новых публикаций в пределах настроенного срока UI показывает «Нет связи», сохраняя строку; это не подтверждение `OFFLINE` контейнера. Живой издатель с неизвестным состоянием компонента остаётся видимым как «Нет данных». API-получение, связь с издателем и здоровье его компонентов — разные факты. Успешное чтение списка не даёт зелёной отметки при потерянной связи или неизвестных состояниях.

Издатель не заменяет неподтверждённые байты при остановке. Намерение отписки сохраняется в собственном журнале; сначала подтверждается прежнее сообщение, затем отписка. Если подтверждение невозможно или процесс аварийно завершился, UI не изображает штатный выход. При возвращении выполняется сохранённая отписка и публикуется новое состояние. Отказ UI не останавливает основную работу владельца.

SQLite оболочки сохраняет только прежнюю производную декларацию, защиту владения, ревизии, последовательности и технический журнал. Неактивные записи не входят в ответ текущего списка; их нельзя использовать как исходный каталог потребителей. Отписка не удаляет доменные данные и техническую историю. Источник восстановления остаётся у владельца.

## Последствия

Строки добавляются и убираются динамически без изменения образа оболочки. При штатной остановке всего комплекса данные и identities сохраняются. Потеря узла, зависание и сетевая изоляция честно обозначаются как потеря связи, без утверждения о причине. Поставка издателя использует новую закреплённую версию публичной технической библиотеки; общих runtime-образов, новых межсервисных доменных путей и административных полномочий нет.

## Критерии проверки

- штатный SIGTERM подтверждает отписку и убирает строку; запуск возвращает прежний UUID с большей последовательностью;
- аварийное завершение без отписки сохраняет строку и после срока даёт «Нет связи»;
- повтор прежней публикации не продлевает связь и не оживляет отписанную строку;
- чужая identity не отписывает и не возобновляет модуль;
- отказ во время отписки сохраняет точные байты и намерение; восстановление не сбрасывает последовательность;
- миграция не показывает старую декларацию как новое присутствие; свежая публикация прежнего владельца возвращает её;
- индикатор не смешивает успешное чтение списка с доступностью владельцев и не остаётся зелёным после прекращения обновлений.

## Миграция и откат

Собственный журнал клиента добавляет колонку намерения отписки. Перед возвратом клиента 1.0.0 требуется остановить владельца после подтверждения всех сообщений и отписки, сохранить резервную копию и выполнить проверяемое автономное удаление только этой колонки; UUID и последовательность не меняются. Старый клиент использует вставку с прежним количеством колонок и без этой подготовки не запускается. Неподтверждённое сообщение или намерение запрещают такой откат; операторский пример и регрессия находятся в user manual оболочки. Прежний API возвращается только после подготовки и возврата прежних издателей.

Сначала обновляется API/оболочка, затем собственные издатели. Новые столбцы добавляются без удаления данных. Старые сохранённые описания до первой новой публикации не считаются подключёнными; активные владельцы возвращаются своим следующим новым sequence. Прежние сообщения без добавочного поля по-прежнему принимаются, но старый издатель не умеет штатную отписку и требует обновления для этого поведения. Новые издатели нельзя запускать против старого API с запретом неизвестных полей. При откате сначала возвращаются прежние издатели, затем API; тома и журналы не удаляются, а семантика старой страницы снова не соответствует этому решению. Необратимого преобразования канонических данных нет.
