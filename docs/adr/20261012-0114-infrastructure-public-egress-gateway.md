# ADR-0114: Независимая инфраструктурная поставка контролируемого публичного доступа

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261012-0114-infrastructure-public-egress-gateway.md`; SHA-256: `0823d2adb65523e1e934c39e9bb7083c1a5d2268d76f2c293cca705df546701a`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному согласованию пользователя от 2026-10-12
- **Дата:** 2026-10-12
- **Основание:** A10, A12, ADR-0001, ADR-0017, ADR-0048, ADR-0082, ADR-0090, ADR-0103, ADR-0113
- **Заменяет (Supersedes):** ADR-0074 с сохранением его сетевых запретов и изоляции полномочий; ADR-0089 только в части обязательных экземпляров и выходных сетей gateway внутри потребителей; ADR-0113 только в части явно согласованного добавления этой поставки в зафиксированный состав. Остальные ограничения и строгий режим согласования сохраняются.

## Контекст

Общая реализация находилась в `shared`, а потребители собирали её из корня монорепозитория и поставляли собственные контейнеры. Это нарушало проверяемую самостоятельность сборки ADR-0082. Выпуск независимого закреплённого образа мог устранить исходную зависимость без изменения прежнего плана; поэтому перенос не объявляется доказанной критической необходимостью. После обсуждения этой альтернативы пользователь явно разрешил точечный пересмотр владения и состава инфраструктуры, реализацию, миграцию потребителей и проверки. Это исключение не открывает новое переходное окно ADR-0113.

## Критерии выбора

- поставка собирается из собственного каталога, самостоятельно запускается и включается тем же Compose в инфраструктуру;
- провайдер не содержит имён, адресов, предметных разрешений или примеров конкретных функциональных потребителей;
- полномочия привязаны к точной удостоверенной identity, не к общей сети, заголовку клиента или объединённому списку;
- неизвестная, просроченная и отозванная identity закрыто отклоняется; локальный запуск не отключает mTLS;
- прямой публичный выход потребителей запрещён, удалённое размещение не требует общей Docker-сети;
- существующие проверки адресов, DNS, TLS, ограниченные потоки и Kafka-домены сохраняются.

## Рассмотренные альтернативы

1. Независимый образ с прежними контейнерами внутри каждого потребителя: устраняет сборочное сцепление, но сохраняет прежнюю классификацию. Не выбран по явному решению пользователя.
2. Общий gateway с объединёнными scopes и квотами: отклонён, поскольку права одного клиента становятся доступны другому.
3. Независимый универсальный провайдер с индивидуальными разрешениями и региональными экземплярами: принят.

## Решение

`services/infrastructure/public-egress-gateway` владеет единственной реализацией, Dockerfile, lock, самостоятельным Compose, env, TLS, универсальными сетевыми запретами, своим состоянием и проверками. Корень включает этот Compose без второй runtime-конфигурации. Поставка может иметь независимые региональные экземпляры; один сервер на весь мир не требуется. Версии Python и ОС сохраняются.

Потребитель хранит у себя декларацию требуемых технических прав и собственный клиентский сертификат. Оператор проверяет декларацию и применяет отдельное разрешение для точного SPIFFE URI в read-only каталоге разрешений провайдера. Каталог является техническим ресурсом, создаваемым при развёртывании, а не встроенным каталогом потребителей; шаблон провайдера пуст. Доступ к нему не выдаётся рабочим клиентам. Провайдер перечитывает разрешение перед каждым новым запросом; удаление и expiry запрещают новые запросы, но не отменяют уже начатый ограниченный поток. Конфигурация и действия оператора в рабочей среде подписываются и поступают в защищённый аудит по ADR-0017; локальная утилита не заменяет эту систему.

Разрешение задаёт режим `EXPLORATION` или `REGULAR`, точные credential/POST scopes, предел ответа, upstream timeout, конкурентность и интервал обращений. Общие пределы провайдера ограничивают эти индивидуальные значения сверху; дополнительные deny CIDR и универсальные запреты невозможно ослабить разрешением. Квоты и интервалы независимы для каждой identity в пределах реплики. Общий предел реплики защищает процесс; это не гарантия справедливого планирования и не распределённая квота. При нескольких репликах оператор учитывает суммарный бюджет, одинаковую доставку разрешений и их отзыв; несогласованная конфигурация не объявляется кластерной авторизацией.

Внешние credentials остаются у потребителя и передаются только в рамках точного разрешения по HTTPS; gateway не сохраняет и не журналирует их. Provider API `/v1/fetch` возвращает технический внешний HTTP-ответ, не интерпретирует доменные данные и не создаёт источник, очередь или каноническое хранилище потребителя. Это явно ограниченное инфраструктурное исключение в [правилах транспортов](../api/grpc.md), не разрешение доменного HTTP RPC. Формат fetch сохраняется.

Прикладные процессы не подключаются к публичной сети gateway. Compose потребителя подключает только сетевые роли к защищённой сети доступа провайдера; при удалённом размещении платформа разрешает только маршрутизируемый HTTPS endpoint gateway и нужные инфраструктурные endpoints. Kubernetes применяет `default-deny` и точные namespace/workload selectors либо контролируемые внешние маршруты. Отказ gateway не открывает прямой fallback. Docker bridge сам по себе не доказывает изоляцию удалённого размещения.

Сервисный env потребителя явно выбирает владение локальным интерфейсом: `EGRESS_NETWORK_EXTERNAL=true` использует существующую access-сеть провайдера на том же host, `false` создаёт собственную маршрутную сеть потребителя к удалённому HTTPS endpoint. Корень инфраструктуры этим выбором не управляет и не создаёт сети клиентов. Маршрутный интерфейс без обязательного host firewall/default-deny не допускается как рабочая защита.

## Последствия

Устраняется зависимость сборки от `shared` и соседних исходников; инфраструктурный провайдер и потребители обновляются независимо. Появляется самостоятельный технический ресурс авторизации; оператор отвечает за доставку, ограничение срока, отзыв и согласованность разрешений. Общий экземпляр имеет общую область отказа и ограниченный общий ресурс; региональное размещение и бюджет реплик выбираются явно.

## Критерии проверки

- изолированная сборка только каталога провайдера и разрешение собственной/корневой модели;
- реальный HTTPS/mTLS, отказ без сертификата и неизвестной identity;
- независимые scopes и квоты двух identities, expiry и отзыв без перезапуска;
- блокировка private, metadata, mixed DNS, redirect, неподдерживаемых методов и превышения размера;
- цикл start/stop/recreate с сохранением разрешений и очисткой только тестовых ресурсов;
- потребители не собирают и не поставляют gateway, не получают его публичную сеть и сохраняют закрытый отказ;
- отчёт отделяет локальные проверки от непроверенной целевой WAN/Kubernetes-платформы, выдачи SPIRE, аудита и отзыва внешних credentials.

## Миграция и откат

Сначала подготовить независимый провайдер, TLS и отдельные одобренные разрешения. Проверить их ограниченные запросы, затем приостановить сетевые роли потребителя, переключить его endpoint/CA/identity, убрать старый gateway из его Compose и возобновить роли после проверки. БД, очереди, snapshots и credentials потребителей не удаляются; рабочий стенд не переключается автоматически. Форма `/v1/fetch` остаётся прежней, но неаутентифицированный local-вызов больше не поддерживается.

Для отката остановить только новые сетевые роли, восстановить прежний закреплённый образ и конфигурацию из Git вместе с прежним режимом изоляции и удостоверениями, затем проверить закрытый отказ. Не возвращать незащищённый HTTP или общий список полномочий и не запускать два писателя поверх состояния. Старые описания сохраняются в `shared/obsolete/public-egress-gateway`, не как второй активный рецепт.
