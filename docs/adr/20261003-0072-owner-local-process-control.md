# ADR-0072: Устойчивое операторское управление процессами зон и crawler

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261003-0072-owner-local-process-control.md`; SHA-256: `103ecdd42355154b280355aefd651fb7b666db6d830ef28e56746aee34c532b7`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному выбору оператора; прежняя общая терминология частично заменена [ADR-0152](20261019-0152-retire-discovery-registry-umbrella.md), остальные действующие решения сохраняются
- **Дата:** 2026-10-03
- **Основание:** A5, A10, A12, ADR-0069, ADR-0071
- **Заменяет:** —; совместимое расширение административных API двух владельцев

## Контекст

Аудит A15 обнаружил отсутствие симметричных pause/resume/reset рабочих ролей. Оператор явно выбрал повтор незавершённых и ошибочных заданий, без повторной обработки готовых результатов и без удаления человеческой истории. Резкая остановка внешнего эффекта или сброс Kafka offsets не является безопасным способом такого управления.

## Критерии выбора

- собственные устойчивые команды, точная ожидаемая ревизия и идемпотентность каждого владельца;
- пауза новых заданий сразу после команды и безопасное завершение уже начатой единицы;
- сброс только после освобождения всех исполнителей затронутой роли;
- неизменность операторских решений, готовых переводов, выпущенных моделей, offsets и ограничений ICANN.

## Рассмотренные альтернативы

1. Выдать frontend Docker socket или прямой доступ к хранилищам. Отклонено: нарушает границы и расширяет полномочия клиента.
2. Обнулить таблицы или Kafka offsets. Отклонено: теряет историю и повторяет внешние эффекты.
3. Команды собственного API, ограниченный барьер исполнения и новое поколение незавершённой работы. Принято.

## Решение

Каждый сервис владеет собственными `process_control`, `process_control_command` и восстанавливаемыми техническими `process_worker_snapshot`. Общая программная библиотека не владеет данными и никогда не соединяет хранилища сервисов. Новые административные чтения и команды доступны прежней операторской роли только через API соответствующего владельца.

`PAUSE` запрещает новые единицы работы; `DRAINING` означает, что уже начатая единица ещё безопасно завершается. `RESUME` возобновляет выдачу. `RESET` устойчиво переводит роль в `RESET_REQUESTED`, ждёт освобождения её барьера, возвращает пригодные незавершённые и технически ошибочные задания в очередь, увеличивает `generation` и автоматически возобновляет роль. Каждая команда и автоматическое завершение сброса увеличивают отдельную `revision`; устаревшая команда отклоняется без автоматического повторения.

Барьер использует собственную advisory lock PostgreSQL с совместными держателями для конкурентных исполнителей и исключительным держателем только на короткое завершение сброса. Во время внешней работы держится сессионная блокировка, но не SQL-транзакция или блокировка строк предметных данных. Сбой соединения освобождает барьер; собственные lease, попытки и проверки каждого задания остаются обязательными и не заменяются этим барьером. Локализация проверяет управление между сохранёнными выражениями; пауза вычисления не удаляет веса и не равна физическому выключению контейнера. Долгая уже начатая неделимая операция остаётся явно видимой как `DRAINING`.

Готовые машинные результаты, готовые локализации, история единиц перевода, решения человека, результаты HOLDOUT и качество допуска не обнуляются. Ошибка после начала HOLDOUT не превращается сбросом в право повторно использовать этот результат. Kafka продолжает прежний непрерывный checkpoint; опубликованные outbox-события не возвращаются в очередь. Отложенное получение зоны не становится разрешённым раньше ICANN-интервала.

## Последствия

Оператор управляет каждой рабочей ролью и видит запрос, исполнение команды, поколение, ресурсы и возраст наблюдения. Конкурентность зон и языков сохраняется. На выполняющуюся роль требуется дополнительное ограниченное соединение для сессионного барьера; бюджет подключений проверяется отдельно. Пауза уже начатой неделимой операции не обещается мгновенной.

## Критерии проверки

- конкурентная выдача сохраняется, новые задания при паузе не начинаются;
- сброс остаётся ожидающим при активной работе и завершается только после её освобождения;
- повтор команды не создаёт второй эффект, stale revision даёт конфликт;
- готовые результаты, история оператора и положенные ограничения не меняются;
- RSS, нити и файловые дескрипторы имеют явный процессный источник и время наблюдения; отсутствие 24-часового теста запрещено выдавать за доказанную стабильность.

## Миграция и откат

Добавляются только собственные таблицы управления. Сначала останавливаются старые рабочие роли, затем применяются миграции и согласованный код API и исполнителей. Повтор после аварии сохраняет запрос сброса. Откат к коду без управления допустим только после явного возобновления всех ролей: иначе старый код проигнорирует паузу. История команд и предметные данные не удаляются.
