# ADR-0106: Выбираемое ограждение экземпляров PostgreSQL

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261010-0106-selectable-postgresql-fencing.md`; SHA-256: `b2921a4c187f6eae79f3799a133dbef156cbe21b1654e7c5e046919ce1484779`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному требованию оператора поддержать Docker, Kubernetes и watchdog, а локально использовать Docker без перезагрузки
- **Дата:** 2026-10-10
- **Основание:** A5, A10, A12, ADR-0017, ADR-0082, ADR-0098, ADR-0103, ADR-0104
- **Частично заменяет (Supersedes):** ADR-0098 и ADR-0103 только в части безусловного требования watchdog и тестового отключения ограждения. Топология, Patroni/etcd, строгая синхронность, TLS, владение и сохранность остаются действующими.

## Контекст

Watchdog перезагружает весь Linux-сервер или виртуальную машину. Узел PostgreSQL может делить сервер с другими сервисами, поэтому такое воздействие недопустимо для общей станции. Простое отключение watchdog, потеря heartbeat, проверка readiness или удаление Pod из API не доказывают прекращение записи прежним ведущим.

## Критерии выбора

- Patroni остаётся единственным координатором, etcd — единственным хранилищем его аренды.
- Общий сервер не перезагружается контейнерными механизмами.
- Неопределённость запрещает продвижение, не трактуется как подтверждение остановки.
- Выбор принадлежит собственному env PostgreSQL и одинаков при самостоятельном и общем запуске.
- Версии PostgreSQL 17.6, Patroni 4.1.5, etcd 3.6.10, Alpine и Python 3.13 не меняются.

## Рассмотренные альтернативы

1. Безусловно сохранить обязательный watchdog: отклонено для общих серверов; оставлено как явно выбираемый механизм выделенного узла.
2. Только перезапуск по healthcheck или удаление Pod: отклонено, поскольку отсутствие объекта или ответа не подтверждает завершение процессов.
3. Угадывать прежнего ведущего по cached readiness или старому `/sync`: отклонено, поскольку продвижение могло завершиться до обновления этих сведений.
4. Штатный `pre_promote` с отдельным ограниченным исполнителем контейнерного ограждения: принято для Docker и Kubernetes.

## Решение

`AELEV_INFRASTRUCTURE_POSTGRESQL_FENCING_MODE` обязательно и принимает только `docker`, `kubernetes` или `watchdog`. Нет режима `off` или автоматического fallback. Сервисная точка Compose выбирает только собственный рецепт; корень не исправляет устройства, роли или env. В режиме watchdog Patroni требует работающее устройство с `safety_margin=-1`; устройство допустимо только на выделенном узле с отдельным разрешением на перезагрузку.

Контейнерные режимы используют штатный Patroni `pre_promote`: после получения native leader lock, до продвижения. Hook проверяет линейным чтением существующий ключ etcd `/aelev-postgresql/<scope>/leader`, имя кандидата, `lease` и `create_revision`; он не создаёт свою аренду и не выбирает ведущего. При каждом продвижении ограждаются прежние экземпляры обоих других участников, даже если они сообщали роль реплики: это устраняет зависимость от запаздывающей истории ролей. Запросы выполняются параллельно, связаны UUID и текущей native арендой; изменившаяся/истёкшая аренда запрещает подтверждение. Первоначальную инициализацию продолжает выполнять native bootstrap Patroni под его initialize lock.

Docker-исполнитель работает только с собственным daemon и явным списком собственных узлов. Он разрешает только точные контейнеры с метками кластера и узла, повторно проверяет ownership и container ID, выполняет stop с ограничением пять секунд и требует `Running=false`, `Restarting=false`, `Pid=0`. Затем ранее работавший контейнер может запуститься заново: прежний процесс и его незавершённое продвижение уничтожены, новый Patroni обязан проверить DCS и следовать действующему кандидату. Остановленный оператором контейнер не включается. Дубли, отсутствие точного контейнера, ошибка runtime, смена аренды и неподтверждённое завершение блокируют продвижение. Executor имеет привилегированный Docker socket, но не передаёт его PostgreSQL, издателю UI или клиенту; его HTTPS API не является общим прокси. Компрометация executor остаётся привилегированной угрозой daemon и требует защиты, независимо от ограничений HTTP API.

Kubernetes-исполнитель имеет отдельный ServiceAccount и Role только для `get`, `list`, `watch`, `delete` точных имён собственных PostgreSQL Pod в одном namespace. Он проверяет метки, фиксирует UID и resourceVersion, выполняет обычное DELETE с UID precondition и положительным grace period, затем читает watch начиная с прежней версии. Принимается только terminal phase и `terminated` всех контейнеров конкретного UID, опубликованные доверенным kubelet. `404`, `DELETED` без terminal status, `Unknown`, `NotReady`, ошибка/истечение watch и force deletion не являются подтверждением. StatefulSet может создать новый Pod, но он запускает новый Patroni под существующей DCS-арендой; запрещены сторонние SQL-писатели и обход hook. Ни controller, ни executor не могут удалять Node или перезагружать host.

Executor использует проверяемый mTLS с собственной серверной identity и разрешённым административным CN. Токен Kubernetes читается из обновляемой проекции ServiceAccount, не хранится в env или Git. До воздействия и после подтверждения fsync фиксирует собственный технический журнал без секретов. Потеря журнала или записи запрещает успешное подтверждение. Этот журнал не заменяет платформенный доказательный аудит ADR-0017.

## Последствия

Общая станция поддерживает локальный Docker-запуск без аппаратного устройства и без отключения ограждения. Перенос в Kubernetes меняет исполнитель и манифесты, не SQL, репликацию или координатор. Остановка обоих соседей при продвижении добавляет задержку и кратковременно прерывает репликацию; strict COMMIT ждёт возврата пригодной реплики. Недоступный host/daemon/kubelet без независимого подтверждения остановки блокирует автоматическое переключение: это сознательный приоритет сохранности, не гарантия доступности при любом отказе. Watchdog на выделенных узлах остаётся альтернативой с иной областью воздействия. Доступ администратора к runtime/DCS и неподтверждённая внешняя force deletion остаются частью модели доверия, не покрываются обещанием изоляции HTTP API.

## Критерии проверки

- Все три режима разрешаются из env; только watchdog монтирует устройство, только executor получает runtime-полномочия.
- Самостоятельная и корневая модели PostgreSQL полностью совпадают.
- Завершение зависшего Patroni без остановки SQL, текущая аренда и возврат прежнего ведущего проверяются на настоящем Docker.
- Чужие контейнеры, метки, UID, stale lease и неподтверждённая остановка отклоняются.
- Kubernetes не принимает исчезновение Pod вместо подтверждения kubelet; реальные кластерные учения и watchdog требуют соответствующей среды и отдельного безопасного допуска.
- Тесты сохраняют исходные ресурсы и результаты в сервисном `test`.

## Миграция и откат

Согласованно выбрать режим всех трёх участников, подготовить executor identity/полномочия или выделенное устройство. Сначала подготовить executor, затем обновлять реплики по одной, выполнить проверенное переключение ведущего и обновить прежнего ведущего. Во время перехода все новые кандидаты должны соблюдать новый барьер; несовместимые кандидаты запрещены. DCS и данные не очищаются, bootstrap не применяется повторно. Локальный `.env` выбирает `docker`; прежний override без ограждения больше не используется. Переключение на watchdog выполняется только на выделенных узлах с подтверждённым устройством; на общей станции такой откат запрещён.
