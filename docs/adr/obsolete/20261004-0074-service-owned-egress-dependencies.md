# ADR-0074: Принадлежащие сервисам зависимости исходящего доступа

> **Происхождение standalone-редакции.** Источник: `docs/adr/obsolete/20261004-0074-service-owned-egress-dependencies.md`; SHA-256: `05f890cdb414418df303c08155a5b29e54d9b8a558e2ad12d2b9c9f20ef3df98`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Заменён [ADR-0114](../20261012-0114-infrastructure-public-egress-gateway.md); сетевые запреты и индивидуальные права сохраняются, владение поставкой и экземплярами изменено
- **Дата:** 2026-10-04
- **Основание:** A10, A12, ADR-0001, ADR-0017, ADR-0048, ADR-0049
- **Заменяет (Supersedes):** —; уточняет владение техническими зависимостями, не отменяя принятые границы доменов и сетевые ограничения

## Контекст

`zone-regular-egress` и `crawler-egress` поставлялись основным Compose инфраструктуры и отображались как её общие компоненты, хотя каждый обслуживает только свой сервис, имеет собственные полномочия и масштабируется вместе с ним. Оператор указал, что эти экземпляры должны структурно принадлежать соответствующим сервисам как внесённые ими зависимости платформы.

## Критерии выбора

- общая инфраструктура работает без установки зон и crawler;
- продукт приносит собственную конфигурацию gateway и независимо сопровождает его жизненный цикл;
- сетевая защита не дублируется и не ослабляется;
- UI показывает владельца по техническим метаданным, а не по зашитому списку сервисов;
- перенос не обрывает активную загрузку без отдельного решения оператора.

## Рассмотренные альтернативы

1. Изменить только подпись в UI. Отклонено: поставка и остановка остаются связаны с инфраструктурной группой.
2. Дублировать реализацию gateway в каждом сервисе. Отклонено: появляются расходящиеся проверки сетевой безопасности.
3. Общая техническая реализация и отдельная поставка экземпляров владельцами. Принято.

## Решение

`zone-ingestion` владеет конфигурацией, выпуском и эксплуатацией `zone-regular-egress` в режиме `REGULAR`; `web-discovery-crawler` — `crawler-egress` в режиме `EXPLORATION`. В локальной среде экземпляры определены только собственными Compose владельцев и не входят в основной Compose инфраструктуры. Они являются техническими зависимостями продуктов, не новыми доменными сервисами.

Единственная общая реализация и её зафиксированное окружение находятся в `shared/public-egress-gateway`. Повторно используется механизм проверки адресов, а не рабочий контейнер, состояние или credentials. Platform UI остаётся инфраструктурной оболочкой. PostgreSQL, Kafka, MinIO, OIDC, наблюдаемость и базовые именованные сети остаются отдельной платформенной инфраструктурой.

Принадлежность продукта не означает sidecar с прямым доступом worker в интернет. В production gateway остаётся отдельной изолированной рабочей нагрузкой с собственной identity, сетевой политикой, ресурсами и внутренним Service. Прямой публичный egress у прикладных процессов запрещён; HTTPS, mTLS, SPIFFE, проверка DNS, закрепление IP, закрытый отказ, ограничения размера и точные области credentials/POST сохраняются.

Локальные внутренние имена и сети сохраняются для совместимости без изменения клиентов. Общая выходная bridge-сеть остаётся техническим ресурсом платформы и доступна только gateway. Новые сети или публичные порты не требуются. Сбой gateway одного продукта не останавливает gateway другого.

Наблюдаемость сохраняет отдельные измерения API и зависимости: `component_group=services`, `component_owner` указывает владельца gateway. Оболочка строит вложенное представление по этим метаданным; отказ gateway не подменяет измерение API, а отсутствующий владелец не скрывает зависимость. Исходное измерение остаётся доступным.

## Последствия

Положительные:

- установка и остановка общей инфраструктуры не определяют состав сервисных gateway;
- продукт содержит необходимую ему зависимость без второй реализации сетевой защиты;
- оператор видит принадлежность и отдельное техническое состояние.

Отрицательные:

- запуск продукта должен включать собственный gateway;
- смена Compose-группы требует отдельного безопасного переключения рабочих контейнеров.

## Критерии проверки

- инфраструктурный Compose не определяет оба gateway; владельцы определяют только свой экземпляр;
- режимы, лимиты, scopes, непривилегированный UID и read-only root не изменены;
- внутренние имена и сетевые пути клиентов остаются прежними;
- реальные readiness, метрики и ограниченное публичное чтение работают после переключения;
- UI показывает gateway внутри своего владельца и не содержит его в инфраструктурном списке;
- тесты проверяют отсутствие владельца, циклы метаданных и независимость состояний;
- остальные API, worker, модели и канонические данные не перезапускаются при переносе gateway.

## Миграция и откат

Сначала проверяются канонические манифесты, сборка и неизменность сетевой защиты. Перед остановкой прежнего экземпляра проверяются активные запросы. Длительный запрос сохраняется до завершения либо прерывается только с явного разрешения оператора; существующие checkpoint и правила повторов не обходятся. В каждый момент для старого внутреннего имени предусмотрен рабочий gateway. Прежние остановленные контейнеры и образы сохраняются для отката без удаления volumes или изменения канонических данных. Новую поставку нельзя выдавать за перенесённый рабочий экземпляр, пока его старый контейнер остаётся в инфраструктурной группе.
