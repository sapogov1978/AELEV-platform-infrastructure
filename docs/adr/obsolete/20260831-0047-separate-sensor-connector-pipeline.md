# ADR-0047: Раздельный конвейер сенсорных коннекторов

> **Происхождение standalone-редакции.** Источник: `docs/adr/obsolete/20260831-0047-separate-sensor-connector-pipeline.md`; SHA-256: `699c6e8242eca59e81592fa69da86ff2b3111065cfdab1208709307bf73f010d`; основание включения: цепочка замены. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Заменён [ADR-0049](../20260901-0049-discovery-registry-engine-service-boundaries.md)
- **Дата:** 2026-08-31
- **Основание:** A5, A10, A12–A14, ADR-0001, ADR-0005
- **Заменяет:** [ADR-0010](20260729-0010-connector-lifecycle.md)

## Контекст

ADR-0010 верно отделил создание коннектора от его независимой проверки, но
оставил разработку, канонический выпуск, сертификацию и назначения внутри
Discovery & Registry. Это заставляло Discovery продолжать сопровождать уже
найденный источник, связывало скорость обхода Web со скоростью разработки кода
и не позволяло независимо выпускать три разных вида нагрузки.

## Решение

Жизненный цикл сенсорного коннектора разделяется между четырьмя независимыми
сервисами:

1. **Source Discovery** исследует публичный Web, выделяет конкретный документ,
   API или набор данных, проверяет допустимость регулярного использования и
   заканчивает работу по точной ревизии кандидата состоянием `HANDED_OFF`.
2. **Sensor Connector Builder** изучает endpoint и документацию, сохраняет
   собственные входы, создаёт воспроизводимый подписанный артефакт и публикует
   `ConnectorBuildCandidate`.
3. **Connector Review & Certification** независимо проверяет кандидат, владеет
   `SourceProfile`, `SensorDefinition`, `ConnectorRelease`, результатом
   сертификации и `ConnectorAssignment` и публикует их для Sensor Runtime.
4. **Sensor Runtime** исполняет только подписанный совместимый
   сертифицированный выпуск по последнему поколению назначения и публикует
   техническое состояние и `Observation`.

Между сервисами передаются только события Kafka. Source Discovery атомарно с
конечным решением записывает `ConnectorBuildRequested` в собственный outbox.
Событие закрепляет идентификатор и ревизию кандидата, хеш предложения, endpoint,
тип требуемого коннектора, найденные ссылки на документацию, ссылки на
доказательства, проверку правил и решения операторов. Секрет в событие не
помещается: передаётся только имя уже подготовленной ссылки на полномочие.

`HANDED_OFF` является конечным состоянием ревизии в Source Discovery. Builder
не пишет в PostgreSQL или MinIO Discovery и не сообщает туда стадии анализа,
сборки либо ошибку. Review & Certification также не возвращает выпуск в
Discovery. Исправление кода идёт из Review & Certification обратно в Builder
новым Kafka-сообщением и новой версией артефакта. Новый факт о самом источнике
может независимо создать новую ревизию обычным путём Discovery.

Хранилища раздельны. Discovery сохраняет frontier, доказательства обнаружения,
решения допуска и outbox. Builder сохраняет снимки разработки, модели и
артефакты сборки. Review & Certification сохраняет отчёты, канонические выпуски
и назначения. Sensor Runtime сохраняет checkpoint, журнал публикации,
документные снимки наблюдений и архив Observation. Ни один сервис не читает
каноническое хранилище другого.

Это решение относится только к сенсорным коннекторам. Владение Discovery &
Registry точными `ExecutionCapabilityGrant`, `AdapterRelease` и сертификацией
исполнительных возможностей площадки по ADR-0028 не изменяется.

## Контракты и состояния

```text
Source Discovery:
PENDING_OPERATOR_REVIEW → WAITING_SECOND_APPROVAL → WAITING_CREDENTIALS
        ├─ исполняемый источник → APPROVED
        └─ требующий коннектора → HANDED_OFF

Sensor Connector Builder:
RECEIVED → ANALYZING → BUILDING → BUILT
                    ↘ NEEDS_INPUT | FAILED

Connector Review & Certification:
RECEIVED → REVIEWING → VALIDATING → CERTIFIED
                               ↘ CHANGES_REQUESTED | REJECTED | SUSPENDED

Назначение:
SHADOW → CANARY → ACTIVE → STOPPED

Экземпляр Sensor Runtime:
STARTING → HEALTHY ↔ DEGRADED ↔ RECOVERING
                         ↓
                      BLOCKED
```

Повтор `ConnectorBuildRequested` идемпотентен по `source + id`; ключ раздела —
`source_candidate_id`. Повтор `ConnectorBuildCandidate` идемпотентен по точной
версии сборки. Успешная публикация downstream не меняет уже зафиксированное
решение Discovery.

## Последствия

- Discovery можно непрерывно масштабировать и запускать до готовности Builder.
- Разработка кода и независимая сертификация имеют отдельные очереди, хранилища,
  выпуски и области отказа.
- Ни статус Builder, ни сертификация не разрастаются в модели и интерфейсе
  оператора Discovery.
- Появляются два обязательных межсервисных контракта и два самостоятельных
  сервиса, которые должны иметь собственные миграции, наблюдаемость и manuals.

## Критерии проверки

- принятие adapter-required кандидата и запись outbox происходят в одной
  транзакции PostgreSQL;
- после сбоя неопубликованный handoff отправляется с прежними байтами и id;
- Discovery не содержит worker анализа endpoint, API очереди разработки,
  административных операций `ConnectorRelease` или `ConnectorAssignment`;
- Builder и Review & Certification не имеют доступа к хранилищам Discovery;
- несертифицированный выпуск невозможно назначить Sensor Runtime;
- Sensor Runtime не принимает рабочее назначение в обход Review & Certification.

## Миграция и откат

Существующая таблица `connector_development_request` переименовывается в
`legacy_connector_development_request` и остаётся только историческим
доказательством прежней реализации. Она больше не выдаёт lease и не меняется.
Ревизии `WAITING_ADAPTER` переводятся в `HANDED_OFF`; backend до открытия
готовности восстанавливает отсутствующие `ConnectorBuildRequested` в outbox.
Откат возвращает прежнее имя таблицы и состояние, но не удаляет опубликованные
Kafka-события; потребитель обязан сохранить идемпотентность.
