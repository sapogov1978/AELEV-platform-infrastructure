# ADR-0134: Единые HTTP-пробы и уникальные сетевые имена владельцев

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261015-0134-uniform-http-probes-and-owner-unique-aliases.md`; SHA-256: `79780744bbb13f9d0a9a78edda9e525e185b6c325fa8ed5d6b4b951be7e6c9b7`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному архитектурному требованию пользователя
- **Дата:** 2026-10-15
- **Основание:** A10, A12, ADR-0082, ADR-0090, ADR-0101, ADR-0105
- **Дополняет:** ADR-0082 в самодостаточной эксплуатации и ADR-0101 в публикации состояния владельцем; границы авторизации, отсутствие обнаружения и независимость UI сохраняются

## Контекст

Самостоятельные API и UI использовали одинаковые короткие Compose-имена `api` и `ui` в разделяемой операторской сети, а успешный `/healthz` возвращал несовместимые `ok\n`, `ready\n` и JSON. В результате DNS мог выбрать одноимённый контейнер другого владельца, а status publisher принимал либо отвергал ответ в зависимости от чужой реализации. У Policy Management это проявлялось чередованием `ONLINE` и `UNKNOWN` у операторского интерфейса без падения собственного контейнера.

## Критерии выбора

- одинаковый endpoint имеет одинаковое успешное представление у всех владельцев;
- живость процесса не смешивается с готовностью его зависимостей;
- техническая проба однозначно адресует компонент своего владельца;
- исправление не создаёт обнаружение контейнеров, общий каталог или межсервисный предметный HTTP;
- локальная Compose-связность и маршрутизируемые production-адреса следуют одному правилу имён.

## Рассмотренные альтернативы

1. Разрешить publisher принимать несколько текстовых и JSON-вариантов. Отклонено: это скрывает расхождение реализаций и не устраняет подмену одноимённого адреса.
2. Оставить короткие имена и выбрать первый DNS-ответ. Отклонено: порядок ответов не является идентичностью владельца.
3. Закрепить единый контракт проб и уникальные адреса владельцев. Принято.

## Решение

Все принадлежащие AELEV HTTP-приложения, которые предоставляют стандартные пробы, реализуют [единый контракт живости и готовности](../api/health-readiness.md). Успешный `GET /healthz` возвращает HTTP 200, `application/json` и точное тело `{"status":"ok"}`. Успешный `GET /readyz` возвращает HTTP 200, `application/json` и точное тело `{"status":"ready"}`. Пробы различаются семантически и не подменяют друг друга; унифицируется ответ каждой точки между владельцами.

В разделяемой сети каждая проба и внутренний прокси используют уникальное имя адресата, содержащее владельца и роль, например `policy-management-api`, `policy-management-ui`, `zone-ingestion-api`. Имена `api`, `ui`, `backend`, `publisher` и другие общие слова нельзя использовать как адрес компонента в разделяемой сети. Короткое имя допустимо только в сети, принадлежащей одному сервису и недоступной другим владельцам.

Издатель состояния проверяет точный уникальный адрес владельца и каноническое успешное тело. Несовпадение точки, тела, HTTP-кода или превышение локального предела ответа даёт `UNKNOWN`; 503 готовности может отображаться как `OFFLINE` только по действующему контракту конкретного издателя. Техническая проба не передаёт предметные данные и не меняет границу Kafka-only.

## Последствия

Сетевой ответ другого владельца больше не может случайно подтвердить или опровергнуть состояние проверяемого компонента. Операторы и автоматические проверки получают один формат без специальных случаев. Цена решения — явные сетевые псевдонимы в локальной композиции и синхронное обновление потребителей проб при переходе со старого текстового ответа.

## Критерии проверки

- API и UI возвращают точные канонические ответы на успешные `/healthz` и `/readyz`;
- издатели состояния Policy Management, Zone Ingestion и Base Screening используют только уникальные адреса владельцев и отвергают иное тело;
- два UI в одной операторской сети проверяются только по разным уникальным адресам владельцев, а общий псевдоним Compose не используется как адрес пробы;
- перезапуск одного владельца не меняет адрес другого и не вызывает чередование его состояния;
- общая оболочка не получает каталог сетевых адресов и не опрашивает владельцев.

## Миграция и откат

Сначала каждый владелец добавляет уникальные сетевые псевдонимы и обе канонические точки, затем переключает собственные прокси и издатели состояния. Короткие псевдонимы могут оставаться автоматическим свойством имени Compose-сервиса, но ни один активный потребитель не должен их использовать в разделяемой сети. Откат требует согласованно вернуть и производитель ответа, и его единственного потребителя; смешанный откат запрещён, поскольку создаёт ложный `UNKNOWN`. Канонические данные, Kafka-контракты и operator identities не изменяются.
