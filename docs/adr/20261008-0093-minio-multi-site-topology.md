# ADR-0093: Многоплощадочная топология инфраструктурного MinIO

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261008-0093-minio-multi-site-topology.md`; SHA-256: `3fb906aaf28ca97162dbc5aaae77184b5c4a0baf45efbaa2e03aac9152a89927`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят
- **Дата:** 2026-10-08
- **Основание:** A12, A19, ADR-0012, ADR-0082, ADR-0088, ADR-0090
- **Частично заменяет (Supersedes):** ADR-0092 в части одного Compose-сервиса, одного тома `minio-data` и одноузловой топологии поставки

## Контекст

AELEV хранит в S3-совместимом хранилище крупные неизменяемые объекты, часть которых является каноническими исходными байтами или необходима для воспроизводимого восстановления. Одноузловой MinIO с одним томом создаёт единую область отказа: потеря сервера или тома уничтожает все размещённые на нём объекты. Такая поставка противоречит назначению долговременного хранилища и не может быть конфигурацией по умолчанию.

Единый MinIO-кластер также нельзя безоговорочно растягивать между географическими регионами. Распределённая площадка использует синхронный кворум erasure set, поэтому WAN-задержка и сетевой раздел непосредственно влияют на доступность записи. MinIO предусматривает отдельную site replication между независимыми кластерами для непрерывности работы и восстановления после потери площадки.

## Решение

Самостоятельная поставка MinIO по умолчанию состоит из двух независимых площадок. Каждая площадка содержит четыре равноправных узла MinIO с одним эксклюзивным локальным томом на узел и `MINIO_STORAGE_CLASS_STANDARD=EC:2`. Все четыре процесса площадки получают одинаковый список из четырёх HTTPS endpoint томов; здоровье процесса определяется кластерным endpoint, а не только жизнью отдельного процесса.

Площадки размещаются в независимых географических областях отказа и связываются MinIO site replication после готовности обоих кластеров. При первичном связывании данные могут находиться не более чем на одной площадке. Обе площадки используют одинаковую закреплённую версию MinIO, один поставщик идентификации, совместимые корневые учётные данные и взаимно доверенные TLS-цепочки. Адрес каждой площадки указывает на собственный балансировщик, а не на один узел.

Один `compose.yml` описывает оба кластера и может запускаться целиком на локальной станции для проверки логической топологии либо запускать точный сервис узла на соответствующем удалённом Docker-сервере. Совместное размещение восьми локальных контейнеров проверяет конфигурацию, но не считается доказательством независимых областей отказа. Платформенная маршрутизация и балансировщики не подменяются Docker DNS в рабочей среде.

Site replication применяется одноразовой профильной задачей `site-replication-applier`. Она не работает постоянно и не запускается обычным `up`. Прикладные bucket, пользователи и политики по-прежнему принадлежат владельцам ресурсов и создаются после связывания площадок отдельной задачей подготовки; MinIO не содержит каталог потребителей.

## Последствия

Положительные:

- потеря одного узла на площадке не останавливает чтение и запись;
- потеря двух из четырёх томов сохраняет read quorum, но безопасно блокирует запись без write quorum;
- уже реплицированные данные переживают потерю целой географической площадки;
- один и тот же комплект поставки используется локально и на удалённых серверах без абсолютных путей рабочей станции;
- отсутствие узла, TLS-файла, тома или обязательного endpoint обнаруживается до штатной работы.

Отрицательные:

- минимальная самостоятельная поставка требует восемь серверных процессов и восемь независимых томов;
- site replication асинхронна и не гарантирует нулевой RPO при мгновенной потере исходной площадки;
- репликация распространяет логические удаления и не заменяет неизменяемую резервную копию;
- рабочая среда требует по одному отказоустойчивому балансировщику на площадку, наблюдение за отставанием репликации и проверенное восстановление;
- изменение состава erasure set или площадок является контролируемой операцией MinIO, а не правкой списка endpoint на работающем кластере.

## Критерии проверки

1. Compose содержит ровно четыре постоянных узла площадки A и четыре постоянных узла площадки B, а одноузловой сервис отсутствует.
2. Каждый узел площадки получает одинаковые четыре endpoint своего erasure set, отдельный постоянный том, TLS и `EC:2`.
3. Проверка здоровья использует `/minio/health/cluster` и не объявляет одиночный процесс готовым без кворума.
4. Одноразовая задача site replication зависит от здоровья восьми узлов, принимает два разных HTTPS-адреса площадок и проверяет итоговую конфигурацию.
5. Задача подготовки bucket выполняется только после успешного связывания площадок.
6. Локальный `.env` полностью разрешает Compose без запасных значений, а его строки документированы.
7. Документация запрещает считать совместное размещение восьми контейнеров независимыми областями отказа и требует балансировщик, резервную копию и наблюдение за replication lag.

## Миграция и откат

Существующий одноузловой том не включается напрямую в новый erasure set. Оператор останавливает прежний процесс записи, разворачивает два новых пустых четырёхузловых кластера, связывает их site replication, создаёт ресурсы владельцев, переносит объекты только через S3-совместимый механизм MinIO, сверяет версии и хеши, переключает потребителей на балансировщик выбранной площадки и лишь после подтверждённой репликации и проверенного восстановления выводит прежний том из эксплуатации.

Откат не означает запуск прежнего и нового процессов записи одновременно. До переключения допускается остановить новую поставку и вернуть потребителей к неизменённому прежнему экземпляру. После начала записи в новую поставку обратный переход требует отдельной синхронизации объектов, сверки хешей и контролируемого переключения.
