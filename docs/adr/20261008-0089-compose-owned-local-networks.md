# ADR-0089: Владение локальными сетями в Compose

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261008-0089-compose-owned-local-networks.md`; SHA-256: `bc079055fe3e601b974c2f8d6de75db924122ce07c1e41ed98ab748e32a11e25`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0114](20261012-0114-infrastructure-public-egress-gateway.md) только в части экземпляров и выходных сетей gateway внутри потребителей; Compose-владение сетями, отсутствие bootstrap и межузловые endpoints сохраняются
- **Дата:** 2026-10-08
- **Основание:** A10, A12, ADR-0017, ADR-0074, ADR-0082, ADR-0088
- **Частично заменяет (Supersedes):** ADR-0074 в части общей выходной bridge-сети и ADR-0088 в части отдельного сетевого bootstrap

## Контекст

После компонентной декомпозиции отдельный `services/infrastructure/prepare-networks.mjs` читал вручную объявленный список сетей из корневого Compose и создавал даже сети, не используемые активными инфраструктурными контейнерами. Сервисные Compose при этом помечали собственные сети gateway как `external`, то есть отказывались создавать ресурс, жизненным циклом которого сами должны владеть. Локальный запуск зависел от скрытого предварительного шага и установленного Node.js, а общая выходная bridge-сеть связывала независимые поставки без production-эквивалента.

Docker-сеть является только механизмом совместного размещения контейнеров на одном узле. Она не является инфраструктурным контрактом между географически разнесёнными компонентами и не должна создаваться отдельным интерпретатором поверх Compose.

## Решение

Каждый Compose создаёт локальные сети, принадлежащие его рабочим процессам. `zone-ingestion`, base-screening и source-research каждый создают собственную внутреннюю сеть между прикладным процессом и своим экземпляром `public-egress-gateway`, а также отдельную не внутреннюю bridge-сеть только для публичного выхода этого gateway. Эти выходные сети не разделяются между сервисами; прикладные процессы к ним не подключаются.

Платформенные сети совместного локального размещения создаются Compose компонента-поставщика или корневой оркестрацией, когда компоненты запускаются одной группой. Потребитель не создаёт сеть чужого компонента. Наблюдаемость подключается к уже работающим локальным целям как потребитель и не становится владельцем их сетей.

Отдельный скрипт подготовки сетей, его тест и обязательный предварительный шаг удаляются. Корневой Compose объявляет только сети, реально используемые его активными компонентами; сервисные сети, необходимые необязательному профилю наблюдаемости, отмечаются внешними и должны уже принадлежать запущенным сервисам.

В распределённой и production-среде Docker network names не являются интерфейсом. Компоненты используют настраиваемые маршрутизируемые endpoints, TLS, workload identity и сетевые политики платформы. Локальный Compose проверяет односерверную топологию, но не подменяет production-связность.

## Последствия

Положительные:

- чистый локальный запуск не требует Node.js или императивного создания Docker-сетей;
- жизненный цикл приватной сети совпадает с жизненным циклом владельца;
- gateway разных сервисов не получают общую выходную bridge-сеть;
- отсутствие сети обнаруживается как отсутствие её реального поставщика, а не устраняется глобальным скриптом;
- production-конфигурация зависит от endpoints и identities, а не от локальных имён Docker.

Отрицательные:

- локальную наблюдаемость, подключаемую непосредственно к приватным сетям сервисов, запускают после владельцев этих сетей;
- прежнее имя общей `aelev-infrastructure_public-egress` не сохраняется, поскольку общей рабочей сети больше нет;
- перенос существующего gateway на новую выходную сеть требует пересоздания только его контейнера без удаления данных сервиса.

## Критерии проверки

1. В `services/infrastructure` нет `prepare-networks.mjs` и его теста, а документация не требует ручного `docker network create`.
2. Внутренние сети gateway имеют `internal: true`, не являются `external` и определены в Compose владельца.
3. Каждый gateway имеет собственную не внутреннюю выходную сеть; прикладные процессы к ней не подключены.
4. Корневой инфраструктурный Compose не объявляет общую `public-egress` и не создаёт сервисные сети gateway.
5. Все самостоятельные и корневой Compose разрешаются без дополнительного скрипта.
6. Production-документация использует endpoints, TLS, workload identity и сетевые политики, а не общие Docker-сети.

## Миграция и откат

Сначала разрешают обновлённые Compose и останавливают только соответствующий gateway. Затем его пересоздают с принадлежащими сервису внутренней и выходной сетями; worker запускают после успешной readiness-проверки gateway. Volumes, базы, Kafka offsets и канонические данные не изменяются. Существующую общую выходную сеть не удаляют автоматически: после подтверждения отсутствия подключённых контейнеров оператор может удалить её отдельным адресным действием.

Откат выполняется возвратом точной предыдущей версии Compose только после остановки нового gateway и проверки отсутствия одновременных writers или сетевых путей. Возврат глобального скрипта подготовки сетей требует нового архитектурного решения.
