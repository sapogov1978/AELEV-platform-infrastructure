# ADR-0090: Границы конфигурации инфраструктурных компонентов

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261008-0090-infrastructure-configuration-boundaries.md`; SHA-256: `1987f6473fa0351463068b8863637da96c274de59b76f39038bcf873c7b99de8`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0091](20261008-0091-service-owned-kafka-topics.md) в части универсального Kafka topic provisioner и центрального перечня topics, [ADR-0092](20261008-0092-minio-technical-identity.md) в части технического имени и пространства переменных MinIO, [ADR-0094](20261009-0094-flat-infrastructure-orchestration-files.md) в части отдельного каталога интеграционных артефактов и [ADR-0099](20261009-0099-consumer-owned-observability.md) в части владения конкретными monitoring targets/rules/dashboards; остальные границы конфигурации действуют; также частично заменён [ADR-0103](20261010-0103-consumer-agnostic-infrastructure-orchestration.md) в части корневой композиции и знания ресурсов потребителей
- **Дата:** 2026-10-08
- **Основание:** A5, A10, A12, ADR-0017, ADR-0082, ADR-0087, ADR-0088, ADR-0089
- **Частично заменяет (Supersedes):** ADR-0088 в части единого корневого шаблона настроек, размещения сведений о потребителях и сохранения прежних имён локальных ресурсов

## Контекст

Компонентная структура ADR-0088 дала каждому инфраструктурному сервису собственный Compose, но первоначальная декомпозиция оставила в провайдерах сведения о потребителях: PostgreSQL перечислял прикладные роли и базы, Kafka — предметные topics, Object Storage — bucket зоны, Keycloak — OIDC-клиенты, а Observability — конкретные цели и dashboards. Корневой `.env.example` одновременно повторял сервисные настройки и параметры объединения. В результате каталог провайдера формально запускался отдельно, но продолжал знать, какие сервисы он обслуживает, а назначение каждой переменной нельзя было определить по имени.

Инфраструктурный компонент должен одинаково запускаться локально и на отдельном production-узле. Его конфигурация описывает только самого поставщика. Состав потребителей, выдача им ресурсов и соединение нескольких поставок относятся к оркестрации конкретного комплекса и не являются знанием PostgreSQL, Kafka, Object Storage, Keycloak или Observability.

## Решение

Переменные `.env` самостоятельного инфраструктурного компонента именуются по схеме `<ПЛАТФОРМА>_<НАЗНАЧЕНИЕ>_<СЕРВИС>_<ПЕРЕМЕННАЯ>`. Для текущей поставки это префикс `AELEV_INFRASTRUCTURE_<SERVICE>_`, например `AELEV_INFRASTRUCTURE_KAFKA_COMPOSE_PROJECT`. В сервисном `.env.example` находятся только значения, необходимые для установки, запуска и работы этого компонента. Внутренние имена переменных контейнерного процесса могут сохраняться, но Compose явно отображает на них публичные переменные поставки.

Корневой `services/infrastructure/.env.example` использует верхнеуровневое пространство `AELEV_INFRASTRUCTURE_*` без дополнительного сегмента `ORCHESTRATION`: этот файл сам является конфигурацией инфраструктурной оркестрации. Его переменные описывают совместное размещение, имена соединяющих компоненты локальных сетей, конкретные ресурсы потребителей и значения, необходимые для соединения компонентов. Data volumes и внутренние сети провайдера остаются его сервисными настройками. Корневая команда загружает отдельные `.env` компонентов и последним — корневой `.env`; он не становится копией сервисных настроек.

PostgreSQL, Kafka, Object Storage и Keycloak предоставляют универсальные одноразовые provisioner-задачи, принимающие точный ресурс параметрами. Их каталоги не содержат имён прикладных ролей, баз, topics, buckets, политик или OIDC-клиентов. Самостоятельная Observability содержит только собственную техническую конфигурацию, пустые прикладные rules и dashboards. Конкретные задачи подготовки параметризует корневой `services/infrastructure/compose.yml`, а Keycloak-конфигурация и цели наблюдаемости находятся в `services/infrastructure/orchestration`; этот каталог не является сервисом и не владеет runtime или каноническими данными.

Совместимость со старыми именами env не сохраняется: aliases вернули бы вторую конфигурационную поверхность и скрыли нарушение границы. Переход выполняется явным созданием новых локальных `.env` из шаблонов. Данные не удаляются автоматически; для подключения существующего volume его точное прежнее имя задаётся новой переменной владельца.

## Последствия

Положительные:

- имя переменной однозначно показывает платформу, назначение и владельца;
- каталог провайдера не меняется при добавлении или удалении потребителя;
- самостоятельный запуск использует только собственный `.env`, а общая сборка явно показывает интеграционные сведения;
- один универсальный provisioner применяется локально и в production без зашитого состава AELEV;
- географическое разнесение меняет endpoints и платформенную оркестрацию, а не поставку провайдера.

Отрицательные:

- прежние локальные `.env` несовместимы и должны быть пересозданы вручную без переноса неиспользуемых ключей;
- общая локальная команда должна перечислить `.env` всех включённых компонентов;
- оркестрационный слой содержит явные определения одноразовых задач и конкретные конфигурации интеграции;
- существующие volumes не подключаются неявно, если оператор не задал их точные имена.

## Критерии проверки

1. Все ключи каждого компонентного `.env.example` начинаются с его `AELEV_INFRASTRUCTURE_<SERVICE>_`.
2. Все ключи корневого `.env.example` начинаются с `AELEV_INFRASTRUCTURE_` и не содержат дополнительный сегмент `ORCHESTRATION`.
3. Исходники универсальных PostgreSQL, Kafka, Object Storage, Keycloak и Observability не содержат идентификаторов потребителей.
4. Конкретные базы, роли, topics, buckets, OIDC-клиенты, цели и дополнительные сети находятся только в корневой оркестрации.
5. Каждый компонент разрешается собственным `docker compose config`; корневая конфигурация разрешается после загрузки отдельных сервисных и оркестрационного env-файлов.
6. Отдельный `local`, сетевой bootstrap и совместимые aliases старых env-переменных отсутствуют.

## Миграция и откат

Перед первым запуском оператор создаёт новый `.env` рядом с Compose каждого нужного компонента и отдельный корневой `.env` из актуальных шаблонов, затем переносит только соответствующие значения секретов и endpoints. Старые env-файлы не коммитятся и не преобразуются автоматически. До `up` выполняется `docker compose config`; существующие данные подключаются только через явно заданные имена volumes, без `down --volumes`.

Откат конфигурации выполняется выбором ранее проверенной версии Compose и соответствующего ей закрытого набора env-файлов после остановки несовместимых процессов. Возврат сведений о потребителях в каталог провайдера или общего env-файла с сервисными настройками требует нового ADR.
