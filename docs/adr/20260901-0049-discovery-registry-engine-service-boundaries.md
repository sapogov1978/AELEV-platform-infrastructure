# ADR-0049: Сервисные границы Discovery Registry Engine

## Контекст

Прежняя модель называла `discovery-registry` одним сервисом, хотя внутри него
оказались получение многогигабайтных zone files, обход Web, классификация,
сборка кода, сертификация сенсорных коннекторов и управление исполнительными
разрешениями. Эти обязанности имеют разные причины запуска, масштабы, профили
безопасности и жизненные циклы. Общая база и общий выпуск мешают запускать
обнаружение до готовности генератора коннекторов и создают неявные связи между
независимыми стадиями.

`Discovery Registry Engine` является ограниченным контекстом и продуктовым
контуром, но не исполняемым сервисом. Ему нужен один операторский интерфейс,
однако это не означает общий backend или каноническое хранилище.

## Решение

Контур состоит из четырёх независимо выпускаемых сервисов.

### `zone-ingestion`

Сервис получает каталог корневых зон IANA и только разрешённые ICANN CZDS zone
files, ведёт сроки и частоту разрешений, проверяет целостность, нормализует
прямые делегации и сравнивает две последовательные ревизии зоны.

Следующую ревизию зоны разрешено получать после того, как предыдущая полностью
скачана, проверена, нормализована и зафиксирована самим `zone-ingestion`.
Ожидание обработки всех доменов crawler не блокирует новую загрузку. Ограничение
частоты CZDS соблюдается независимо для каждой зоны и никогда не ослабляется
ручным запуском.

PostgreSQL сервиса хранит каталог зон, разрешения, состояния получения,
манифесты, контрольные точки и outbox. Компактные отсортированные ревизии
делегаций являются крупными неизменяемыми артефактами в отдельной области
объектного хранилища, принадлежащей только `zone-ingestion`. Другие сервисы их
не читают.

Сравнение выполняется потоково и публикует через Kafka ограниченные по размеру
`DomainDelegationDeltaBatch` с операциями `ADDED`, `REMOVED`,
`NAMESERVERS_CHANGED` и `REINTRODUCED`. Файл различий не является
межсервисным интерфейсом. Если потребитель отстаёт, сервис может объединить
промежуточные изменения в новую последовательную ревизию, но не скрывает
удаление или повторное появление делегации.

### `web-discovery-crawler`

Сервис потребляет изменения делегаций, ведёт собственные устойчивые frontier и
расписание повторного обхода, безопасно читает HTTP и HTTPS через egress
gateway, выполняет первичную оценку ценности и исследует только наблюдаемые
ссылки согласно ADR-0048. Удаление делегации прекращает новые обходы её
авторитетного корня, но не переписывает историю; повторное появление создаёт
новую ревизию.

`directory`, `search` и `reference` не являются отдельными сервисами или
каноническими ролями. Это могут быть внутренние стратегии одного crawler,
выбираемые по документу. Они используют одно состояние frontier и один
контракт результата.

Crawler владеет кандидатами, доказательствами обнаружения, снимками
исследованных технических документов, классификацией, решениями оператора и
outbox. Он не владеет состояниями сборки или сертификации. Для каждого точного
endpoint и требуемой возможности он атомарно фиксирует конечное состояние
ревизии `HANDED_OFF` и публикует отдельный `ConnectorBuildRequested`. Один домен
может породить несколько запросов. Ошибка последующих сервисов не возвращает
кандидата в crawler; новый факт о сайте создаёт новую ревизию обычным путём.

### `connector-builder`

Сервис потребляет `ConnectorBuildRequested`, самостоятельно получает
зафиксированные в событии публичные документы и проверяет их хеши, строит
воспроизводимый кандидат и публикует `ConnectorBuildCandidate`. Он сначала
пытается применить проверенный универсальный шаблон и генерирует специальный
код только когда шаблона недостаточно.

Один backend и одна модель состояния обслуживают два изолированных пула
работников: `SENSOR` для получения Observation и `EXECUTION` для технических
операций на площадках. Пулы имеют отдельные очереди, образы, полномочия,
пространства артефактов и политики проверки. Builder не получает рабочие
секреты площадок, не совершает внешние операции и не выдаёт разрешение на
использование ресурсов внешнего потребителя. Кандидат содержит происхождение, тесты, SBOM, подпись и неизменяемую
ссылку на артефакт.

### `connector-review-certification`

Сервис независимо проверяет кандидаты в изолированных validation runner без
доступа к рабочим предметным топикам, рабочим секретам и реальным внешним ресурсам. Он
канонически владеет отчётами проверки, подписанными `ConnectorRelease` и
`AdapterRelease`, `SourceProfile`, `SensorDefinition`, назначениями Sensor
Runtime и точными `ExecutionCapabilityGrant`.

Ручное решение требуется только при правовой или смысловой неоднозначности и
может отклонить либо сузить область. Оно не может обойти обязательную проверку
безопасности, целостности, совместимости или точной исполнительной возможности.
Замечания к коду публикуются Builder как новый запрос исправления; crawler их
не получает.

Sensor Runtime остаётся отдельным следующим слоем. Проверочный runner может
исполнять кандидат в изоляции, но не публикует рабочие Observation. Production
Sensor Runtime исполняет только подписанный совместимый сертифицированный
выпуск. Execution Brain действует только под точным непросроченным
`ExecutionCapabilityGrant`.

## Общий интерфейс и Registry

`platform-ui` предоставляет четыре раздела: зоны, исследование Web, сборка,
проверка и сертификация. У каждого сервиса собственный административный backend
и собственная ролевая модель записи. Общий ingress или BFF разрешён только для
OIDC-аутентификации, маршрутизации, объединения read-only представлений и SSE;
он не хранит доменное состояние и не записывает его от имени сервисов.

Отдельного пятого сервиса Registry сейчас нет. Registry является составным
представлением сервисных реестров: зонами владеет `zone-ingestion`, кандидатами
— `web-discovery-crawler`, сборками — `connector-builder`, выпусками,
назначениями и разрешениями — `connector-review-certification`. Объединённый
экран не создаёт общего канонического владельца.

## Контракты и изоляция данных

Межсервисные доменные переходы идут только через Kafka:

```text
zone-ingestion
  -- DomainDelegationDeltaBatch --> web-discovery-crawler
web-discovery-crawler
  -- ConnectorBuildRequested --> connector-builder
connector-builder
  -- ConnectorBuildCandidate --> connector-review-certification
connector-review-certification
  -- ConnectorBuildRevisionRequested --> connector-builder
  -- ConnectorRelease / ConnectorAssignment --> Sensor Runtime
  -- AdapterRelease / ExecutionCapabilityGrant --> Execution Brain
```

Каждый сервис имеет собственные PostgreSQL, миграции Alembic, backup и
учётные данные. Крупные артефакты располагаются только в области объектного
хранилища владельца. Прямое чтение таблиц, файлов, MinIO bucket или API другого
сервиса для доменного перехода запрещено. Получатель сохраняет нужный ему
публичный payload и происхождение события в своей области.

Доставка Kafka как минимум однократная. Каждый переход фиксируется локально с
outbox, а потребитель дедуплицирует сообщение по устойчивому id и версии.
Перезапуск Kafka, Redis или worker не должен терять каноническое задание. Redis
разрешён только как восстанавливаемый ускоритель и не является владельцем
очереди или состояния.

## Порядок миграции и готовность

Разделение выполняется последовательно; следующий сервис не разрабатывается до
рабочей готовности предыдущего:

1. выделить и запустить `zone-ingestion`, включая реальный CZDS цикл, diff,
   Kafka outbox, миграции, восстановление и операторский раздел;
2. выделить и запустить `web-discovery-crawler`, потребляющий реальные delta,
   обходящий Web и публикующий handoff;
3. реализовать `connector-builder` и оба изолированных пула;
4. реализовать `connector-review-certification` и изолированную проверку.

Сервис считается рабочим только после проверки реального штатного входа,
перезапуска во время незавершённой работы, идемпотентного повтора Kafka,
изоляции хранилища, понятного операторского сценария, наблюдаемости, backup и
восстановления. Fixture могут проверять ошибки и крайние случаи, но не заменяют
сквозную проверку на реальных данных. До переноса конкретного владельца прежний
`discovery-registry` остаётся временной реализацией; после переноса он не имеет
права создавать новые записи этого владельца.

## Последствия

- получение zone files не зависит от скорости обхода и разработки кода;
- crawler можно постоянно запускать до готовности Builder;
- сборка сенсорных и исполнительных программ использует общий процесс, но
  сохраняет необходимую изоляцию риска;
- общий интерфейс показывает полный конвейер без общей базы;
- появляются четыре независимо наблюдаемых и восстанавливаемых сервиса и три
  обязательные Kafka-границы до runtime;
- первоначальное выделение требует переноса схем, credentials, исторических
  данных и UI из существующего `discovery-registry` без потери происхождения.

## Критерии проверки решения

- ни один из четырёх сервисов не читает хранилище другого;
- `zone-ingestion` может получить новую ревизию при backlog crawler;
- crawler после перезапуска продолжает frontier без Redis как источника истины;
- один домен может создать несколько идемпотентных build request;
- Builder не может подписать канонический выпуск или grant;
- ручное решение не сертифицирует проваленную обязательную проверку;
- общий UI записывает решение только через backend канонического владельца;
- остановка одного downstream-сервиса создаёт Kafka backlog, но не останавливает
  предыдущую независимую стадию сверх её собственной политики ёмкости.
