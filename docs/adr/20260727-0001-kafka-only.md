# ADR-0001: Kafka как единственный межсервисный транспорт

> **Происхождение standalone-редакции.** Источник: `docs/adr/20260727-0001-kafka-only.md`; SHA-256: `ac4fdbff6521f5d2fd9656e45fcd4c0f69cb99d64d0725751417fea54af7ca85`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят
- **Дата:** 2026-07-27
- **Основание:** A10, A12
- **Заменяет:** —

## Контекст

Ограниченные контексты должны обмениваться версионированными сообщениями, не используя внутренние модели или хранилища друг друга. Обмен включает высокочастотные наблюдения, управляющие события и асинхронные запросы и ответы с возможностью повторной обработки.

## Критерии выбора

- слабая связанность издателей и потребителей;
- воспроизводимая доставка и повторная обработка;
- независимое масштабирование и развёртывание;
- явное владение контрактами;
- единая модель межсервисного взаимодействия.

## Рассмотренные альтернативы

1. Синхронные вызовы HTTP или gRPC между сервисами.
2. Интеграция через общую базу данных.
3. Смешанная модель с синхронными командами и асинхронными событиями.
4. Kafka как единая межсервисная шина доменных сообщений.

## Решение

Все межсервисные доменные сообщения передаются только через Kafka как события CloudEvents 1.0 в структурированном JSON с отдельной JSON Schema.

Доступ сервиса к собственному хранилищу, взаимодействие Execution Brain с внешней площадкой и технические точки проверки работоспособности и готовности не считаются межсервисным доменным обменом.

Запросы и ответы, включая оценку исполнения, реализуются коррелированными событиями с предельным сроком. Доставка гарантируется как минимум один раз; потребители обязаны быть идемпотентными. Порядок гарантируется только внутри одного ключа раздела Kafka. Гарантия ровно однократной обработки за границами Kafka не предоставляется.

## Последствия

Положительные:

- сервисы не зависят от синхронной доступности друг друга;
- события можно повторно обработать в пределах срока хранения;
- потребители масштабируются независимо.

Отрицательные:

- асинхронный запрос и ответ сложнее синхронного RPC;
- необходимы идемпотентность, сопоставление, предельные сроки и обработка дублей;
- глобальный порядок отсутствует.

## Критерии проверки

- нет межсервисных доменных вызовов HTTP/gRPC и чтения чужих баз;
- каждый потребитель проходит проверку идемпотентности;
- проверки контрактов охватывают топик, ключ раздела и корреляцию;
- повторная обработка не изменяет итоговое состояние второй раз.

## Миграция и откат

Для нового проекта миграция не требуется. При замене существующего канала сначала запускаются потребители Kafka, затем издатель. Старый канал удаляется после проверки эквивалентности. Откат возвращает издателя на предыдущий канал без удаления уже опубликованных событий.
