# ADR-0162: Deep Screening показывает отобранные домены и управление в карточке очереди

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261027-0162-deep-screening-operator-presentation.md`; SHA-256: `dd1667177402bcb68d56344cc087ac62fb2e14b296db6df07374d8cc1c61c2d6`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0164](20261027-0164-deep-screening-literal-advance-layout.md) в составе и расположении операторских блоков и [ADR-0168](20261028-0168-deep-screening-durable-sensor-surface-pipeline.md) в отсутствии очереди и Process Control; название результата, управление внутри карточки очереди и запрет фиктивной паузы сохраняются
- **Дата:** 2026-10-27
- **Основание:** A5, A10, A12, ADR-0158, ADR-0159, ADR-0160
- **Частично заменяет (Supersedes):** [ADR-0159](obsolete/20261027-0159-deep-screening-visible-read-only-slice.md) и ADR-0160 в отображении `PAUSED`, предметного результата и отдельной поверхности сенсора; owner-controlled инъекция и запрет фиктивных результатов сохраняются

## Контекст

Первый интерфейс показывал статическое `PAUSED` в шапке, хотя у Deep Screening ещё нет Process Control и worker, поэтому пауза не была подтверждённым состоянием управляемого процесса. Он также выделял будущую поверхность разделов и страниц в самостоятельный экран и называл основной положительный счётчик «Пригодные сенсоры». Для оператора значим итоговый отбор доменов, а внутренний состав будущего пакета не должен становиться отдельной навигацией.

## Решение

Основной положительный показатель UI называется «Отобранные домены». Числа найденных разделов, страниц и сформированных пакетов остаются только метрическими карточками обзора; самостоятельная вкладка или экран их перечня в операторском интерфейсе отсутствует. Канонический `SensorSurfacePackage` ADR-0158, точные адреса и Kafka-передача не меняются: это изменение представления, а не предметного результата.

Управление обработкой размещается внутри карточки «Входящая очередь» по тому же визуальному и логическому шаблону, что у Advance Screening. Пока Process Control, worker, собственная авторизация команд и аудит не реализованы, API сообщает `state=UNAVAILABLE`, `command_available=false` и точный blocker `DSS_PROCESS_CONTROL_NOT_IMPLEMENTED`; кнопка «Включить» видима, но отключена. UI не показывает `PAUSED`, потому что пауза допустима только как состояние реально существующего управляемого процесса.

## Последствия

- оператор видит доменный результат, а не внутреннее название будущего сенсора;
- детализация разделов, страниц и пакетов не разрастается в отдельные экраны, но их счётчики остаются наблюдаемыми;
- место будущей команды совпадает с Advance Screening без фиктивного допуска команды;
- появление рабочего Process Control потребует собственного backend-контракта, OIDC/PKCE, ожидаемой ревизии и аудита до включения кнопки.

## Критерии проверки

- UI содержит показатель «Отобранные домены» и не содержит «Пригодные сенсоры»;
- разделы, страницы и пакеты представлены только числовыми карточками обзора, без отдельной вкладки поверхности;
- шапка и техническое состояние не показывают `PAUSED`;
- карточка входящей очереди содержит индикатор «Обработка недоступна» и отключённую кнопку «Включить» с точным blocker-кодом;
- POST по-прежнему закрыто отклоняется и не создаёт состояние команды.

## Миграция и откат

API и UI обновляются одной поставкой. Старый UI несовместим с новым внутренним снимком обработки, поэтому его образ откатывается вместе с API; Kafka, принятые входные сообщения, module UUID и status outbox не меняются. Откат не разрешает возвращать статическое `PAUSED` как факт Process Control.
