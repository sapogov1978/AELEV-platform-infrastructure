# ADR-0138: Технические идентификаторы операторских команд Base Screening создаёт backend

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261016-0138-base-screening-server-generated-command-identifiers.md`; SHA-256: `84e915f2715c66c40cf6bd2744028763b82b5b33de3a7303b1fab20005033b52`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят
- **Дата:** 2026-10-16
- **Основание:** A5, A10, A12, ADR-0119, ADR-0131, ADR-0132
- **Частично заменяет (Supersedes):** [ADR-0131](20261015-0131-base-screening-operator-route-decisions.md) и [ADR-0132](20261015-0132-base-screening-inline-queue-processing-control.md) только в требовании передавать обязательный `Idempotency-Key` из операторского UI; неизменяемый аудит, проверка редакции, идемпотентность backend и остальные положения сохраняются

## Контекст

Технический ключ повтора не является пользовательским вводом и не должен создаваться браузером для каждого нажатия. Обязательный заголовок в Swagger и UI перекладывал инфраструктурную деталь на оператора, но не обеспечивал надёжный повтор после неопределённого сетевого результата: новый случайный ключ мог создать другое намерение, а человек не имел устойчивого источника исходного значения.

## Решение

Для `decision`, `reschedule` и команд owner-local процессов backend самостоятельно создаёт устойчивый технический идентификатор, вычисляет digest нормализованного запроса и сохраняет их вместе с actor, редакцией и результатом в неизменяемом аудите. Операторский UI и Swagger не запрашивают и не передают `Idempotency-Key`.

Существующий заголовок остаётся скрытой необязательной совместимостью для программного клиента, который сохранил точное значение до отправки и повторяет тот же запрос после неопределённого сетевого результата. Повтор одного ключа с другим телом закрыто отклоняется. Отсутствие заголовка не ослабляет проверку `expected_revision`, уникальность действующей команды или сохранность истории.

Решение относится только к административному HTTP API Base Screening. Kafka-контракты, идентификаторы доменных событий, владельцы данных и маршрутизация Discovery не меняются.

## Последствия и проверка

Оператор работает с предметным действием и текущей редакцией, не управляя техническим ключом. Backend остаётся единственным местом, где связываются идентификатор, digest, actor и результат команды. Проверки подтверждают отсутствие заголовка в OpenAPI и UI, создание идентификатора backend, устойчивый повтор совместимого программного клиента и конфликт при повторе ключа с другим запросом.

## Миграция и откат

Миграция хранилища не требуется: существующие столбцы технического ключа и digest сохраняются. Откат к клиентскому обязательному ключу возможен только новым решением, потому что повторное раскрытие технического параметра меняет операторский контракт.
