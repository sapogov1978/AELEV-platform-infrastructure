# ADR-0097: Явная Kafka-зависимость поставки translator-service

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261009-0097-translator-kafka-dependency.md`; SHA-256: `a25b0ae95a1a2d35fd7e7dc1d4e1e84931b8485d401fbe1c0b7db1749af102f1`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному архитектурному требованию оператора
- **Дата:** 2026-10-09
- **Основание:** A5, A10, A12, ADR-0001, ADR-0017, ADR-0082, ADR-0088, ADR-0090, ADR-0091, ADR-0096
- **Частично заменяет (Supersedes):** [ADR-0088](20261008-0088-componentized-infrastructure-orchestration.md) только в части правила, по которому зависимый инфраструктурный компонент при самостоятельном запуске всегда получает Kafka как заранее подготовленный внешний endpoint; для translator-service обычная точка запуска теперь включает каноническую поставку Kafka, а распределённая точка запуска сохраняет внешний endpoint

## Контекст

Поставка translator-service содержит Kafka consumers, outbox и принадлежащую ей задачу подготовки topics, но прежний `compose.yml` только подключал эти процессы к заранее созданной сети. Оператор должен был отдельно обнаружить зависимость, запустить Kafka и вручную выполнить provisioner. Поэтому наличие собственных файлов ещё не делало обычный запуск переводчика завершённым: без Kafka рабочие процессы не могли принять или опубликовать ни одного сообщения.

Kafka при этом остаётся самостоятельным универсальным компонентом и ничего не должна знать о переводчике. Её отдельный запуск обязан поднимать только broker/controller. Для размещения на разных серверах Docker Compose одного узла не может и не должен выдавать локальный контейнер за удалённый процесс: связь задаётся маршрутизируемым endpoint и защищённой identity, а готовность проверяется на стороне зависимого сервиса.

## Критерии выбора

- обычный запуск translator-service поднимает translator-service, его собственную PostgreSQL и Kafka без скрытой предварительной подготовки сети или ручного запуска provisioner;
- отдельный запуск Kafka поднимает только Kafka и не содержит имён, topics, credentials или настроек translator-service;
- Kafka использует только свой `.env`, translator-service использует только свой `.env`, а параметры broker не копируются в конфигурацию переводчика;
- при разнесении по узлам translator-service не запускает ложную локальную Kafka, использует точный маршрутизируемый endpoint и не становится готовым без реального соединения и трёх принадлежащих ему topics;
- рабочие identities переводчика не получают административных прав, а создание topics остаётся одноразовой идемпотентной задачей deployment identity.

## Рассмотренные альтернативы

1. Оставить только текстовое требование предварительно запустить Kafka. Отклонено: порядок жизненного цикла не проверяется и обычная команда запуска создаёт неработоспособную поставку.
2. Скопировать определение Kafka и его параметры в каталог translator-service. Отклонено: появляются второй источник настроек и знание потребителя внутри провайдера.
3. Всегда запускать локальную Kafka рядом с translator-service, включая распределённую установку. Отклонено: это создаёт лишний broker и не обеспечивает связь с каноническим удалённым журналом.
4. Дать translator-service две явные точки входа: совместную поставку с каноническим Kafka Compose и распределённую поставку с обязательной проверкой endpoint. Принято.

## Решение

`services/infrastructure/translator-service/compose.yml` является обычной односерверной точкой запуска. Он подключает неизменённый `services/infrastructure/kafka/compose.yml` через Compose `include`, загружает настройки Kafka только из Kafka `.env`, подключает broker и роли переводчика к одной принадлежащей Kafka внутренней сети и объявляет `translator-topic-provisioner` зависимым от healthy Kafka. Собственные определения ролей переводчика находятся в `compose.service.yml` и используются также корневой инфраструктурной оркестрацией; это не вторая реализация Kafka и не копия её настроек.

В обычной точке запуска собственная PostgreSQL активна без профиля. После готовности Kafka автоматически запускается идемпотентный `translator-topic-provisioner`; при временной недоступности broker он повторяется с политикой `on-failure`. Оба consumer, outbox и операционный API запускаются только после успешного provisioning. Ручной профиль `provision` удаляется. Отдельный Kafka Compose по-прежнему содержит только service `kafka` и запускается независимо.

`compose.remote.yml` является распределённой точкой запуска translator-service. Он не включает и не запускает Kafka на локальном Docker daemon. Bootstrap servers, `SSL`, CA, клиентский сертификат и ключ задаются в translator-service `.env`; локальная Docker-сеть служит только выходом контейнеров к маршрутизируемому endpoint и не изображает межсерверную сеть. Provisioner тем же реальным запросом metadata создаёт или сверяет topics и остаётся обязательным барьером перед Kafka-ролями. `/readyz` проверяет собственную БД, соединение с Kafka и наличие всех трёх topics, поэтому потеря удалённого broker переводит сервис в состояние неготовности.

Compose не управляет Docker daemon другого сервера. Поэтому распределённая установка сначала развёртывает Kafka её собственной поставкой на назначенном узле или кластерным оркестратором, затем запускает `compose.remote.yml` на узле переводчика. Это не ослабление зависимости: переводчик не проходит provisioning и readiness до фактической доступности указанной Kafka. Для production endpoint обязан использовать защищённый listener, доверенную CA, отдельные runtime и deployment identities и минимальные ACL по ADR-0017.

## Последствия

Положительные:

- `docker compose up` из каталога translator-service выражает полную односерверную зависимость и поднимает Kafka автоматически;
- Kafka можно запускать, обновлять и проверять отдельно, не затрагивая translator-service;
- настройки broker остаются в одном Kafka `.env`, а translator-service хранит только параметры своего подключения, topics и runtime;
- одна и та же проверка реального Kafka metadata закрывает порядок локального запуска и ошибочный удалённый endpoint;
- корневая оркестрация использует те же определения ролей и не становится вторым источником runtime-конфигурации.

Отрицательные:

- поставка содержит две явно разные точки входа для физически разных топологий;
- Compose `include` требует современную версию Docker Compose, проверяемую конфигурационным тестом;
- запуск на двух Docker hosts требует внешнего средства доставки или двух адресных команд, поскольку локальный Compose не имеет полномочий управлять удалённым daemon.

## Критерии проверки

1. Разрешённый обычный Compose содержит ровно Kafka и роли translator-service, а Kafka является healthy-зависимостью provisioner.
2. Разрешённый распределённый Compose не содержит service `kafka`.
3. Kafka Compose отдельно разрешается только в service `kafka` и не содержит идентификаторов translator-service.
4. Consumer, outbox и API зависят от успешного завершения provisioner; его ошибка не заменяется продолжением запуска.
5. `/readyz` возвращает готовность только при доступных БД, Kafka и трёх topics.
6. Отсутствующая обязательная переменная каждого владельца останавливает разрешение Compose до запуска контейнеров.

## Миграция и откат

Оператор создаёт Kafka `.env` из её шаблона и translator-service `.env` из его шаблона. Для совместного размещения используется `compose.yml`; прежний отдельный ручной запуск provisioner удаляется из процедуры. Для существующего удалённого Kafka endpoint используется `compose.remote.yml`, а topics сверяются до старта рабочих ролей. Данные Kafka и PostgreSQL, offsets, contracts и имена topics не меняются.

Откат возвращает прежний ручной порядок запуска, но не удаляет volumes и topics. Такой откат снова требует предварительно поднятой Kafka и потому не считается сохранением достигнутой самодостаточности.
