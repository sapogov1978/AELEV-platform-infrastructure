# ADR-0095: Самостоятельные UI сервисов без инфраструктурного каталога

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261009-0095-service-owned-standalone-ui.md`; SHA-256: `63c065112fba1ed317545f6b5ed3bb243d20d469d04fede10ca33dd026e886f5`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0101](20261009-0101-provider-injected-platform-ui.md) в части изолированного встраивания разделов и инъекции названия/состояния; запрет исходного каталога, обнаружения Docker/Kubernetes и передачи чужих токенов сохраняется
- **Дата:** 2026-10-09
- **Основание:** A5, A10, A12, ADR-0082, ADR-0090
- **Частично заменяет (Supersedes):** ADR-0073 в части инфраструктурного обнаружения, каталога, манифестов подключения, сервисных вкладок и встраивания функциональных UI в `platform-ui`; самостоятельные UI в границах владельцев сохраняются

## Контекст

ADR-0073 отделил функциональные web-приложения от общей сборки, но оставил инфраструктуре реестр их идентификаторов, адресов, точных образов и манифестов. Локальный издатель опрашивал Docker, а `platform-ui` монтировал результат, строил сервисные вкладки и загружал приложения в iframe. Такая схема не содержит предметные данные, однако инфраструктура всё равно знает конкретных потребителей и их состав, поэтому изменение функционального сервиса требует инфраструктурной регистрации.

## Критерии выбора

- инфраструктурные компоненты не содержат идентификаторов, адресов, манифестов или допусков функциональных сервисов;
- каждый UI устанавливается, запускается, обновляется и используется вместе со своим сервисом;
- удалённое или географически разнесённое размещение не требует общего Docker discovery;
- инфраструктурный интерфейс не получает Docker socket, Kubernetes metadata или код функционального UI;
- удаление каталога не меняет backend, канонические данные, административные API или Kafka-контракты.

## Рассмотренные альтернативы

1. Оставить универсальный каталог, но перенести записи допуска в сервисы. Отклонено: инфраструктура продолжала бы собирать и интерпретировать состав потребителей.
2. Заменить обнаружение статическим списком в корневой оркестрации. Отклонено: список остаётся вторым владельцем адресов и идентификаторов функциональных сервисов.
3. Оставить каждый UI полностью самостоятельным, а `platform-ui` ограничить собственными инфраструктурными функциями. Принято: граница владения совпадает с поставкой и жизненным циклом.

## Решение

Инфраструктура не предоставляет каталог функциональных UI и не обнаруживает их контейнеры. Каталог `services/infrastructure/ui-catalogue`, генерируемые `admitted.json` и `ui-catalogue.json`, Docker labels `org.aelev.ui.module`, публичная публикация `ui-manifest.json` для инфраструктурного обнаружения и mount каталога в `platform-ui` удаляются.

`platform-ui` является самостоятельным интерфейсом только инфраструктурных компонентов. Он не показывает вкладки функциональных сервисов, не загружает их в iframe, не принимает их manifests, origins или image digests и не отображает их состояние. Его сетевые настройки и CSP не содержат origin функциональных UI.

Каждый функциональный сервис самостоятельно поставляет и открывает свой UI, владеет его OIDC-клиентом, адресом, настройками, документацией и проверками. Инфраструктурный запуск, обновление или отказ не определяет жизненный цикл функционального UI. Общего технического контракта каталога больше нет; прежний контракт архивируется.

## Последствия

Положительные:

- инфраструктура не меняется при добавлении, удалении или перемещении функционального сервиса;
- UI сервиса не зависит от доступности общего каталога или инфраструктурной оболочки;
- исчезают host-скрипт Node, ручной `watch`, локальные image IDs и доверие к метаданным Docker;
- `platform-ui` не выполняет код функциональных сервисов и не требует их origin в CSP.

Отрицательные:

- единой инфраструктурной навигации по функциональным UI больше нет;
- оператор открывает UI каждого сервиса по адресу его собственной поставки;
- общая инфраструктурная страница не агрегирует состояние или управление функциональными сервисами.

## Критерии проверки

1. Каталог `services/infrastructure/ui-catalogue` отсутствует.
2. `platform-ui` не читает `/ui-catalogue.json`, не монтирует каталог и не содержит service navigation или iframe функциональных UI.
3. Инфраструктурный Compose и env не содержат настроек каталога или origin функциональных UI.
4. Compose функциональных сервисов не публикуют labels для инфраструктурного обнаружения UI.
5. Сборки UI не публикуют `ui-manifest.json` как интерфейс инфраструктурного обнаружения.
6. Каждый функциональный UI продолжает собираться и запускаться самостоятельно.

## Миграция и откат

Удаление затрагивает только производную конфигурацию обнаружения и представление. Backend, базы, Kafka topics, объектные данные и история оператора не изменяются. Перед обновлением удаляется прежний host-процесс `publish.mjs`, если оператор запускал его вручную; оставшиеся локальные JSON каталога больше не используются. Откат требует вернуть согласованную предыдущую ревизию ADR, каталога, оболочки и сервисных manifests одновременно; частичный возврат создаст неработающий второй путь подключения.
