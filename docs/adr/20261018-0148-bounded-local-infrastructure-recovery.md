# ADR-0148: Ограниченное локальное восстановление инфраструктуры

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261018-0148-bounded-local-infrastructure-recovery.md`; SHA-256: `381bc7ea5145b3a2d5983321d39dd09e195f3afccafb2a4233f04cbb4ca611d9`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Частично заменён [ADR-0155](20261023-0155-automatic-recovery-after-cooldown.md) в пожизненном пределе попыток и [ADR-0171](20261028-0171-recovery-resume-and-compose-handoff.md) в передаче Compose-инкарнации, паузе хоста и ожидании зависимостей; остальные барьеры и единственный оператор сохраняются
- **Дата:** 2026-10-18
- **Основание:** A5, A10, A12, ADR-0113, ADR-0106, ADR-0134
- **Заменяет:** —; дополняет локальную эксплуатацию явно выбранных экземпляров, не состав продуктов и не механизм HA PostgreSQL

## Контекст

Docker `unless-stopped` восстанавливает завершившийся процесс, но не живой `unhealthy`; без отдельного ограничения повторные отказы могут вызывать бесконечные рестарты. Дорогие пробы и смешение живости с неготовностью зависимости создают дополнительные ложные сигналы. Пользователь потребовал исправить пробы и обеспечить конечное число попыток восстановления; отдельно согласовал задачу на хосте без Docker socket в runtime, с точными целями и сохранением правил кворума/ограждения PostgreSQL.

## Критерии выбора

- Не вводить новый инфраструктурный продукт, обнаружение сервисов, общий канал оповещений или предметное управление очередями.
- Сохранить владельцев конфигурации, данные, TLS и канонический координатор PostgreSQL.
- Ограничить общий бюджет рестартов и сохранить причины, включая неопределённый результат воздействия.

## Рассмотренные альтернативы

1. Перезапускать все `unhealthy` без лимита — отклонено: цикл не устраняет внешнюю причину и может усилить отказ.
2. Передать Docker socket издателям или рабочим процессам — отклонено: лишние полномочия внутри runtime.
3. Новый общий сервис обнаружения и управления — отклонено: меняет план и владение.
4. Отдельная операторская задача текущего пользователя с явной регистрацией экземпляров — принято.

## Решение

`services/infrastructure/recovery.py` является операторским инструментом локального жизненного цикла, не сервисом Compose или Kubernetes и не частью Platform UI. Оператор регистрирует точное имя уже существующего постоянного контейнера. Сохраняются локальный Docker endpoint/daemon, container ID, digest образа, Compose project/service и hash конфигурации; другая инкарнация не принимается автоматически. Библиотека не содержит каталога функциональных потребителей. Docker-доступ имеет только доверенная задача хоста; компрометация этого пользователя остаётся привилегированной угрозой daemon.

Для зарегистрированного экземпляра задаётся конечная native-политика `on-failure:3`; её последующий бюджет может только уменьшаться. Аварийные native-рестарты и воздействия по `unhealthy` учитываются совместно. После подтверждения отрицательной/устаревшей пробы выдерживаются интервалы 30, 120 и 300 секунд. За один проход допускается не более одного воздействия. Намерение и расход попытки атомарно фиксируются с fsync до Docker-команды; неопределённый результат не возвращает бюджет. После трёх попыток автоматическая политика отключается и остаётся блокировка до явного разбора и `reset`. Успех, перезапуск задачи, длительный простой и сон Mac не обнуляют бюджет. Обнаруженный скачок времени требует заново подтвердить отказ.

Наблюдаемый остановленный контейнер не запускается, новые контейнеры не создаются и реплики не размножаются. Перед воздействием повторно сверяются идентичность и `Running`; для согласованной ручной остановки используется `suspend` под тем же операторским барьером. Произвольные внешние Docker-команды не образуют атомарную транзакцию с инструментом: перед обслуживанием оператор должен приостановить зарегистрированную цель. Изменённая политика, guard или инкарнация требуют нового явного допуска.

Кластерный PostgreSQL использует собственный read-only `recovery_guard.py`: положительное подтверждение текущей native-аренды из двух DCS endpoints, минимум двух живых SQL-участников и доступного ограждения для SQL/etcd. Действующий ведущий не перезапускается этой задачей: сначала требуется штатный switchover Patroni. Восстановление самого исполнителя ограждения не требует положительного ответа от него самого, но сохраняет DCS/SQL-барьеры. Неопределённость запрещает воздействие; guard не выбирает ведущего, не меняет DCS, не отключает fencing и не очищает данные.

Живость издателя проверяется по собственному heartbeat, живость HTTP не подменяется readiness внешних зависимостей. Задача сохраняет локальные технические `state.json`, `report.json`, историю намерений и последнюю причину отказа без секретов. Существующие издатели и наблюдение продолжают показывать недоступность компонентов; отдельный SMTP, Grafana или другой канал уведомлений не создаётся. Сам локальный отчёт не объявляется внешней доставкой тревоги.

## Последствия

Положительные:

- Нет бесконечного собственного цикла восстановления и скрытого обнуления попыток.
- Runtime не получает полномочий оркестратора; очереди и данные сохраняются.
- Причина отказа и блокировка доступны для операторского разбора.

Отрицательные:

- На Mac задача выполняется после логина и не работает во сне/при выключенном хосте; Linux использует свой действующий планировщик с той же командой `once`.
- Выбранная `on-failure` не заменяет запуск после перезапуска daemon и не восстанавливает завершение с кодом 0; такие остановки требуют подтверждённого операторского запуска. Это ограничение выбранного локального режима, не изменение обычных незарегистрированных поставок.
- После замены контейнера нужен повторный допуск; после исчерпания бюджета нужна ручная диагностика, не новый автоматический цикл.
- Недоступный ведущий или непроверенный кворум могут сохранить отказ до штатного вмешательства; доступность не достигается обходом защиты данных.

## Критерии проверки

- Три воздействия, выдержки и устойчивая блокировка проверяются модульно и на отдельном реальном fault-контейнере без сети/данных.
- Native-выходы расходуют тот же бюджет; неизвестный результат воздействия не обнуляет намерение.
- Остановленная, заменённая или вышедшая за согласованный scope цель не запускается.
- Реальные read-only проверки PostgreSQL допускают реплику при здоровом кластере и отказывают действующему ведущему.
- Задача установлена под текущим пользователем без sudo; реальные рабочие отказы не инсценируются ради теста.

## Миграция и откат

Сначала исправляются и проверяются дешёвые пробы и собственные издатели, выполняется адресная либо последовательная выкладка владельца с сохранением томов и identities. Затем регистрируются только согласованные постоянные экземпляры и устанавливается таймер. Административные/завершённые задания исключаются. Не регистрируются все контейнеры daemon автоматически.

Для обслуживания сначала `suspend` точной цели; для снятия всей задачи — остановка только её LaunchAgent. Прежняя native-политика каждого экземпляра сохранена в состоянии и может быть восстановлена отдельным операторским действием после проверки ID. Это возвращает прежние ограничения Docker, не чинит причину отказа. `reset` выполняется только после разбора и не удаляет предыдущую историю. Данные, задания, Kafka offsets и желаемое состояние обработки не меняются.
