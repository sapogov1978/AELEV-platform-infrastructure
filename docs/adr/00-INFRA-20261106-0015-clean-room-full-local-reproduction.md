# 00-INFRA-20261106-0015-clean-room-full-local-reproduction — Clean-room воспроизведение полного локального профиля

- **Статус:** Принят
- **Дата:** 2026-11-06
- **Происхождение:** повторный аудит воспроизводимости полного состава Platform Infrastructure

## Контекст

Отдельные владельческие тесты, документация и быстрый core-профиль не доказывают, что инженер без знания истории репозитория сможет из чистого состояния воспроизвести весь технический продукт и проверить пользовательски наблюдаемые функции.

## Ключевые решения

- `full-local.json` является машиночитаемым полным локальным профилем: владельцы, Compose service sets, внешние входы, локальные builds и обязательные функции приёмки перечисляются явно.
- Core quickstart сохраняется для ограниченного ознакомительного запуска; он не выдаётся за полный функциональный профиль.
- Build никогда не запускает контейнеры. Runtime preflight закрыто отклоняет отсутствующие env/owner inputs, mutable pull images, недопущенные digest-образы и отсутствующее одноразовое SPIRE approval.
- Release BOM связывает точный source commit, Compose model digests и фактические image IDs/repository digests; грязное дерево по умолчанию не допускается.
- Clean-room результат имеет `PASS` только при доказательстве всех обязательных функций, чистого baseline и сохраняющей cleanup. Старые отчёты, health endpoints и частичный прогон не заполняют пропуски.
- Единый runner сам запускает реальные owner lifecycle-сценарии, формирует хешированное evidence вне checkout и сверяет исходные Docker/source состояния; отдельный verifier не доверяет runner и повторно проверяет полный контракт evidence.
- Translator проверяется через непрозрачный capability port: сервис использует перевод, но не владеет и не знает модель, её версию или способ исполнения.
- Готовность `full-local` и допуск production-площадки остаются разными решениями; при отсутствии нового полного evidence статус профиля — `BLOCKED`.

## Последствия

- Новый инженер получает один runbook и исчерпывающий preflight вместо восстановления скрытых предпосылок по истории.
- Непредоставляемые репозиторием образы и операторские полномочия становятся явными входами, а не неявной причиной позднего отказа.
- Добавление или удаление владельца, runtime-роли либо обязательной функции требует обновления manifest, tests и clean-room evidence contract.

## Проверка и откат

Обычный CI валидирует manifest, stage coverage, JSON schema, документацию и fail-closed verifier. Ручной gate на отдельном clean-room runner выполняет build без запуска, preflight, BOM, все lifecycle-сценарии, cleanup и независимую проверку нового evidence. Откат инструмента возвращает прежний quickstart, но не позволяет использовать старое evidence для нового commit и не удаляет runtime/данные.

## Официальные основания

- [SLSA provenance v1.1](https://slsa.dev/spec/v1.1/provenance) описывает проверяемую связь артефактов с исходниками и build process.
- [NIST SSDF SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final) требует определённых и проверяемых практик выпуска безопасного ПО.
- [Docker Compose profiles](https://docs.docker.com/compose/how-tos/profiles/) описывает явное включение профилей без изменения модели сервисов.
- [Docker image digests](https://docs.docker.com/dhi/core-concepts/digests/) описывает неизменяемую адресацию образов.
