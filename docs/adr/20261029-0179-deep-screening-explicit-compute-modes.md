# ADR-0179: Явные режимы вычисления Deep Screening

> **Происхождение standalone-редакции.** Источник: `docs/adr/20261029-0179-deep-screening-explicit-compute-modes.md`; SHA-256: `ccff14ded52aa2f9ea6cd5bf925c6bd171b920de5c0bc033f8ad70a12c4f6ceb`; основание включения: прямая ссылка из поставки. Сохранены номер, статус, история замены и применимые решения; упоминания исключённых bounded contexts нейтрализованы без переноса их контрактов.

- **Статус:** Принят по явному требованию пользователя от 2026-10-29
- **Дата:** 2026-10-29
- **Основание:** A5, A10, A11, A12, ADR-0082, ADR-0167, ADR-0169, ADR-0170, ADR-0178
- **Частично заменяет (Supersedes):** [ADR-0178](20261029-0178-quality-first-heavyweight-model-cohort.md) только в требовании немедленно использовать локальный LoRA-capable выпуск Deep Screening; выбор семейства `Qwen3.8-Max`, приоритет качества и запрет компактного fallback сохраняются

## Контекст

Полный локальный выпуск `Qwen3.8-Max` требует вычислительной инфраструктуры, несоразмерной домашнему пилоту. При этом замена на компактную модель нарушила бы принятый приоритет качества. Официальный удалённый выпуск того же семейства позволяет начать последовательное испытание Deep Screening без покупки кластера, но не предоставляет владельческую LoRA и не должен выдаваться за допущенный локальный выпуск.

Основной runtime уже отделён от реализации модели владельческим контрактом `/v1/status` и `/v1/infer`. Поэтому выбор размещения можно сделать явной настройкой Deep Screening, сохранив один соединитель, один предметный контракт и отдельный точный вычислительный модуль, который один знает API провайдера и хранит его credential.

## Критерии выбора

- качество семейства `Qwen3.8-Max` не понижается ради имеющегося оборудования;
- основной runtime и Platform UI не получают API key, provider endpoint или совместимость со сторонним API;
- удалённый пилот не заявляет `LORA_ADAPTER` и не становится production-допуском;
- режим нельзя менять автоматически после ошибки или исчерпания квоты;
- переключение сохраняет очередь, активные решения, provenance и точный digest владельческого модуля;
- публичный материал не смешивается с секретами, персональными данными или внутренними документами.

## Рассмотренные альтернативы

1. Автоматически отправлять запрос в удалённый API при отказе локальной модели. Отклонено: один и тот же job мог бы незаметно сменить гарантии, выпуск, стоимость и границу раскрытия данных.
2. Встроить клиент Alibaba Model Studio непосредственно в worker Deep Screening. Отклонено: основной runtime узнал бы внешнего провайдера и credential, а заменяемость владельческого модуля была бы утрачена.
3. Считать удалённый официальный API эквивалентом локального LoRA-выпуска. Отклонено: режим не предоставляет владельческую адаптацию и не прошёл тот же допуск артефакта.
4. Добавить два явных режима за одним owner-local контрактом и переключать их только через управляемую остановку. Принято.

## Решение

Deep Screening поддерживает закрытую настройку `AELEV_DSS_COMPUTE_MODE` с двумя значениями:

| Режим | Назначение | Обязательные возможности модуля |
|---|---|---|
| `LOCAL_RELEASE` | локальный либо принадлежащий владельцу точный выпуск на выделенной вычислительной станции | `INFERENCE`, `LORA_ADAPTER` |
| `REMOTE_PILOT` | последовательный домашний пилот через отдельный владельческий шлюз к официальному Alibaba Model Studio | `INFERENCE`, `REMOTE_PILOT` |

Значение по умолчанию — `LOCAL_RELEASE`. Значения `AUTO`, `FALLBACK` и одновременная маршрутизация запрещены. Несовпадение настроенного режима с возможностями точного модуля закрыто блокирует обработку.

В `REMOTE_PILOT` используется закреплённый model ID `qwen3.8-max-0902`, `reasoning_effort=xhigh` и не более одного одновременного вызова. Изменяемый alias `qwen3.8-max` не является точной ревизией. Внешний API вызывает отдельный точный образ вычислительного модуля Deep Screening; основной API, worker и UI продолжают обращаться только к владельческим `/v1/status` и `/v1/infer`. Provider API key монтируется в этот образ отдельным read-only файлом и не передаётся через переменную окружения, журнал, ответ статуса или Platform UI.

Удалённый пилот принимает только общедоступный материал, который Deep Screening вправе исследовать. Внутренние документы, credentials, персональные данные и иной материал с запретом внешней передачи закрыто исключаются до вызова. Результат сохраняет provider-independent предметную схему, точный владельческий `release_digest`, входные digests и provenance; имя провайдера не становится полем межсервисного события.

Смена режима не является runtime fallback. Оператор обязан поставить worker на `PAUSE`, дождаться отсутствия активной аренды, остановить прежний вычислительный модуль, изменить режим, exact image, release digest и endpoint как одну конфигурационную ревизию, запустить и проверить новый модуль и только затем выполнить явный `RESUME`. Очередь и PostgreSQL не очищаются. Попытка запустить несовместимый модуль остаётся `UNAVAILABLE`.

`REMOTE_PILOT` предназначен для функционального пилота и сбора benchmark. Он не удовлетворяет требованию владельческой LoRA, не допускается как production-выпуск и не отменяет подготовку `LOCAL_RELEASE`. Переход к другому семейству модели требует отдельного ADR.

## Последствия

Положительные:

- Deep Screening можно начать испытывать дома без понижения выбранного семейства модели;
- основной сервис остаётся независимым от внешнего API и его credential;
- Platform UI честно отличает собственный выпуск от удалённого пилота;
- локальный выпуск и LoRA остаются целевым production-путём;
- стоимость и скорость регулируются последовательной обработкой без изменения качества модели.

Отрицательные:

- удалённый пилот зависит от доступности, квоты, цены и политики внешнего провайдера;
- общедоступные входные материалы покидают инфраструктуру владельца;
- LoRA и полностью воспроизводимый artifact digest модели в удалённом режиме недоступны;
- смена режима требует управляемой эксплуатационной процедуры и отдельного точного образа шлюза.

## Критерии проверки

- неизвестное значение `AELEV_DSS_COMPUTE_MODE` закрыто отклоняется до обращения к модели;
- `LOCAL_RELEASE` не принимает модуль без `LORA_ADAPTER`, а `REMOTE_PILOT` не принимает модуль без `REMOTE_PILOT`;
- удалённый overlay использует точный владельческий image reference, fixed model ID, один concurrent request и API key из read-only файла;
- UI показывает режим, но не provider endpoint, model ID или credential;
- ни ошибка, ни timeout, ни квота не переключают режим автоматически;
- смена режима не удаляет очередь и не выполняет `RESUME` автоматически.

## Миграция и откат

Существующая конфигурация без нового параметра продолжает означать `LOCAL_RELEASE`. Для пилота сначала создаётся и испытывается точный owner image шлюза, затем worker переводится в `PAUSE` и осушается, модуль переключается на `REMOTE_PILOT`, а основной runtime получает тот же режим, новый точный `release_digest` и endpoint. Откат выполняется той же процедурой в `LOCAL_RELEASE`; автоматический откат запрещён.
