# ADR-0005: Управление межсервисными контрактами

> **Происхождение standalone-редакции.** Источник: `docs/adr/20260727-0005-event-contract-governance.md`; SHA-256: `5ea06dabe55232c2b37279b4f0af23e70b4569fee36401270510b0707123b381`; основание включения: применимая зависимость ADR. Сохранены номер, статус, история замены и применимые решения.

- **Статус:** Принят
- **Дата:** 2026-07-27
- **Основание:** A5, A10, A12
- **Заменяет:** —

## Контекст

Kafka задаёт транспорт, но не обеспечивает единую семантику сообщений, совместимость схем и безопасную миграцию потребителей. Без общего порядка каждый сервис может создать собственную копию контракта.

## Критерии выбора

- человекочитаемый и языково-независимый формат;
- однозначное владение;
- автоматическая проверка совместимости;
- поддержка обработки старых событий;
- безопасная миграция старших версий.

## Рассмотренные альтернативы

1. Локальные модели Pydantic в каждом сервисе.
2. Protobuf или Avro как источник схем.
3. Неверсионированный JSON с ручной проверкой.
4. JSON Schema как проектный источник и Schema Registry как рабочий каталог.

## Решение

- Издатель владеет контрактом.
- Единственный проектный источник схем — `shared/contracts`.
- Модели Pydantic, примеры и документация генерируются из JSON Schema.
- Рабочие схемы публикуются в Schema Registry.
- Конверт сообщения — CloudEvents 1.0 в формате структурированного JSON.
- Деньги, цены и количества передаются десятичными строками или масштабированными целыми числами.
- Текущая старшая версия использует `BACKWARD_TRANSITIVE`.
- Несовместимое изменение получает новую схему, тип события и старшую версию топика.
- Потребители обновляются раньше издателя; версии работают параллельно.
- Старые версии читает версионированный преобразователь.
- Потребители идемпотентны по `source + id`.

Переход на бинарный формат допустим только через заменяющий ADR и нагрузочное исследование, показывающее, что JSON не выполняет требования по задержке, пропускной способности или точности.

## Последствия

Положительные:

- контракт не дублируется между языками и сервисами;
- совместимость проверяется до рабочей среды;
- события остаются читаемыми и удобными для аудита.

Отрицательные:

- JSON создаёт больший объём и нагрузку на процессор, чем бинарные форматы;
- генерация моделей и преобразование старых версий становятся обязательными;
- несовместимая миграция требует параллельных топиков.

## Критерии проверки

- CI проверяет JSON Schema и режим `BACKWARD_TRANSITIVE`;
- схемы публикуются только после проверок контрактов потребителей;
- модели воспроизводимо генерируются из `shared/contracts`;
- наборы повторной обработки покрывают поддерживаемые старшие версии;
- нагрузочное исследование измеряет стоимость сериализации и размер сообщения.

## Миграция и откат

Потребители обновляются до издателя. Несовместимая миграция использует параллельные топики старших версий и преобразователь событий. Откат возвращает издателя на предыдущую схему и сохраняет новую версию для аудита.
