# Руководство SPIRE

## Назначение и граница

Поставка устанавливает SPIRE Server, отдельный агент каждой установки и ограниченный оператор регистрации. Удостоверения обновляются автоматически, конечные ключи не попадают в argv, `.env` или журнал. Рабочие контейнеры не получают Docker socket, административный API или CA key. Это технический провайдер, не общий каталог приложений. Контракт входов и выдачи находится в [описании API](../docs/api/workload-identity.md).

## Исходные входы

На каждой машине нужны доступный локальный Docker с Linux Engine, Compose и разрешённые runtime/installer-образы одной ревизии. Shell-вход различает macOS/Linux; PowerShell-вход предназначен для Windows с Docker Desktop в Linux-режиме. Удалённый Docker context запрещён: команда исполняется на нужной машине, а не незаметно меняет другой сервер. GPU для SPIRE не требуется. Установщик не устанавливает Docker Desktop, драйверы или административные права вместо владельца корпоративной машины.

Владелец задаёт проект установки, среду, trust domain и маршрутизируемый адрес сервера. Для production дополнительно передаются утверждённый внешний промежуточный issuer и trust bundle через защищённый каталог `AELEV_INFRASTRUCTURE_SPIRE_AUTHORITY_SOURCE`: `issuer.crt`, `issuer.key`, `bundle.crt`. Ключ читается серверным UID 10001 и не имеет групповых/общих прав; root private key не передаётся. Источник должен оставаться доступным серверу после установки; автоматическая доставка исходных секретов принадлежит утверждённому механизму площадки. Самоподписанный issuer в production отклоняется. Установочные и экспортные helper-контейнеры имеют доступ к Docker socket и тем самым полномочия, эквивалентные root на Docker host; оператор задаёт `DRP_SPIRE_DOCKER_SOCKET_APPROVAL=operator-root-equivalent-v1` только в окружении конкретной команды после проверки закреплённых образов и локального endpoint. Значение не записывается в `.env`, secret store или shell profile.

Сборка из этого каталога:

```sh
docker build --target runtime -t aelev/infrastructure-spire:approved .
docker build --target operator-installer -t aelev/infrastructure-spire-installer:approved .
docker build --target telemetry-sender -t aelev/spire-telemetry-sender:approved .
```

В production используются допущенные образы по `@sha256`, а не подвижные теги примера. Native SPIRE закреплён версией и SHA-256 отдельно для Linux ARM64/AMD64 в `artifacts.lock.json`; установщик дополнительно сравнивает исходный выпуск runtime со своим. Закрепление digest не заменяет подпись и admission площадки.

Стадия `telemetry-sender` наследует независимо выпущенный owner-controlled Sender, не исходники соседнего продукта. Его исходный digest задаётся `OWNER_SENDER_IMAGE`; он должен соответствовать архитектуре и допуску площадки. По умолчанию выбран подписанный multi-architecture выпуск `ghcr.io/sapogov1978/aelev-platform-infrastructure-observability-sender@sha256:162f07e6fd043eb3d9e04e7c415bee07771321a6f7f3864fcba0ce1f80dd941e` из [release run 42308900143](https://github.com/sapogov1978/AELEV-platform-infrastructure/actions/runs/42308900143) с SBOM/provenance, контролем критических циклов, устойчивой диагностикой фаз/ограниченных позиций потоков и минимальной локальной пробой. Для отдельно допущенного выпуска передайте `--build-arg OWNER_SENDER_IMAGE=<утверждённый-образ@sha256:digest>`. В первоначальном плане наблюдения выбирается полученный собственный образ `aelev/spire-telemetry-sender:approved`. Базовые ОС не меняются; в обоих образах сборка проверяет фактическую SQLite 3.53.4. GCC и заголовки остаются только в сборочных стадиях.

## Установка сервера

Без редактирования конечного `.env` на macOS/Linux:

```sh
sh install.sh server identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved --environment local --trust-domain local.example
```

На Windows эквивалентный вход:

```powershell
.\install.ps1 server identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved --environment local --trust-domain local.example
```

По умолчанию порт 18081 опубликован только на loopback. Для другой физической машины владелец явно задаёт `--bind-address` и `--public-port` на разрешённом маршрутизируемом интерфейсе, защищает порт сетевой политикой и передаёт тот же адрес/порт в запросе регистрации агента. Локальный CA создаётся только в local/test. Для production используются `--environment production`, утверждённый trust domain, образы по digest и внешний issuer, описанный выше.

Операторский контейнер одноразовый; только он получает Docker-доступ. Конфигурация, разрешённый план, сведения о daemon/release, node/server state и история сохраняются в собственных именованных Docker volumes. Конечные SVID и административный socket находятся в отдельных tmpfs volumes. Установщик проверяет точные метки владельца и не присваивает неизвестные данные. Конечный Compose JSON автоматически получается из канонических Compose-файлов, а не поддерживается вручную.

Повтор той же команды без исходных параметров использует сохранённое намерение и не пересоздаёт существующий контейнер:

```sh
sh install.sh server identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved
```

Успешный выход означает свежую фактическую готовность native SPIRE; один лишь запуск контейнера не считается успехом. Другой план/роль сохраняет существующую установку и возвращает ошибку. `--update` допускает только новый согласованный выпуск при прежних плане, роли и issuer source; прежнее описание сохраняется. Автоматического удаления volumes, сброса отзыва или смены корня нет.

Если native-повторы уже переданы ограниченному хостовому recovery-контроллеру, первоначальный запуск/обновление выполняется с `--native-restart-policy no`. Флаг применим к `server`, `agent` и `observation`; для последней команды выбираются три постоянные роли наблюдения, не одноразовые задачи. Наблюдаемый `no` также сохраняется при обычном повторе. Выбор записывается по ролям в собственный marker и переживает отсутствие контейнера; повтор без флага не возвращает `on-failure:3`. Старый установщик закрыто отклоняет расширенный marker. Эта команда не переносит и не обнуляет attempts, не снимает blocked/hold и не включает автоматическое восстановление: прежняя история и явное подключение точной новой инкарнации остаются у существующего контроллера.

## Передать уже одобренное первоначальное разрешение

На узле оператора вызовите `install.sh export-bootstrap PROJECT RUNTIME_IMAGE INSTALLER_IMAGE` либо эквивалентный `install.ps1` с тем же закрытым `request.json`, который уже получил `authorize`. Исходный каталог задаётся прежним `AELEV_INFRASTRUCTURE_SPIRE_INITIAL_INPUT`; приложение формирует запрос автоматически. Эта команда не выполняет `authorize` и не выдаёт новый token при отказе. Требуется установочный образ с `io.aelev.spire.bootstrap-export=1`; runtime и installer должны содержать одну ревизию исходников.

JSON-ответ содержит только точные узел/операцию/срок и ссылку `export_volume`, `export_directory=package`. Операторский результат остаётся в собственном Docker volume SPIRE. Защищённый установочный канал переносит только `plan.json`, `bundle.crt`, `join-token`, `receipt.json` в закрытый каталог целевого узла; это начальное полномочие, не файл для Git, stdout или общего доступа. Маркер `owner.json` остаётся технической защитой исходного volume и не требуется входу агента. Не монтируйте канонические server/operator volumes на целевой машине.

Целевой установщик вызывает `agent` с `--exported-bootstrap --bootstrap-operation <исходный UUID>` и этим каталогом как прежним первоначальным входом. В каталоге нужны права `0700`, у четырёх файлов — `0600`; права доставки из Windows проверяются внутри Linux Engine. После проверки целостности, исходного срока и области выполняется штатная установка и фактическая готовность агента. Срок 600 секунд начинается при первоначальной выдаче, не при экспорте или переносе; повтор его не продлевает. Если времени не осталось, новая авторизация требует отдельного решения владельца, а не обхода проверки. Передача уже экспортированного секрета не может быть отозвана удалением файла у получателя: доступ к workload всё равно ограничивает native entry SPIRE. Сквозной защищённый межмашинный канал относится к установщику потребителя, а не к этой команде экспорта.

## Подключить установленный SPIRE к общей композиции

Для существующей установки используйте публичный экспорт оператора с поддержкой `aelev_spire.composition`, а не вручную подставленные образы/тома или исходные значения по умолчанию. Команда выполняется из собственного каталога и не требует исходных полномочий CA/IdP/Grafana:

```sh
sh export.sh identity-server "$AELEV_INFRASTRUCTURE_SPIRE_INSTALLER_IMAGE"
```

В Windows:

```powershell
.\export.ps1 -Project identity-server -ExportOperatorImage $env:AELEV_INFRASTRUCTURE_SPIRE_INSTALLER_IMAGE
```

Экспорт автоматически создаёт поколение публичного Compose и его квитанцию в `runtime/installed-composition`, затем собственный `.env` с единственной ссылкой на поколение. Ручной `.env` или изменённый после начала операции файл не перезаписывается. Повтор при неизменной установке даёт тот же результат. Поколение содержит четыре постоянные роли, их точные разные образы, внешние тома/сети и остатки рестартов; ни одного закрытого ключа, токена, пароля, пакета первоначального подключения или задания регистрации в нём нет. Исходное операторское состояние и прежние защитные записи остаются в Docker volume.

Общий инфраструктурный Compose подключает `compose.group.yml` и автоматически читает собственный `.env` SPIRE. До начальной установки сохраняются канонические явно включаемые шаблоны; после экспорта выбрана только проверенная установленная композиция. Экспорт не выполняет `up`, не меняет работающий сервер и не закрывает отдельную проверку сохраняющего переключения. Не редактируйте сгенерированную композицию: исправьте собственную установку штатным оператором и повторите экспорт. Источники, происхождение, хранение и восстановление проекции определены в [SPEC](SPEC.md#публичная-композиция-установленного-провайдера).

После физического переноса продолжайте передавать установщику, экспорту и адресному восстановлению **прежний логический PROJECT**, а не имя общего Compose. Операторы сами проверяют физический проект по собственным runtime-меткам; marker, планы, регистрационные идентификаторы, имена томов и остатки попыток не переименовываются. Если остались две инкарнации роли или перенос выполнен только частично, команда закрыто откажет с `SPIRE_INSTALL_COORDINATOR_*` либо `SPIRE_COMPOSITION_COORDINATOR_MIXED`: сохраните состояние и завершите согласованный перенос, не создавая вторую установку под именем общего проекта. Новое runtime-обновление по-прежнему требует согласованной пары образов и прежних барьеров; выбор физического проекта не разрешает обновить остальные провайдеры.

## Регистрация и агент

Установщик потребителя формирует `request.json` по техническому контракту; человек не перечисляет приложение в исходниках SPIRE. `AELEV_INFRASTRUCTURE_SPIRE_INITIAL_INPUT` указывает только первоначальный защищённый каталог запроса. Операции выполняются на машине сервера теми же образами и проектом:

Потребитель может передать публичному оператору физический `--compose-project aelev_<читаемая_область>`, отдельный от логического `--project`; при первоначальном запуске он задаёт имя группы Compose, но не меняет имена томов, метки установки, регистрацию или SPIFFE identity. Если действующая инкарнация уже существует, её проверенное физическое имя сохраняется до отдельного пересоздания поверх прежних внешних томов. Для постоянного агента потребитель также может передать `--container-name aelev_<читаемый_владелец_и_роль>`. Оба имени допускают только строчные латинские буквы, цифры и `_`; имя контейнера не содержит UUID и не используется как удостоверение. Точные установка, регистрация и право владения по-прежнему сверяются по сохранённому плану, меткам и состоянию узла. Имя контейнера не разрешено SPIRE Server и одноразовым административным ролям.

```sh
sh install.sh authorize identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved
sh install.sh inspect identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved
```

Ответ содержит только фазу, UUID операции и место bootstrap в Docker, не token. Повтор использует тот же UUID и scope. На той же машине установка отдельного агента может непосредственно прочитать защищённый output volume сервера:

```sh
sh install.sh agent workload-agent aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved --bootstrap-volume identity-server_bootstrap-output --bootstrap-operation OPERATION_UUID --access-network identity-server-access
```

`OPERATION_UUID` — публичный UUID из сгенерированного запроса/ответа, не новый случайный идентификатор при каждом повторе. `--access-network` на этой же машине использует только помеченную сеть провайдера; запрос агента в таком случае содержит адрес `spire-server` и внутренний порт 8081. Чужая сеть запрещена. Это позволяет не создавать вторую подсеть для одной технической ячейки. На другом физическом компьютере утверждённый оператор доставки передаёт только соответствующий bootstrap-каталог через защищённый канал и задаёт его как первоначальный `AELEV_INFRASTRUCTURE_SPIRE_INITIAL_INPUT`; команда `agent` не требует `--bootstrap-volume`/`--access-network` и создаёт собственную сеть узла. Сам SPIRE не получает SSH-пароли и не выполняет произвольные команды на удалённой машине. Windows-вход поддерживает те же роли и параметры.

Первоначальный token действует 600 секунд. После успешной аттестации постоянный agent state обеспечивает штатное обновление; token не обновляется и не превращается в бессрочный пароль. Простой дольше срока agent SVID или утрата node state требуют новой явной авторизации владельца, а не автоматического возврата старого доступа. Нельзя удалять state, чтобы обходить отзыв.

SPIRE по умолчанию наследует TTL удостоверения узла от `--svid-ttl`: здесь нет неявного часового допуска. Для планируемого восстановления в пределах часа можно при первоначальной установке сервера явно выбрать `--agent-ttl 3600`, сохранив короткий TTL конечных удостоверений. Значение ограничено 300–3600 секунд (в test — 20–3600); отсутствие флага сохраняет прежнее значение. Это отдельный допуск владельца, не бессрочная аттестация или автоматический новый token. В восстановительном тесте workload TTL — 20 секунд, явно выбранный node TTL — 3600 секунд; восстановление проверяется до его истечения.

Конечный собственный volume `<agent-project>_svid` монтируется потребителем только для чтения. Файлы и правила проверки описаны в контракте. Перезапуск потребителя не требует выдачи нового права; обновлённый TLS-контекст применяется к новым соединениям без перезапуска модели.

## Отзыв

Для того же точного запроса:

```sh
sh install.sh revoke identity-server aelev/infrastructure-spire:approved aelev/infrastructure-spire-installer:approved
```

Отзыв устойчивый и идемпотентный. Последующий authorize того же намерения возвращает `SPIRE_OPERATOR_REVOKED`, не восстанавливает entry. При уже удалённой entry отзыв также завершается. Таймаут/недоступный сервер не трактуются как отсутствие регистрации. Удаление entry прекращает обновление, но не является мгновенным криптографическим отзывом ранее выданного сертификата; для немедленной изоляции применяются отдельные сетевые/авторизационные меры.

## Диагностика и восстановление

Для подключения прежней установки к общему восстановлению сначала сохраните полные остановленные журналы и собственное операторское состояние. Читающий `python -m aelev_spire.recovery_history --state EXACT_OWN_STATE --role sender` (аналогично `observer`) возвращает сумму попыток уникальных предшественников и хеш доказательства; рабочие тома в этом шаге доступны только для чтения. После проверки происхождения переносите историю через [точный хостовый импорт](../USER_MANUAL.md#сохранение-исчерпанной-истории-остановленного-предшественника), не обычную новую регистрацию нулевого Docker-счётчика. Для server/publisher прежний счётчик берётся из подтверждённых собственных записей и текущего Docker. Операторский start требует отдельного согласования; `auto-enable` после healthy сохраняет накопленные attempts и оставляет единственным исполнителем прежний контроллер. После перехода повторите штатный `export.sh`, чтобы общий Compose также сохранил `restart=no`.

Docker-проба читает только локальный heartbeat через `python -S`. Неготовая зависимость не маскируется падением живости; runtime сохраняет конкретные безопасные причины в `heartbeat.json`/`current.json`, native JSON-журнал — в собственном постоянном state. Ошибка процесса допускает максимум три native рестарта, ручная остановка не отменяется. Пробы издателя также читают только локальный heartbeat. Восстановление по Docker unhealthy, если оно требуется на площадке, регистрируется в существующей [ограниченной операторской задаче](../USER_MANUAL.md#ограниченное-восстановление-по-unhealthy), не новым циклом рестартов и не Docker socket в SPIRE.

| Код | Действие |
|---|---|
| `SPIRE_INSTALL_IMAGE_RELEASE_MISMATCH` | Выбрать согласованные runtime и installer одной ревизии |
| `SPIRE_INSTALL_FOREIGN_VOLUME_REFUSED` / `SPIRE_UNKNOWN_STATE_PRESERVED` | Остановиться и проверить владельца, не удалять чужие данные |
| `SPIRE_INSTALL_EXISTING_DEPLOYMENT_PRESERVED` | Проверить прежний план; другой scope не является обновлением |
| `SPIRE_OPERATOR_INITIAL_AUTHORIZATION_EXPIRED` | Получить новое явное начальное разрешение; повтор не продлевает старое |
| `SPIRE_OPERATOR_AMBIGUOUS_TOKEN_ISSUE` | Разобрать журнал и незавершённую выдачу, не создавать token автоматически |
| `SPIRE_OPERATOR_REVOKED` | Сохранить отказ; новое право требует отдельного разрешения |
| `SPIRE_INSTALL_READINESS_DEADLINE` | Проверить native журнал, доверие, маршрут и сроки; не объявлять установку успешной |
| `SPIRE_INSTALL_NETWORK_ADDRESS_POOL_EXHAUSTED` | На той же машине использовать разрешённую собственную access-сеть SPIRE; на другом узле исправить адресный план Docker. Чужие сети автоматически не удаляются |
| `SPIRE_INSTALL_HELPER_TIMEOUT` | Свой одноразовый helper ограниченно завершён; проверить точную фазу намерения, не повторять неоднозначную выдачу новым token |
| `SPIRE_INSTALL_HELPER_STATE_UNKNOWN` / `SPIRE_INSTALL_HELPER_OWNER_MISMATCH` | Проверить операторское состояние и точный helper через Docker; неизвестный/чужой контейнер автоматически не удаляется |
| `SPIRE_GRAFANA_HTTP_403` | Проверить отдельные первоначальные права API provisioning правил; не расширять права постоянного издателя или identity панели |

Резервирование server/node/operator state выполняется отдельным инструментом ниже после остановки их писателей и включает весь volume с WAL, ключами, запретами и историей. Копирование только открытого SQLite-файла не является backup. Конечный tmpfs не резервируется как долговечный ключ. Восстановление не снимает серверный отзыв. Аппаратный HA, независимые failure domains и измеренные RPO/RTO проверяются на конкретной площадке, не выводятся из локального restore.

## Подключить наблюдение

### Автоматическое сопровождение локальных сертификатов

Локальное наблюдение использует три независимых state-каталога оператора Telemetry Delivery: шесть телеметрических identity, `status-query` и `status-publisher`. Не объединяйте query CA SPIRE и publisher CA Platform UI в одном approval. Каждый state устанавливает собственный минутный LaunchAgent, доставляет публичную квитанцию в volume `certificate-renewal-status` под отдельным именем и проходит `renewal.py check --max-age 180`. Готовность требует `status.json`, `status-query.json` и `status-publisher.json`; удаление любого файла, отрицательный отчёт либо срок менее 30 дней переводят `/readyz` и компонент состояния в отрицательное состояние, не завершая живой процесс.

Перед сменой локального CA сначала подготовьте новое поколение owner-оператором, затем добавьте старый и новый публичные корни во все точные trust bundles. Только после этого выполняйте `once --force` и проверяйте новое mTLS-соединение. Старый root не удаляется автоматикой. Для query/server/write используется `python -m aelev_spire.authority_rotation prepare|stage-trust`; publisher CA готовит и активирует владелец Platform UI через `publisher_authority.py prepare|stage`. В production эти команды закрыто запрещены: нужен внешний issuer с KMS/HSM/Vault.

После установки проверьте три независимых deployment gate, `GET /readyz`, восемь серий `aelev_spire_certificate_expires_at`/`aelev_spire_certificate_ca_expires_at`, `aelev_spire_certificate_renewal_ready 1` и свежую публикацию состояния `ONLINE`. Docker health означает только живость и не заменяет эти проверки. Compose/config до rollout сохраняются в owner installer/config volumes; журналы и история renewal state не удаляются при откате.

Используется прежняя система DRP: собственный Prometheus и устойчивый sender → центральный delivery → Prometheus/Loki/Tempo; панель и правило тревоги публикуются в существующую Grafana. Собственная строка Platform UI имеет компоненты сервера, наблюдателя, доставки и издателя. Никакого отдельного SMTP или уведомителя SPIRE нет. Если в Grafana пока заглушка вместо SMTP, правило видно и срабатывает там, но доставку письма нельзя считать проверенной.

Владелец среды один раз доставляет начальные полномочия в собственный закрытый каталог `AELEV_INFRASTRUCTURE_SPIRE_INITIAL_INPUT`. Это не конечный `.env`: установщик сам формирует конфигурацию, Docker volumes, адреса и команды. Входы выдаются утверждёнными операторами PKI/IdP/Grafana, не копируются из соседнего сервиса. Файлы секретов имеют права 0600, каталог — 0700. Он содержит только следующие отдельные наборы:

| Подкаталог | Файлы и назначение |
|---|---|
| `observer` | `metrics.crt/key` с SAN `spire-observer`; `query-ca.crt` для чтения; `observer.crt/key` для записи в местный sender; `sender-ca.crt` |
| `sender` | `sender.crt/key` с SAN `localhost`, `spire-telemetry-sender`; `server-ca.crt` для собственных серверов; `local-write-ca.crt`, `local-write.crt/key`; `central-ca.crt`, `central-write.crt/key`; `local-query.crt/key` и `local-query-ca.crt` — bundle доверия чтения и серверного сертификата собственной диагностики |
| `status` | `publisher.crt/key`, `shell-ca.crt`, `identity-ca.crt`; собственные `query-ca.crt`, `query.crt/key` только для чтения наблюдателя и диагностики sender |
| `status-admin` | `admin-user`, `admin-password` только одноразовой подготовки OIDC-клиента |
| `grafana` | `grafana-ca.crt` и `token` ограниченной identity публикации панели в собственной папке `infrastructure-spire`, без административных прав |
| `grafana-admin` | `grafana-ca.crt` и временный `token` первоначального оператора с правом API provisioning правил Grafana; только отдельная одноразовая задача фиксированного собственного правила, не постоянный runtime |

Собственные области `clientAuth` записи/чтения и `serverAuth` не взаимозаменяемы. CA для endpoint сервера/observer и CA клиента sender согласуются по таблице, проверка TLS не отключается. Исходная папка Grafana и ограниченный токен поступают через [операторский вход провайдера](../observability/grafana/USER_MANUAL.md#6-отдельная-учётная-запись-для-публикации); конечный runtime токена Grafana не получает. Внешняя PKI ротации этих технических identities и trust anchors остаётся входом площадки; этот первоначальный набор не является бессрочным секретом или выдачей production root в SPIRE.

Публичный sender использует `health_ca` и для допуска клиентского сертификата чтения, и для проверки серверного сертификата своей CLI-пробой. Поэтому `local-query-ca.crt` должен содержать обе соответствующие цепочки. При раздельной локальной PKI в этот bundle входят собственные CA чтения и серверов; CA записи туда не добавляется, а серверная CA выпускает только `serverAuth`. В `observer/query-ca.crt` остаётся только доверие к клиентам чтения. Подмена этого набора общей CA записи нарушает разделение полномочий.

После успешной установки сервера выполните из каталога SPIRE, подставив первоначальные публичные адреса и утверждённые образы, а не редактируя `.env`:

```sh
sh install.sh observation identity-server "$AELEV_INFRASTRUCTURE_SPIRE_IMAGE" "$AELEV_INFRASTRUCTURE_SPIRE_INSTALLER_IMAGE" \
  --sender-image "$AELEV_INFRASTRUCTURE_SPIRE_SENDER_IMAGE" \
  --central-url "$AELEV_INFRASTRUCTURE_SPIRE_CENTRAL_URL" \
  --ui-url "$AELEV_INFRASTRUCTURE_SPIRE_UI_URL" \
  --identity-url "$AELEV_INFRASTRUCTURE_SPIRE_UI_IDENTITY_URL" \
  --realm "$AELEV_INFRASTRUCTURE_SPIRE_UI_REALM" \
  --publisher-client-id "$AELEV_INFRASTRUCTURE_SPIRE_UI_CLIENT_ID" \
  --grafana-url "$AELEV_INFRASTRUCTURE_SPIRE_GRAFANA_URL" \
  --datasource-uid "$AELEV_INFRASTRUCTURE_SPIRE_DATASOURCE_UID"
```

Все переменные в этой команде — первоначальные входы владельца. В production образы закреплены digest. Для заранее назначенного UUID есть `--module-id`; иначе он устойчиво выводится из собственного имени установки. Машинный установщик потребителя может вместо флагов передать `observation.json` с полями `owner`, `schema_version`, `sender_image`, `central_url`, `grafana_url`, `datasource_uid` и `presentation` (`url`, `identity_url`, `realm`, `client_id`, `audience`, `module_id`). Это один формат исходного плана, не ручной второй `.env`.

Для локального Docker-стенда необязательный `host_gateway_aliases` в первоначальном `observation.json` содержит до четырёх разных DNS-имён уже объявленных внешних endpoint. Установщик сохраняет явные `extra_hosts`: Linux использует `host-gateway`, macOS/Windows — подтверждённый IPv4 `host.docker.internal` внутри Docker Desktop. Например, это позволяет обратиться по имени из SAN сертификата к опубликованному порту провайдера на хосте, не подключая его контейнер к новой сети. Произвольные имена, собственные внутренние имена SPIRE и `localhost` запрещены. В production этот механизм отклоняется; там нужны действительные маршрутизация и DNS. URL, CA и проверка SAN остаются прежними. Настройка не выполняется ручным `docker network connect` и переживает повтор установки.

Общий Python-оператор Shell/PowerShell при объявленных Desktop aliases разрешает фиксированное имя отдельным непривилегированным read-only helper без socket, секретов и host mounts. После проверки единственного private IPv4 оператор с `network=none` сохраняет адрес в `extra_hosts` собственных runtime-рецептов; вручную задавать gateway IP или менять `/etc/hosts` машины не требуется. Отказ разрешения имеет код `SPIRE_OBSERVATION_DESKTOP_HOST_UNAVAILABLE` и не разрешает другую сеть привилегированному оператору. Установка без aliases не требует Desktop resolver.

Одноразовая подготовка OIDC имеет собственный предел 30 секунд на административный HTTP-запрос: проверка пароля и запись настроек IdP не являются лёгкой health-пробой. Установщик дополнительно ограничивает свою Docker-операцию; неоднозначный результат не очищает состояние. Рабочий издатель сохраняет предел 2 секунды, а Docker-пробы — прежние интервалы и таймауты. Увеличение административного бюджета не выдаёт рабочему процессу пароль администратора.

Команда сохраняет собственные итоговые файлы в именованных Docker volumes, готовит OIDC и публикует панель/правило отдельными задачами, затем ждёт healthy собственных ролей. Повтор той же команды без флагов читает собственное сохранённое состояние; первоначальный каталог больше не обязателен. Утраченный собственный постоянный том даёт `SPIRE_INSTALL_STATE_RESTORE_REQUIRED`, а не новую последовательность публикации. Другие провайдеры и рабочие сертификаты потребителей команда не обновляет. Остановка собственной наблюдаемости не останавливает выдачу SVID.

После подтверждённой первоначальной подготовки сохраняется квитанция её ревизии; обычный повтор не требует заново использовать временные административные tokens. Явное обновление получает новую ревизию и требует действующих полномочий первоначальной подготовки. Ограниченная identity панели не получает глобальные права управления правилами Grafana. Контакты и политика уведомлений не создаются и не изменяются этой поставкой.

Для согласованного переноса технических адресов или ротации собственных конечных удостоверений повторите команду с `--update` и новым первоначальным набором. UUID модуля, realm, client ID и audience сохраняются; смена этого scope отвергается. Конфигурация обновляется оператором, собственные роли наблюдения адресно пересоздаются по новой непрозрачной ревизии без удаления журналов; секретные хеши не становятся Docker labels. Сам SPIRE Server и его регистрации не перезапускаются этой командой. Обычный повтор без `--update` не заменяет отличающиеся файлы. Это управляемая доставка собственных технических identities, не автоматическое продление внешнего issuer/root вместо PKI площадки.

Итоговая наблюдаемая модель хранится в `<project>_installer` как `observation-compose.json`; нативная — как `compose.json`. Это производные канонических рецептов данной поставки. Редактировать их вручную или запускать второй Compose над теми же данными нельзя. `compose.observation.yml` также включается корнем инфраструктуры как собственный дополнительный рецепт; профили `spire-observation`/`spire-observation-provision` не включаются обычным `ui` и требуют подготовленных входов владельца. Оба способа управления нельзя одновременно применять к одному набору volumes.

### Адресно восстановить исчерпанный sender

Эта отдельная операция не запускает `observation --update`, не повторяет SSO/Grafana provision и не пересоздаёт остальные роли. Сначала сверяют точный остановленный container ID, `RestartCount=3`, владельца и собственные mounts; сохраняют полный остановленный каталог `/var/lib/delivery`, включая Prometheus/WAL, в закрытое независимое хранение. `test/check_sender_snapshot.py` внутри выбранного sender-образа открывает только изолированный дубль копии и проверяет SQLite, неизменяемые записи и счётчики. Контрольная сумма полной копии фиксируется в операторском намерении; она не заменяет само хранение и проверку копии.

Одноразовый операторский контейнер из стадии `operator-installer` получает только Docker socket и собственный volume `<project>_installer`; runtime его не получает. Выполняется `python -m aelev_spire.sender_recovery --project <project> --daemon-id <точный-ID-daemon> --expected-container <прежний-полный-ID> --image <собственный-sender@sha256:digest> --backup-sha256 <хеш-проверенной-полной-копии>`. Требуется явное согласование этого восстановления. Docker должен уже содержать выбранный образ; автоматического выбора mutable tag нет.

Оператор сохраняет прежний Compose в `sender-before-<container-ID>.json`, фиксирует `sender-recovery.json` до воздействия и выполняет `up --no-deps` только для sender. Политика замены — `restart=no`: прежние три попытки остаются в устойчивом намерении, не становятся новым бюджетом. Повтор после потери ответа лишь подтверждает точную здоровую замену. При её новой остановке нужен разбор и отдельное решение, а не повторный старт тем же намерением. Обычная новая компиляция наблюдения сохраняет выбранный sender и `restart=no` из этой записи. Отсутствующая прежняя диагностика не восстанавливается задним числом; новые конкретные коды сохраняются штатным sender в его журнале.

Для отдельно согласованного дальнейшего обновления только sender сначала штатно остановите ровно этот собственный контейнер и проверьте свежую полную копию. Тот же CLI с `--update` требует его точный ID и завершённое прежнее намерение, архивирует предшественника и сохраняет исходные три израсходованные попытки. Для sender 1.0.4 добавляется `--local-liveness`: проба в производном Compose становится `python -S /opt/aelev/delivery_health.py`, а не mTLS-опросом. Прежний выпуск без этого файла сохраняет прежнюю пробу. Это не разрешение на обычный повтор старта после нового отказа и не обновление остальных ролей.

После восстановления marker собственного volume установщика содержит `sender_recovery_schema=1`. Установщики до этой версии отклоняются с `SPIRE_STATE_OWNER_MISMATCH` до изменения Compose: это защита исчерпанного бюджета, не потерянная identity. Не удаляйте поле или журнал для обхода проверки. Используйте согласованный оператор с поддержкой нового marker; последующее обычное обновление Server по-прежнему требует согласования и проверки единого выпуска, а адресный CLI sender не меняет работающий Server.

### Адресно восстановить исчерпанный observer

`SPIRE_OBSERVATION_WORKER_STALLED` означает отсутствие завершённых подшагов, не длительность всей доставки двух пакетов. Свежая диагностическая фаза не равна свежему прогрессу; отчёт сохраняет наблюдавшийся отказ, но сам по себе не доказывает, что процесс затем завершился: supervisor повторяет проверку после записи. Текущее состояние подтверждайте собственной heartbeat-пробой, готовность — отдельным mTLS-запросом. Пакеты удаляются только после прежней точной устойчивой квитанции, не по отметке прогресса.

Используйте тот же отдельный операторский `python -m aelev_spire.sender_recovery`, добавив `--role observer`. Остальные обязательные входы прежние: точные project/daemon/full container ID, закреплённый runtime и SHA-256 полной проверенной остановленной копии. Архивируйте собственные `observation` и `installation` штатным зашифрованным backup и подтвердите восстановление всех файлов в отдельный пустой каталог. Не передавайте `--local-liveness`: собственная лёгкая проба observer сохраняется без замены. Никакого `observation --update`, SSO/Grafana provision или обновления server/sender эта операция не выполняет.

Исчерпанные три попытки сохраняются в `observer-recovery.json`, исходный рецепт — в `observer-before-<old_id>.json`; `restart=no` переносится в последующие компиляции. Marker `observer_recovery_schema=1` в собственном installer-state закрывает несовместимый старый установщик. Используйте согласованный операторский выпуск, поддерживающий оба recovery-marker. Потерянный ответ согласуется по единственной новой инкарнации, не по повторному старту; её новая остановка требует отдельного решения.

При следующем `SPIRE_OBSERVATION_WORKER_STALLED` либо `SPIRE_OBSERVATION_WORKER_STOPPED` сначала сохраните собственные `diagnostics/*.json` и полный stdout/stderr. Отчёт содержит только позиции потоков и безопасную фазу; он не подтверждает причину прежнего отказа, для которого таких данных не было. Подтвердите отдельно свежие `/readyz` и метрики по mTLS, уменьшение своей очереди и принятый heartbeat publisher. [Фактическое восстановление и границы вывода](test/observer-context-20261022.md) отделены от обещания отсутствия будущих отказов.

## Снять и проверить резервную копию

Инструмент находится в том же runtime-образе: `python -m aelev_spire.backup`. Он не получает Docker socket и не останавливает чужие контейнеры. Планировщик площадки сначала штатно останавливает только писателей выбранной установки и сохраняет их прежнее состояние; при использовании bounded recovery сначала приостанавливает зарегистрированные цели. Сам backup проверяет файловые блокировки и возвращает `SPIRE_BACKUP_WRITER_ACTIVE`, если писатель ещё работает. Ручная остановка не превращается в автоматическое включение.

В `/recovery/<role>` монтируются точные собственные volumes. Для сервера сохраните `server`, `operator`, `configuration`, `installation` и, если были регистрации, `bootstrap-output`; отдельно для каждого узла — `agent` и его `configuration`. Если подключено наблюдение, дополнительно сохраните `status`, `observation`, `telemetry`, `observation-configuration`, `observer-secrets`, `sender-secrets`, `status-secrets`, `status-admin`, `grafana-secrets`, `grafana-admin`; эти роли также поддерживаются инструментом и защищены шифрованием. Нельзя сохранять только БД без node/issuer state и журнала операторских запретов. Временные `admin`, `svid`, `observation-source` не являются резервной копией.

Первоначальный 32-байтовый криптографически случайный ключ резервирования выдаёт оператор защищённого хранения. Он не попадает в runtime SPIRE, Git, env, образ, имя команды или журнал. Смонтируйте его отдельным файлом 0600 `/backup-key/key`; каталог `/backup-output` принадлежит оператору. После подключения точных собственных volumes команда внутри отдельного контейнера:

```sh
python -m aelev_spire.backup create --role server --role operator --role configuration --role installation --role bootstrap-output \
  --archive /backup-output/spire.enc --key /backup-key/key
```

Получаются зашифрованный `spire.enc` и `spire.enc.receipt.json`. Существующий файл не перезаписывается. Сохраните архив независимо от исходного host; последнюю утверждённую квитанцию и ключ — отдельно защищённым способом. Предел одного архива — 2 ГиБ и 100000 файлов; превышение завершает операцию без успешной квитанции. Исходный `.env` не является резервной копией.

Для восстановления подключите **пустые собственные** целевые volumes с теми же логическими ролями, сохранённый архив/ключ и независимо полученную последнюю квитанцию. UID/GID целевого `installation` — `0:0`: установщик работает от root и пишет private state только как его владелец; `DAC_READ_SEARCH` позволяет читать явно подключённые read-only host inputs другого UID, но не даёт обхода прав записи. Остальные roots подготавливаются под собственных runtime-писателей `10001:10001`, с mode `0700`. Restore запускается отдельной offline-операторской задачей от root с `CHOWN` и `DAC_OVERRIDE`, без сети и Docker socket; создаваемые файлы и вложенные каталоги получают UID/GID соответствующего целевого root. Постоянные runtime-роли по-прежнему имеют UID 10001 и нулевые capabilities. Неверный владелец `installation` отклоняется до записи, формат существующих архивов не меняется. Пример команды внутри операторского контейнера:

```sh
python -m aelev_spire.backup restore --role server --role operator --role configuration --role installation --role bootstrap-output \
  --archive /backup-input/spire.enc --key /backup-key/key \
  --trusted-receipt /trusted-receipt/spire.enc.receipt.json
```

Состав `--role` должен совпадать с квитанцией. Проверяются весь зашифрованный архив и все хеши **до** записи целевых файлов. Непустая цель отвергается; инструмент не удаляет прежние данные. Прерванная запись оставляет `.restore-incomplete`; не удаляйте этот барьер вручную, сохраните неудачную цель для разбора и повторите на новом пустом наборе. После восстановления сравните identity среды, цепочку доверия, состояния регистраций/отзывов, UUID/последовательности и задолженность наблюдения, затем выполните ограниченную выдачу/отзыв в изоляции. Только после этой сверки открывается рабочий сетевой доступ.

Старый корректный архив не знает об отзывах после его создания. Если актуальность квитанции или последующие отзывы неизвестны, запуск выдачи запрещён до сверки с независимым операторским журналом. Восстановление не создаёт новый bootstrap и не отменяет `REVOKED`. Ключ внешнего root/KMS не резервируется этой утилитой; внешний issuer возвращается собственным механизмом PKI владельца.

## Проверки

```sh
poetry install
poetry run ruff check .
poetry run ruff format --check .
poetry run pyright
poetry run pytest
```

Модульный набор также поставляется отдельной стадией того же Dockerfile, без установки Python на хост:

```sh
docker build --target checks -t aelev/infrastructure-spire-checks:approved .
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true \
  --tmpfs /tmp:size=32m,mode=1777 --memory 512m aelev/infrastructure-spire-checks:approved
```

Реальные Docker-проверки включаются только явными `AELEV_INFRASTRUCTURE_SPIRE_TEST_IMAGE` и для установщика `AELEV_INFRASTRUCTURE_SPIRE_INSTALLER_TEST_IMAGE`. Наблюдение дополнительно требует `AELEV_INFRASTRUCTURE_SPIRE_SENDER_TEST_IMAGE`, проверка Grafana — `AELEV_INFRASTRUCTURE_SPIRE_GRAFANA_TEST_IMAGE`. Это выбранные утверждённые образы, а не команда обновить рабочие контейнеры. Нативные проверки запускаются из операторского окружения с Docker-доступом, не из runtime или из изолированной стадии `checks`. Они создают уникальные тестовые проекты, проверяют выдачу/ротацию/отзыв/повтор и удаляют только свои ресурсы после сверки владельца. [Отчёт](test/lifecycle-20261020.md) отделяет фактические результаты от невыполненных внешних проверок. Ни одна из этих команд не переключает рабочий стенд.
