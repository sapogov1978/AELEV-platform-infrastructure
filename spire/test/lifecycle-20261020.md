# SPIRE: проверка от 20 октября 2026

## Область

Новая поставка по ADR-0154 проверяется на Apple Silicon с Linux ARM64 в Docker Desktop. Закреплён официальный SPIRE 1.15.4, Python 3.13.7 / Debian Bookworm; SHA-256 архивов ARM64/AMD64 находятся в `artifacts.lock.json`. Рабочие PostgreSQL, очереди, сертификаты и остальные поставки не переключались. Результаты — датированный снимок, не текущая проверка рабочего стенда.

Итог — `PRODUCTION_READY` для поддерживаемого одноузлового профиля: собственные 38 модульных и четыре настоящих интеграционных сценария прошли. Допуск внешней площадки не заменяется этим статусом; её непроверенные условия перечислены ниже.

## Подтверждено

- Собраны отдельные runtime и operator-installer; последний содержит закреплённые Docker CLI/Compose и является единственным компонентом с операторским Docker-доступом.
- Полный нативный жизненный цикл: настоящий SPIRE Server, два отдельных агента, разные SVID, обновление обоих серийных номеров, отзыв только первой регистрации, отрицательная доставка и запрет её повторной авторизации; второй агент сохранил готовность и восстановил удостоверение узла после перезапуска. Один сценарий прошёл за 188,65 секунды. Тестовые контейнеры, тома и сеть удалены по точным собственным меткам.
- Нативный сервер фактически использует SQLite 3.53.4. Обнаруженное зависание инициализации с единственным SQL-соединением устранено ограниченным пулом 4/2; рабочий PostgreSQL к этой проблеме не относился.
- Повторный расширенный нативный прогон прошёл оба сценария за 688,01 секунды: полный жизненный цикл двух агентов с зашифрованным резервированием и возвратом в новые тома; отдельный настоящий sender/Prometheus с разрывом доставки и последующим восстановлением. После возврата сервера прежний отзыв сохранился, оставшийся агент вернул прежнее удостоверение узла без новой авторизации. Ускоренный TTL конечного удостоверения равен 20 секундам, TTL узла явно задан 3600 секунд; срок не увеличивается неявно в рабочем профиле.
- Настоящие метрики, журналы и трассы OTLP дошли в изолированный центральный архив существующего delivery. При его остановке собственный журнал отправителя удержал задолженность; после перезапуска отправителя и возвращения приёмника число архивных пакетов увеличилось. Prometheus проверил конфигурацию и собственные правила через штатный `promtool`. Это проверка устойчивой доставки, не внешних Loki/Tempo или SMTP.
- Настоящая Grafana 12.1 прошла отдельный сценарий за 40,94 секунды: создание и повтор панели ограниченной identity, создание и повтор собственного правила отдельной одноразовой административной identity. Попытка административного действия токеном панели получила 403. Приложение проверялось через изолированный loopback HTTP; TLS-контекст клиента и настоящий loopback mTLS проверены отдельно. Внешние HTTPS/IdP и отправка уведомлений площадки этим не подтверждаются.
- Модульные проверки: атомарное поколение, частичная запись, чужой volume/identity, сохранение точного намерения, потеря подтверждения создания entry, неясная выдача token, необратимость отзыва, разделение NotFound и таймаута, внешний issuer и запрет production root key.
- В Advance прошли 23 проверки собственных SPIRE/mTLS/регистрационных сценариев: реальный TLS на loopback, exact URI, среда/свежесть/хеши, стабильные UUID запросов, горячая смена сертификата, запрет новых соединений при отрицательном состоянии и ожидание первоначального SVID без рестарта процесса. Сертификаты этого TLS-теста синтетические, модель не запускалась; это не совместный сетевой прогон двух физических машин.
- Backend Advance: 340 passed, 70 skipped. В локальном dev-прогоне путь контрактного пакета переназначен с контейнерного `/opt/aelev/contracts` на собственные поставляемые `contracts`; валидация схем не отключалась. Пропуски требуют отдельных PostgreSQL/Kafka/нагрузочных профилей. Повторно прошли 44 проверки инфраструктурной оркестрации и ограниченного восстановления, один явный Docker fault-профиль не включался; корневой Compose `--profile ui config --quiet` прошёл. Полный набор инфраструктурных инструментов не запускался из окружения SPIRE: он не содержит Black из отдельного `test_infrastructure/poetry.lock`; эта проверка не заменяет регрессии остальных продуктов.

## Проверка установщика

Полный повтор Shell-сценария прошёл за 725,90 секунды: установка/повтор сервера без пересоздания, точная регистрация/повтор, установка/повтор агента в собственной сети провайдера, устойчивый отзыв и запрет повторного `authorize`. Тестовые ресурсы сняты после сверки собственных меток. До этого Docker-проба обнаружила затенение стандартного модуля `operator` соседним прикладным модулем при запуске файла: добавлен `python -S -P`, отдельная регрессия и обязательная проверка фактического Docker healthcheck перед успехом установщика.

Окончательная пара `ready-20261020` прошла тот же полный сценарий повторно за 882,78 секунды. Проверены согласованный выпуск установщика/runtime, положительная готовность до успеха команды, повтор агента и окончательный запрет возврата отзыва. Все контейнеры, тома и сеть этого сценария удалены по собственным меткам; рабочие поставки не пересоздавались.

Во время заключительного прогона несколько лёгких Docker-проб агента превысили предел 3 секунды, затем проба снова завершилась успешно; это отражено в Docker health history, не скрыто увеличением таймаута. При завершении нагрузка хоста `vm.loadavg` составляла 16,88/16,95/17,24. Успешный функциональный сценарий не доказывает гарантированную задержку проб на перегруженном узле; запас ресурсов и длительная нагрузка проверяются при допуске площадки.

Причина отказа создания агента установлена отдельной сетевой проверкой: при 37 Docker-сетях одна новая стандартная подсеть создавалась, следующая получала `all predefined address pools have been fully subnetted`. Обе временные проверочные сети удалены после сверки собственных меток; чужие сети не удалялись. Добавлен точный код `SPIRE_INSTALL_NETWORK_ADDRESS_POOL_EXHAUSTED` и явный `--access-network` только для помеченной сети этого провайдера. Агент на той же машине не требует второй подсети; удалённая установка сохраняет собственную сеть. Это исправление адресного размещения, не ослабление mTLS или выдача новых прав.

## Артефакты проверки

Локальные теги обозначают только датированные испытательные сборки, не опубликованный или подписанный production-выпуск. Установщик сверяет отпечаток исходников и native lock своего образа с выбранным runtime; совпадения изменяемого тега недостаточно.

После нативной сборки добавлены только первоначальная проверка TTL/порта/адреса до сохранения конфигурации и получение выбранного отсутствующего образа sender. Первая дополнительно проверена модульно; используемый в нативном прогоне sender уже присутствовал локально, загрузка из удалённого реестра образов этим не проверяется. Механизм нативной выдачи, отзыва, резервирования и доставки между этими сборками не менялся. Отдельный окончательный Docker `checks` прошёл 38 тестов за 9,57 секунды без внешней сети и рабочих подключённых томов; четыре нативных сценария намеренно не запускаются внутри этой стадии. Ruff, форматирование, строгий Pyright, Poetry lock и синтаксис Shell прошли.

## Неподтверждённые границы

38 модульных/loopback проверок прошли; четыре нативных сценария по умолчанию требуют явных образов и выполняются отдельно. Покрыты точная квитанция доставки, сохранение задолженности, устаревание проекции, разделение живости/готовности, чужие полномочия Grafana, занятый писатель и повреждённая резервная копия, проверка первоначального плана до записи состояния. Обработка Windows-пути issuer проверена модульно через подтверждённый mount собственного контейнера; настоящего PowerShell на этом Mac нет. Внешние issuer/KMS/HSM, подписанный admission, аппаратные области отказа, длительное отключение сверх TTL, Windows/PowerShell, исполнение Linux AMD64 и два физических компьютера не испытаны. Shell прошёл синтаксическую проверку. Незавершённый общий установщик потребителя не является частью ответственности SPIRE. Испытания не дают модели или LoRA новый допуск и не включают обработку сайтов.

Начальные полномочия PKI/IdP/Grafana принадлежат владельцам инфраструктуры. Собственный OIDC-оператор использует неизменяемый публичный клиент Platform UI; отдельная новая копия настоящего Keycloak этим прогоном не поднималась. Проверки конкретной площадки выполняются до её допуска по ADR-0017, а не подменяются результатами локального профиля.
