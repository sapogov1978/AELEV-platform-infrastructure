# Kafka — руководство пользователя

## Структура поставки

```text
kafka/
├── README.md, SPEC.md, TASKS.md, CHANGELOG.md
├── compose.yml                   # брокер, собственный издатель и его provision
├── .env.example                  # шаблон; .env — рабочие настройки вне Git
├── Dockerfile.status             # собственный образ издателя и проверок
├── pyproject.toml, poetry.lock   # зависимости технической роли
├── status_publisher.py           # нативная проба и публикация состояния
├── vendor/                       # закреплённый публичный транспортный wheel
├── secrets/                      # доставляется отдельно, вне Git/образа
│   ├── status/                   # TLS, доверие UI/IdP, client-secret
│   └── status-admin/             # реквизиты только одноразового provision
└── test/                         # проверки и читаемые результаты
```

Дерево показывает значимые файлы поставки, а не кэши инструментов. `.env`, содержимое `secrets/` и производные `runtime/` создаются оператором и не входят в Git или образ; документация `secrets/README.md`, где она есть, остаётся в Git. Постоянные данные находятся в именованных Docker volumes из Compose, не в каталоге исходников.

## Назначение


Самостоятельный одноузловой инфраструктурный Kafka для локального профиля. Компонент запускает и настраивает только broker/controller, не содержит каталога прикладных topics, не читает межсервисные контракты и не знает потребителей. Автоматическое создание topics отключено.

Собственный издатель имеет `stop_grace_period: 2m`: это время на завершение текущего запроса и подтверждение отписки через удалённый HTTPS, не запасное значение env и не бесконечное ожидание. Если связь недоступна, неподтверждённый выход сохраняется в журнале, а UI не скрывает строку как штатно завершённую.

В «Состоянии» верхняя строка называется «Межсервисное взаимодействие» (`Inter-service communication`) и отражает назначение, а раскрываемый состав показывает технологии и процессы этой поставки. Названия публикует сам владелец в ревизии 2; оболочка не содержит таблицы переименований. UUID, identity, состав и последовательность сохраняются.

## Секреты: получение и подготовка

Сам брокер в текущем одноузловом PLAINTEXT-рецепте не читает паролей, TLS-ключей или ACL-секретов. Это не означает защищённый доступ: данная поставка ограничена локальным профилем. Не создавайте фиктивные Kafka TLS-файлы и не открывайте текущий listener в интернет; защищённый удалённый broker требует отдельного реализованного рецепта. Следующий материал нужен только собственной UI-роли.

### Секреты издателя состояния

Пути ниже соответствуют шаблону `UI_SECRET_ROOT=./secrets/status`; при другом значении используйте собственный настроенный каталог. Источники доверия определяются адресами, не совместным размещением: узел в другой стране получает публичные цепочки CA и своё удостоверение через защищённую доставку, а не доступ к чужой папке.

| Файл | Откуда получить и зачем |
|---|---|
| `shell-ca.crt` | Проверенная публичная цепочка CA HTTPS-сервера оболочки; получить у её оператора. Это не CA клиентских издателей. |
| `identity-ca.crt` | Проверенная публичная цепочка CA HTTPS IdP; получить у оператора IdP. |
| `publisher.crt`, `publisher.key` | Собственное удостоверение `clientAuth`; его выпускающая CA должна входить в `publisher-ca.crt` приёмника UI. Закрытый ключ принадлежит только этому издателю. |
| `client-secret` | Выдаёт Keycloak для собственного confidential client; сохраняет `kafka-status-provision`. Не генерируйте произвольный пароль вместо секрета существующего OIDC-клиента. |

`UI_ADMIN_ROOT` содержит отдельные `admin-user` и `admin-password`: имя и действующий пароль администратора развёртывания Keycloak получают у оператора IdP или из внешнего хранилища. Это не пароль service account и не пароль пользователя браузера. Доставьте их файловым механизмом; например, `install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password`, а имя запишите в `admin-user` без секрета. Provision должен иметь право записи в `UI_SECRET_ROOT`, runtime — только чтение.

Перед локальной подписью проверьте `openssl version` и поддержку OpenSSL 3; при отсутствии используйте утверждённый пакет вашей ОС (`brew install openssl@3` на macOS, `sudo apt-get install openssl` на поддерживаемой Debian/Ubuntu) или подготовленную операторскую станцию. Эти команды не устанавливают CA в системное доверие и не выполняются при запуске контейнера.

Первичная доставка административных файлов (пути источника и имя замените данными своего IdP, не пароль в команде):

```sh
umask 077
install -d -m 750 secrets/status-admin
test ! -e secrets/status-admin/admin-user && test ! -e secrets/status-admin/admin-password || exit 1
STATUS_ADMIN_USER=deployment-admin
printf '%s\n' "$STATUS_ADMIN_USER" > secrets/status-admin/admin-user
install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password
chmod 640 secrets/status-admin/admin-user
```

Имя deployment-admin — пример существующей identity, не команда создания пользователя. Если у вас другое имя или UI_ADMIN_ROOT, задайте их явно; GID каталога/файлов должен совпадать с UI_SECRET_GID, а владелец — с UI_PROVISION_UID. Уже доставленные пароли не перезаписываются первичной командой. После удаления одноразового контейнера пароль не нужен рабочему издателю; локальную административную доставку уберите из runtime-узла или выдавайте заново только на время provision.


Для новой локальной identity можно создать ключ и CSR на доверенной операторской машине. Нужен OpenSSL 3 для `-copy_extensions`; пути `/secure/...` ниже заменяются выбранными операторскими файлами, это не обязательные каталоги сервиса. Публичные CA берутся из проверенного источника; неизвестный сертификат из сети не становится доверенным только потому, что назван `ca.crt`.

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/publisher.key && test ! -e secrets/status/publisher.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=publisher -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/publisher.key -out secrets/status/publisher.csr
# Только локальный тест: ключ CA остаётся на операторской машине, не в runtime.
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/publisher.csr \
  -CA /secure/ui-publisher-ca.crt -CAkey /secure/ui-publisher-ca.key \
  -CAcreateserial -out secrets/status/publisher.crt
install -m 640 /secure/ui-server-ca.crt secrets/status/shell-ca.crt
install -m 640 /secure/idp-ca.crt secrets/status/identity-ca.crt
chmod 640 secrets/status/publisher.key secrets/status/publisher.crt
```

Тестовую CA издателей создаёт оператор локальной оболочки при её явной подготовке PKI; берутся именно `issuer/publisher.crt/key`, не серверный ключ UI. В рабочей среде последнее подписание локальной CA не выполняют: удостоверение и обновляемую identity доставляет утверждённая PKI/SPIRE по [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md). CSR можно передать CA, закрытый ключ нельзя. Перед включением издателя доставьте также перечисленные файлы нативных проб и выполните собственный `--profile provision run --rm kafka-status-provision` из раздела запуска.

### Хранение, доступ и ротация

Секреты разделяются по среде, владельцу и роли. Локальные файлы — только материал стенда или доставка, не каноническое production-хранилище; рабочий источник — внешнее утверждённое хранилище, доставка в память/tmpfs по 00-INFRA-20261106-0007-workload-and-operator-identity. Не включайте секреты в Git, образ, архив исходников, команды с подстановкой содержимого или отчёты. Не запускайте `set -x`, не публикуйте раскрытый `docker compose config`; проверяйте через `config --quiet`. Резервные копии секретов хранятся отдельно, зашифрованно, с ограниченным доступом; закрытые CA — только у оператора/KMS/HSM, никогда у рабочего процесса.

Для status-файлов установите каталоги `0750`, файлы `0640`, группу из собственного `UI_SECRET_GID`; владельцем каталога должен быть оператор с `UI_PROVISION_UID`, которому разрешена запись client-secret. UID рабочего издателя остаётся заданным собственным образом/Compose; дополнительная группа даёт только чтение. В командном примере ниже STATUS_SECRET_GID — числовое значение уже настроенного UI_SECRET_GID, не новая переменная сервисного env. Не делайте ключи общедоступными ради запуска. Права нативных секретов описаны отдельно выше.

```sh
: "${STATUS_SECRET_GID:?set the numeric GID from your UI_SECRET_GID}"
chgrp "$STATUS_SECRET_GID" secrets/status secrets/status/*
chmod 750 secrets/status
chmod 640 secrets/status/*
```

Для отдельного административного каталога примените ту же группу, `0750` каталогу и `0640` обоим файлам; владельцу из UI_PROVISION_UID должно быть разрешено чтение admin-password и запись client-secret в status. Keycloak использует административный пароль через env, а не status-admin.

Проверьте срок, SAN/EKU и цепочку сертификата до запуска: `openssl x509 -in secrets/status/publisher.crt -noout -dates -ext extendedKeyUsage`, `openssl verify -CAfile /secure/ui-publisher-ca.crt -purpose sslclient secrets/status/publisher.crt`. Локальное удостоверение из команды действует 30 дней и не обновляется автоматически. Для смены CA сначала доставляют доверие старой и новой цепочкам, затем новые удостоверения, проверяют соединения и только после этого отзывают старые. Ротацию проводят через отдельный подготовленный набор файлов и контролируемое пересоздание собственной роли; генераторы первичного запуска не используют для перезаписи активных ключей. Новый client-secret сначала создают в собственном клиенте Keycloak, затем доставляют повторным собственным provision и пересоздают издателя; обычный повтор provision сам по себе не является ротацией. UUID, identity, ревизия и журнал последовательностей при этом сохраняются.


## Подготовка и самостоятельный запуск

Команды выполняются из этого каталога. Нужны работающий Docker и Compose с поддержкой `include` для включения в общий комплекс; Python 3.13 нужен только операторским Python-проверкам. Существующий `.env` не перезаписывайте шаблоном. Если данные уже используются общей группой инфраструктуры, управляйте Kafka через её [Compose](../README.md), не запускайте поверх неё самостоятельного писателя тех же томов.

```sh
docker version
docker compose version
if [ ! -f .env ]; then
  (umask 077; cp .env.example .env)
fi
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --wait kafka
```

`compose.yml` не содержит запасных значений сервисных настроек. Отсутствующая или пустая обязательная переменная останавливает `docker compose config` с сообщением, какой ключ нужно определить в Kafka `.env`; единственным шаблоном значений служит `.env.example`, а рабочие значения находятся только в игнорируемом `.env`.

## Параметры `.env`

| Переменная | Текущее значение | Назначение и влияние |
|---|---|---|
| `AELEV_INFRASTRUCTURE_KAFKA_COMPOSE_PROJECT` | `aelev-infrastructure-kafka` | Имя проекта Docker Compose. Определяет группировку ресурсов и автоматически формируемые имена контейнеров и неименованных ресурсов. Для второго независимого экземпляра вместе с этим значением необходимо задать отдельные имена сети и data volume. |
| `AELEV_INFRASTRUCTURE_KAFKA_BIND` | `127.0.0.1` | Интерфейс машины, на котором публикуется порт Kafka. `127.0.0.1` разрешает подключение только с этой машины. Значение `0.0.0.0` откроет порт на всех интерфейсах и недопустимо без отдельной сетевой защиты и защищённого listener. |
| `AELEV_INFRASTRUCTURE_KAFKA_PORT` | `19092` | Порт машины, перенаправляемый в контейнерный порт `9092`. Меняет только точку входа со стороны машины; контейнеры внутри Docker-сети продолжают обращаться к `kafka:9092`. |
| `AELEV_INFRASTRUCTURE_KAFKA_ADVERTISED_LISTENERS` | `PLAINTEXT://kafka:9092` | Адрес, который брокер возвращает клиентам в metadata. Он должен быть достижим из сети клиентов. Текущее значение предназначено для контейнеров, подключённых к Kafka-сети с alias `kafka`; публикация `127.0.0.1:19092` открывает исходное соединение с контейнером, но сама по себе не делает возвращаемый адрес `kafka:9092` доступным процессу на машине. Для другой топологии требуется маршрутизируемое имя и отдельно спроектированная защищённая listener-конфигурация. |
| `AELEV_INFRASTRUCTURE_KAFKA_HEAP_OPTS` | `-Xms256m -Xmx512m` | Начальный и максимальный Java heap брокера. Увеличение может снизить давление сборщика мусора при большей нагрузке, но повышает потребление памяти; уменьшение повышает риск `OutOfMemoryError`. Эти пределы не включают page cache и прочую память процесса. |
| `AELEV_INFRASTRUCTURE_KAFKA_MESSAGE_MAX_BYTES` | `8388608` | Максимальный размер принимаемого broker record batch — 8 МиБ. Producer, topic и consumer limits должны быть согласованы; batch больше предела будет отклонён. Увеличение повышает требования к памяти, сети и дисковому вводу-выводу. |
| `AELEV_INFRASTRUCTURE_KAFKA_DATA_VOLUME` | `aelev-infrastructure-kafka-data` | Явное имя постоянного Docker volume с журналами Kafka и служебным состоянием. Изменение имени подключает другое хранилище и внешне выглядит как новый пустой брокер; старый volume автоматически не удаляется и не переносится. |
| `AELEV_INFRASTRUCTURE_KAFKA_NETWORK` | `aelev-infrastructure-kafka` | Имя внутренней Docker-сети, принадлежащей самостоятельному Kafka-компоненту. Сеть имеет `internal: true`; клиент должен быть явно подключён к ней либо получить Kafka через оркестрацию и другую утверждённую связность. |

Список topics и их параметры отсутствуют как в сервисном `.env`, так и в Compose Kafka. Декларация topic принадлежит издателю — владельцу публикуемого контракта и поставляется вместе с ним. Отдельная одноразовая задача развёртывания издателя применяет декларацию до запуска рабочих процессов и потребителей, используя выделенную административную identity; рабочие процессы сервисов не получают права создавать, изменять или удалять topics и ACL. Корневая инфраструктурная оркестрация не хранит общий каталог topics.

## Сохранность сообщений

Kafka-компонент не определяет прикладной срок хранения и поэтому не содержит `log.retention.*` или других предметных retention-настроек в своём `.env`. Для каждого прикладного topic издатель — владелец контракта явно задаёт `retention.ms`, `retention.bytes` и `cleanup.policy` в собственной версионируемой декларации, а отдельная deployment-задача владельца применяет эти параметры на уровне topic. Runtime-паблишер не передаёт срок хранения вместе с сообщением и не изменяет конфигурацию при старте; потребитель также не владеет этой политикой. Значение broker по умолчанию остаётся только техническим fallback и не считается объявленной политикой хранения DRP. Каноническое распределение ответственности закреплено в [00-INFRA-20261106-0005-kafka-cloudevents-contracts](../docs/adr/00-INFRA-20261106-0005-kafka-cloudevents-contracts.md), а профильные требования — в [документации развёртывания](../docs/architecture/deployment.md#граница-конфигурации-инфраструктуры).

|---|---|

| `KAFKA_LISTENERS`, `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP`, `KAFKA_CONTROLLER_LISTENER_NAMES`, `KAFKA_INTER_BROKER_LISTENER_NAME` | Разделяют клиентский порт `9092` и непубликуемый controller-порт `9093`. Оба используют `PLAINTEXT`: это ограниченная локальная поставка, не защищённый удалённый Kafka. |
| `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1`, `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=1`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=1` | Позволяют служебным topics существовать на единственном брокере; не обеспечивают вторую копию или высокую доступность. |
| `KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS=0` | Убирает начальную задержку формирования группы в небольшом локальном стенде; не задаёт срок обработки сообщений. |
| `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false` | Отсутствующий topic должен создать отдельный процесс его владельца; брокер не угадывает контракт и параметры. |
| `KAFKA_LOG_DIRS=/var/lib/kafka/data`, `kafka-data` | Постоянные журналы сообщений и состояние Kafka, не каталог текстовых системных логов. |
| `healthcheck`, `restart`, `networks`, `ports` | Проверка доступа к Kafka-протоколу, восстановление завершившегося процесса и локальная связность. `healthy` не доказывает наличие нужного клиенту topic, его ACL, продвижение потребителя или резервную копию. |

## Остановка, обновление и восстановление

Для самостоятельной установки команды ниже сохраняют данные. Профиль `ui` нужен, только если подготовлен собственный издатель; его штатная остановка требует доступного UI для подтверждения отписки.

```sh
docker compose --env-file .env --profile ui ps --all
docker compose --env-file .env --profile ui stop
docker compose --env-file .env --profile ui up -d --no-build --pull never
docker compose --env-file .env --profile ui down
```

`down` снимает контейнеры и собственные сети, но не именованные тома. Для рабочего хранилища запрещены `down --volumes`, удаление data volume и запуск второго проекта с тем же томом. Обновление версии Kafka — отдельная проверяемая операция совместимости, не изменение адреса или повторное создание topics. Перед ней сохраните закрытые настройки и согласованную резервную копию корректно остановленного полного data volume; восстановление сначала проверьте отдельно на совместимой версии, не поверх единственного рабочего тома. Журнал издателя также сохраняется вместе с его UUID и identity. Жизненный тест ниже подтверждает сохранность при перезапуске, но не аварийное восстановление из резервной копии, кластер или WAN. Открытые ограничения перечислены в [TASKS.md](TASKS.md).

## Обновление нативной пробы

`AELEV_INFRASTRUCTURE_KAFKA_IMAGE` выбирает собственный проверенный образ, собранный из `Dockerfile`; для рабочей выкладки закрепляется фактический image ID. Базовый Apache Kafka 3.9.1, ОС, JVM, пользователь, entrypoint, listeners и формат данных остаются прежними. Нативный C-клиент и `init: true` заменяют только тяжёлую периодическую проверку и уборку детей. `Dockerfile` компилирует статическую пробу в отдельной стадии того же base; компилятор и его зависимости не попадают в runtime. Обычный standalone `build kafka` использует только этот каталог. Самовольная замена базовой версии не является настройкой пробы. Для уже проверенного существующего data volume задаётся `AELEV_INFRASTRUCTURE_KAFKA_DATA_VOLUME_EXTERNAL=true`: Compose требует его наличие и не перепомечает прежнюю собственность. Новая самостоятельная установка использует `false` из примера; переключение общей группы не создаёт новый пустой том.

Перед рабочей заменой выполните `python3 test/test_configuration.py`, `pytest test/test_native_health.py` и `python3 test/native_health_docker.py --docker-host <точный-local-unix-endpoint> --image <проверенный-image-ID>`. Для C-тестов нужен установленный компилятор, для изолированной проверки — Docker. Последняя создаёт только новый помеченный контейнер/том без внешней сети и портов, проверяет готовность, запись/чтение двух тестовых сообщений через перезапуск, отсутствие zombie и удаляет только свои подтверждённые ресурсы. Эти проверки не обращаются к рабочим topics и не сбрасывают бюджеты. Старый shell lifecycle использует выбранный Compose-образ, а не подразумевает исходный образ без новой пробы.

При обновлении зафиксируйте прежние container/image ID, native count, Compose scope, все именованные и анонимные volumes, listeners и node ID. Существующую зарегистрированную цель сначала удерживайте штатным `suspend`; для ещё не зарегистрированной первая регистрация учитывает прежний native count, не нулевой счётчик будущей инкарнации. Сохраните согласованную остановленную копию данных/конфигурации по прежней процедуре. Обновляйте только `kafka` из того же общего или самостоятельного проекта через `up -d --no-deps --no-build --pull never`, без `--renew-anon-volumes`, `down`, изменения томов или обновления издателя. Перед остановкой native-restart должен быть выключен; новая конфигурация также сохраняет `restart=no` до подтверждения бюджета.

После healthy сверяйте прежние volumes, данные кластера, конфигурацию и готовность, затем выполняйте штатный `recovery.py replace` с точными ID предшественника, его финальным native count и новым image ID. Эта команда не запускает контейнер и сохраняет общий лимит из трёх попыток; новый счётчик Docker не означает новые три попытки. Если подтверждение потеряно, повторяют тот же переход, не `reset`. Для первого экземпляра без предшественника используется явный `enroll`. Исчерпанный бюджет остаётся `CIRCUIT_OPEN` и `restart=no`. Политики издателя и других провайдеров не меняются этим обновлением.

При отказе допуска сохраните причины, копии и прежний образ. Возврат прежнего совместимого image ID с теми же томами выполняется отдельным согласованным переходом под удержанием ограничителя; не возвращайте `unless-stopped`, не удаляйте данные и не выдавайте новую квоту. Наличие открытого TCP-порта, один успешный `ApiVersions` или успешная сборка не заменяют жизненный тест и рабочую сверку. Нормативные пределы находятся в [SPEC](SPEC.md#нативная-проба-brokercontroller).

## Проверка конфигурации

Python-проверка принадлежит Kafka-компоненту и находится в [`test/test_configuration.py`](test/test_configuration.py). Она проверяет состав обязательных файлов, единое пространство `AELEV_INFRASTRUCTURE_KAFKA_*`, отсутствие запасных значений и прикладных topics, ошибку при отсутствии `.env` и политику перезапуска. Проверка требует Python 3.13 и Docker Compose, но не запускает контейнеры и не изменяет Docker-ресурсы.

```sh
python3 test/test_configuration.py
```

## Жизненный тест

`test/single-node-lifecycle.test.sh` запускает изолированный одноузловой broker без публикации host-порта, проверяет готовность и реальную запись/чтение, останавливает и повторно поднимает контейнер, подтверждает сохранность сообщения в data volume, проверяет новую запись и затем удаляет созданные контейнер, сеть и volume. Если образ `apache/kafka:3.9.1` отсутствовал до проверки, тест удаляет и загруженный им образ; существовавший ранее образ сохраняется. Cleanup выполняется также при ошибке или прерывании.

```sh
./test/single-node-lifecycle.test.sh
```

Последний фактический результат хранится рядом с тестом в `test/single-node-lifecycle-result.md`.

Для географически удалённого Kafka этот Compose не используется. Каждый потребитель или издатель получает собственные bootstrap servers, TLS-материал, workload identity и минимальные ACL через свой `.env` или утверждённое хранилище секретов.

## Собственное состояние в platform-ui

Повторная проверка названия назначения и технологического состава: [результат](test/status-labels-result.md). Она не подменяет прежние испытания жизненного цикла.

Профиль `ui` включает только собственную техническую роль публикации; обычный запуск не зависит от оболочки или IdP. Отдельная строка имеет тип `INFRASTRUCTURE`, не добавляет функциональные разделы. Состав: broker и собственный издатель; ApiVersions проверяет настоящий Kafka-протокол, не создаёт и не перечисляет topics. Подтверждённая отрицательная native readiness отличается от отсутствия связи: transport/TLS-ошибка означает `UNKNOWN`. При штатной остановке издатель подтверждает отписку, и строка исчезает; при исчезновении публикаций без отписки строка остаётся с «Нет связи» после срока свежести приёмника.

Поставка использует собственный образ и включённый публичный `aelev-platform-ui-client==1.1.2` в `vendor`; SHA-256 закреплён собственным Poetry lock. Это библиотека транспорта, не общий runtime-образ/каталог продуктов. Сборка после извлечения этого каталога не читает соседние исходники. Протокол, установка артефакта и пример собственного издателя: [руководство оболочки](../platform-ui/USER_MANUAL.md#отправить-метаданные-из-python).

Из этого каталога, после подготовки удостоверений:

```sh
docker compose --env-file .env --profile ui build kafka-status-publisher
docker compose --env-file .env --profile provision run --rm kafka-status-provision
docker compose --env-file .env --profile ui up -d --no-build kafka-status-publisher
docker compose --env-file .env --profile ui stop kafka-status-publisher
```

Рабочий процесс получает только `secrets/status/{shell-ca.crt,identity-ca.crt,publisher.crt,publisher.key,client-secret}`. Одноразовый `provision` получает отдельные `secrets/status-admin/{admin-user,admin-password}`, не монтируемые в runtime. Закрытые ключи CA не доставляются в контейнеры. Используйте утверждённые цепочки CA, SAN/EKU и ротацию; генерация локального удостоверения описана в руководстве и не заменяет production PKI/SVID. HTTPS-адреса могут находиться в разных странах; общей Docker-сети с UI/IdP нет. `host.docker.internal` и `keycloak:host-gateway` — только локальные адресные alias примера; для удалённой установки задайте реальные FQDN/порты и доступность сети. Проверка сертификатов не отключается.

| Переменная | Назначение |
|---|---|
| `AELEV_INFRASTRUCTURE_KAFKA_UI_URL` | HTTPS-адрес платформенного технического API. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_IDENTITY_URL` | HTTPS-адрес IdP; должен совпадать с SAN сертификата. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_REALM` | Realm собственной машинной identity. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_CLIENT_ID` | Client ID только собственной роли публикации. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_AUDIENCE` | Аудитория JWT платформенного API. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_MODULE_ID` | Постоянный UUID собственного описания. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_INTERVAL_SECONDS` | Интервал публикации; браузер по-прежнему опрашивает раз в минуту. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_TIMEOUT_SECONDS` | Предел каждой собственной сетевой пробы/отправки. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_SECRET_ROOT` | Собственные рабочие удостоверения, без административных файлов. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_SECRET_GID` | Дополнительная группа чтения собственных секретов. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_ADMIN_ROOT` | Отдельные operator credentials только явной одноразовой задачи. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_PROVISION_UID` | UID оператора для одноразовой записи собственного client secret. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_STATE_VOLUME` | Постоянный журнал последовательности и точных повторяемых байтов. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_MEMORY_LIMIT` | Лимит памяти только издателя. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_IMAGE` | Собственный образ издателя, не общий образ инфраструктуры. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_PYTHON_IMAGE` | Закреплённый Python 3.13.7 builder/runtime издателя. |
| `AELEV_INFRASTRUCTURE_KAFKA_UI_EGRESS_NETWORK` | Отдельная сеть HTTPS-выхода издателя; внутренний broker network остаётся закрытым. |

Журнал `UI_STATE_VOLUME` сохраняется при stop/start и обновлении; не удаляйте его как кэш: приёмник помнит sequence прежнего UUID. Восстановление требует собственного backup журнала или согласованного нового UUID, не сброса чужой БД/повторного sequence=1. Повторная публикация восстанавливает только текущую декларацию владельца, не прежние sequence, маркеры отзыва, владение или журнал приёмника; его собственная копия остаётся необходимой по 00-INFRA-20261106-0006-technical-storage-boundaries. Канонический источник описания/состава принадлежит владельцу.

`test/status_publication.py` работает с уже существующей настоящей установкой: OIDC/API/DOM, stop/start частей и издателя, реальное истечение TTL, возврат исходных контейнеров. Пример: `python3.13 test/status_publication.py --ui-url https://<ui-host>:<port> --viewer-user <viewer> --viewer-password-file <password-file> --chromium <installed-chromium> --status-ttl-seconds 120`. Требуются Python 3.13 и Playwright 1.56.0 в операторской тестовой среде; runtime-образ их браузерную роль не запускает. Исключение браузерной проверки сертификата допустимо только явным `--allow-local-certificate` на loopback с локальной PKI; рабочие издатели всегда проверяют TLS. Тест не создаёт фиктивных identities, каталогов, контейнеров, сетей или томов и восстанавливает исходное состояние; отчёт/снимок остаются в `test`. Полный остановленный приёмник UI физически не может доставить собственный свежий отчёт: проверяется UNKNOWN в уже открытом браузере и восстановление после старта.

Результаты текущей проверки публикации состояния: [читаемый отчёт](test/status-validation-result.md), [проверка издателя и нативной части](test/status-publication-result.md). Прежние предметные/кластерные испытания не подменяются этой проверкой.

## Обновление журнала издателя

Сборка собственного издателя использует закреплённую SQLite 3.53.4; ОС, Python и SDK не заменяются. До первого запуска задайте `AELEV_INFRASTRUCTURE_KAFKA_UI_RESTART_POLICY=no`. При обновлении сначала удержите точного предшественника через [существующий ограничитель](../USER_MANUAL.md#ограниченное-восстановление-по-unhealthy), остановите только издателя и сохраните полный его том с WAL, inspect и журналы. Не вызывайте отписку, не удаляйте том и не меняйте UUID.

На изолированных копиях проверьте целостность, схему и все строки старым и новым движками. Запускайте только проверенный издатель с прежними mounts и `restart=no`, без запуска зависимостей. После healthy передайте прежний бюджет штатным `replace`; только для действительно незарегистрированной истории с подтверждёнными нулевыми рестартами допустим `enroll`. Значение env оставьте `no`: фактический оставшийся бюджет выставляет ограничитель, а новая инкарнация должна пройти передачу истории снова. Исчерпанный или заблокированный бюджет не сбрасывайте. Перед следующей заменой повторяйте эту процедуру, а не обычный пересоздающий `up`.

## Лёгкая проба издателя

При обновлении сохраняйте фактическое имя Compose-проекта работающего издателя и передавайте его явно через `-p`. Имя самостоятельной группы из примера не подставляется вместо действующей общей группы: два издателя одного журнала одновременно запрещены.

Соберите собственный совместимый образ с закреплённым клиентом Platform UI 1.1.1. Закрепите его в `AELEV_INFRASTRUCTURE_KAFKA_UI_IMAGE` и проверьте Compose. До адресного обновления только `kafka-status-publisher` сохраните согласованную SQLite-копию собственного журнала и конфигурацию; не удаляйте том, UUID, sequence или ожидающие байты. Одной замены команды healthcheck без совместимого образа недостаточно. Применяйте `up -d --no-deps --no-build --pull never` только к издателю с профилем `ui`, затем проверьте свежий heartbeat, продвижение sequence и доставку состояния. Нативные процессы, данные, секреты и бюджеты восстановления не меняются. Точные свойства пробы определены в [SPEC](SPEC.md); её успех не заменяет проверки готовности и доставки.

При откате остановите только новый издатель и выберите сохранённый совместимый образ с прежней командой пробы, не меняя журнал. Схема журнала этим обновлением не меняется; возврат более старого клиента с несовместимым форматом без отдельной подготовки не допускается. Если процесс не восстановился, сохраняйте журналы и безопасную причину ошибки, не обнуляйте последовательность и не увеличивайте таймаут вместо устранения причины.
