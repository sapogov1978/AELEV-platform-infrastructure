# Platform UI — эксплуатация поставщика

## Структура поставки

```text
platform-ui/
├── README.md, SPEC.md, USER_MANUAL.md, TASKS.md, CHANGELOG.md
├── compose.yml, .env.example     # .env — рабочие настройки вне Git
├── Dockerfile, pyproject.toml, poetry.lock
├── package.json, package-lock.json, vite.config.ts, tsconfig.json
├── index.html, src/              # собственная оболочка React
├── public/                       # favicon и версионированное оформление
├── api.py, health.py, provision.py, status_publisher.py
├── nginx.conf                   # исходный шаблон, не готовый runtime
├── prepare.py                   # init, render, локальная PKI
├── client/                      # исходник публичной технической библиотеки
├── vendor/                      # закреплённый артефакт собственного runtime
├── secrets/                     # отдельная доставка, вне Git/образа
│   ├── nginx/, api/, provision/
│   ├── issuer/                  # только локальный оператор, не runtime
│   └── status/, status-admin/
├── runtime/                     # производные config/API/nginx/provision
└── test/                        # проверки и читаемые результаты
```

Дерево показывает значимые файлы поставки, а не кэши инструментов. `.env`, содержимое `secrets/` и производные `runtime/` создаются оператором и не входят в Git или образ; документация `secrets/README.md`, где она есть, остаётся в Git. Постоянные данные находятся в именованных Docker volumes из Compose, не в каталоге исходников.

## Назначение

Постоянные `platform-ui`, `platform-ui-api` и `platform-ui-status-publisher` создаются с native `restart=no` и явным допуском к первоначальной точной регистрации в единственном recovery-контроллере 00-INFRA-20261106-0010-bounded-recovery-and-process-control. Обычный `docker compose up`, который пересоздал зарегистрированную роль, не завершает обновление: после healthy новой инкарнации передайте прежние ID, native-счётчик и новый точный image ID штатным `replace`, сохранив накопленные attempts и историю. `/healthz` оболочки остаётся локальной живостью nginx, а её `/readyz` требует готового `platform-ui-api`; поэтому отказ приёмника виден как неготовность оболочки, но не вызывает цикл перезапуска живого nginx.


Собственный издатель имеет `stop_grace_period: 2m`: это время на завершение текущего запроса и подтверждение отписки через удалённый HTTPS, не запасное значение env и не бесконечное ожидание. Если связь недоступна, неподтверждённый выход сохраняется в журнале, а UI не скрывает строку как штатно завершённую.

В «Состоянии» верхняя строка называется «Интерфейс платформы» (`Platform interface`) и отражает назначение, а раскрываемый состав показывает технологии и процессы этой поставки. Названия публикует сам владелец в ревизии 2; оболочка не содержит таблицы переименований. UUID, identity, состав и последовательность сохраняются.

Название в шапке и вкладке браузера — `Discovery Research Platform`, одинаковое при русском и английском интерфейсе. Значок вкладки — [favicon.svg](public/favicon.svg): мятная «А» на тёмно-зелёном скруглённом квадрате, как в шапке; буква задана векторным контуром и не требует загрузки шрифта.

Название левого меню — «Подключенные сервисы» (`Connected services`), а не «Разделы». Оно показывает только описания с `service_kind=FUNCTIONAL` и хотя бы одним разделом, которые публикует сам владелец. Единственный раздел представлен одной кнопкой с названием сервиса; название раздела появляется в меню только при нескольких разделах. Необязательный `navigation_order` сортирует функциональные модули по возрастанию, отсутствие означает `0`, равные значения стабилизируются по UUID. После выбора оболочка не добавляет над iframe название модуля или раздела: заголовок страницы принадлежит самому UI владельца. `INFRASTRUCTURE`, функциональные описания без разделов и описания без типа либо с `null` остаются на странице состояния. Старые описания принимаются без изменения хеша; для появления прежнего функционального UI в меню или смены его порядка владелец публикует новую ревизию после обновления API/оболочки. Категория и порядок не дают новых прав и не определяются из списка продуктов. Совместимость и порядок отката — в [контракте](../docs/api/platform-ui-injection.md#инъекция).

Слева от кнопки «Состояние» находится один общий индикатор получения данных: первая загрузка, фоновое обновление, время последнего успешного ответа и ошибка. По [00-INFRA-20261106-0008-platform-ui-owner-injection](../docs/adr/00-INFRA-20261106-0008-platform-ui-owner-injection.md) им управляет UI открытого раздела через `AELEV_UI_REFRESH`; этот интерфейс доступен любому владельцу без списка участников в оболочке. На странице состояния источником служит собственный API оболочки, для него рабочая настройка `POLL_SECONDS=60`. Пояснение «Данные обновляются раз в минуту» появляется только для действительного интервала 60 секунд текущего источника; до его сообщения режим неизвестен. Ошибка и новый запрос сохраняют прежнее успешное время, а переключение раздела или перезагрузка iframe сбрасывает чужие показания. Фоновый опрос оболочки не перехватывает индикатор открытого сервиса. Детали подключения — в [контракте](../docs/api/platform-ui-injection.md#общий-индикатор-получения-данных).

На странице состояния зелёная отметка не появляется только от HTTP 200: при `UNKNOWN` у владельцев или составных частей индикатор сообщает неизвестные состояния, для пустого списка — отсутствие активных публикаций. После получения известных состояний показаны «Состояния получены» и время без дополнительной подписи; оно обозначает получение API-ответа, не время отчётов в строках. Если текущий источник перестал обновляться, прежний успех сменяется задержкой по [правилам свежести индикатора](../docs/api/platform-ui-injection.md#общий-индикатор-получения-данных), без нового запроса и без изменения состояния сервисов.

`platform-ui` — универсальная оболочка DRP: оформление, навигация, вход и отображение названия/состояния, присланных владельцами. Встроенного перечня сервисов нет. Владелец сам публикует описание страниц и состояние; его UI работает на отдельном HTTPS origin и сохраняет свои данные, команды и авторизацию. Без публикаций оболочка показывает пустое, готовое к подключению пространство. Нормативные источники: [00-INFRA-20261106-0008-platform-ui-owner-injection](../docs/adr/00-INFRA-20261106-0008-platform-ui-owner-injection.md), [контракт инъекции](../docs/api/platform-ui-injection.md), [SPEC](SPEC.md).

Текущее оформление и базовая геометрия владельческих страниц принадлежат Platform UI. Публичный артефакт — `/presentation/v6.css`; его точная автономная проекция входит в `@aelev/operator-ui-kit` 0.1.4 вместе с единым `PlatformPage`; тот же выпуск SDK экспортирует канонические путь и SHA-256, поэтому bridge владельца не хранит их копию. Опубликованные `/presentation/v1.css`–`/presentation/v5.css` сохраняются без изменения байтов. Перед выпуском выполните `python3 build_presentation.py`, проверьте побайтовое совпадение публичного файла и SDK-проекции, затем повторите `prepare.py render`, чтобы runtime SHA-256 соответствовал текущей версии оформления.

Порядок создания и подключения нового UI с примерами описания, состояния, Python-издателя, страницы, оформления и общего индикатора находится в [USER_MANUAL](USER_MANUAL.md#создание-и-подключение-ui-нового-сервиса). Все файлы и полномочия такого UI принадлежат его сервису; правка каталога оболочки не требуется.

## Секреты: получение и подготовка

Перечень всех обязательных файлов по ролям приведён в [HTTPS и файлах секретов](#https-и-файлы-секретов). Публичные цепочки CA получают у оператора соответствующего сервера и сверяют с утверждённым источником; имя файла не подтверждает доверие.

| Материал | Источник и кому доставляется |
|---|---|
| `nginx/server.crt/key` | Удостоверение публичного HTTPS origin; для браузера нужна доверенная им цепочка, не установка нашей CA в корпоративную систему. |
| `nginx/client.crt/key`, `nginx/ca.crt` | Отдельная клиентская identity и доверие внутреннему API. |
| `nginx/publisher-ca.crt` | Только публичные CA допущенных клиентских удостоверений издателей. Не копия серверного сертификата и не каталог клиентов. |
| `api/server.crt/key`, `api/ca.crt`, `api/health.crt/key` | Собственный сервер API, доверие клиентам и отдельная clientAuth-проба. |
| `api/oidc-ca.crt`, `provision/oidc-ca.crt` | Публичная цепочка HTTPS IdP для проверки ключей/административного обмена. |
| `provision/admin-password` | Действующий пароль отдельного администратора развёртывания из внешнего хранилища. Имя задаёт PROVISION_ADMIN_USER; случайная строка не заменяет пароль существующего пользователя. |
| `provision/operator-password` | Первоначальный пароль нового OPERATOR_USER из внешнего хранилища; локальный генератор создаёт его случайно. Повтор provision не является сменой пароля существующего пользователя. |
| `issuer/transport.key`, `issuer/publisher.key` | Только операторские ключи локальной PKI; runtime их никогда не получает. |

Новая локальная PKI создаётся после `prepare.py init` и настройки собственного env:

```sh
# Публичная CA IdP и пароль администратора уже доставлены оператору.
python3.13 prepare.py development-pki \
  --identity-ca /secure/idp-ca.crt \
  --admin-password-file /secure/idp-admin-password
python3.13 prepare.py render
docker compose --env-file .env --profile provision run --rm platform-ui-configuration-init
```

Команда создаёт nginx/API удостоверения, две локальные CA и начальный пароль оператора; отказывается при существующих ролевых каталогах. Локальные серверы/CA действуют 30 дней и не обновляются автоматически. Закрытые CA можно применять только на доверенной операторской станции; публичную publisher CA доставляют выдающему удостоверения оператору, ключ — никогда обычному издателю. Собственные API/nginx получают только узкие ролевые mounts. Изменение доверия macOS для локального стенда не требуется и данной инструкцией не разрешается.

Доставка: файлы `0640`, каталоги `0750`, группа SECRET_GID; ключи issuer `0600` и только оператору. Provision получает только свой каталог. Для обычного повторного запуска не повторяйте development-pki и не генерируйте новый пароль оператора. При рабочей ротации обновляется конкретная роль и её доверие, затем адресно пересоздаётся собственный nginx/API; OIDC/JWKS ключи приходят от IdP, не создаются оболочкой. Не удаляйте SQLite и журнал издателя ради новой PKI.

### Секреты издателя состояния

Пути ниже соответствуют шаблону `UI_SECRET_ROOT=./secrets/status`; при другом значении используйте собственный настроенный каталог. Источники доверия определяются адресами, не совместным размещением: узел в другой стране получает публичные цепочки CA и своё удостоверение через защищённую доставку, а не доступ к чужой папке.

| Файл | Откуда получить и зачем |
|---|---|
| `shell-ca.crt` | Проверенная публичная цепочка CA HTTPS-сервера оболочки; получить у её оператора. Это не CA клиентских издателей. |
| `identity-ca.crt` | Проверенная публичная цепочка CA HTTPS IdP; получить у оператора IdP. |
| `publisher.crt`, `publisher.key` | Собственное удостоверение `clientAuth`; его выпускающая CA должна входить в `publisher-ca.crt` приёмника UI. Закрытый ключ принадлежит только этому издателю. |
| `client-secret` | Выдаёт Keycloak для собственного confidential client; сохраняет `platform-ui-status-provision`. Не генерируйте произвольный пароль вместо секрета существующего OIDC-клиента. |
| `probe-ca.crt`, `probe.crt/key` | CA внутреннего API и собственная clientAuth-проба, подписанная CA из `api/ca.crt`; не ключ администратора или другого издателя. |
`UI_ADMIN_ROOT` содержит отдельные `admin-user` и `admin-password`: имя и действующий пароль администратора развёртывания Keycloak получают у оператора IdP или из внешнего хранилища. Это не пароль service account и не пароль пользователя браузера. Доставьте их файловым механизмом; например, `install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password`, а имя запишите в `admin-user` без секрета. Provision должен иметь право записи в `UI_SECRET_ROOT`, runtime — только чтение.

Перед локальной подписью проверьте `openssl version` и поддержку OpenSSL 3; при отсутствии используйте утверждённый пакет вашей ОС (`brew install openssl@3` на macOS, `sudo apt-get install openssl` на поддерживаемой Debian/Ubuntu) или подготовленную операторскую станцию. Эти команды не устанавливают CA в системное доверие и не выполняются при запуске контейнера.

Первичная доставка административных файлов (пути источника и имя замените данными своего IdP, не пароль в команде):

```sh
umask 077
install -d -m 750 secrets/status-admin
test ! -e secrets/status-admin/admin-user && test ! -e secrets/status-admin/admin-password || exit 1
STATUS_ADMIN_USER=deployment-admin
printf '%s\n' "$STATUS_ADMIN_USER" > secrets/status-admin/admin-user
install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password
chmod 640 secrets/status-admin/admin-user
```

Имя deployment-admin — пример существующей identity, не команда создания пользователя. Если у вас другое имя или UI_ADMIN_ROOT, задайте их явно; GID каталога/файлов должен совпадать с UI_SECRET_GID, а владелец — с UI_PROVISION_UID. Уже доставленные пароли не перезаписываются первичной командой. После удаления одноразового контейнера пароль не нужен рабочему издателю; локальную административную доставку уберите из runtime-узла или выдавайте заново только на время provision.


Для новой локальной identity можно создать ключ и CSR на доверенной операторской машине. Нужен OpenSSL 3 для `-copy_extensions`; пути `/secure/...` ниже заменяются выбранными операторскими файлами, это не обязательные каталоги сервиса. Публичные CA берутся из проверенного источника; неизвестный сертификат из сети не становится доверенным только потому, что назван `ca.crt`.

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/publisher.key && test ! -e secrets/status/publisher.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=publisher -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/publisher.key -out secrets/status/publisher.csr
# Только локальный тест: ключ CA остаётся на операторской машине, не в runtime.
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/publisher.csr \
  -CA /secure/ui-publisher-ca.crt -CAkey /secure/ui-publisher-ca.key \
  -CAcreateserial -out secrets/status/publisher.crt
install -m 640 /secure/ui-server-ca.crt secrets/status/shell-ca.crt
install -m 640 /secure/idp-ca.crt secrets/status/identity-ca.crt
chmod 640 secrets/status/publisher.key secrets/status/publisher.crt
```

Тестовую CA издателей создаёт оператор локальной оболочки при её явной подготовке PKI; берутся именно `issuer/publisher.crt/key`, не серверный ключ UI. В рабочей среде последнее подписание локальной CA не выполняют: удостоверение и обновляемую identity доставляет утверждённая PKI/SPIRE по [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md). CSR можно передать CA, закрытый ключ нельзя. Перед включением издателя доставьте также перечисленные файлы нативных проб и выполните собственный `--profile provision run --rm platform-ui-status-provision` из раздела запуска.


Для новой локальной пробы (не рабочей SVID) используйте собственную операторскую CA, которой доверяет данный health endpoint; существующие файлы не перезаписываются. Если issuer расположен иначе, замените путь. Это отдельная пара, не копия native client.key:

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/probe.key && test ! -e secrets/status/probe.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=probe -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/probe.key -out secrets/status/probe.csr
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/probe.csr \
  -CA secrets/issuer/transport.crt -CAkey secrets/issuer/transport.key \
  -CAcreateserial -out secrets/status/probe.crt
install -m 640 secrets/issuer/transport.crt secrets/status/probe-ca.crt
chmod 640 secrets/status/probe.key secrets/status/probe.crt
```


### Хранение, доступ и ротация

Секреты разделяются по среде, владельцу и роли. Локальные файлы — только материал стенда или доставка, не каноническое production-хранилище; рабочий источник — внешнее утверждённое хранилище, доставка в память/tmpfs по 00-INFRA-20261106-0007-workload-and-operator-identity. Не включайте секреты в Git, образ, архив исходников, команды с подстановкой содержимого или отчёты. Не запускайте `set -x`, не публикуйте раскрытый `docker compose config`; проверяйте через `config --quiet`. Резервные копии секретов хранятся отдельно, зашифрованно, с ограниченным доступом; закрытые CA — только у оператора/KMS/HSM, никогда у рабочего процесса.

Для status-файлов установите каталоги `0750`, файлы `0640`, группу из собственного `UI_SECRET_GID`; владельцем каталога должен быть оператор с `UI_PROVISION_UID`, которому разрешена запись client-secret. UID рабочего издателя остаётся заданным собственным образом/Compose; дополнительная группа даёт только чтение. В командном примере ниже STATUS_SECRET_GID — числовое значение уже настроенного UI_SECRET_GID, не новая переменная сервисного env. Не делайте ключи общедоступными ради запуска. Права нативных секретов описаны отдельно выше.

```sh
: "${STATUS_SECRET_GID:?set the numeric GID from your UI_SECRET_GID}"
chgrp "$STATUS_SECRET_GID" secrets/status secrets/status/*
chmod 750 secrets/status
chmod 640 secrets/status/*
```

Для отдельного административного каталога примените ту же группу, `0750` каталогу и `0640` обоим файлам; владельцу из UI_PROVISION_UID должно быть разрешено чтение admin-password и запись client-secret в status. Keycloak использует административный пароль через env, а не status-admin.

Проверьте срок, SAN/EKU и цепочку сертификата до запуска: `openssl x509 -in secrets/status/publisher.crt -noout -dates -ext extendedKeyUsage`, `openssl verify -CAfile /secure/ui-publisher-ca.crt -purpose sslclient secrets/status/publisher.crt`. Локальное удостоверение из первичной команды действует 30 дней и само не обновляется. Для смены CA сначала доставляют доверие старой и новой цепочкам, затем новые удостоверения, проверяют соединения и только после этого отзывают старые. Ротацию проводят через отдельный подготовленный набор файлов и контролируемое пересоздание собственной роли; генераторы первичного запуска не используют для перезаписи активных ключей. Новый client-secret сначала создают в собственном клиенте Keycloak, затем доставляют повторным собственным provision и пересоздают издателя; обычный повтор provision сам по себе не является ротацией. UUID, identity, ревизия и журнал последовательностей при этом сохраняются.

Для принятого локального автоматического профиля 00-INFRA-20261106-0013-owner-certificate-lifecycle прежняя ручная leaf-команда заменяется отдельным owner-state Telemetry Delivery: 90 дней, выпуск за 30 дней до срока и минутный LaunchAgent. Publisher CA остаётся полномочием Platform UI. Его перекрывающую смену выполняют `python3.13 publisher_authority.py prepare --source secrets/issuer --output <закрытое-поколение> --environment local`, затем `python3.13 publisher_authority.py stage --source secrets/issuer --output <то-же-поколение> --trust secrets/nginx/publisher-ca.crt --environment local` и перечитывают nginx-конфигурацию. До выпуска leaf trust bundle обязан содержать старый и новый root; автоматическое удаление старого запрещено. В production обе команды запрещены.


## Самостоятельная поставка

По [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md) и [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md) внешняя операторская ссылка и внедряемый раздел могут быть HTTP только на точном loopback компьютера браузера; UI/API проверяют это без списка продуктов. Это не разрешение удалённого plaintext или отключения авторизации. Владелец выбирает свой локальный режим и loopback bind, а сетевые установки сохраняют HTTPS. Подробные ограничения, порядок обновления и отката — в [контракте](../docs/api/platform-ui-injection.md#ссылки-на-собственные-интерфейсы).

В строках состояния есть кнопка «Открыть» только при наличии опубликованного владельцем адреса собственного UI или Swagger. Для функционального сервиса с внедрёнными разделами допустим только Swagger; для инфраструктуры UI имеет приоритет. Переход выполняется в отдельной вкладке без токенов оболочки и требует собственных прав целевого интерфейса. Оболочка не угадывает адреса и не содержит перечня продуктов. Примеры, mTLS и порядок обновления — в [USER_MANUAL](USER_MANUAL.md#опубликовать-ссылку-открыть), нормативные правила — в [контракте](../docs/api/platform-ui-injection.md#ссылки-на-собственные-интерфейсы).

В «Состоянии» владелец может объявить свой состав: группа раскрывается щелчком по названию или клавиатурой, у каждой строки своё состояние и время. Открытая группа сохраняется при обновлении данных; без состава остаётся обычная строка. Оболочка не знает названий компонентов заранее, не опрашивает их и не копирует состояние родителя. Объявление и проверяемый пример — в [USER_MANUAL](USER_MANUAL.md#показать-состав-сервиса-в-состоянии), правила совместимости и свежести — в [контракте](../docs/api/platform-ui-injection.md#составные-компоненты).

Два постоянных контейнера: nginx обслуживает статическую оболочку и HTTPS; собственный Python API проверяет JWT и принимает технические метаданные в свой SQLite-том. `platform-ui-configuration-init` — только явный одноразовый профиль `provision`, не постоянный контейнер. Он создаёт собственный публичный OIDC-клиент, две роли и первого оператора; чужие клиенты не перечисляет. Удостоверение администратора не доступно nginx/API. Один API-писатель и один том — намеренно одноузловая поставка интерфейса; несколько API с независимыми SQLite не образуют кластер. Отказ оболочки не останавливает владельцев.

SQLite входит в согласованный техстек как встроенное техническое хранилище по [00-INFRA-20261106-0006-technical-storage-boundaries](../docs/adr/00-INFRA-20261106-0006-technical-storage-boundaries.md), не как замена доменной PostgreSQL. API использует `/var/lib/platform-ui/metadata.sqlite` в DATA_VOLUME; издатель — отдельный `/var/lib/aelev-status/outbox.sqlite` в UI_STATE_VOLUME. Ни nginx, ни другие сервисы не получают прямого доступа к этим файлам. Разнесённые владельцы используют JWT/mTLS-публикацию, не общий файловый том через WAN. Схема API подготавливается идемпотентно до обработки, схема издателя поставляется закреплённой версией его библиотеки; обновление проверяет прежние записи, совместимость и откат. Для требуемого кластера API понадобилось бы отдельное согласование серверного хранилища; текущая поставка кластером не является.

По [00-INFRA-20261106-0004-self-contained-service-delivery](../docs/adr/00-INFRA-20261106-0004-self-contained-service-delivery.md) имя `platform-ui-configuration-init` одинаково при самостоятельном и общем запуске. В прежних операторских командах замените `configuration-applier` этим именем; корневого переименования или совместимого псевдонима нет. Том, identities и исполняемый код задачи не меняются.

Сборка использует только этот каталог. Настройки читаются при запуске из подготовленных собственных файлов, не зашиваются в JavaScript. Нет зависимости от исходников соседнего UI-kit, Prometheus, Docker socket, каталога потребителей или общих сетей. Keycloak — явная инфраструктурная зависимость по HTTPS, он может находиться на другой машине. Прямой доменный транспорт через оболочку не появляется.

## Требования и подготовка

Нужны Docker Engine/Desktop с Compose v2, Python 3.13 для подготовки и проверок API, OpenSSL только для генерации локальной PKI. Node 22.18.0 нужен только для проверок frontend вне Docker. Проверьте наличие:

```sh
docker version
docker compose version
python3.13 --version
openssl version
```

При отсутствии Python/OpenSSL: macOS — `brew install python@3.13 openssl@3`; Linux с Python 3.13 в утверждённом репозитории ОС — установите пакеты `python3.13` и `openssl` штатным пакетным менеджером. Если версия отсутствует, используйте утверждённую сборку Python 3.13 или образ проверок ниже, не подменяйте runtime другой версией. Docker устанавливается по [официальной инструкции](https://docs.docker.com/engine/install/); Compose — по [инструкции плагина](https://docs.docker.com/compose/install/linux/). `keytool` этой поставке не нужен. В runtime-контейнерах генераторы ключей не требуются.

Из этого каталога:

```sh
python3.13 prepare.py init
# Отредактируйте .env: адрес оболочки, адреса IdP, realm и собственные ресурсы.
```

`init` создаёт живой `.env` с текущей группой файлов и отказывается перезаписывать существующий. Ни `.env`, ни `secrets`, ни подготовленный `runtime` не коммитятся. Исторический env до 00-INFRA-20261106-0008-platform-ui-owner-injection несовместим: сохраните его отдельно, создайте новый по текущему шаблону и перенесите только актуальные настройки адреса/IdP. Прежние OIDC-клиенты не удаляются автоматически.

## HTTPS и файлы секретов

Для обычной установки доставьте из утверждённой PKI собственные сертификаты и ключи. В `SECRET_ROOT` должны быть:

| Каталог | Обязательные файлы и назначение |
|---|---|
| `nginx` | `server.crt/server.key` — публичный сервер с SAN адреса оболочки и `127.0.0.1` для пробы; `ca.crt` — доверие внутреннему API; `client.crt/client.key` — mTLS-клиент API; `publisher-ca.crt` — доверие издателям. |
| `api` | `server.crt/server.key` — сервер с SAN `platform-ui-api` и `127.0.0.1`; `ca.crt` — доверие внутренним клиентам; `health.crt/health.key` — отдельный клиент проверки здоровья; `oidc-ca.crt` — CA HTTPS IdP. |
| `provision` | `oidc-ca.crt` — CA IdP; `admin-password` — пароль отдельной identity развёртывания; `operator-password` — пароль создаваемого первого оператора. |

Публичная цепочка должна быть доверена браузером. Внутренние серверы используют `serverAuth`, клиенты — `clientAuth`. Ключи — `0640`, каталоги — `0750`, группа соответствует `SECRET_GID`; для runtime доступны только каталоги соответствующих ролей. Закрытые ключи CA на серверы приложения не доставляются. Поставщик разрешает конкретному издателю роль `platform-ui-publisher` и аудиторию клиента оболочки отдельно; это не автоматический доступ любого зарегистрированного пользователя.

Только для локальной работы и теста можно явно создать короткоживущую PKI:

```sh
python3.13 prepare.py development-pki \
  --identity-ca /path/to/idp-ca.crt \
  --admin-password-file /path/to/deployment-admin-password
```

Команда использует OpenSSL, создаёт отдельные transport/publisher CA, сертификаты с правильными назначениями и случайный пароль оператора. CA keys остаются в игнорируемом `secrets/issuer`, не монтируются в runtime. Повтор поверх существующего удостоверения запрещён. Это явная локальная PKI, а не production-доверие; тестовый сертификат браузера можно разрешать только для проверенного локального адреса. Внешнее размещение использует те же Compose/API, но с действительными адресами, SAN и доверенной PKI, без отключения проверки TLS.

## Подготовка и запуск

```sh
python3.13 prepare.py render
docker compose --env-file .env config --quiet
docker compose --env-file .env build
docker compose --env-file .env --profile provision run --rm platform-ui-configuration-init
docker compose --env-file .env up -d --wait
docker compose --env-file .env ps
```

Эти команды используют основной удалённый HTTPS-маршрут. Если Platform UI и Keycloak размещены в одной локальной Compose-установке, сначала запустите Keycloak, задайте `KEYCLOAK_BACKCHANNEL_URL=https://keycloak:8443` и точное имя его ingress-сети в `KEYCLOAK_INGRESS_NETWORK`, затем добавьте владельческий overlay ко всем командам: `docker compose -f compose.yml -f compose.local-keycloak.yml ...`. Overlay подключает только API и одноразовый provisioner к внешней для этого владельца, но создаваемой владельцем Keycloak ingress-сети; БД IdP и закрытая backend-сеть не доступны. TLS CA и SAN `keycloak` продолжают проверяться. Корневая композиция включает тот же overlay и сама создаёт сеть через поставку Keycloak, поэтому это не зависимость от заранее подготовленного пользовательского ресурса. Официальная семантика такого слияния определена Docker Compose для [merge](https://docs.docker.com/reference/compose-file/merge/) и [external networks](https://docs.docker.com/reference/compose-file/networks/#external).

`render` проверяет полный набор переменных и обязательных файлов; создаёт публичный `config.json`, конфигурацию API/nginx и несекретную конфигурацию provision. Это не дополнительный источник настроек: файлы производны от `.env`, SHA-256 собственного CSS и неизменяемых внутренних путей; ручное редактирование `runtime` не поддерживается. Отсутствующая настройка — ошибка, запасных значений в Compose/коде нет. При изменении env повторите `render` и `up -d --force-recreate`.

Realm должен уже существовать. `OPERATOR_USER` обязан быть `platform-operator`; это единственная обычная человеческая identity операторского контура по 00-INFRA-20261106-0007-workload-and-operator-identity. Одноразовая настройка использует отдельную deployment identity; повтор проверяет собственный клиент и уже выданную роль оператора, не сбрасывает его пароль. Первый оператор — техническая начальная учётная запись с профилем DRP Operator и недоставляемым адресом `platform-operator@bootstrap.invalid`; реальный оператор меняет профиль и единый пароль через IdP, исходящие письма этой задачей не отправляются. Чужой одноимённый клиент или существующий оператор без роли не перезаписываются: требуется явное решение администратора. Сервисы назначают ему собственные роли и используют отдельные OIDC-клиенты/audience; publisher identities остаются машинными. Роль `platform-ui-viewer` разрешает просмотр, но не предметные операции внутри страниц.

`PUBLIC_URL` открывается в браузере. В основном самостоятельном режиме локальный `https://keycloak:18443` означает опубликованный host endpoint через явный `keycloak:host-gateway`; сертификат IdP должен подтверждать DNS `keycloak`. На Linux host loopback не маршрутизируется из bridge-контейнера, поэтому для совместного локального размещения используется описанный выше overlay и `https://keycloak:8443` внутри ingress-сети. Не меняйте host bind на `0.0.0.0` ради обхода. Для удалённого узла задайте его реальный HTTPS FQDN в `KEYCLOAK_BACKCHANNEL_URL`; это сетевой адрес зависимости, не путь к соседнему каталогу. Публичный `KEYCLOAK_URL` определяет точный issuer JWT и должен быть доступен браузеру. Исправьте firewall и SAN, а не отключайте TLS. Все относительные файловые пути считаются от собственного env; ни одного абсолютного пути рабочей станции в поставке нет.

Остановка без удаления данных: `docker compose --env-file .env down`. Том хранит описания, происхождение, защиту владения, ревизии/последовательности, маркеры отзыва, сообщения состояния и журнал технических изменений. Владельцы сохраняют канонические декларации; повторная публикация возвращает только актуальные описания и новое состояние. Она не восстанавливает прежнюю историю приёмника и его защитные записи: для этого нужна его согласованная резервная копия. Перед обслуживанием сохраните копию через SQLite backup API либо остановите API и сохраните весь том; не копируйте один живой `.sqlite` без WAL. Удаление тома — отдельное решение оператора, не штатное восстановление.

## Обновление и восстановление

Все команды выполняются из каталога platform-ui для собственного проекта. Если оболочка уже запущена корневой инфраструктурой, пересоздавайте её роли через корневой Compose, не запускайте второй API-писатель над тем же DATA_VOLUME. После первичной настройки обычный повторный запуск — `docker compose --env-file .env --profile ui up -d --no-build --pull never`; профиль ui нужен только для публикации собственного состояния. IdP должен быть доступен по настроенному HTTPS, но его контейнеры этот Compose не запускает.

Перед обновлением сохраните согласованную копию DATA_VOLUME и, при включённой собственной публикации, UI_STATE_VOLUME, а также настройки и защищённые удостоверения. Сборка и `prepare.py render` должны соответствовать одному выпуску: digest оформления не берётся из старого runtime. API обновляется перед издателями новых добавочных полей; откат выполняется в обратном порядке по [контракту](../docs/api/platform-ui-injection.md). Старый образ допустим лишь при совместимости SQLite-схемы и сохранённых сообщений, иначе нужна проверенная соответствующая копия; последовательности и чужие identities не сбрасываются.

На узле образа проверьте фактическую библиотеку SQLite без чтения базы или секретов: `docker compose exec -T platform-ui-api python -c 'import sqlite3; print(sqlite3.sqlite_version)'`. Версия Python не заменяет версию движка; поддержка и исправления оцениваются для закреплённого образа/пакета. Фактическая SQLite 3.49.2 остаётся в принятом стеке, а API исключает известную WAL-reset race сериализацией полного времени жизни всех своих соединений одним процессным `RLock`; конкурентная регрессия не допускает второго соединения до закрытия первого. Издатель использует один последовательный цикл. Обновление до SQLite 3.51.3+ остаётся совместимым усилением, но не заменяет проверку этой инварианты. WAL/FULL не является независимой копией диска: обе базы резервируются отдельно, резервная копия не монтируется одновременно действующему и восстановленному писателю. Проверки конкурентной границы, backup/restore и повторной публикации находятся в [test/test_storage_boundaries.py](test/test_storage_boundaries.py), результат восстановления — в [test/sqlite-boundaries-result.md](test/sqlite-boundaries-result.md).

Восстановление проверяйте на отдельном томе и отдельном адресе: реальный OIDC-вход, приём разрешённого собственного описания/состояния, запрет чужой identity, свежесть, штатная отписка и возврат. Восстановление старой SQLite-копии само по себе не обновляет состояния: нужны свежие подтверждённые публикации владельцев. Канонические UI/декларации остаются у владельцев, а история рабочего приёмника и защитные записи владения сохраняются в его backup. Выпуск собственного состояния нельзя начинать с sequence 1 при сохранённом UUID и потерянном журнале. Локальные отчёты не закрывают независимое восстановление/PKI/WAN, перечисленные в [TASKS](TASKS.md).

## Все настройки

Каждая строка ниже имеет обязательный префикс `AELEV_INFRASTRUCTURE_PLATFORM_UI_`. Значения находятся только в собственном `.env`; шаблон — пример, не резервный источник.

| Суффикс | За что отвечает и зачем нужен |
|---|---|
| `COMPOSE_PROJECT` | Идентичность собственного Compose-проекта; разделяет жизненные циклы поставок. |
| `IMAGE` / `API_IMAGE` | Имена собираемых/доставленных образов оболочки и API. |
| `NODE_IMAGE` | Закреплённый образ сборки React; в runtime Node нет. |
| `NGINX_IMAGE` | Закреплённый непривилегированный HTTPS-сервер оболочки. |
| `PYTHON_IMAGE` | Закреплённый Python API и задачи provision; версии соответствуют техстеку. |
| `BIND` | Интерфейс host для опубликованного порта; `127.0.0.1` ограничивает локальный доступ. |
| `PORT` | Порт host; внутри nginx слушает неизменяемый `8443`. |
| `PUBLIC_URL` | Точный публичный HTTPS origin, OIDC redirect/logout и запрет встраивания на origin оболочки. |
| `KEYCLOAK_URL` | Публичный origin IdP для браузера и проверки точного issuer JWT. |
| `KEYCLOAK_BACKCHANNEL_URL` | HTTPS origin IdP, доступный API/provision; может отличаться от публичного адреса, но не от issuer. |
| `KEYCLOAK_INGRESS_NETWORK` | Точное имя ingress-сети Keycloak только для владельческого local co-location overlay; удалённый основной режим её не использует. |
| `KEYCLOAK_REALM` | Граница идентификации, откуда принимаются JWT; realm заранее создан. |
| `KEYCLOAK_CLIENT_ID` | Собственный публичный PKCE-клиент и требуемая аудитория API. |
| `PROVISION_ADMIN_USER` | Имя отдельного администратора установки; пароль в файле, не в env. |
| `OPERATOR_USER` | Обязательное имя единственного обычного оператора: только `platform-operator`. |
| `RUNTIME_ROOT` | Собственный каталог производных конфигураций; не хранилище канонических настроек. |
| `SECRET_ROOT` | Собственные файловые удостоверения по ролям; секреты других компонентов не монтируются. |
| `SECRET_GID` | Дополнительная группа чтения секретов штатным непривилегированным UID. |
| `MEMORY_LIMIT` / `API_MEMORY_LIMIT` | Отдельные ограничения памяти nginx/API; не обещание пропускной способности. |
| `BACKEND_NETWORK` | Собственная внутренняя сеть nginx/API, API не публикуется на host. |
| `BACKEND_SUBNET` | Явная непересекающаяся подсеть локальной внутренней сети; оператор проверяет её до создания сети. |
| `EGRESS_NETWORK` | Собственная выходная сеть для HTTPS к IdP; не общая сеть потребителей. |
| `EGRESS_SUBNET` | Явная непересекающаяся подсеть локальной выходной сети; не выдаёт дополнительных полномочий или маршрутов. |
| `DATA_VOLUME` | Постоянная рабочая копия технических метаданных и журнал. |
| `STATUS_TTL_SECONDS` | Максимальный возраст присланного состояния; затем только `UNKNOWN`. |
| `POLL_SECONDS` | Пауза последовательного чтения метаданных браузером после завершения запроса; текущая установка и шаблон задают `60` секунд. Этот же параметр определяет пояснение в индикаторе, а не отдельная настройка интерфейса. |
| `JWKS_CACHE_SECONDS` | Время хранения доверенных ключей IdP; неизвестный `kid` вызывает обновление, отказ доверия закрывает API. |
| `MAX_MODULES` | Ограничение числа идентификаторов вместе с отозванными: происхождение и ревизии не забываются. |
| `MAX_BODY_BYTES` | Верхняя граница JSON публикации на nginx/API; защита ресурсов, не ограничение доменных данных. |

## Опции Compose и Dockerfile

`build.context: .` обеспечивает переносимость; `target` разделяет nginx/API/проверки без общей предметной сборки. `depends_on` ждёт только здоровье собственного API; удалённую готовность IdP проверяет HTTPS, не Docker-сеть. Публикуется только nginx. Read-only binds и `create_host_path: false` запрещают случайное создание пустых секретов. `read_only`, ограниченный `/tmp`, `cap_drop: ALL`, `no-new-privileges` и непривилегированные UID ограничивают запись и полномочия. Named volume нужен для подтверждённой записи; отдельная внутренняя сеть не даёт внешнего прямого доступа к API. `restart: unless-stopped` действует только на постоянные процессы, provision имеет `restart: no`. Healthchecks проверяют настоящие HTTPS endpoints с CA/mTLS, не существование процесса. `profiles: [provision]` исключает административную задачу из обычного `up`. В `.dockerignore` исключены тесты, история, env, секреты и runtime.

nginx проверяет TLS backend и предъявляет собственный клиентский сертификат; пользовательский заголовок `X-Verified-Publisher` перезаписывается результатом проверки сертификата. CSP не допускает внешнего JavaScript в оболочке и запрещает встраивание самой оболочки; внешний HTML разрешён только в sandbox iframe по HTTPS либо точному локальному loopback HTTP. API проверяет issuer/audience/RS256/exp/iat/sub и собственные роли. Владелец не может изменить чужой модуль. Нет proxy к предметным API и передачи токенов в `postMessage`.

## Собственное состояние в platform-ui

Подтверждённая штатная отписка скрывает модуль, а исчезновение публикаций без отписки оставляет строку с «Нет связи» по [контракту присутствия](../docs/api/platform-ui-injection.md#присутствие-и-штатная-отписка). `STATUS_TTL_SECONDS` ограничивает отдельно возраст наблюдения и время без нового подтверждённого сообщения. Точные повторы не продлевают присутствие. Старые декларации при миграции сохраняют защиту владения, но не входят в текущий список до нового сообщения владельца; API не восстанавливает каталог из своей истории. При `LOST` общий индикатор красный, даже если список успешно получен.

Реальную проверку этого поведения на собственной поставке запускайте из этого каталога: `python3.13 test/presence.py --chromium <Chromium>`. Только для локального loopback с проверенной локальной PKI допускается `--allow-local-certificate`. Тест проверяет stop/start собственного издателя, исчезновение/возврат строки, pause/unpause без отписки, настоящий серверный TTL, состояние браузера и общий индикатор; исходные контейнеры восстанавливаются, данные не удаляются. [Отчёт](test/presence-result.md) и снимки сохраняются в собственном `test`. Проверка индикатора и управления из произвольного iframe: `python3.13 test/refresh.py --chromium <Chromium>`, [отчёт](test/refresh-result.md).

Повторная проверка названия назначения и технологического состава: [результат](test/status-labels-result.md). Она не подменяет прежние испытания жизненного цикла.

Результаты текущего прогона: [читаемый отчёт валидации](test/status-validation-result.md), [реальные stop/start nginx/API/издателя](test/status-publication-result.md), [снимок](test/status-publication.png). Отдельная итоговая сверка всех инфраструктурных строк: [обзор](test/status-overview-result.md).

Общую сверку инъектированных строк выполняет `python3.13 test/status_overview.py --expected-module-count <число-запущенных-владельцев>` с теми же обязательными `--ui-url`, `--viewer-user`, `--viewer-password-file` и `--chromium`, что у браузерной проверки жизненного цикла ниже. Она читает описание каждого владельца динамически и сверяет все компоненты в API/DOM, не содержит встроенного перечня продуктов и не останавливает контейнеры. Исключение сертификата разрешено только явно для loopback через `--allow-local-certificate`.

Профиль `ui` включает только собственную техническую роль публикации; её наличие не является условием старта nginx/API. Для входа пользователя и получения издателем токена нужен настроенный доступный IdP: профиль не устраняет эту зависимость и не открывает анонимный доступ при его отказе. Отдельная строка имеет тип `INFRASTRUCTURE`, не добавляет функциональные разделы. Состав: nginx, собственный API и издатель; публикация проходит тот же авторизованный API, а не прямой доступ к рабочей SQLite. Подтверждённая отрицательная native readiness отличается от отсутствия связи: transport/TLS-ошибка означает `UNKNOWN`. При штатной остановке издатель подтверждает отписку, и строка исчезает; при исчезновении публикаций без отписки строка остаётся с «Нет связи» после срока свежести приёмника.

Поставка использует собственный образ и включённый публичный `aelev-platform-ui-client==1.1.0` в `vendor`; SHA-256 закреплён собственным Poetry lock. Это библиотека транспорта, не общий runtime-образ/каталог продуктов. Сборка после извлечения этого каталога не читает соседние исходники. Протокол, установка артефакта и пример собственного издателя: [руководство оболочки](USER_MANUAL.md#отправить-метаданные-из-python).

Из этого каталога, после подготовки удостоверений:

```sh
docker compose --env-file .env --profile ui build platform-ui-status-publisher
docker compose --env-file .env --profile provision run --rm platform-ui-status-provision
docker compose --env-file .env --profile ui up -d --no-build platform-ui-status-publisher
docker compose --env-file .env --profile ui stop platform-ui-status-publisher
```

Рабочий процесс получает только `secrets/status/{shell-ca.crt,identity-ca.crt,publisher.crt,publisher.key,client-secret}`. Одноразовый `provision` получает отдельные `secrets/status-admin/{admin-user,admin-password}`, не монтируемые в runtime. Закрытые ключи CA не доставляются в контейнеры. Используйте утверждённые цепочки CA, SAN/EKU и ротацию; генерация локального удостоверения описана в руководстве и не заменяет production PKI/SVID. HTTPS-адреса могут находиться в разных странах; общей Docker-сети с UI/IdP нет. `host.docker.internal` и `keycloak:host-gateway` — только локальные адресные alias примера; для удалённой установки задайте реальные FQDN/порты и доступность сети. Проверка сертификатов не отключается.

Восстановление требует собственного backup журнала или согласованного нового UUID, не сброса чужой БД/повторного sequence=1. Состояние оболочки восстанавливается повторной публикацией, canonical источник описания/состава остаётся у владельца.

`test/status_publication.py` работает с уже существующей настоящей установкой: OIDC/API/DOM, stop/start частей и издателя, реальное истечение TTL, возврат исходных контейнеров. Пример: `python3.13 test/status_publication.py --ui-url https://<ui-host>:<port> --viewer-user <viewer> --viewer-password-file <password-file> --chromium <installed-chromium> --status-ttl-seconds 120`. Исключение браузерной проверки сертификата допустимо только явным `--allow-local-certificate` на loopback с локальной PKI; рабочие издатели всегда проверяют TLS. Тест не создаёт фиктивных identities, каталогов, контейнеров, сетей или томов и восстанавливает исходное состояние; отчёт/снимок остаются в `test`. Полный остановленный приёмник UI физически не может доставить собственный свежий отчёт: проверяется UNKNOWN в уже открытом браузере и восстановление после старта.
