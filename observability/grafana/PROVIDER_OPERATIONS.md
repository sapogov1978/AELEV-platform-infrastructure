# Grafana — эксплуатация поставщика

## Структура поставки

```text
grafana/
├── README.md, USER_MANUAL.md, SPEC.md, TASKS.md, CHANGELOG.md
├── compose.yml, .env.example     # .env — рабочие настройки вне Git
├── Dockerfile.status             # свои технические роли и проверки
├── dashboards/                  # свои технические панели, README и JSON
├── examples/owner-metrics/       # проверяемый нейтральный пример владельца, не runtime Grafana
├── pyproject.toml, poetry.lock
├── vendor/                       # публичные wheels, закреплённые SHA-256
├── prepare.py                    # собственные init/tls/render
├── deployment.json               # правила подготовки и перечень секретов
├── config/                       # grafana-datasources.yml, grafana-dashboards.yml, notifications-*.json
├── status_publisher.py            # только собственные проверки и публикации
├── oidc_provision.py             # одноразовая подготовка входа оператора
├── secrets/                      # доставка вне Git и образа
│   ├── native/                   # собственные TLS и дополнительные секреты
│   ├── status/                   # собственный издатель и нативная проба
│   ├── status-admin/             # только явные одноразовые задачи
│   └── oidc/                     # публичная CA IdP и секрет клиента Grafana
├── runtime/                      # подготовленные файлы из config/env
└── test/                         # проверки и читаемые результаты
```

Дерево показывает значимые файлы, без кэшей и подробного списка отчётов. `.env`, `secrets/` и производные `runtime/` создаются/доставляются оператором и исключены из Git и сборки. Именованные тома данных и журнала издателя объявлены в Compose; это не папки исходников. `config/`, `deployment.json` и собственный env — источники подготовки, `runtime/` — их результат.

## Назначение

Подключение метрик и собственных панелей нового владельца пошагово описано в [USER_MANUAL](USER_MANUAL.md): получение удостоверений, местный Prometheus с устойчивым отправителем, отдельные права Grafana, JSON панели, повторная публикация, диагностика и очистка. [Изолированный сквозной тест](test/onboarding.py) использует настоящие закреплённые компоненты без новых записей в рабочий архив; [результат](test/onboarding-result.md) фиксирует проверенные границы.

В ревизии 3 собственный издатель публикует кнопку «Открыть» на существующий интерфейс Grafana в группе и строке нативного процесса: адрес формируется из уже имеющихся `PUBLIC_HOST` и `PORT` собственного env. Это публичный адрес для браузера, не `UI_HEALTH_URL` внутри Docker-сети; при переносе он должен разрешаться и быть доступен оператору с корректным TLS. Издатель и другие части ссылку не наследуют. Обычный вход в консоль выполняет `platform-operator` через собственный OIDC-клиент Grafana и общую SSO-сессию Keycloak; локальная форма и Basic Auth отключены. Правила изменения ревизии, HTTPS и совместимости — в [контракте](../../docs/api/platform-ui-injection.md#ссылки-на-собственные-интерфейсы).

Текущие проверки самостоятельной поставки: [результат](test/standalone-validation-result.md).

[Результат проверки ссылки](test/open-link-result.md): собственные регрессии и открытие настоящего интерфейса в браузере.

Собственный издатель имеет `stop_grace_period: 2m`: это время на завершение текущего запроса и подтверждение отписки через удалённый HTTPS, не запасное значение env и не бесконечное ожидание. Если связь недоступна, неподтверждённый выход сохраняется в журнале, а UI не скрывает строку как штатно завершённую.

Повторная проверка названия назначения и технологического состава: [результат](test/status-labels-result.md). Она не подменяет прежние испытания жизненного цикла.

В «Состоянии» верхняя строка называется «Панели наблюдения и уведомления» (`Monitoring dashboards and notifications`) и отражает назначение, а раскрываемый состав показывает технологии и процессы этой поставки. Переименование выполнено в исторической ревизии 2; текущая ревизия 3 дополнительно содержит ссылку на собственную консоль. Названия публикует сам владелец; оболочка не содержит таблицы переименований. UUID, identity, состав и последовательность сохраняются.

Это полная самостоятельная поставка Grafana: нативный процесс, собственные настройки, сеть, удостоверения и данные, а также независимая UI-часть. Она предоставляет запросы, панели и уведомления; предметные панели создаёт и поставляет наблюдаемый владелец. Родитель observability только включает этот Compose без поправок.

Сборка использует только этот каталог, собственный Poetry lock и включённый публичный артефакт `aelev-platform-ui-client` 1.1.0. Общего образа издателя нет; библиотека содержит транспорт, а не перечень продуктов. Канонический протокол: [инъекция UI](../../docs/api/platform-ui-injection.md). При извлечении UI-части в отдельный репозиторий публичный контракт доставляется как документация выпуска, не как приватный импорт соседнего сервиса.

Скопируйте `.env.example` в `.env`, задайте реальные HTTPS-адреса UI, IdP и собственного продукта, доступность DNS/портов и правильные SAN сертификатов. Удалённому издателю не нужна Docker-сеть другого узла. Локальный `UI_HEALTH_URL` использует имя собственного процесса в собственной сети; удалённая проба использует маршрутизируемый HTTPS-адрес. Никаких запасных значений Compose не содержит; отсутствие переменной запрещает разрешение конфигурации.

Секреты `secrets/status`: `shell-ca.crt`, `identity-ca.crt`, собственные `publisher.crt/key`, `client-secret`, а также `probe-ca.crt`, `probe.crt/key` для чтения своего health-интерфейса. `secrets/oidc` содержит проверенную публичную CA Keycloak и выданный только OIDC-клиенту Grafana `client-secret`. Закрытые ключи CA рабочим процессам не передаются. Для явной одноразовой подготовки обоих Keycloak-клиентов используется отдельный `secrets/status-admin` с `admin-user/admin-password`, не монтируемый в постоянные процессы. Генерация и установка публичного клиента издателя описаны в [руководстве](../../platform-ui/USER_MANUAL.md#создание-и-подключение-ui-нового-сервиса).

Из этого каталога:

```sh
docker compose --env-file .env --profile ui build grafana-status-publisher
docker compose --env-file .env --profile provision run --rm grafana-oidc-provision
docker compose --env-file .env --profile provision run --rm grafana-status-provision
docker compose --env-file .env --profile ui up -d --no-build grafana-status-publisher
docker compose --env-file .env --profile ui stop grafana-status-publisher
```

Общее развёртывание из родительского каталога сохраняет тот же код и параметры. `provision` не стартует автоматически и не является постоянно работающим компонентом. Права на Docker API, остановку чужих процессов или доменные данные не выдаются.

| Суффикс `AELEV_INFRASTRUCTURE_GRAFANA_` | Назначение |
|---|---|
| `COMPOSE_PROJECT` | Имя самостоятельной Compose-поставки нативного процесса и UI-части. |
| `UI_IMAGE`, `UI_PYTHON_IMAGE` | Собственный образ издателя и закреплённая база сборки Python 3.13.7. |
| `UI_URL`, `UI_IDENTITY_URL` | HTTPS-адреса технического API оболочки и IdP, без привязки к их географии. |
| `UI_REALM`, `UI_CLIENT_ID`, `UI_AUDIENCE` | Собственная identity и аудитория JWT, только роль публикации. |
| `UI_MODULE_ID` | Постоянный UUID собственного описания, не переиспользуется для другого владельца. |
| `UI_INTERVAL_SECONDS`, `UI_TIMEOUT_SECONDS` | Интервал отчёта и предел каждого сетевого ожидания; опрос браузера остаётся минутным. |
| `UI_HEALTH_URL` | Только собственный проверяемый HTTPS-интерфейс готовности. |
| `UI_SECRET_ROOT`, `UI_SECRET_GID` | Каталог рабочих удостоверений и дополнительная группа чтения. |
| `UI_ADMIN_ROOT`, `UI_PROVISION_UID` | Отдельные учётные данные оператора и UID явной одноразовой подготовки. |
| `UI_STATE_VOLUME` | Устойчивый журнал последовательности/точных повторяемых байтов, сохраняется при stop/start. |
| `UI_NETWORK` | Собственная сеть издателя; при совместном запуске только его нативный процесс подключается к ней. |
| `UI_MEMORY_LIMIT` | Ограничение памяти издателя, не нативного продукта. |
| `OIDC_BROWSER_URL`, `OIDC_INTERNAL_URL`, `OIDC_REALM` | Публичный адрес Keycloak для браузера, внутренний проверяемый адрес для Grafana и realm. |
| `OIDC_CLIENT_ID`, `OIDC_OPERATOR_USER`, `OIDC_SECRET_ROOT` | Собственный OIDC-клиент Grafana, единственная человеческая identity `platform-operator` и каталог его CA/секрета. |

При ошибке транспорта или TLS результат `UNKNOWN`, а не выдуманный отказ. Подтверждённый ответ собственного интерфейса 503 означает `OFFLINE`; 200 означает готовность только с подтверждённым `database=ok`. Штатная подтверждённая отписка скрывает строку; отсутствие публикаций без отписки оставляет строку с «Нет связи» после срока свежести приёмника. Техническая проба не доказывает отсутствие потерь, производительность или правильность содержимого хранилища.

Модульные тесты находятся в `test/test_status_publisher.py`. `test/status_publication.py` проверяет существующую реальную самостоятельную установку, stop/start собственного процесса и издателя, изменения API/браузера и продолжение публикаций прочих исходно доступных владельцев. Тест не создаёт фиктивных сервисов и восстанавливает исходные контейнеры в `finally`; данные не удаляет. Аргументы и проверки PKI описаны в родительском README. Отчёт сохраняется в `test/status-publication-result.md`.

При штатной остановке издателя его подтверждённая отписка скрывает строку; без отписки строка остаётся с `connection=LOST` после TTL. Остальные строки продолжают обновляться. При окончательной замене продукта новый владелец получает новые UUID и identity, не захватывает прежний журнал. Прежнее описание снимает прежний владелец через `DELETE` по каноническому контракту инъекции; новый продукт не удаляет чужую строку.

Результат реальной браузерной проверки: [status-publication-result.md](test/status-publication-result.md), [снимок страницы](test/status-publication.png). Дополнительные проверки описаны в [отчёте валидации](test/status-validation-result.md).

## Секреты: получение и подготовка

Стандартный SECRET_ROOT этого владельца — `./secrets/native`; изменённый путь подставляйте во все команды. Обязательные имена перечислены в собственном `deployment.json` и проверяются `prepare.py render`. Открытые сертификаты не являются секретами, но требуют проверенного происхождения.

| Файл в SECRET_ROOT | Источник и назначение |
|---|---|
| `server.crt`, `server.key` | Собственное серверное удостоверение с цепочкой, SAN PUBLIC_HOST и внутренних адресов данного процесса, EKU serverAuth. Выпускает утверждённая PKI. |
| `ca.crt` | Публичные цепочки доверия техническим клиентам/серверам данного контура. Не закрытый ключ CA. |
| `client.crt`, `client.key` | Собственное clientAuth для проверок/исходящих технических соединений. Выдаёт PKI, которой доверяет фактический endpoint. Не ключ другого продукта. |
| `admin-password` | Первоначальный пароль `ADMIN_USER` пустой БД Grafana. Выдаёт внешнее хранилище; локальный tls-генератор создаёт случайно. Это аварийный/bootstrap-материал, не обычный человеческий вход: локальная форма и Basic Auth отключены. |
| `encryption-key` | Долговечный ключ защищённых настроек Grafana; выдаёт внешнее хранилище, локально создаёт генератор. Сохранить защищённо вместе с совместимой резервной копией БД. |
| `smtp-password` | Пароль SMTP-аккаунта у оператора выбранного relay. Файл обязателен, но может быть пустым только при SMTP_ENABLED=false; локальный генератор создаёт именно пустой файл. |
| `trusted-ca/` | Публичные цепочки для внешнего SMTP; подготовить каталог и хешированные ссылки OpenSSL rehash. Это не приватные ключи relay. |

Новый случайный SMTP-пароль не создаёт почтовый аккаунт: сначала получите сервер, пользователя и реквизиты у владельца relay. При включении почты доставьте действующий пароль и доверие, настройте SMTP-поля, повторите `render` и проверьте реальное письмо. Аварийный `admin-password` меняют штатным административным способом Grafana и синхронизируют с внешним источником, но обычный оператор им не входит. Не заменяйте `encryption-key` произвольной строкой при рестарте: существующие защищённые значения связаны с прежним ключом; используйте поддерживаемую процедуру миграции ключа и проверенный backup.

Для новой локальной установки заполните собственный env и вызовите `python3.13 prepare.py tls --issuer-dir /secure/local-observability-issuer`, затем `python3.13 prepare.py render`. Генератор создаёт только файлы этого владельца: сертификаты на 30 дней, локальные CA на 365 дней; непустой SECRET_ROOT не перезаписывает. Один явно выбранный оператором issuer может выдавать совместимые локальные удостоверения независимо размещённых тестовых продуктов, но не становится их общим runtime или общей папкой данных. При самостоятельном вызове без --issuer-dir issuer находится в собственном `secrets/issuer`, не монтируется в контейнеры. Общий запуск через слой сам по себе не подготавливает UI/OIDC-секреты.

В production генератор локальной CA пропускают: собственные ключи/SVID и цепочки доставляет утверждённый внешний источник по ADR-0017. Если PKI работает через CSR, создайте отдельный ключ `openssl req -new -newkey rsa:3072 -nodes -keyout <новый-каталог>/server.key -out <новый-каталог>/server.csr -subj /CN=grafana -addext 'subjectAltName=DNS:<реальный-host>' -addext 'extendedKeyUsage=serverAuth'`; CA возвращает server.crt с правильными SAN/EKU. Для clientAuth выполняется отдельная выдача, не повторное использование server.key. Private CA key в SECRET_ROOT запрещён.

Каталоги имеют `0750`, нативные файлы `0640`, группа SECRET_GID: tls-генератор выставляет её из env; Compose добавляет её нативному процессу независимо от его UID. При внешней доставке примените те же права и группу до запуска, не `chmod 777`. Источники/закрытые CA остаются на операторской машине с `0700/0600`. Перед сменой доверия подготовьте обе цепочки и новый собственный набор, обновите render и контролируемо пересоздайте изменённую роль в действующем проекте; автоматическая ротация локальным генератором не реализована.

### Человеческий вход через Keycloak

Grafana имеет собственный confidential OIDC-клиент и точный callback `<public-origin>/login/generic_oauth`; authorization code защищает PKCE S256. Одноразовый `grafana-oidc-provision` создаёт клиент, аудиторию, realm-роль `grafana.operator`, назначает её точному включённому пользователю `platform-operator` и атомарно сохраняет `client-secret`. При входе Grafana строго сопоставляет эту роль с организационной ролью `Admin`, чтобы оператор видел все панели владельцев и мог управлять ресурсами организации; серверное право Grafana Admin из OIDC не выдаётся. Прочие identity отклоняются. `allow_sign_up` лишь создаёт локальную проекцию уже допущенной OIDC-identity; строгая роль не позволяет ему открыть доступ другим пользователям.

Браузер переадресуется на Keycloak автоматически: действующая SSO-сессия впускает `platform-operator` без повторного ввода пароля. Platform UI не передаёт Grafana свой token. Локальная форма, Basic Auth и анонимный доступ отключены; первичный локальный администратор остаётся только аварийным/bootstrap-механизмом, не обычным входом оператора.

До запуска `grafana-oidc-provision` оператор доставляет проверенную публичную CA Keycloak как `OIDC_SECRET_ROOT/ca.crt`. Каталог имеет `0750`, CA и создаваемый `client-secret` — `0640`; владец из `UI_PROVISION_UID` должен иметь право записи, а нативная Grafana — только чтение через `SECRET_GID`. Не копируйте частный ключ CA и не создавайте `client-secret` случайной строкой: его получает и атомарно сохраняет только одноразовая роль.

### Секреты издателя состояния

Пути ниже соответствуют шаблону `UI_SECRET_ROOT=./secrets/status`; при другом значении используйте собственный настроенный каталог. Источники доверия определяются адресами, не совместным размещением: узел в другой стране получает публичные цепочки CA и своё удостоверение через защищённую доставку, а не доступ к чужой папке.

| Файл | Откуда получить и зачем |
|---|---|
| `shell-ca.crt` | Проверенная публичная цепочка CA HTTPS-сервера оболочки; получить у её оператора. Это не CA клиентских издателей. |
| `identity-ca.crt` | Проверенная публичная цепочка CA HTTPS IdP; получить у оператора IdP. |
| `publisher.crt`, `publisher.key` | Собственное удостоверение `clientAuth`; его выпускающая CA должна входить в `publisher-ca.crt` приёмника UI. Закрытый ключ принадлежит только этому издателю. |
| `client-secret` | Выдаёт Keycloak для собственного confidential client; сохраняет `grafana-status-provision`. Не генерируйте произвольный пароль вместо секрета существующего OIDC-клиента. |
| `probe-ca.crt`, `probe.crt/key` | Публичная CA собственного health-сервера и отдельная clientAuth-проба этого владельца; выдаёт его техническая PKI. Не административные файлы IdP и не закрытый ключ native-процесса. |
`UI_ADMIN_ROOT` содержит отдельные `admin-user` и `admin-password`: имя и действующий пароль администратора развёртывания Keycloak получают у оператора IdP или из внешнего хранилища. Это не пароль service account и не пароль пользователя браузера. Доставьте их файловым механизмом; например, `install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password`, а имя запишите в `admin-user` без секрета. Provision должен иметь право записи в `UI_SECRET_ROOT`, runtime — только чтение.

Перед локальной подписью проверьте `openssl version` и поддержку OpenSSL 3; при отсутствии используйте утверждённый пакет вашей ОС (`brew install openssl@3` на macOS, `sudo apt-get install openssl` на поддерживаемой Debian/Ubuntu) или подготовленную операторскую станцию. Эти команды не устанавливают CA в системное доверие и не выполняются при запуске контейнера.

Первичная доставка административных файлов (пути источника и имя замените данными своего IdP, не пароль в команде):

```sh
umask 077
install -d -m 750 secrets/status-admin
test ! -e secrets/status-admin/admin-user && test ! -e secrets/status-admin/admin-password || exit 1
STATUS_ADMIN_USER=deployment-admin
printf '%s\n' "$STATUS_ADMIN_USER" > secrets/status-admin/admin-user
install -m 640 /secure/idp-admin-password secrets/status-admin/admin-password
chmod 640 secrets/status-admin/admin-user
```

Имя deployment-admin — пример существующей identity, не команда создания пользователя. Если у вас другое имя или UI_ADMIN_ROOT, задайте их явно; GID каталога/файлов должен совпадать с UI_SECRET_GID, а владелец — с UI_PROVISION_UID. Уже доставленные пароли не перезаписываются первичной командой. После удаления одноразового контейнера пароль не нужен рабочему издателю; локальную административную доставку уберите из runtime-узла или выдавайте заново только на время provision.


Для новой локальной identity можно создать ключ и CSR на доверенной операторской машине. Нужен OpenSSL 3 для `-copy_extensions`; пути `/secure/...` ниже заменяются выбранными операторскими файлами, это не обязательные каталоги сервиса. Публичные CA берутся из проверенного источника; неизвестный сертификат из сети не становится доверенным только потому, что назван `ca.crt`.

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/publisher.key && test ! -e secrets/status/publisher.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=publisher -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/publisher.key -out secrets/status/publisher.csr
# Только локальный тест: ключ CA остаётся на операторской машине, не в runtime.
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/publisher.csr \
  -CA /secure/ui-publisher-ca.crt -CAkey /secure/ui-publisher-ca.key \
  -CAcreateserial -out secrets/status/publisher.crt
install -m 640 /secure/ui-server-ca.crt secrets/status/shell-ca.crt
install -m 640 /secure/idp-ca.crt secrets/status/identity-ca.crt
chmod 640 secrets/status/publisher.key secrets/status/publisher.crt
```

Тестовую CA издателей создаёт оператор локальной оболочки при её явной подготовке PKI; берутся именно `issuer/publisher.crt/key`, не серверный ключ UI. В рабочей среде последнее подписание локальной CA не выполняют: удостоверение и обновляемую identity доставляет утверждённая PKI/SPIRE по [ADR-0017](../../docs/adr/20260803-0017-zero-trust-and-operational-security.md). CSR можно передать CA, закрытый ключ нельзя. Перед включением издателя доставьте также перечисленные файлы нативных проб и выполните собственный `--profile provision run --rm grafana-status-provision` из раздела запуска.


Для новой локальной пробы (не рабочей SVID) используйте собственную операторскую CA, которой доверяет данный health endpoint; существующие файлы не перезаписываются. Если issuer расположен иначе, замените путь. Это отдельная пара, не копия native client.key:

```sh
umask 077
install -d -m 750 secrets/status
test ! -e secrets/status/probe.key && test ! -e secrets/status/probe.crt || exit 1
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -subj /CN=probe -addext 'extendedKeyUsage=clientAuth' \
  -keyout secrets/status/probe.key -out secrets/status/probe.csr
openssl x509 -req -sha256 -days 30 -copy_extensions copy \
  -in secrets/status/probe.csr \
  -CA /secure/local-observability-issuer/internal-ca.crt -CAkey /secure/local-observability-issuer/internal-ca.key \
  -CAcreateserial -out secrets/status/probe.crt
install -m 640 secrets/native/ca.crt secrets/status/probe-ca.crt
chmod 640 secrets/status/probe.key secrets/status/probe.crt
```


### Хранение, доступ и ротация

Секреты разделяются по среде, владельцу и роли. Локальные файлы — только материал стенда или доставка, не каноническое production-хранилище; рабочий источник — внешнее утверждённое хранилище, доставка в память/tmpfs по ADR-0017. Не включайте секреты в Git, образ, архив исходников, команды с подстановкой содержимого или отчёты. Не запускайте `set -x`, не публикуйте раскрытый `docker compose config`; проверяйте через `config --quiet`. Резервные копии секретов хранятся отдельно, зашифрованно, с ограниченным доступом; закрытые CA — только у оператора/KMS/HSM, никогда у рабочего процесса.

Для status-файлов установите каталоги `0750`, файлы `0640`, группу из собственного `UI_SECRET_GID`; владельцем каталога должен быть оператор с `UI_PROVISION_UID`, которому разрешена запись client-secret. UID рабочего издателя остаётся заданным собственным образом/Compose; дополнительная группа даёт только чтение. В командном примере ниже STATUS_SECRET_GID — числовое значение уже настроенного UI_SECRET_GID, не новая переменная сервисного env. Не делайте ключи общедоступными ради запуска. Права нативных секретов описаны отдельно выше.

```sh
: "${STATUS_SECRET_GID:?set the numeric GID from your UI_SECRET_GID}"
chgrp "$STATUS_SECRET_GID" secrets/status secrets/status/*
chmod 750 secrets/status
chmod 640 secrets/status/*
```

Для отдельного административного каталога примените ту же группу, `0750` каталогу и `0640` обоим файлам; владельцу из UI_PROVISION_UID должно быть разрешено чтение admin-password и запись client-secret в status. Keycloak использует административный пароль через env, а не status-admin.

Проверьте срок, SAN/EKU и цепочку сертификата до запуска: `openssl x509 -in secrets/status/publisher.crt -noout -dates -ext extendedKeyUsage`, `openssl verify -CAfile /secure/ui-publisher-ca.crt -purpose sslclient secrets/status/publisher.crt`. Локальное удостоверение из команды действует 30 дней и не обновляется автоматически. Для смены CA сначала доставляют доверие старой и новой цепочкам, затем новые удостоверения, проверяют соединения и только после этого отзывают старые. Ротацию проводят через отдельный подготовленный набор файлов и контролируемое пересоздание собственной роли; генераторы первичного запуска не используют для перезаписи активных ключей. Новый client-secret сначала создают в собственном клиенте Keycloak, затем доставляют повторным собственным provision и пересоздают издателя; обычный повтор provision сам по себе не является ротацией. UUID, identity, ревизия и журнал последовательностей при этом сохраняются.


## Нативный процесс: отдельный запуск

Проверьте Docker Compose, Python 3.13 и OpenSSL; команды установки и назначение PKI приведены в [руководстве слоя](../USER_MANUAL.md#подготовка-и-запуск). Для новой установки из этого каталога:

```sh
python3.13 prepare.py init
# Задайте адреса, bind и доверие в собственном .env.
python3.13 prepare.py tls --issuer-dir /secure/local-observability-issuer
python3.13 prepare.py render
docker compose --env-file .env --profile ui --profile provision build
docker compose --env-file .env --profile provision run --rm grafana-configuration-init
docker compose --env-file .env --profile provision run --rm grafana-oidc-provision
docker compose --env-file .env --profile provision run --rm grafana-status-provision
docker compose --env-file .env --profile ui up -d --no-build
python3.13 test/startup.py
docker compose --env-file .env --profile ui stop
docker compose --env-file .env --profile ui down
```

`init` не перезаписывает существующие настройки, `tls` не заменяет ключи и создаёт только явную локальную PKI. Production использует утверждённые удостоверения с правильными SAN и ротацией. Общий issuer — вход оператора, не секрет рабочего процесса. Подготовка работает через публичный wheel с SHA-256 в собственном lock; общего рабочего образа нет. Нативный процесс не требует профиля; `ui` добавляет только издателя. Явный init без сети и секретов проверяет только свой том. Не запускайте весь provision через up. При смене общей/самостоятельной группы сначала снимите прежних писателей без удаления томов.

| Суффикс `AELEV_INFRASTRUCTURE_GRAFANA_` | Назначение нативной настройки |
|---|---|
| `COMPOSE_PROJECT` | Имя самостоятельной группы, не идентичность данных. |
| `PUBLIC_HOST` | DNS/IPv4 в SAN при локальной выдаче сертификата; не bind. |
| `IMAGE`, `MEMORY_LIMIT` | Закреплённый образ Grafana и лимит памяти только её процесса. |
| `BIND`, `PORT` | Интерфейс и опубликованный HTTPS-порт; удалённый доступ требует маршрутизации и firewall. |
| `RUNTIME_ROOT` | Собственные производные файлы, монтируемые только для чтения; исходники в config и dashboards. |
| `SECRET_ROOT`, `SECRET_GID` | Собственные файловые секреты и группа чтения; ключи CA не монтируются. |
| `DATA_VOLUME`, `DATA_OWNER` | Постоянное имя тома и неизменная идентичность его маркера; переименование не переносит данные. |
| `ADMIN_USER` | Начальный администратор пустой БД; первоначальный пароль в собственном `SECRET_ROOT/admin-password`. Это аварийный/bootstrap-материал; обычный оператор входит как `platform-operator` через OIDC. |
| `OIDC_BROWSER_URL`, `OIDC_INTERNAL_URL`, `OIDC_REALM` | Точные HTTPS-адреса Keycloak для браузера и контейнера, а также realm. |
| `OIDC_CLIENT_ID`, `OIDC_OPERATOR_USER`, `OIDC_SECRET_ROOT` | Имя собственного confidential client, точная identity `platform-operator` и каталог `ca.crt`/`client-secret`. |
| `SMTP_ENABLED` | Явное включение почты; сейчас false, доставки писем нет. |
| `SMTP_HOST` | Внешний SMTP host:port с проверяемым STARTTLS; обязателен при включённой почте. |
| `SMTP_USER` | SMTP-пользователь; пароль в smtp-password, не env. |
| `SMTP_FROM`, `SMTP_TO` | Отправитель и получатель; обязательны при включённой почте. |
| `PROMETHEUS_URL`, `LOKI_URL`, `TEMPO_URL` | HTTPS-адреса назначенных источников метрик, журналов и трасс; опубликованные порты с проверкой CA и клиентским сертификатом. |

`encryption-key` защищает собственные сохранённые секреты Grafana; его потеря не устраняется сменой env. `render` сохраняет отдельно доставленные файлы панелей и создаёт только объявленные производные конфигурации. Панели наблюдаемого сервиса принадлежат ему: доставка по HTTPS API либо оператором в рабочий каталог, не запись приложением в общую удалённую папку. Не занимайте системный UID панели; [USER_MANUAL](USER_MANUAL.md#7-создание-и-публикация-панели) содержит полный API-пример с отдельной identity и проверкой повторного применения, а [dashboards](dashboards/README.md) описывает границу собственных технических панелей Grafana.

Адреса зависимостей — реальные защищённые опубликованные интерфейсы. Локальные aliases host-gateway не создают межстрановой сети; для разнесения меняются адреса, SAN, доверие, bind и firewall. На Linux loopback host не доступен из bridge. Поставка одноузловая; SQLite и собственный том требуют независимой резервной копии. `down` без `--volumes` сохраняет данные и удостоверения.

## Обслуживание, обновление и восстановление

Команды этого README выполняются из собственного каталога владельца. Сначала проверьте, какой Compose-проект использует его данные: самостоятельный, слой observability или корень infrastructure. Если контейнеры принадлежат верхнему проекту, выполняйте адресное действие через его Compose; второй самостоятельный up поверх тех же томов запрещён. Первичную генерацию env/PKI не повторяют при обычном старте. Проверяйте конфигурацию через `docker compose --env-file .env --profile ui config --quiet`, чтобы не выводить секреты.

Сохраняйте весь DATA_VOLUME при остановленной собственной Grafana, encryption-key, настройки источников, рабочие инъекции панелей и журнал издателя. Один живой grafana.db без согласованного состояния SQLite/WAL не является резервной копией. Потеря encryption-key лишает доступа к сохранённым защищённым реквизитам. Восстановление проверяйте на другом томе, с изолированными источниками и выключенной почтой, чтобы не отправлять рабочие уведомления.

Обновление — отдельная операция владельца: согласуйте закреплённый образ, сохраните согласованную копию данных и журнала издателя, подготовьте производные файлы командой `prepare.py render`, затем адресно пересоздайте только изменённые роли в действующем проекте. Не запускайте весь provision и не удаляйте тома. Проверьте нативную готовность, фактический запрос/доставку и подтверждённую публикацию. Старый образ можно вернуть только при совместимости формата данных; иначе нужна соответствующая проверенная резервная копия.

UUID, identity, ревизии и последовательность публикаций также входят в восстановление. UI_STATE_VOLUME не очищают как кэш; после его утраты прежний UUID нельзя начинать с sequence 1. Штатный down без --volumes сохраняет данные. Перенос требует доступных DNS/IP, SAN, доверия и firewall, не общей удалённой папки. Непроверенные WAN, внешняя PKI, нагрузка и резервное восстановление отмечены в собственном [TASKS](TASKS.md); прежний локальный отчёт их не закрывает.

## Проверки

Для собственной уже запущенной самостоятельной поставки проверку UI с остановками запускайте только в согласованном окне. Она адресует проект из собственного env, не уже работающий верхний проект. Подготовьте Python 3.13, Playwright 1.56.0, установленный Chromium и файл пароля существующего оператора:

```sh
python3.13 test/status_publication.py \
  --ui-url https://<адрес-оболочки>:<порт> \
  --viewer-user <оператор> --viewer-password-file <файл-пароля> \
  --chromium <установленный-Chromium> --status-ttl-seconds <TTL-приёмника>
```

Это не читающая диагностика: тест останавливает и возвращает собственные компоненты. Для проверенного loopback с локальной PKI можно явно добавить --allow-local-certificate; рабочие TLS-проверки не отключаются. Наличие издателя подтверждает получение отчёта, не качество или полноту телеметрии. Отчёты прежних выпусков сохраняют историческое значение.

```sh
docker build --build-arg PYTHON_IMAGE=python:3.13.7-alpine3.22 --target checks --build-context tests=./test -f Dockerfile.status -t aelev/grafana-checks:local .
docker run --rm --network none aelev/grafana-checks:local pytest -p no:cacheprovider
```

Реальный вход и повторное использование Keycloak SSO проверяет собственный сценарий; он не печатает пароль и требует явного флага только для исключения доверия на loopback:

```sh
python3.13 test/operator_login.py \
  --grafana-url https://<адрес-Grafana>:<порт> \
  --operator-password-file <файл-пароля-platform-operator> \
  --chromium <установленный-Chromium>
```

Конфигурационные регрессии — `test/test_configuration.py`. Проверка запущенной реальной поставки без создания ресурсов — `test/startup.py`, [результат](test/startup-result.md). Она проверяет TLS готовности и подтверждённую публикацию, не полный stop/start, WAN или восстановление резервной копии. Прежние UI-отчёты исторические; новый полный цикл проверяется собственным `test/status_publication.py`.
