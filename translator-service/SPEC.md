# translator-service: нормативная спецификация

Издатель использует отдельный собственный образ `AELEV_INFRASTRUCTURE_TRANSLATOR_UI_IMAGE`, цель `status-runtime` без модельных весов и нативного исполнителя. Его Docker-проба запускает автономный файл `health.py` из закреплённого `aelev-platform-ui-client==1.1.1` через `python -S`, читает только собственный подтверждённый heartbeat и UUID. Она не импортирует приложение, не выполняет PostgreSQL/Kafka/TLS-запросы и не меняет прежний предел свежести. Минимальный локальный предел памяти этой роли составляет 256 MiB, чтобы повторяющиеся ограниченные TLS-попытки при недоступном приёмнике не завершали издатель по OOM; это не резерв памяти доменного сервиса. Готовность переводчика по-прежнему определяется собственными компонентами, не успехом контейнерной пробы издателя.

Необязательное время выполнения v2-результата измеряется монотонными часами только вокруг вызова непрозрачного провайдера, до записи и публикации результата, по [контракту](../docs/api/translation.md#измерение-времени-выполнения). Оно не включает очередь, прежние незавершённые попытки или повторную доставку; сохранённый результат и его измерение воспроизводятся побайтно. Реализация перевода неизвестна как потребителю, так и `translator-service`; v1 не расширяется.

По [00-INFRA-20261106-0012-translator-technical-capability](../docs/adr/00-INFRA-20261106-0012-translator-technical-capability.md) операторский listener дополнительно принимает `POST /v1/translate` с отдельным OIDC-правом `operator-translate`. Прежние ограничения read-only ниже относятся к частному listener и диагностическим GET, а не к этому явно согласованному исключению. Вход публикуется только через штатный Kafka topic, не прямой записью задания или вызовом модели; API читает свой точный результат после ACK outbox. Определения входа, пределов, ошибок и неидемпотентного нового POST находятся в [контракте](../docs/api/translation.md#операторский-перевод). Перевод не является межсервисным HTTP-интерфейсом, а API не становится владельцем второго источника данных.

Локальное исключение операционного API по [00-INFRA-20261106-0007-workload-and-operator-identity](../docs/adr/00-INFRA-20261106-0007-workload-and-operator-identity.md) выбирается явно HTTP origin в собственной конфигурации только при `ENVIRONMENT=local` и опубликованных loopback-портах. Документация/схема публичны, пять диагностических GET требуют собственного OIDC access token и client role `operator-read`; POST по 00-INFRA-20261106-0012-translator-technical-capability требует отдельного `operator-translate`. Issuer, audience, authorized party, подпись и сроки проверяются владельцем. HTTPS остаётся mTLS-режимом с дополнительным OIDC для POST, без автоматического HTTP при ошибке TLS. IdP сохраняет проверенное HTTPS, callback и origin точны, PKCE S256 обязателен. Административные OIDC-учётные данные доступны только собственной одноразовой задаче `provision`, не API. Исключение не касается межсервисного Kafka, iframe или удалённого размещения; прочие требования TLS ниже относятся к HTTPS-режиму.

Присутствие собственного издателя, штатная подтверждённая отписка и потеря связи определяются только [каноническим UI-контрактом](../docs/api/platform-ui-injection.md#присутствие-и-штатная-отписка) и 00-INFRA-20261106-0008-platform-ui-owner-injection. Отписка скрывает модуль без удаления журнала или изменения ревизии; отсутствие публикаций без отписки оставляет строку с потерей связи. Повтор и восстановление сохраняют владельца, UUID, последовательность и точные неподтверждённые байты.

Собственное состояние инъектируется по [техническому UI-контракту](../docs/api/platform-ui-injection.md) отдельной ролью `ui`: тип INFRASTRUCTURE, собственные БД, Kafka-соединение, consumers, провайдер перевода, outbox, API и издатель. Одна строка «Провайдер перевода» сообщает только доступность непрозрачного порта: `ONLINE` при подтверждённой готовности порта, `OFFLINE` при подтверждённой недоступности и `UNKNOWN` при неполном наблюдении. Семейство, версия, движок, веса и внутренние компоненты провайдера не публикуются и не сохраняются Translator. Наличие UI/IdP не является зависимостью нативного запуска. Источник присутствия — heartbeat worker, provider-neutral `/runtimez` с единственным `{"status":"ok"}` и явное `COMPUTE_DESIRED_STATE`; техническая таблица `translation_runtime_presence` хранит только состояние и время наблюдения. TTL задаёт неизвестность, не удаление заданий или результатов; heartbeat доказывает присутствие, не продвижение очереди.

Общий инфраструктурный компонент владеет контрактом перевода, двумя входными и одним выходным topic каждой версии v1/v2, собственной PostgreSQL-очередью, техническими попытками и результатами. Он не владеет и не выбирает реализацию перевода. Назначение текста и решения клиентов он также не знает и не изменяет. Публичная граница задана [Kafka-контрактом](../docs/api/translation.md), а provider-neutral граница — [00-INFRA-20261106-0012-translator-technical-capability](../docs/adr/00-INFRA-20261106-0012-translator-technical-capability.md).

## Вход и вычисления

По [00-INFRA-20261106-0012-translator-technical-capability](../docs/adr/00-INFRA-20261106-0012-translator-technical-capability.md) действующий публичный запрос v2 содержит только текст, языки и техническую корреляцию. Внутренний `execution_ref` является технической областью checkpoints контракта, а не идентификатором модели, версии или провайдера; он отсутствует в публичном запросе и результате. Незавершённое задание после обновления может выполняться любым совместимым провайдером; новый перевод может отличаться. Исторический ответ сохраняется, а повторная доставка того же завершённого технического сообщения остаётся идемпотентной. V1 принимается дополнительно для миграционного завершения старых клиентов и воспроизведения прежних результатов; новые клиенты используют v2.

Миграционный вход — `TranslationRequested` v1 через `translation.requests.priority.v1` или `translation.requests.v1`. Схема проверяет техническую identity издателя, но не закрепляет список клиентов. Отдельный consumer каждого topic проверяет артефакт схем, время, SHA-256 текста и идентификатор, транзакционно сохраняет точные байты до Kafka commit. Приоритет определяется только topic: 0 для приоритетного и 100 для обычного. Конфликт идентификатора или неверный контракт сохраняется в собственном карантине. При отказе БД consumer прекращает работу без commit и читает от последнего подтверждённого offset после перезапуска.

Работник получает одно задание с отдельным token и lease 360 секунд, используя `FOR UPDATE SKIP LOCKED`. Под блокировкой управляющей записи счётчик допускает не более настроенного количества последовательных приоритетных leases, после чего при наличии выдаётся обычное задание. Внутри класса допущенные задания выдаются по неизменяемому `created_at`, затем `request_id`; `available_at` только запрещает преждевременный повтор и не является ключом сортировки. Технический повтор сохраняет исходную дату и байты задания. Текст детерминированно делится по абзацам и пределу 800 символов; `translation_segment` хранит точный источник, digest, перевод и warnings. Worker передаёт провайдеру только текст и языки через приватный порт с bounded timeout. Проверка модели, словаря, внешнего API или человеческого workflow выполняется исключительно провайдером и не входит в процесс Translator.

Независимый клиент отправляет `TranslationRequestedV2` с исходным языком, целевым языком и текстом, без поля операции или исполнителя. Прежние `PROFILE_UNIT` и `OPERATOR_REVIEW` сохраняются только как совместимые значения v1, но на приватной границе также превращаются в тот же текст. Worker использует один `POST /v1/translate` через приватный Unix socket; запрос содержит только версию контракта, текст и два языка, а ответ — версию контракта, строку перевода и необязательные ограниченные warnings. `translator_ref`, digest, операция, модель, версия, движок и provider-specific параметры через порт не проходят. Полный оригинал остаётся у клиента.

Provider image самостоятельно объявляет Docker `HEALTHCHECK`; Translator Compose не знает его команду и не переопределяет её. Успешная проба допускает запуск worker, но не раскрывает модель, версию, движок или provider identity. Любая внутренняя реализация и критерии её готовности принадлежат поставщику образа; Translator сохраняет очередь при недоступности порта.

Docker-проба API использует тот же автономный файл, но подтверждает только работающий общий цикл и оба запущенных listener. Она не проверяет БД, Kafka, провайдера или продвижение очереди: готовность зависимостей остаётся отдельным `/readyz`. Остановка одного listener завершает оба и отзывает сигнал; зависший цикл не обновляет heartbeat. Сигналы не являются каноническими данными, живут в собственном tmpfs и удаляются при штатном завершении; интервал Docker 10 секунд, timeout 5 секунд и прежние числа отказов provider/API 30/12 сохранены.

## Устойчивый результат

Docker-пробы обоих consumers, worker и outbox читают автономный локальный сигнал через `python -S`; они не загружают SQLAlchemy, HTTP/Kafka-клиенты или приложение и не обращаются к зависимостям. Сигнал атомарно обновляет только основной цикл, а не независимый поток присутствия. Пауза или пустая очередь остаются живым состоянием. Обычное окно свежести — 30 секунд; явно обозначенное ожидание Kafka у consumer допускает 120 секунд, отдельное обращение worker к провайдеру — 300 секунд при timeout запроса 240 секунд. Окно не продлевается фоновым потоком; новый сегмент получает его только при фактическом переходе основного цикла к следующему вызову. Неизвестная фаза, устаревшая отметка, смерть или повторное использование PID закрывают пробу. При штатном завершении сигнал отзывается. Проба подтверждает живость, не успешную обработку или доступность зависимости.

Все свежие собственные Python runtime и издатель используют SQLite 3.53.4 с закреплённым архивом и проверенным SHA3 исходного `sqlite3.c`; ABI подключается без замены Python, ОС, SDK и схемы журнала. Адресные maintenance-цели Docker сохраняют слои прежнего собственного образа. Отдельный `BACKGROUND_IMAGE` выбирает только четыре фоновые роли и не переключает работающие API или провайдера; он не разрешает рассогласование Alembic head. Перед заменой издателя полный остановленный журнал проверяется новой библиотекой на изолированной копии, включая `integrity_check` и точные данные.

Успех или доказуемая ошибка входа сохраняется вместе с неизменяемым результатом и исходящим журналом в одной SQL-транзакции. Публикация подтверждается только после Kafka ACK. Повтор завершённого запроса переочередяет прежний результат без вычисления и без изменения байтов. Повтор незавершённого не создаёт второго задания. Временная ошибка провайдера или хранилища не создаёт `CANCELLED` и не требует решения оператора: собственное задание возвращается в `PENDING` с паузой 30 секунд либо восстанавливается после lease.

`FAILED` разрешён только для неверного запроса, неподдерживаемого языка и доказуемо некорректного ответа провайдера; он не принимается за готовую локализацию. Технический сбой провайдера и timeout повторяются автоматически. Политики повторов и итоговую языковую проверку выполняет канонический владелец локализации.

Причина технического повтора записывается только ограниченным совместимым кодом в собственный `translation_job.error_code` и структурированный журнал с `request_id`, `correlationid` и `traceparent`. Частный 503 различает только классы отказа непрозрачного порта; исторические имена кодов с `MODEL` или `NATIVE` не являются сведениями о фактической реализации. Worker отдельно различает недоступный socket, транспорт и HTTP-ошибку. Разрешённые коды определены в `src/translator_service/retry.py`; произвольный текст исключения или тела HTTP не переносится в диагностику. Неизвестная причина остаётся `TRANSLATOR_UNAVAILABLE`, старым строкам точная причина не приписывается задним числом. Эти внутренние коды не создают публичного `FAILED` и не изменяют Kafka-схемы или сохранённые результаты.

## Управление и восстановление

Время старта и внутренняя готовность определяются только provider image. Station ограничивает лишь общее ожидание `start --wait`; оно не становится настройкой провайдера и не увеличивает 240-секундный timeout одного вызова Translator. Ограниченный 503 или транспортный сбой оставляет задание для bounded retry без попытки определить внутреннюю причину.

Команды `PAUSE`, `RESUME`, `RESET` требуют `command_id`, `actor`, `expected_revision`, `rationale`; журнал неизменяем. Идентичный повтор идемпотентен, изменение тела того же идентификатора и конфликт ревизии запрещены. Пауза останавливает выдачу новых lease, активная единица может завершиться. RESET требует отсутствия активного lease и возвращает только незавершённое в очередь; готовые переводы не удаляются.

Канонические данные находятся только в собственной PostgreSQL-базе `translator_service`; credentials и данные клиентов недоступны. Задания, исходные байты, результаты, outbox, карантин и журнал команд не имеют календарного удаления. Каждый клиент хранит собственную проекцию результатов. Резервная копия Translator содержит собственную БД и digest публичных контрактов, но не модель, provider lock или provider credentials. После проверки незавершённые leases безопасно повторяются через любой совместимый провайдер.

## Поставка и безопасность

Обновление SQL-ролей и отдельного издателя обязано согласовывать точную ревизию БД с ожидаемым head выбранных образов до допуска писателей; частичная выкладка не разрешает обход schema gate. Миграция 0005 добавляет checkpoints без изменения прежних заданий/результатов/команд, проверяется на восстановленной копии и повторно на замороженной рабочей БД. Порядок, технические fingerprint и ограничения совместимого отката определены в [руководстве](USER_MANUAL.md#согласованное-обновление-схемы).

Реализации провайдера, её lock, модель, словарь, runtime, prompts и tests в поставке Translator отсутствуют. Ими владеет поставщик внешнего provider image; совместимая реализация может вообще не использовать модель.

Исходный и целевой языки разрешаются по собственному каталогу 150 заявленных поставщиком языков и явным псевдонимам; неизвестные коды отклоняются без угадывания. `TRANSLATE_TEXT` сохраняет полный ограниченный текст: фрагментация и повтор обрезанного ответа не разрешают молча отбросить конец. Общий deadline остаётся ограниченным, а временный сбой и timeout оставляют задание для повтора. Кэш результата включает исходный и целевой языки; контекст чужого задания не становится входом следующего. Заявленный охват языков не заменяет смысловую проверку качества.

По [00-INFRA-20261106-0012-translator-technical-capability](../docs/adr/00-INFRA-20261106-0012-translator-technical-capability.md) все диагностические GET, включая состояние очереди, относятся к `default`; группа `translator` содержит только включённый операторский перевод. Это метаданные оформления: гарантии проверки здоровья, ответы и права не усиливаются и не меняются.

Порядок и состав трёх групп Swagger (`default`, `translator`, `metrics`) определяет [контракт операционного API](../docs/api/translation.md). Метаданные групп общие; частная схема содержит только пять GET, операторская — также POST перевода только при явном `API_TRANSLATION_ENABLED=true`. При `false` маршрута нет; обычная HTTPS/mTLS-диагностика не зависит от IdP, но локальное HTTP-чтение сохраняет OIDC. Существующие GET, ответы и проверки доступа сохраняются; задания создаёт только Kafka consumer. В HTTPS-режиме чтение по-прежнему защищено mTLS, включённый POST дополнительно требует собственный OIDC и отдельную роль. Недоступные/неверные обязательные для выбранного режима настройки пределов, OIDC или TLS закрывают запуск до listener.

Собственные Dockerfile, `compose.yml`, `.env.example`, PostgreSQL, миграции, одноразовый topic provisioner и автоматически экспортированные схемы достаточны для воспроизводимой сборки Translator без исходников клиента или провайдера. `compose.remote.yml` принимает маршрутизируемые Kafka/PostgreSQL endpoints. Рабочие роли не имеют Kafka admin ACL; `/readyz` требует собственной БД, Kafka и topics, но не раскрывает и не допускает конкретного провайдера. Основной стек Translator остаётся Python 3.13.7, Debian Bookworm и Poetry 2.2.1. Внешний provider image допускается отдельно точным digest за непрозрачным портом.

Provider-neutral Unix socket доступен только provider и worker одной ячейки. Частный read-only API Translator публикует `/healthz`, `/readyz`, агрегированный `/v1/status`, `/v1/components` и `/metrics`; он не принимает межсервисный перевод и не возвращает тексты или результаты. Runtime исполняется непривилегированно, файловая система доступна только для чтения, заданы пределы памяти и CPU. Production требует TLS, раздельных identities, минимальных ACL, секретов, подписи образов и независимого восстановления; допуск provider image не переносится на Translator и наоборот.

Логи содержат технические коды, идентификаторы корреляции, длительность и исход, но не текст перевода, SQL или credentials. Kafka consume/process/publish и HTTP-операции создают spans и продолжают входной `traceparent`; production требует HTTPS/mTLS OTLP endpoint. Собственный telemetry sender имеет постоянный журнал, собирает ограниченные Prometheus metrics и доставляет их вместе с logs/traces в центральный delivery; недоступность центра не удаляет локальный журнал. CLI выводит только запрошенный технический статус. Идентификаторы и точные байты перевода доступны как доказательства у владельца, не в обычном журнале.

Операционный API сохраняет частный HTTP listener с прежними путями для собственных проб и отдельный операторский listener в том же контейнере/процессе. Внешняя документация `/docs` показывает операции Translator и согласованный операторский POST через Kafka; она не раскрывает приватный порт или внутренности провайдера. В HTTPS-режиме обязательны TLS 1.2+, отдельная CA операторов, клиентское удостоверение и отказ без сертификата; локальное исключение сохраняет 00-INFRA-20261106-0007-workload-and-operator-identity. Swagger UI поставляется локально из закреплённого официального артефакта с digest.
